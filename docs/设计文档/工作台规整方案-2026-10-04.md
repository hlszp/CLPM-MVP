# 工作台规整方案（2026-10-04）

> 状态：实施中（裁决已定，当日执行）
> 背景：全站存在四个"工作台"（全局工作台 / 回路工作台 / 诊断工作台 / 整定工作台），功能与命名双重重叠。经梳理（见本文 §1），用户于 2026-10-04 做出四项裁决。
> 关联事实源：`docs/MVP设计/00-信息架构.md`（IA 现行口径，随本方案同步更新）、回路工作台三件套（原型/设计方案 v3/API 契约，2026-10-02）。

## 1. 背景与问题

四个工作台分三层：全局工作台是"面"（全厂聚合，0929 三屏裁决已定保留）、回路工作台是"点"（单回路全生命周期，P1-P4 已验收合入 main d40f8138）、诊断/整定工作台是"专项操作台"。核心矛盾：

- **入口冗余**：回路工作台 DiagSection 的发起能力与诊断工作台完全等价（DiagTriggerModal 算子选择代码注释明确"与旧页 submitDiagnosis 完全一致"）；TuningSection 整件复用 use-tuning-workbench 四步组件。诊断工作台独立价值最薄（队列职能 2026-10-01 已分家出诊断概览页），整定工作台独有价值在总览（961 回路可整定性总览 + 在途建议排程）。
- **权限错位**：EXPERT 可在回路工作台发起诊断但后端 `_DIAGNOSIS_TRIGGER_ROLES` 不含 EXPERT；PE 可在回路工作台走整定四步但后端 tuning 端点 `require_roles` 不含 PE。同一操作"A 入口放行、B 入口拦截"。
- **命名四义**：四个入口都叫"工作台"，用户无区分线索。

## 3. 目标形态

- 菜单：**运维工作台**（/workbench，全角色）→ 监控 → 回路工作台（/loop/workbench360）→ 评估 → **诊断**（概览/记录/任务 三页）→ **整定**（**整定总览**/记录/验证 三页）→ 处置 → …
- 单回路诊断/整定操作的**唯一入口 = 回路工作台剖面**；模块页承担"面"（队列、总览、档案）。
- 外部跳转统一协议：`/loop/workbench360?loopId=<id>&section=<assess|diagnosis|tuning|handling>`（本方案新增 query 通道，一次性消费）。
