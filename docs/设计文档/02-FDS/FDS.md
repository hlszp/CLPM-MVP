### 1.3 设计原则
本 FDS 遵循 PRD v3.1 确立的四项产品化设计原则：
1. **产品化、工具化**：系统是可复用的产品，非项目型定制化系统。提供充分的配置组态能力，用户自助完成配置。
2. **模块内聚、自包含**：每个功能模块自包含其"配置 → 运行 → 分析"三态功能，减少模块间交叉。
3. **配置驱动**：指标公式、诊断算法、引擎规则等均支持用户自助配置，无需开发介入。
4. **实体内聚**：回路作为核心实体，其配置态（台账/映射）和运行态（监控）归属同一模块管理。

## 2. 功能范围界定 (Scope)

本 FDS 覆盖 **Phase 1 (MVP)** 全部功能规格，并包含 **Phase 2 回路整定模块**的原型先行设计规格。

### 2.1 范围内功能 (In Scope)
* **工作台（门户）**：性能总览首页，聚合多模块数据，全角色日常作业入口。
* **回路管理**：AAS Tag 同步、工厂层级配置、回路台账管理、Tag 关联管理、回路监控列表与运行详情。
* **性能评估**：性能指标配置、引擎规则配置、全量持续计算、全局看板、低效回路排行、性能统计报表、自动报表快照。
* **诊断中心**：诊断指标配置、差等生自动预诊、波形查看、异常跟踪子模块（状态标签/PDF 导出/A-B 对比）、诊断统计报表。
* **回路整定（原型先行设计）**：整定工作台、模型辨识、整定算法、闭环仿真、整定效果统计（Phase 2 实现算法）。
* **系统管理**：用户与角色管理、审计日志、安全边界说明、自动报表管理。
* **RBAC 权限模型**：基于角色的权限控制与操作日志。
* **产品化配置能力**：所有指标公式、诊断算法、引擎规则均支持用户自助配置，配置变更即时生效并记录审计日志。

### 2.2 范围外功能 (Out of Scope - 规划于 Phase 2/3)
* **回路整定算法实现**：在线/离线控制对象模型辨识、PID 参数推荐计算、闭环阶跃仿真（Phase 2 实现，本 FDS 仅完成原型设计规格）。
* **AI 与大语言模型**：自动波形解读报告、智能专家问答。
* **复杂工单系统**：系统内的多节点维修工单派发、退回、会签等重度流转。
* **多厂区规模化**：1200+ 回路并发优化、厂级振荡源追踪、批次性能分析与经济效益折算模型（Phase 3）。

## 4. 数据流转逻辑 (Data Flow)

系统的核心命脉是数据流的无缝自动化流转。v3.0 在数据接入层前增加 **AAS Tag 同步层**，并明确回路创建流程。v4.0 在数据清洗层与指标计算层之间新增 **数据编排层 (DataPlanner)**，引入 tagGroup 概念与 DataBlock 缓存以合并查询计划、降低 TDengine 压力。

1. **AAS Tag 同步层 (Tag Sync)**：系统定期从 AAS 同步所有 OPC tag 位号信息（tag 名/描述/当前值/数据质量）。AAS 同步的是 **tag 位号**（非回路实体），回路由用户在 CLPM 系统中创建并关联 tag。PV tag 携带数据质量码（Good/Bad/Uncertain）。
2. **数据接入层 (Ingestion)**：调度器按引擎规则配置（如 1 小时/次）触发，通过 OPC/API/离线 CSV 拉取已关联 tag 的原始 `PV, SP, OP, MODE, PID_P, PID_I, PID_D` 时序数据。
3. **数据清洗层 (Cleansing)**：执行**KEEP_ALL_WITH_VALIDITY** 质量码处理策略——不删除任何数据点，为每个时间戳的每个 Tag 打 `valid=True/False` 标记（Good → valid=True，Bad/Uncertain/超量程/断线 → valid=False）。计算**好值率**（valid=True 点占比）。后续各指标通过 **Metric Validity Mask** 决定有效点（详见 §5.3.1.2）。
4. **数据编排层 (DataPlanner)** [v4.0 新增]：读取**指标数据需求契约**（每个指标声明所需的 tagGroup / 采样频率 / 质量策略）→ 按相同 tagGroup **合并查询计划** → 优先查询 **DataBlock 缓存**（详见 §5.3.9）→ 未命中时查询 TDengine → 调用预处理模块（重采样 / 对齐 / 补点）→ 生成 **MetricDataBundle** → 分发给对应指标计算器。引入 **tagGroup** 概念，5 个 tagGroup 定义如下：
   * **BASE**：PV / SP / MODE / PV_QUALITY，按控制类型采样（1s/5s/10s/30s/1min）。
   * **OP_HF**：OP，固定 1s。
   * **PVOP_HF**：PV / OP，固定 1s。
   * **MODE_HF**：MODE，固定 1s。
   * **QUALITY_HF**：PV_QUALITY，固定 1s。
   * **复用规则**：当 BASE 已是 1s（流量回路）时，OP_HF / PVOP_HF / MODE_HF / QUALITY_HF 可直接复用 BASE，无需重复查询。
5. **指标计算层 (Calculation)**：对 MetricDataBundle 切片，按性能指标配置并行执行 3+1+8 指标体系算法（详见 §5.3.1）。
6. **聚合与排名层 (Aggregation)**：加权计算得出单回路得分；向上卷起 (Roll-up) 计算单元、装置级评分；排序生成低效回路排行。
7. **自动诊断层 (Auto-Diagnosis)**：监听低效回路队列，命中后按诊断指标配置触发 FFT/散点拟合等算法，生成预诊结论入库。
8. **统计与报表层 (Statistics & Reporting)**：各业务模块按自身维度输出统计报表；系统管理模块按周期生成《控制回路性能评估报告》快照。

### 4.1 回路创建流程
`用户创建回路 → 关联 7 个 OPC tag → 配置扩展参数（评分权重/启用状态/备注）→ 状态就绪/Partial`

* **就绪 (Ready)**：PV/SP/OP/MODE 四个必填 tag 全部关联成功，回路进入评估流程。
* **部分就绪 (Partial)**：必填 tag 缺失，回路标红提示，不参与评估计算。

##### 5.3.1.1 3+1+8 指标体系 [v4.0 更新]

CLPM 性能指标体系由"3 核心 + 1 投用 + 8 辅助诊断"三层结构构成：

| 层级 | 指标代码 | 中文名称 | 是否参与评分 | Metric Validity Mask |
|---|---|---|:---:|---|
| **3 核心质量指标** | `ACCURACY` (A) | 准确率 | ✅ 加权评分 | `pv_valid && sp_valid` |
| | `FASTNESS` (F) | 快速率 | ✅ 加权评分 | `pv_valid && sp_valid` |
| | `STABILITY` (S) | 稳定率 | ✅ 加权评分 | `pv_valid && sp_valid` |
| **1 投用指标** | `R_AUTO` (R) | 有效自控率 | ✅ 折扣因子 | `mode_valid && op_valid` |
| **8 辅助诊断指标** | `GOOD_RATE` | 好值率 | ❌ 影响可信度 | 不删除行，统计质量码占比 |
| | `OSCILLATION_RATE` | 振荡率 | ❌ | `pv_valid` |
| | `SATURATION_RATE` | 饱和率 | ❌ | `op_valid && mode_valid` |
| | `STICTION_INDEX` | 粘滞系数 | ❌ | `pv_valid && op_valid` |
| | `OUTPUT_TRAVEL` | 输出值行程指数 | ❌ | `op_valid && consecutive_valid` |
| | `STEADY_TIME` | 稳态时间 | ❌ | `pv_valid && sp_valid` |
| | `IDEAL_STEADY_TIME` | 理想稳态时间 | ❌ | `pv_valid && sp_valid` |
| | `AUTO_RATE` | 自控率 | ❌ | `mode_valid` |

* **3 核心质量指标 (A/F/S)**：参与综合评分加权求和，构成评分主体。
* **1 投用指标 (R)**：作为折扣因子乘到评分公式外层，反映回路实际投用情况。
* **8 辅助诊断指标**：不参与评分，仅用于诊断与可视化。**好值率** 不直接参与评分公式，而是**影响指标可信度**（valid_rate 越低，指标可信度等级越低，详见 §5.3.10）。

##### 5.3.1.2 KEEP_ALL_WITH_VALIDITY 与 Metric Validity Mask [v4.0 新增]

数据清洗层采用 **KEEP_ALL_WITH_VALIDITY** 策略，**不删除任何数据点**，为每个时间戳的每个 Tag 打 `valid=True/False` 标记。不同指标通过 **Metric Validity Mask** 决定其有效点集合：

* **准确率 / 稳定率 / 快速率**：`pv_valid && sp_valid`
* **行程指数**：`op_valid && consecutive_valid`（consecutive_valid 为连续性校验标记）
* **粘滞系数**：`pv_valid && op_valid`
* **好值率**：不删除行，统计 valid=True 点数 / 总点数（质量码占比）
* **饱和率 / 自控率**：`mode_valid`（自控模式段）

指标计算时仅在有效点集合上执行算法，无效点保留用于波形可视化与诊断算法参考。

**指标配置管理详细规则**：

* **阈值配置（threshold）**：采用 JSONB 结构存储，格式 `{min: Float, max: Float, alert: Float}`，分别对应最小值/最大值/告警阈值。例如稳定率阈值 `{min: 80, max: 100, alert: 90}` 表示低于 90 触发告警，低于 80 视为不合格。
* **权重配置（weight）**：3 项核心指标 (A/F/S) 权重总和须为 1.0（100%），按控制类型默认配置（详见 §5.3.7 综合评分）。
* **控制类型（control_type）**：枚举值 `STABLE` / `SLOW` / `FAST` / `LOGIC`，用于自动选择权重模板，存储于 `metric_config.control_type` 字段。
* **公式配置（formula）**：TEXT 字段，存储用户自定义计算公式，由表达式引擎执行（详见 §5.3.8）。
* **数据需求契约（data_contract）** [v4.0 新增]：JSONB 字段，声明每个指标所需的 tagGroup / 采样频率 / 质量策略，供 DataPlanner 合并查询计划使用。示例：`{"tagGroup": "BASE", "sampling_freq": "1s", "quality_policy": "KEEP_ALL_WITH_VALIDITY"}`。

#### 5.3.7 综合评分计算与 INCONCLUSIVE 处理

| 功能点 | 输入参数 / 前置条件 | 处理规则 | 输出结果 / 界面表现 | 异常处理 |
|---|---|---|---|---|
| **综合评分计算** | 3 核心指标值 (A/F/S)、核心权重 (a/f/s)、投用指标 R（有效自控率）。 | 按公式 **`P = (A·a + F·f + S·s)/(a+f+s) × R`** 计算综合评分（0~100）。其中 A=准确率、F=快速率、S=稳定率，(a+f+s)=1.0；R 为有效自控率，作为折扣因子乘在评分外层（自控且输出不饱和且控制有效的时长占比）。8 项辅助诊断指标不参与评分。 | 综合评分落库至 `kpi_snapshot_hourly.score`，供看板与排行调用。 | 某项核心指标因数据不足无法计算时，该指标权重按比例分配给其他核心指标。 |
| **权重模板（按控制类型）** | 回路控制类型。 | 按控制类型分 4 类权重模板： | 自动套用对应权重模板。 | 控制类型未配置时默认套用 STABLE 模板。 |
| **INCONCLUSIVE 处理** [v4.0 更新] | 指标可信度为 E 级（`valid_rate < 0.20`）。 | 整条快照标记为 `INCONCLUSIVE`，综合评分置为 NULL（不以 0 分掩盖数据缺失）。该回路不参与装置级聚合计算，但在装置级报告中单独统计数量与占比。 | 快照状态字段 `status = INCONCLUSIVE`，`score = NULL`；看板以灰色标签展示。 | - |
| **装置级聚合评分** | 装置内所有回路评分与级别权重。 | 按公式 `Score_unit = Σ(wᵢ_level × Scoreᵢ) / Σ wᵢ_level` 加权聚合，级别权重：一级=3、二级=2、三级=1（对齐 GB/T 44693.2-2024 附录 E.2）。INCONCLUSIVE 回路不参与聚合。 | 装置级/单元级评分落库，供全局看板调用。 | 装置内全部回路均为 INCONCLUSIVE 时，装置级评分置为 NULL。 |

**综合评分权重模板（4 类控制类型）** [v4.0 更新]：

| 控制类型 | a (准确率) | f (快速率) | s (稳定率) | 适用场景 |
|---|:---:|:---:|:---:|---|
| **STABLE（稳定型）** | 0.25 | 0.20 | 0.55 | 温度、压力控制 |
| **SLOW（慢速型）** | 0.30 | 0.15 | 0.55 | 缓慢调节回路 |
| **FAST（快速型）** | 0.20 | 0.40 | 0.40 | 副回路、流量控制 |
| **LOGIC（逻辑型）** | 0.00 | 0.20 | 0.80 | 防回流、防超温 |

* **权重归一**：a + f + s = 1.0，权重模板可按回路覆盖。
* **R 折扣因子**：R ∈ [0, 1]，反映回路实际投用情况；R=0 时综合评分为 0，R=1 时综合评分为核心指标加权均值。
* **INCONCLUSIVE 触发**：当指标可信度为 E 级（`valid_rate < 0.20`，详见 §5.3.10）时，整条快照标记 INCONCLUSIVE，不参与装置级聚合。

#### 5.3.9 DataBlock Cache 设计 [v4.0 新增]

DataPlanner 在查询 TDengine 前优先查询 DataBlock 缓存，降低高频查询对时序库的压力。缓存采用 Redis 存储，zstd 压缩，分层 TTL，LRU 淘汰策略。

| 功能点 | 输入参数 / 前置条件 | 处理规则 | 输出结果 / 界面表现 | 异常处理 |
|---|---|---|---|---|
| **缓存查询** | loopId / tagGroup / 时间窗 / 采样频率 / 质量策略 / 配置版本。 | DataPlanner 拼装缓存 Key 后查询 Redis；命中则直接返回 DataBlock（zstd 解压）；未命中则查询 TDengine 后回填缓存。 | 命中：返回 DataBlock；未命中：返回 MISS 标记。 | Redis 不可用：降级直查 TDengine，记录告警日志。 |
| **缓存写入** | TDengine 查询结果 + 预处理结果。 | zstd 压缩后通过 **Pipeline 批量写入** Redis，按 tagGroup 设置分层 TTL。 | 缓存写入成功。 | 写入失败：重试 3 次，仍失败则跳过缓存（不影响主流程）。 |
| **缓存淘汰** | Redis 内存占用达阈值。 | LRU 淘汰最近最少访问的 DataBlock。 | 老旧 DataBlock 被回收。 | - |
| **缓存失效** | 指标配置/引擎规则变更。 | 配置版本号 (cfgVersion) 变更后，旧版本 Key 自动失效（不再命中）。 | 新查询使用新版本 Key。 | - |

**缓存 Key 设计**：

```
pdb:{loopId}:{tagGroup}:{startTime}:{endTime}:{samplingFreq}:{qualityPolicy}:{preVersion}:{cfgVersion}
```

* `loopId`：回路 ID
* `tagGroup`：BASE / OP_HF / PVOP_HF / MODE_HF / QUALITY_HF
* `startTime` / `endTime`：时间窗（Unix 毫秒）
* `samplingFreq`：采样频率（1s/5s/10s/30s/1min）
* `qualityPolicy`：质量策略（KEEP_ALL_WITH_VALIDITY）
* `preVersion`：预处理版本号
* `cfgVersion`：指标配置版本号

**分层 TTL 策略**：

| tagGroup | TTL | 说明 |
|---|---|---|
| BASE | 5 min | 按控制类型采样，数据量大、变化快，TTL 较短 |
| OP_HF / PVOP_HF / MODE_HF / QUALITY_HF | 10 min | 固定 1s 高频数据，复用率高，TTL 较长 |

#### 5.3.10 数据血缘与指标可信度 [v4.0 新增]

每条指标结果必须包含**数据口径**与**可信度等级**，支撑结果可追溯与可信度分级展示。

**数据口径字段（每条指标结果必填）**：

| 字段 | 类型 | 说明 |
|---|---|---|
| `sampling_freq` | String | 实际采样频率（1s/5s/10s/30s/1min） |
| `quality_policy` | String | 质量策略（KEEP_ALL_WITH_VALIDITY） |
| `tag_group` | String | 数据来源 tagGroup（BASE/OP_HF/PVOP_HF/MODE_HF/QUALITY_HF） |
| `valid_rate` | Float | 有效点率（valid=True 点数 / 总点数），∈ [0, 1] |

**指标可信度 A/B/C/D/E 五级**：

| 等级 | valid_rate 范围 | 含义 | 系统表现 |
|:---:|:---:|---|---|
| **A** | ≥ 0.95 | 高可信 | 正常参与评分与聚合 |
| **B** | 0.80 ~ 0.95 | 较高可信 | 正常参与评分与聚合 |
| **C** | 0.60 ~ 0.80 | 中等可信 | 正常参与评分，看板标注"可信度 C" |
| **D** | 0.20 ~ 0.60 | 低可信 | 评分仅供参考，看板标注"可信度 D，谨慎使用" |
| **E** | < 0.20 | 不可信 | 标记 INCONCLUSIVE，综合评分置 NULL，不参与装置级聚合 |

* **valid_rate 计算**：基于 Metric Validity Mask 的有效点数 / 总点数。
* **可信度展示**：全局看板、低效回路排行、回路运行详情均展示指标可信度等级标签（A 绿/B 蓝/C 黄/D 橙/E 灰）。
* **INCONCLUSIVE 触发**：当指标可信度为 E 级（`valid_rate < 0.20`）时，整条快照标记 INCONCLUSIVE。

#### 5.3.11 任务管理 [v4.0 新增]

性能评估任务区分为**标准任务**与**自定义任务**两类，结果分别落库至不同快照表。

| 任务类型 | 触发方式 | 存储表 | 是否参与装置级聚合 | 说明 |
|---|---|---|:---:|---|
| **标准任务** | 每小时定时评估（调度器按引擎规则配置触发） | `kpi_snapshot_hourly` | ✅ 参与 | 系统自动周期性评估，作为装置级/单元级聚合与全局看板的数据源 |
| **自定义任务** | 按需触发（用户手动指定回路 + 时间窗 + 指标范围） | `kpi_snapshot_custom` | ❌ 不参与 | 用户临时分析或对比验证用，结果独立存储，不进入装置级聚合与排行 |

**任务管理详细规则**：

* **标准任务**：调度器按引擎规则配置（默认 1 小时/次）自动触发，覆盖所有 `Ready` 状态回路；结果落库 `kpi_snapshot_hourly`，供全局看板、低效排行、装置级聚合、统计报表调用。
* **自定义任务**：用户在工作台或回路详情页手动触发，指定回路集合 / 时间窗 / 指标范围；结果落库 `kpi_snapshot_custom`，仅在用户侧展示，**不参与装置级聚合、不进入低效排行、不影响标准任务评分**。
* **任务状态**：两类任务均记录 `task_status`（PENDING/RUNNING/SUCCESS/FAILED/INCONCLUSIVE），支持任务查询与重试。
* **并发控制**：自定义任务与标准任务共享计算资源池，自定义任务优先级低于标准任务，避免影响周期性评估。

#### 5.4.7 Dempster-Shafer 证据融合

当多个诊断算法同时输出结果时，采用 Dempster-Shafer 证据理论融合置信度，解决多算法结果冲突与置信度聚合问题。

| 功能点 | 输入参数 / 前置条件 | 处理规则 | 输出结果 / 界面表现 | 异常处理 |
|---|---|---|---|---|
| **多算法置信度融合** | n 个诊断算法输出的置信度 {c₁, c₂, ..., cₙ}。 | 按公式 `C_fused = (Π cᵢ) / (Π cᵢ + Π (1-cᵢ))` 融合置信度。 | 输出融合后的置信度 C_fused（0~100）。 | 算法结果完全冲突时（如一个 0.9 一个 0.1），融合置信度趋近 0.5，触发 MANUAL_REVIEW。 |
| **兜底规则** | 所有算法置信度均 < 50%。 | 输出 `MANUAL_REVIEW`（人工复查）标签，建议专家人工介入分析。 | 诊断结果标签为 `MANUAL_REVIEW`，置信度记录原始值。 | - |
| **证据链构建** | 各算法输出特征值与中间结果。 | 构建证据链，记录每个算法的输入特征、中间计算值、输出置信度，支持诊断详情页可视化展示。 | 证据链数据落库至 `diagnosis_result.evidence_chain`（JSONB）。 | - |

#### 5.5.2 模型辨识（原型先行设计）

| 功能点 | 输入参数 / 前置条件 | 处理规则 | 输出结果 / 界面表现 | 异常处理 |
|---|---|---|---|---|
| **辨识参数配置** | 数据段选择、采样周期、模型类型（FOPDT/SOPDT）。 | 配置辨识算法输入参数。FOPDT 采用两点法 + 面积法组合辨识；SOPDT 采用继电器反馈法 + 非线性最小二乘拟合。 | 配置表单展示。 | Phase 1 原型阶段不执行真实辨识。 |
| **辨识结果** | 辨识参数配置完成。 | Phase 2 执行模型辨识算法，输出传递函数参数（K/τ/θ 或 K/T₁/T₂/θ）、拟合度 R²、阶跃响应对比曲线。FOPDT 拟合度 R²<0.85 时自动升级为 SOPDT。 | 结果区展示传递函数参数表、拟合度与阶跃响应对比曲线。 | Phase 1 原型阶段展示占位结果。 |

**模型辨识算法详细规则**：

* **FOPDT 模型辨识**：模型形式 G(s) = K·e^(-θs) / (τs+1)。采用两点法（记录 PV 到达 28.3% 与 63.2% 终值的时间 t₁、t₂，计算 τ=1.5(t₂-t₁)、θ=t₂-τ）+ 面积法（计算阶跃响应曲线下面积）组合辨识，取平均值，拟合度 R² 高者优先。
* **SOPDT 模型辨识**：模型形式 G(s) = K·e^(-θs) / (T₁T₂s² + (T₁+T₂)s + 1)。采用继电器反馈法（记录等幅振荡周期 T_u 与幅值 A）+ 非线性最小二乘精化 T₁、T₂、θ。
* **拟合度计算**：R² = 1 - SS_res/SS_tot，其中 SS_res 为残差平方和，SS_tot 为总平方和。R² > 0.9 为优秀拟合，R² < 0.85 建议升级为 SOPDT。
* **整定记录字段**：辨识结果落库至 `tuning_record` 表，含 `model_type`、`model_params`（JSONB）、`fitting_score`（拟合度 R²，DECIMAL(5,2)）字段。

| **参数推荐** | 辨识结果 + 算法选择。 | Phase 2 执行整定算法，推荐 PID 参数表（P/I/D 三组对比）、性能预测指标。 | 推荐参数表与性能预测指标卡片。 | Phase 1 原型阶段展示占位推荐。 |

**7 种整定方法及适用场景**：

| 序号 | 算法名称 | 算法类型 | 适用场景 | 关键参数 |
|---|---|---|---|---|
| 1 | FOPDT 模型辨识 | 模型辨识 | 一阶惯性加纯滞后过程 | K, τ, θ, fitting_score |
| 2 | SOPDT 模型辨识 | 模型辨识 | 高阶过程、欠阻尼过程（FOPDT R²<0.85 时升级） | K, T₁, T₂, θ, fitting_score |
| 3 | IMC 整定法 | PID 整定 | 工业界最常用，平衡鲁棒性与响应速度 | λ（默认 = θ，可调 0.8θ~3θ） |
| 4 | Lambda 整定法 | PID 整定 | 纸业及对超调极其敏感的化工过程 | λ（默认 = τ，可调 3θ~3τ） |
| 5 | Ziegler-Nichols 整定法 | PID 整定 | 经典基于临界振荡或阶跃响应的工程算法 | K_u, T_u（闭环临界法）或 K, τ, θ（开环法） |
| 6 | Cohen-Coon 整定法 | PID 整定 | θ/τ > 0.5 的大滞后系统 | K, τ, θ |
| 7 | SIMC 整定法 | PID 整定 | 简化 IMC 方法，工程实用性强 | τ_c（默认 = θ） |

#### 5.5.4 闭环仿真（原型先行设计）

| 功能点 | 输入参数 / 前置条件 | 处理规则 | 输出结果 / 界面表现 | 异常处理 |
|---|---|---|---|---|
| **仿真参数** | 当前 PID vs 推荐 PID 切换、扰动类型、仿真时长。 | 配置仿真输入参数。 | 仿真参数配置表单。 | - |
| **仿真结果** | 仿真参数配置完成。 | Phase 2 执行闭环仿真，采用 RK4（四阶 Runge-Kutta）ODE 求解器对 FOPDT/SOPDT 被控对象数值积分，PID 控制器采用增量式离散化。输出阶跃响应双波形对比、性能指标对比表（上升时间/超调/settling time/ITAE）。 | 双波形对比图与性能指标对比表。 | Phase 1 原型阶段展示占位仿真结果。 |

**闭环仿真验证详细规则**：

* **PID 控制器离散化**（增量式）：Δu(k) = K_p × [Δe(k) + (T_s/T_i) × e(k) + (T_d/T_s) × Δ²e(k)]，其中 e(k) = SP(k) - PV(k)，T_s 为采样周期。
* **被控对象数值积分**（RK4）：基于 FOPDT 状态方程 ẋ(t) = -(1/τ)·x(t) + (K/τ)·u(t-θ)，y(t) = x(t)，采用四阶 Runge-Kutta 法离散化求解。
* **性能指标提取**：上升时间 T_r（PV 从 10% 到 90% 终值的时间）、超调量 M_p、稳定时间 T_s（PV 进入 SP ± 2% 范围的时间）、ITAE（∫ t·|e(t)| dt）。
* **对比输出**：当前 PID vs 推荐 PID 的响应曲线对比与性能指标对比，量化展示整定效果改善程度。

## 6. 异常分支与数据容错规则

CLPM 系统的核心设计理念是**"绝对真实，不掩盖数据缺失"**。

1. **Inconclusive (数据不足) 处理**：
   * **触发条件**：某条回路在评估窗内，因通讯故障或未开机导致"好值率"低于设定阈值（默认 20%）。
   * **系统表现**：该回路**不计算**评分，不参与全厂聚合，强制打上灰色 `Inconclusive` 标签。波形区显示断线状态。
2. **Partial (批次部分就绪) 处理**：
   * **触发条件**：全厂回路中，存在 >1 条处于 `Inconclusive` 状态，或缺乏完整的 tag 关联（PV/SP/OP/MODE 必填 tag 缺失）。
   * **系统表现**：当期的全厂评估报告顶部必须强制显示黄色的 `Partial (部分数据缺失)` 警告横幅，保障报告严谨性。
3. **PV 质量码处理（KEEP_ALL_WITH_VALIDITY 策略）** [v4.0 更新]：
   * **触发条件**：PV tag 质量码为 Bad 或 Uncertain。
   * **系统表现**：采用 **KEEP_ALL_WITH_VALIDITY** 策略，**不删除任何数据点**，为每个时间戳的每个 Tag 打 `valid=True/False` 标记（Good → valid=True，Bad/Uncertain/超量程/断线 → valid=False）。波形图 PV 线按质量码与 valid 标记分段着色（Good 实线、Bad 灰色虚线断线、Uncertain 黄色虚线）。不同指标通过 **Metric Validity Mask** 决定有效点：
     * **准确率 / 稳定率**：`pv_valid && sp_valid`
     * **行程指数**：`op_valid && consecutive_valid`
     * **粘滞系数**：`pv_valid && op_valid`
     * **好值率**：不删除行，统计质量码占比（valid=True 点数 / 总点数）
   * KPI 好值率基于 PV 质量码统计，Bad/Uncertain（valid=False）时段不计入好值，但**仍保留在数据集中**供诊断算法与可视化使用。
4. **安全边界兜底**：
   * 前后端代码中**彻底剔除**任何针对 DCS OPC 节点的 `Write` / `Set` 接口调用。数据流为纯单向只读。
5. **配置变更容错**：
   * 性能指标配置、诊断指标配置、引擎规则配置的变更需二次确认，确认后记录审计日志。
   * 指标停用后导致权重总和不足 100% 时，系统阻止保存并提示用户调整。

## 7. 非功能规格要求 (NFRs)

### 7.1 性能与并发要求
* **前端渲染**：单页面展示 100 条以上回路表格时，FPS 不低于 40；单波形图加载 10,000 个数据点渲染耗时 < 1 秒（使用 Canvas/WebGL）。
* **后端计算**：支持 1200+ 回路的并发调度计算，1 小时粒度的数据聚合分析耗时 < 3 分钟。
* **AAS Tag 同步**：单次同步 10,000+ tag 耗时 < 30 秒。

### 7.2 兼容性要求
* **浏览器**：支持 Chrome (v90+), Edge (v90+), Safari (v14+)。
* **响应式**：
  * Desktop (>=1440px): 完整多栏工作台体验。
  * Tablet (1024px): 侧边栏自动折叠，采用抽屉式详情。

### 7.3 安全性要求
* **数据存储**：所有 OPC 数据源连接配置、账号密码必须在数据库中加密存储（如 AES-256）。
* **审计留痕**：所有的状态变更、配置修改操作必须落入 `sys_audit_log` 表，不可物理删除。
* **只读边界**：系统启动时校验不存在任何针对 DCS OPC 节点的 Write/Set 接口调用。

### 7.4 产品化配置要求
* **配置即时生效**：性能指标配置、诊断指标配置、引擎规则配置的变更即时生效，无需重启服务。
* **配置变更审计**：所有配置变更记录审计日志，含操作人/时间/变更前后值。
* **配置校验**：权重总和、阈值范围、参数合法性等校验在前端实时反馈，后端二次校验。
* **配置回退**：支持配置版本回退，可恢复至任意历史版本。

### 7.5 追溯与合规要求
* **算法版本追溯**：每一条评估结果与诊断结论，必须在数据库中关联其依据的算法版本号、指标阈值版本及时间戳（详见 §8 算法版本管理）。
* **数据一致性**：不掩盖数据缺失，"数据不足/无效"必须通过 `Inconclusive` 状态显式反馈给用户，而非用 0 替代。

## 8. 算法版本管理

为确保算法可追溯与合规审计，系统对所有算法实行版本管理，每条计算结果关联对应的算法版本号。

### 8.1 版本号格式

算法版本号格式：`<algorithm_name>v<major>.<minor>`

* `<algorithm_name>`：算法类别代码（大写 + 下划线）
* `<major>`：主版本号，算法公式变更时递增
* `<minor>`：次版本号，参数调整时递增

**示例**：`KPI_CALC_v1.0`（KPI 计算 v1.0）、`IMC_TUNE_v1.0`（IMC 整定 v1.0）

* **数据血缘追溯** [v4.0 新增]：每条指标结果除算法版本号外，还携带数据口径字段（sampling_freq / quality_policy / tag_group / valid_rate），支撑结果可追溯（详见 §5.3.10）。
* **版本变更审计**：算法版本升级时，需记录变更内容（公式/参数）、变更人、变更时间，并支持历史版本回退。
