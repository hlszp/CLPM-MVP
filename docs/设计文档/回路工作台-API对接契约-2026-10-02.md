# 回路工作台（新版）API 对接契约

> 日期：2026-10-02 ｜ 配套：《回路工作台-设计方案-2026-10-02.md》v3 §11-§12
> 用途：前端按本矩阵对接，禁止凭猜测调用；后端缺口（G1-G4）排期后在本文件回填结论。
> 路径前缀 `/api/v1` 省略。核实方式=backend 源码只读核对（2026-10-02）。

## 1. 剖面 × 端点矩阵

### 1.1 旅程状态条 + 缩略卡（页头聚合，并行直调）

| 数据 | 端点 | 关键参数 | 消费字段 |
|---|---|---|---|
| 评估段 | `GET /performance/loops/snapshots` | `loopId`、`latestOnly=true` | score、grade、ts、dataLineage（失分摘要前端算） |
| 诊断段 | `GET /diagnosis/runs/latest` | `loopId` | primaryCategory(+Label)、severity、primaryConfidence、reviewStatus、resultAt、runCount |
| 整定段 | `GET /tuning/tasks` | `loopId`、`pageSize=1` | status（10 态）、algorithm、recommendedPid、createdAt |
| 处置段 | `GET /handling/orders` + `GET /handling/suggestions` | `loopId`、`status` 过滤 | 在办数、建议 5 态计数 |
| 时钟 | 前端本地 | — | "数据截至"=最新数据时间戳 |

> 可选后端优化（不阻塞）：新增 `GET /loops/{id}/overview` 一次聚合以上四段，减少 4→1 请求。MVP 先并行直调。

### 1.2 监视趋势图

| 数据 | 端点 | 说明 |
|---|---|---|
| 历史窗口序列 | `GET /loops/{id}/monitor?trendWindow=` 或 `GET /timeseries/{loop_id}/waveform?startTime&endTime&maxPoints≤2000` | 后端 LTTB；前端再聚合/插值到 3600 点绘制；窗口九档映射 trendWindow 预设（1H/2H/4H/8H 无档位时用 waveform 自定义起止） |
| 实时推送 | WS `/ws/realtime`（订阅制） | 追加式右推；token 过期重订阅沿用现有机制 |
| 质量码/MODE 段 | waveform 的 valid_mask/outlier_reason；MODE 历史暂无端点 | MODE 历史段：P1 先渲染当下 MODE，历史段留 TODO 登记到阶段任务书 |
| 事件锚点 | `GET /diagnosis/runs/latest`、`GET /tuning/tasks?loopId`、处置工单时间 | 换算视口百分比；标注层徽标点击→剖面 |

### 1.3 性能评估剖面

| 动作 | 端点 | 备注 |
|---|---|---|
| 最新快照摘要 | `GET /performance/loops/snapshots?loopId=&latestOnly=true` | 行内含 24 KPI 全字段 |
| 评估历史列表 | 同上 `latestOnly=false` + 分页/时间窗 | **G2**：仅 hourly（自动+重算）；手动 custom 待并接 |
| 24 KPI 详情抽屉 | 同上（行内字段即详情）+ `GET /loops/{id}/confidence-latest` | 12 子指标 |
| 发起评估（整点回算） | `POST /tasks/backfill` + `POST /tasks/{taskId}/start` | loopIds 优先；≤30 天；覆盖 hourly |
| 发起评估（自定义时段） | `POST /tasks/custom/evaluate` | loopIds+metrics+起止必填；写 custom 表 |
| 进度轮询 | `GET /tasks/{taskId}` | 复用 use-workbench-task-runner |
| 失分→诊断联动 | 前端切剖面并预填时间窗 | 不发新请求 |

### 1.4 回路诊断剖面

| 动作 | 端点 | 备注 |
|---|---|---|
| 预检 | `GET /diagnosis/precheck?loopIds=&window=` | 徽标 |

| 最新结论卡 | `GET /diagnosis/runs/latest?loopId=` | 含 metricSummary 正负指标 |
| 结论全量抽屉 | `GET /diagnosis/runs/{runId}` | operatorResults/fusionResults/symptomTags/rationale/recommendations/evidenceCharts |

| 演变时间线 | `GET /diagnosis/runs/loop-archive?loopId=&window=30d/90d/all` | 泳道+置信趋势+KPI mini+处置/整定事件线 |
| 复核/建议 | `POST /diagnosis/runs/{id}/review`、`GET/POST .../actions` | 页内可用 |

### 1.5 参数整定剖面

| 动作 | 端点 | 备注 |
|---|---|---|

| 四步流程 | `POST /tuning/identify` → `POST /tuning/tune/matrix` → `POST /tuning/simulate|compare` → `POST /tuning/tasks` | 无服务端会话；模型凭据 sourceRecordId/riskConfirmed 按 tuning.py 规则；复用 `use-tuning-workbench` |

## 2. 后端缺口与排期（G1-G4）

| # | 缺口 | 核实结论（2026-10-02 只读核对） | 建议 | 状态 |
|---|---|---|---|---|
| G1 | fitness 出口缺失 | `workbench_summary.py` 无 fitness 字段；旧前端读 `summary.fitnessLevel` 为空挂；服务层 `get_latest_fitness_per_loop`（services/loop_fitness.py）已存在 | 推荐：`/monitor/loops/{id}/summary` 补 `fitnessLevel/fitnessTags`（服务层现成，改动小）；备选：新端点 `GET /loops/{id}/fitness` | 待后端排期，阻塞 P2-5 |
| G2 | 评估历史缺手动来源 | `performance.py` 仅查 `KpiSnapshotHourly`（自动整点+backfill 重算覆盖）；手动 custom 在 `kpi_snapshot_custom` 独立表，无按 loop 查询端点 | 方案 a：snapshots 加 `includeCustom=true` 联合两表（推荐，一次返回+dataLineage 区分）；方案 b：前端并行调 custom 任务结果接口拼装 | 待后端排期，阻塞 P2-2 |
| G3 | `/tasks` 无 loopId 筛选 | tasks.py 查询参数无 loopId | 可选增强：加 loopId 参数（任务级"发起记录"精确查询） | 不阻塞，登记待办 |
| G4 | 效果验证数据 | `verification/data` 现成可用（波形+kpi_before/after+afterTruncated；windowHours ∈ 1/2/4/8/24/72/168） | 无需改动；前端窗口选择器限 7 档并处理 afterTruncated | 关闭 |

## 3. 对接纪律

1. 前端一律走 `src/api/` 现有封装层新增 `api/workbench360.ts`，禁止组件内直连 URL；
2. 所有列表默认带分页与总数回显（诚实化：静默截断禁止）；
3. 状态字典只引用 `#/constants/clpm-ui.ts`；本页新增 UI 状态（旅程条段色、包络图例）在该文件扩展；
4. G1/G2 落定前，对应 UI 元素按"缺数据显式提示"渲染（诚实化原则），禁止用演示数据填充。
