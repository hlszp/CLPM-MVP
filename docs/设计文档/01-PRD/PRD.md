## 1. 文档概述

### 1.1 文档目的
本文件将前期的预研需求、系统架构及最新的业务战略补充要求收敛为"面向最终产品交付"的正式产品需求文档。本文档详细规划了 CLPM 的完整功能模块与底层算法指标边界，作为后续功能规格设计 (FDS)、系统架构设计 (ADS) 及前后端开发的**唯一事实来源 (Single Source of Truth)**。

版本号按用途分层管理：本文档的 v6.1 表示产品需求与设计基线；后端 `APP_VERSION`（当前默认 `1.0.0`）表示运行时 API 元数据；Git tag 表示可发布构建。三者不属于同一序列，不要求数值相同。

### 1.2 引用标准与规范
本产品的业务逻辑、指标计算与工程实践需严格参考或符合以下行业标准及规范：
* **GB/T 44693.1-2024** 《危险化学品企业工艺平稳性 第1部分：管理导则》
* **GB/T 44693.2-2024** 《危险化学品企业工艺平稳性 第2部分：控制回路性能评估与优化技术规范》
* **GB/T 33009-2016** 《工业自动化和控制系统网络安全》
* **ISA-112** SCADA Systems Standards (控制系统生命周期管理规范参考)

### 1.3 专用术语与缩略语定义
| 术语 / 缩略语 | 英文全称 | 定义说明 |

## 2. 产品定义与商业价值

### 2.1 产品定位
面向**所有具备大量自动化控制回路的流程工业**（如石油、化工、电力、冶金、造纸、医药中间体等），支撑企业安全生产与工艺平稳性的控制回路全生命周期绩效治理与优化闭环平台。

**产品化定位**：本系统是**产品化、工具化**的产品，不是项目型定制化系统。系统提供充分的配置组态功能，便于用户在工程实践中自助、自主进行相关配置，减少工程实施过程中开发团队的介入。

### 2.2 核心价值链
`可信数据 -> 自动性能评估 -> 异常自动定位 -> 回路诊断 -> 建议与整定 -> 轻量跟踪与验证 -> 规模化交付`

### 2.3 边界说明 (非目标)
* **不是** 单机版或离线版的手动 PID 调参软件。
* **不是** 自动下写 DCS 的黑盒自整定系统（保持绝对安全边界）。
* **不是** APC (先进过程控制)、RTO 或 SIS 的替代品。
* **不是** 繁重且包含多节点审批流的通用设备维修工单系统（EAM）。

### 2.4 产品化设计原则
本系统遵循以下产品化设计原则：
1. **产品化、工具化**：系统是可复用的产品，非项目型定制化系统。提供充分的配置组态能力，用户自助完成配置。
2. **模块内聚、自包含**：每个功能模块自包含其"配置 → 运行 → 分析"三态功能，减少模块间交叉。
3. **配置驱动**：指标公式、诊断算法、引擎规则等均支持用户自助配置，无需开发介入。
4. **实体内聚**：回路作为核心实体，其配置态（台账/映射）和运行态（监控）归属同一模块管理。

## 3. 用户角色与权限模型 (RBAC)

系统采用基于角色的访问控制，确保操作合规与安全审计。系统定义 5 个角色，英文枚举对齐实现契约 v2.0 §5 与 UIUX v6.1 §2.6。

| 用户角色 | 英文枚举 | 核心关注点 / 典型场景 | 权限与职责边界 |
|---|---|---|---|
| **系统管理员** | `ADMIN` | 算法配置是否合理？平台运行是否健康？ | **管理层**：全模块、全配置、全审计；管理工厂模型，配置指标与算法阈值，管理用户，查看审计日志。 |
| **仪控工程师** | `IC_ENGINEER` | 每天查看"低效回路排行榜"，分析诊断原因，导出维修/整定建议单。 | **执行层**：业务模块全流程，可编辑异常跟踪和回路配置；配置回路与 tag 关联，查看性能看板，分析波形，标记异常跟踪状态。 |
| **工艺/设备工程师** | `PE_ENGINEER` | 回路波动是否由工艺扰动或阀门设备引起？对质量有何影响？ | **协同层**：可查看评估、监控、诊断汇总；可参与异常跟踪；确认工艺扰动/阀门粘滞问题，协助排查。 |
| **外部专家团队** | `EXPERT` | 疑难回路的根因分析与高级参数整定支持。 | **服务层**：可查看诊断与整定相关页面，可参与异常跟踪和专家建议；诊断复核，出具高级诊断意见与整定模型样例。 |

### 4.2 回路管理

回路是系统核心实体。AAS 同步的是 **tag 位号**（非回路实体），回路由用户在 CLPM 系统中创建并关联 tag。本模块管理回路全生命周期。

#### 4.2.0 回路状态机

回路状态枚举对齐实现契约 v2.0 §6，共 3 个状态。历史文档中的 `ACTIVE`/`PAUSED`/`DECOMMISSIONED` 统一视为旧命名。

| 状态枚举 | 中文显示 | 含义 |
|---|---|---|
| `READY` | 就绪 | 回路配置完整（PV/SP/OP/MODE 必填 tag 已关联），可参与评估 |
| `PARTIAL` | 部分配置 | 回路必填 tag 缺失或配置不完整，标红提示，不参与评估聚合 |
| `INACTIVE` | 已停用 | 回路已退役或人工停用，不参与评估 |

#### 4.2.1 AAS Tag 同步
* **Tag 同步**：系统定期从 AAS 同步所有 OPC tag 位号信息（tag 名/描述/当前值/数据质量）。
* **数据质量**：AAS 中的数据质量主要针对 **PV（过程测量）值**，PV tag 携带质量码（`GOOD` / `BAD` / `UNCERTAIN`，对齐实现契约 v2.0 §6 PV Quality 状态机）。
* **当前接口边界**：数据源配置与连接测试使用 `/api/v1/datasource/*`；DCS 品牌、型号与 MODE 映射配置使用 `/api/v1/dcs/*`，该接口不提供参数下写。
* **实现口径（D1，2026-07-21 对齐）**：后端 `/api/v1/aas/*` 端点与 Celery 同步任务保留，承担 AAS 配置、同步触发、同步状态与日志、Tag 列表查询能力；前端 AAS 同步入口以实现契约 v2.0 §2 与当前路由模块为准。历史文档中描述的"独立 AAS 同步管理 UI"死代码条款已删除，不再作为需求项。

#### 4.2.2 工厂层级配置
* **工厂空间建模**：支持可视化的 `工厂 -> 装置 -> 单元` 多级层级结构配置。

#### 4.2.3 回路台账管理
* **回路创建**：用户创建回路，填写回路位号、描述、所属单元。
* **扩展配置**：用户配置评分权重、启用状态、备注等扩展参数。
* **回路分类配置（v6.0 新增，对齐 DDS v6.0 §3.6 `loop_ledger` 新增字段）**：
  * **控制类型 (control_type)**：流量 FLOW / 压力 PRESSURE / 温度 TEMPERATURE / 液位 LEVEL / 成分 COMPOSITION（用于异常值检测阈值差异化，详见 §5.5.3）。
  * **重要性等级 (importance_level)**：高/中/低，影响装置级聚合权重与告警优先级。
  * **是否纳入评估 (include_in_evaluation)**：布尔值，标记为 false 的回路不参与装置级/单元级评分聚合。
* **运行态读取（只读）**：控制方式（从 MODE tag 读取）、PID 参数（从 PID tag 读取）为只读展示，不可手动编辑。
* **AAS 同步状态**：展示最后同步时间、tag 总数。

#### 4.2.4 Tag 关联管理
* **Tag 关联**：从 AAS 同步的 tag 列表中，为回路关联 7 个 OPC tag：
  * **PV tag**（必填，过程测量值，含质量码）
  * **SP tag**（必填，设定值）
  * **OP tag**（必填，输出值）
  * **MODE tag**（必填，控制模式）
  * **PID_P tag**（可选，比例参数）
  * **PID_I tag**（可选，积分参数）
  * **PID_D tag**（可选，微分参数）
* **关联校验**：PV/SP/OP/MODE 必填，缺失时回路状态为 `PARTIAL`，标红提示。

#### 4.2.5 回路监控
* **回路监控列表**：以列表/卡片双视图展示所有控制回路的运行态（位号/PV/SP/OP/MODE 当前值/控制方式/评分/状态）。支持按装置/单元筛选和回路号模糊查询。
  > **实现状态（D6，2026-07-21 对齐）**：卡片视图与监控数据导出功能当前**未实现**，列为后续阶段交付。当前版本仅提供列表视图；导出能力见 §4.3.5 性能统计报表与 §4.4.5 诊断统计报表。
* **回路运行详情**：点击回路展示详情，含基础信息、Tag 关联信息、运行态参数、PV/OP/SP 时序趋势波形（PV 线根据质量码断线）、近期 KPI 摘要。

#### 4.2.6 Tag 管理子页（v6.0 新增）

Tag 管理为回路管理模块的独立子页，路由 `/tag/list`（对齐实现契约 v2.0 §2 与 UIUX v6.1）。

* **Tag 列表**：展示 AAS 同步的所有 OPC tag 位号信息（tag 名/描述/当前值/数据质量/最后同步时间）。
* **筛选与查询**：支持按 tag 类型（PV/SP/OP/MODE/PID_P/PID_I/PID_D）、数据质量（GOOD/BAD/UNCERTAIN）、是否已关联回路、所属装置筛选。
* **状态展示**：明确展示每个 tag 的关联状态（已关联回路/未关联），便于用户排查未关联的孤立 tag。
* **编辑与导入（D2，2026-07-21 对齐）**：Tag 管理页除展示 AAS 同步结果外，支持编辑 tag 描述等属性，并支持批量导入 tag。tag 来源以 AAS 同步为主，支持手工补充与修正；历史文档中"Tag 管理页仅展示、不支持手动新增/编辑"的只读条款已废止。

#### 4.2.7 实时数据断点续传（D4，2026-07-20 上线）

实时数据源（SignalR Hub）中断后，系统需自动检测缺口并在恢复后补齐缺失数据，确保 TDengine 本地时序存储的连续性，避免计算任务因数据缺口产出 `INCONCLUSIVE` 快照。

* **Checkpoint 机制**：实时订阅器维护接收 checkpoint（最后成功落库时间戳）；连接中断时 checkpoint 不丢失，恢复后作为缺口检测起点。
* **缺口检测与补数**：连接恢复后，系统按 checkpoint 与当前时间检测缺口窗口，对存在缺口的回路触发 gap backfill 任务（`GAP_BACKFILL_*`），从远端历史接口拉取缺失时段数据写入本地 TDengine。
* **补数安全约束**：gap backfill 复用 `import_history_data` 时必须采用 `conflict_strategy="skip"`，禁止 overwrite（overwrite 会先 DELETE 误删实时行）。
* **失败处理**：补数失败不推进 checkpoint，启动延迟重试（指数退避）；失败任务登记 Redis 任务记录（来源标记 `auto-backfill`），任务列表可见，失败接告警。
* **数据架构口径**：补数走远端历史接口；计算类历史数据查询一律本地 TDengine（详见 §8 数据架构需求与 `docs/过程文档/data-architecture-decision-local-first-2026-07-20.md`）。

### 4.3 性能评估

本模块自包含"指标配置 → 引擎规则 → 全量持续计算 → 全局看板与低效排行 → 统计分析 → 任务管理 → 历史重算"全流程。

#### 4.3.1 性能指标配置（路由 `/metric/config`）

* **指标管理**：基于 3+1+8 指标体系管理 12 项指标（3 核心质量指标 A/F/S + 1 折扣因子 R + 8 扩展指标）的计算公式、权重、阈值、启用状态。详见 §5.1。
* **权重约束** [R2 口径，2026-07-22 裁决]：3 核心质量指标 (A/F/S) 的权重总和须大于 0；**`metric_config.weight`（权重配置管理页面，按指标维护）为唯一用户入口**。
* **权重模板（出厂默认 / 兜底）** [R2 口径]：系统内置 4 类控制类型权重模板（`loop_type_weight` 表），作为**出厂默认 / 兜底回退**——仅当 `metric_config.weight` 缺失时按回路 `control_type` 回退取值。运行时优先级链：`MetricConfig.weight` > `LoopTypeWeight` > `None`（对应 `kpi_calc._build_weights_map`）。
  * `STABLE`：稳定型回路，权重 (a/f/s) = (0.2 / 0.3 / 0.5)，侧重平稳率。
  * `SLOW`：慢速响应回路，权重 = (0.3 / 0.1 / 0.6)，侧重准确率与平稳率。
  * `FAST`：快速响应回路，权重 = (0.2 / 0.5 / 0.3)，侧重快速响应率。
  * `LOGIC`：逻辑控制回路，权重 = (0.0 / 0.4 / 0.6)，不考核准确率，侧重快速响应率与平稳率。
* **性能定级配置（v6.0 新增，对齐 FDS v6.0 §1.3 与 DDS v6.0 §3.6 `metric_config.grading_thresholds`）**：系统支持 5 级性能定级阈值配置（EXCELLENT/GOOD/FAIR/WARNING/POOR），阈值作用于综合评分 P，由系统管理员按工厂/装置维度配置，详见 §5.1.5。
* **指标数据需求配置（v6.0 新增，对齐 DDS v6.0 §3.2 `clpm_metric_data_requirement` 表）**：每个指标声明其数据需求，包括依赖 tagGroup（详见 §8.3）、采样频率、数据窗口长度、Metric Validity Mask（详见 §5.5.4）。DataPlanner 基于指标数据需求生成取数计划，详见 §8.1。
* **可信度阈值配置**：系统管理员通过 `/api/v1/configs/confidence-thresholds` 维护 A/B/C/D/E 阈值；配置变更持久化到数据库、记录审计日志，并在处理该请求的 API 进程内即时更新可信度判定缓存。独立 Celery worker 的跨进程同步机制尚未实现，当前不承诺配置变更对全部运行时进程即时生效。
* **指标启停**：指标停用后，相关指标显示 `INCONCLUSIVE`。停用核心质量指标时其权重置零并重新归一化；停用扩展指标不影响综合评分但影响诊断能力。

#### 4.3.2 引擎规则配置（`/metric/config` 内聚合配置 Tab）
* **引擎管理**：配置评估引擎的计算周期、数据拉取规则、调度参数。
* **规则变更**：规则变更需确认，变更记录审计日志。

#### 4.3.3 全量持续计算
* **自动计算**：后台服务按设定节拍自动拉取全量运行数据，持续计算性能指标，无需人工干预。
* **多维层级评估**：输出单回路综合评分，自动聚合生成单元级、装置级评分。
* **装置级三大 KPI（v6.0 明确，对齐 FDS v6.0 §1.3）**：装置级聚合输出三项核心 KPI —— **自控率 (auto_mode_rate) / 好值率 (good_value_rate) / 平稳率 (stability_rate，unit-level 聚合字段名)**。装置级 KPI 阈值要求对齐 DB32/T 4822—2024：自控率/平稳率 ≥ 95%。
* **装置级汇总排除（v6.0 新增，对齐 DDS v6.0 §3.6 `unit_kpi_summary` 字段）**：装置级 KPI 汇总支持排除指定回路（`excluded_loops`，如停用回路、`include_in_evaluation=false` 回路、`INCONCLUSIVE` 快照），并维护汇总状态（`status`）。

#### 4.3.4 装置性能与回路性能（路由 `/metric/pid-dashboard` + `/metric/loop-performance`）
* **全局看板**：展示 3+1+8 指标体系摘要卡片（3 核心质量指标 + 1 折扣因子 + 综合评分 + 好值率可信度指示）、全厂平稳率趋势、`PARTIAL` 警告横幅、**装置级三大 KPI 卡片（自控率/好值率/平稳率，对齐 DB32/T 4822—2024 ≥ 95% 阈值要求）**。
* **低效回路排行**：多维筛选 + 排行表格（排名/位号/单元/评分/平稳率/预诊/计算状态/处理状态/可信度等级）。

#### 4.3.5 性能统计报表（路由 `/metric/kpi-report`）
* **统计分析**：KPI 趋势对比折线图、装置评分排名柱状图、差等生分布饼图。
* **条件筛选**：支持时间范围/装置/单元/指标筛选，图表结合呈现，支持导出。

#### 4.3.6 自动报表快照
* **周期报表**：系统按班、日、周、月自动生成标准的《控制回路性能评估报告》并归档（报表管理归入系统管理模块）。

#### 4.3.7 任务管理 (Evaluation Tasks)

任务管理为性能评估模块的子模块（非独立模块），统一路由为 `/metric/tasks`；任务列表、历史重算、历史快照与任务策略均为该页面内部 Tab。系统应支持两类评估任务，分别服务"持续监测"与"按需分析"两种场景。

**A. 标准评估任务 (Standard Evaluation Task)**
* **触发方式**：每小时定时执行（cron 调度），全量回路覆盖。
* **数据窗口**：默认 1 小时滚动窗口。
* **结果存储**：结果写入 **KPI 小时快照表** (`kpi_snapshot_hourly`，表名对齐 DDS v6.0 §3.2)，作为装置级/单元级聚合统计与周期报表的唯一数据源。
* **聚合参与**：参与装置级、单元级、工厂级评分聚合（见 §4.3.3）。
* **失败重试**：任务失败自动重试 3 次，失败记录入审计日志并告警。

**B. 自定义评估任务 (Custom Evaluation Task)**
* **触发方式**：用户按需手动触发，选择目标回路（单回路/多回路）、目标指标（3 核心质量指标 + 1 折扣因子 + 8 扩展指标的子集）、自定义时间范围（历史回溯）与数据窗口。
* **结果存储**：结果写入 **KPI 自定义快照表** (`kpi_snapshot_custom`，表名对齐 DDS v6.0 §3.2)，与 KPI 小时快照表物理隔离。
* **聚合参与**：**不参与**装置级/单元级/工厂级评分聚合，仅用于用户临时分析与对比。
* **并发限制**：单用户并发自定义任务数受限（默认 ≤ 3），全系统并发自定义任务数受限（默认 ≤ 20），避免抢占标准任务资源。

**C. 任务状态查询**
* **任务状态机**：任务状态为 `PENDING` → `RUNNING` → `SUCCESS` / `FAILED` / `CANCELLED`。
* **KPI 快照状态机（与任务状态机是两个独立对象，对齐实现契约 v2.0 §6）**：每条 KPI 快照记录的状态为 `SUCCESS`（成功，数据完整）/ `PARTIAL`（部分有效，部分指标 INCONCLUSIVE）/ `INCONCLUSIVE`（数据不足，综合评分留空）。任务状态与快照状态分离：一个 `SUCCESS` 任务可产出多条 `PARTIAL` 或 `INCONCLUSIVE` 快照（如某回路数据不足）。
* **进度查看**：RUNNING 状态下展示进度（已处理回路数/总回路数、已计算指标数/总指标数、当前阶段：取数/预处理/指标计算/可信度判定）。
* **结果查看**：SUCCESS 后可直接跳转结果详情；FAILED 展示失败原因（取数失败/算法异常/超时等）。
* **任务列表**：支持按任务类型（标准/自定义）、状态、时间范围、创建人筛选查询。

#### 4.3.8 历史重算 (Historical Recomputation，`/metric/tasks` 内部 Tab)

该能力在当前 IA 中并入评估任务页面，不暴露独立主菜单路由。

* **重算场景**：当指标公式/权重/阈值/算法版本变更后，用户可对指定时间范围的历史数据触发重算，使历史快照与新配置对齐。
* **重算范围**：支持按回路（单回路/多回路）、时间范围、目标指标子集选择重算范围。
* **结果处理**：重算结果覆盖原 `kpi_snapshot_hourly` 记录（保留原值的版本快照入审计日志），不写入 `kpi_snapshot_custom`。
* **并发控制**：重算任务复用自定义任务的并发配额（避免与标准任务资源抢占），重算进度在 `/metric/tasks` 的历史重算 Tab 展示。
* **审计留痕**：每次重算记录操作人、时间、范围、变更前后配置版本号。

#### 4.3.8.1 回路历史数据导入

回路历史数据导入使用 `/api/v1/loops/data-import/*`，支持预览、提交、进度查询、取消与删除；导入任务与历史重算任务在 UI 上统一归入任务型操作，但使用独立的接口与任务记录。

#### 4.3.9 快照查询（`/metric/tasks` 内部 Tab）

该能力在当前 IA 中并入评估任务页面，不暴露独立主菜单路由。

* **快照列表**：支持按回路/装置/时间范围/快照状态（SUCCESS/PARTIAL/INCONCLUSIVE）/可信度等级（A/B/C/D/E）筛选 KPI 快照记录。
* **快照详情**：展示单条快照的完整指标值、综合评分、可信度等级、数据血缘信息（详见 §5.4.1）。

### 4.4 诊断中心

### 5.1 性能评估指标池 (Performance Metrics)
系统需内置并支持 3+1+8 指标体系结构的计算与配置，严格对齐 GB/T 44693.2-2024 附录 B（性能评估指标）与附录 F（故障诊断指标）以及《关键算法设计说明 v2.0》与 FDS v6.0 §1.3。所有指标均支持用户自助配置（公式/权重/阈值/启停/控制类型）。

#### 5.1.1 指标体系结构（3+1+8）

指标体系由三组共 12 项指标构成（3 核心 + 1 折扣 + 8 扩展 = 12 项指标计算器，对齐 FDS v6.0 §1.3），分别承担"参与综合评分"、"投用系数修正"与"扩展诊断/可信度修正"三类职责。

> **术语统一说明（v6.0 对齐 FDS v6.0 §1.3 / DDS v6.0 §3.7）**：
> * "快速响应率"（非"快速率"），英文 Fast Response Rate。
> * "平稳率"（非"稳定率"），loop-level 字段名为 `steady_rate`，unit-level 聚合字段名为 `stability_rate`。
> * "有效自控率"（非"自控率"）作为折扣因子 R；`AUTO_MODE_RATE` 作为基础统计指标，归入扩展指标。
> * Action Tracker 使用"已实施" `IMPLEMENTED`；Diagnosis Tag 使用"已处理" `RESOLVED`，两者是不同对象，不互相替换。
>
> **命名规范说明**：扩展指标的 `metric_code` 以《关键算法设计说明 v2.0》、FDS v6.0 §1.3 与 DDS v4.1 数据库列名为准。原 PRD v3.x 中的 `VALVE_STICTION_RATE`/`OVERAGGRESSIVE_RATE`/`OVERCONSERVATIVE_RATE`/`EXTERNAL_DISTURBANCE_RATE`/`QUALITY_ABNORMAL_RATE` 已调整：前四项迁入诊断标签体系（详见 §5.2）；v4.0 的 `STICTION_COEFF`/`OUTPUT_TRAVEL_INDEX`/`STEADY_STATE_TIME` 在 v6.0 中对齐 FDS v5.1 重命名为 `STICTION`/`OUTPUT_TRIP_RATE`/`SETTLING_TIME`。

> **装置级三大 KPI（v6.0 明确，对齐 FDS v6.0 §1.3 与 DB32/T 4822—2024）**：装置级聚合输出三项核心 KPI —— 自控率 (`AUTO_MODE_RATE`) / 好值率 (`GOOD_VALUE_RATE`) / 平稳率 (unit-level `stability_rate`)。装置级自控率/平稳率阈值要求 ≥ 95%。

> **已迁入诊断标签的指标**：原 v3.x 的 `OVERAGGRESSIVE_RATE`/`OVERCONSERVATIVE_RATE`/`EXTERNAL_DISTURBANCE_RATE`/`QUALITY_ABNORMAL_RATE` 不再作为独立指标计算，改为诊断标签体系（§5.2）中的 `OVERAGGRESSIVE`/`OVERCONSERVATIVE`/`EXTERNAL_DISTURBANCE`/`QUALITY_ABNORMAL` 标签，由诊断引擎基于多指标特征综合判定。

#### 5.1.2 综合评分模型

综合评分基于 3 个核心质量指标 (A/F/S) 加权求和，并由折扣因子 (R，有效自控率) 进行投用系数修正。公式如下：

```
P = (A·a + F·f + S·s) / (a + f + s) × R
```

**公式变量说明**：
* `A`、`F`、`S`：分别为准确率、快速响应率、平稳率的归一化值（0~1）。
* `a`、`f`、`s`：分别为准确率、快速响应率、平稳率的权重，用户通过"权重配置管理"页面在 `metric_config.weight` 维护（唯一用户入口）；4 类控制类型模板（STABLE/SLOW/FAST/LOGIC，存储于 `loop_type_weight` 表）为出厂默认兜底，仅当 `metric_config.weight` 缺失时按回路 `control_type` 回退取值。运行时优先级链：`MetricConfig.weight` > `LoopTypeWeight` > `None`。三项权重总和须大于 0。权重模板详见 §4.3.1。
* `R`：投用系数，即有效自控率（`EFFECTIVE_AUTO_MODE_RATE`），由基础自控率（`AUTO_MODE_RATE`）派生（如 `R = auto_mode_rate / 100`），用于将评分按投用水平折算。当自控率为 0 时，R=0，综合评分为 0；当自控率为 100% 时，R=1，评分等于核心质量指标的加权平均。

**与 v3.1 评分模型的差异**：
* v3.1 模型 `Score = (Σ wᵢ × ηᵢ_norm) × R_auto` 将 6 大 KPI 全部纳入加权求和（含好值率/振荡率/饱和率）。
* v4.0+ 模型仅将 3 核心质量指标 (A/F/S) 纳入加权求和，振荡率/饱和率等迁入扩展指标，**好值率不再直接参与评分，而是通过指标可信度间接影响评估结果有效性**（详见 §5.4）。

#### 5.1.3 指标启停与 INCONCLUSIVE 处理
* **指标启停**：指标停用后，相关指标值显示 `INCONCLUSIVE`，并联动影响综合评分（停用核心质量指标时其权重置零并重新归一化）。
* **INCONCLUSIVE 处理**：当回路好值率导致指标可信度降为 E 级时（详见 §5.4），整条快照标记为 `INCONCLUSIVE`，综合评分留空（不以 0 分掩盖数据缺失）。
* **指标方向说明**：正向指标值越高越好；反向指标值越低越好。反向指标在排序/展示时需 UI 明确标注。

#### 5.1.4 表达式引擎
`metric_config.formula` 字段的自定义计算公式采用 `simpleeval` 安全沙箱执行，支持变量域（PV/SP/OP/MODE/abs/sqrt/...）与白名单函数库，禁止 import/exec/eval 等危险操作，表达式长度限制 500 字符，执行超时 5 秒。

#### 5.1.5 性能定级 (Performance Grading，v6.0 新增)

系统支持 5 级性能定级（对齐 FDS v6.0 §1.3 与 DDS v6.0 §3.6 `metric_config.grading_thresholds` 字段），作用于综合评分 P，由系统管理员按工厂/装置维度配置阈值：

| 定级 | 英文枚举 | 含义 | 默认阈值（P 值，可配置） |
|---|---|---|---|
| 优秀 | `EXCELLENT` | 回路性能优秀，无需干预 | P ≥ 90 |
| 良好 | `GOOD` | 回路性能良好，可保持 | 80 ≤ P < 90 |
| 合格 | `FAIR` | 回路性能合格，需关注 | 70 ≤ P < 80 |
| 警告 | `WARNING` | 回路性能较差，需排查 | 60 ≤ P < 70 |
| 差 | `POOR` | 回路性能极差，需立即处置 | P < 60 |

> 定级阈值支持用户自助配置（系统管理员权限），配置变更记录审计日志。定级结果在低效回路排行、装置级看板、报表中统一展示。

### 5.2 故障诊断指标与模式范围 (Diagnostic Features)
系统自动诊断引擎需支持对以下 8 类诊断标签的识别与输出，标签体系严格对齐《关键算法设计说明 v2.0》§5.0 诊断标签体系。所有诊断算法支持用户自助配置（算法类型/参数阈值/计算方法/启停）。诊断标签的管理维度需求（严重等级/来源指标/触发条件/状态管理）详见 §5.6。

| 序号 | 标签代码 | 中文名称 | 业务含义 | 建议处置方向 |
|---|---|---|---|---|
| 1 | `OSCILLATION` | 振荡 | 回路存在周期性振荡，控制偏差呈规律性正负交替 | 检查回路耦合，排查振荡传播源 |
| 2 | `VALVE_STICTION` | 阀门粘滞 | 阀门执行机构存在摩擦粘滞，OP 变化但 PV 响应迟缓 | 检查阀门执行机构，清洁或更换阀门填料 |
| 3 | `OVERAGGRESSIVE` | 过度激进 | PID 参数过于灵敏，设定值变更时超调过大或持续振荡 | 减小 Kp 或增大 Ti，参考 IMC 整定 |
| 4 | `OVERCONSERVATIVE` | 过度保守 | PID 参数过于迟缓，响应慢、偏差长时间不收敛 | 增大 Kp 或减小 Ti |
| 5 | `EXTERNAL_DISTURBANCE` | 外部扰动 | 回路频繁受到外部扰动，PV 突变与 SP 变更无关 | 排查上游工艺扰动，考虑前馈控制 |
| 6 | `QUALITY_ABNORMAL` | 质量异常 | PV 质量码异常（通信中断/仪表故障/数据冻结/超量程） | 检查仪表与通信链路 |
| 7 | `OUTPUT_SATURATION` | 输出饱和 | 控制器输出 OP 长时间停留在限位（0% 或 100%） | 检查阀门选型，排查积分饱和 |
| 8 | `MANUAL_REVIEW` | 人工复查 | 多算法置信度均不足，无法自动判定根因 | 建议专家人工介入分析 |

**诊断算法矩阵**：每个标签对应一种或多种诊断算法（详见 FDS §5.4 诊断算法矩阵），多算法结果采用 Dempster-Shafer 证据理论融合置信度。当所有算法置信度均 < 50% 时，输出 `MANUAL_REVIEW` 兜底标签。

### 5.3 参数整定方法支持范围 (Tuning Methods) [二期]
系统需内置以下 7 种主流的工业级模型辨识与参数整定算法，严格对齐 GB/T 44693.2-2024 §8 性能优化要求，供不同场景选用：

**A. 模型辨识算法（2 种）**

| 序号 | 算法名称 | 模型形式 | 适用场景 |
|---|---|---|---|
| 1 | FOPDT 模型辨识 | G(s) = K·e^(-θs) / (τs+1) | 一阶惯性加纯滞后过程，采用两点法 + 面积法组合辨识 |
| 2 | SOPDT 模型辨识 | G(s) = K·e^(-θs) / (T₁T₂s² + (T₁+T₂)s + 1) | 高阶过程、欠阻尼过程，FOPDT 拟合度 R²<0.85 时自动升级 |

**B. PID 整定算法（5 种）**

| 序号 | 算法名称 | 适用场景 | 特点 |
|---|---|---|---|
| 3 | IMC 整定法 (Internal Model Control) | 工业界最常用，平衡鲁棒性与响应速度 | 基于一阶 Padé 近似，λ 可调（0.8θ~3θ） |
| 4 | Lambda 整定法 | 纸业及对超调极其敏感的化工过程 | λ 可调（3θ~3τ），无超调 |
| 5 | Ziegler-Nichols 整定法 (Z-N) | 经典基于临界振荡或阶跃响应的工程算法 | 闭环临界法 + 开环反应曲线法 |
| 6 | Cohen-Coon 整定法 | θ/τ > 0.5 的大滞后系统 | 基于反应曲线的大滞后整定 |
| 7 | SIMC 整定法 (Skogestad) | 简化 IMC 方法，工程实用性强 | PI/PID 均支持，τc 默认等于 θ |

**整定流程**：模型辨识 → 整定公式计算 → 闭环仿真验证（RK4 ODE 求解器）→ 性能指标对比（上升时间/超调/稳定时间/ITAE）。整定记录需保存模型拟合度 fitting_score（R²），R² > 0.9 为优秀拟合。

### 5.4 数据质量与可信度需求 (Data Quality & Credibility)

本节定义系统在数据质量追溯与指标可信度分级方面的需求，确保每一条评估结果可追溯、可解释、可判定有效性。本节为 v4.0 新增需求。

#### 5.4.1 数据血缘追溯 (Data Lineage)
系统应为每个指标结果记录完整的数据血缘信息，支撑结果可追溯与可审计。**数据血缘字段结构对齐 DDS v6.0 §3.5**，`kpi_snapshot_hourly` 与 `kpi_snapshot_custom` 均包含 5 个独立字段 + 1 个 `data_lineage` JSONB 字段：

**5 个独立血缘字段（数据库列）**：
* `sampling_freq`：采样频率 —— 指标计算所基于的原始数据采样频率（如 1s/1min）。
* `quality_policy`：质量策略 —— 数据预处理采用的质量策略（详见 §5.5，默认 `KEEP_ALL_WITH_VALIDITY`）。
* `valid_rate`：有效数据率 —— 评估时段内有效数据点数占总数据点数的比例（剔除 Bad 质量码、超量程、冻结等异常后的数据可用率）。
* `confidence_level`：可信度等级 —— 该指标的 A/B/C/D/E 可信度等级（详见 §5.4.2）。
* `data_lineage`：JSONB 字段，内部包含以下 6 个子字段：
  * `tag_group`：指标计算取数所用的 tagGroup 分组（BASE/OP_HF/PVOP_HF/MODE_HF/QUALITY_HF，详见 §8.3）。
  * `window_start`：评估窗口起始时间。
  * `window_end`：评估窗口结束时间。
  * `window_length`：评估窗口长度（秒）。
  * `algorithm_version`：计算所用的算法版本号。
  * `threshold_version`：指标阈值版本号。

数据血缘信息随指标快照一并持久化，UI 详情页与导出报告中可下钻查看。

#### 5.4.2 指标可信度分级 (Metric Credibility Grading)
系统应基于有效数据率自动判定指标可信度等级，分为 A/B/C/D/E 五级（阈值对齐 FDS v6.0 §1.3：valid_rate 阈值 95/80/60/20%）：

| 可信度等级 | 有效数据率范围 | 含义 | 对评估结果的影响 |
|---|---|---|---|
| A | ≥ 95% | 高可信 | 评估结果正常使用 |
| B | 80% ~ 95% | 较高可信 | 评估结果正常使用，UI 标注可信度 |
| C | 60% ~ 80% | 中等可信 | 评估结果可用，UI 显著标注可信度，建议复核 |
| D | 20% ~ 60% | 低可信 | 评估结果仅供参考，UI 警告提示 |
| E | < 20% | 极低可信 | **评估结果标记为 `INCONCLUSIVE`**，综合评分留空 |

**分级规则**：
* 可信度按"指标级"判定，每个指标独立计算其有效数据率与可信度等级。
* 综合评分的可信度取 3 核心质量指标 (A/F/S) 可信度的最低值。
* 可信度等级阈值支持用户自助配置（系统管理员权限）。

#### 5.4.3 INCONCLUSIVE 处理
* 当任一核心质量指标可信度为 E 级时，整条评估快照标记为 `INCONCLUSIVE`，综合评分留空（不以 0 分掩盖数据缺失）。
* INCONCLUSIVE 快照在排行/聚合统计中单独计数展示，不参与装置级/单元级评分聚合的"正常评分"分位，但需在数据完整性看板中显式暴露。
* 好值率（`GOOD_VALUE_RATE`）作为影响可信度的关键扩展指标，不直接参与综合评分，但其值通过有效数据率路径影响可信度等级判定。

#### 5.4.4 KPI 快照状态机 (KPI Snapshot State Machine，v6.0 新增)

每条 KPI 快照记录的状态枚举对齐实现契约 v2.0 §6，共 3 个状态：

| 状态枚举 | 中文显示 | 含义 |
|---|---|---|
| `SUCCESS` | 成功 | 数据完整，所有指标计算成功，综合评分有效 |
| `PARTIAL` | 部分有效 | 部分指标计算成功，部分指标 `INCONCLUSIVE`，综合评分仍可输出但需标注可信度 |
| `INCONCLUSIVE` | 数据不足 | 核心质量指标可信度为 E 级，综合评分留空 |

> KPI 快照状态机与任务状态机（§4.3.7 C，`PENDING`/`RUNNING`/`SUCCESS`/`FAILED`/`CANCELLED`）是两个独立对象：任务状态描述评估任务的执行进度，快照状态描述单条快照记录的数据有效性。一个 `SUCCESS` 任务可产出多条 `PARTIAL` 或 `INCONCLUSIVE` 快照（如某回路数据不足）。

### 5.5 数据预处理需求 (Data Preprocessing)

本节定义系统在原始时序数据进入指标计算前的预处理需求，确保计算输入数据的质量可控、异常可识别。本节为 v4.0 新增需求。

#### 5.5.1 质量策略 (Quality Strategy)
系统采用 `KEEP_ALL_WITH_VALIDITY` 质量策略作为默认策略：
* **保留所有数据点**：原始时序数据点不进行物理剔除，所有采样点均保留在 DataBlock 中。
* **打有效性标记**：每个数据点附加 `validity` 标记（VALID/INVALID），INVALID 点在指标计算时按指标各自的 Metric Validity Mask 决定是否参与计算（详见 §5.5.4）。
* **策略可配置**：质量策略支持后续扩展（如 DROP_INVALID、IMPUTE_INVALID），但 v4.0 默认且仅实现 `KEEP_ALL_WITH_VALIDITY`。

#### 5.5.2 异常值检测 (Outlier Detection)
系统应支持 8 类异常值检测，检测结果写入数据点的 `validity` 标记与异常原因码：

| 序号 | 异常类型 | 检测说明 | 典型原因码 |
|---|---|---|---|
| 1 | 超量程 (Out-of-Range) | 数值超出配置的量程上下限 | `OUT_OF_RANGE` |
| 2 | 冻结 (Freeze/Stuck) | 数值在滑动窗口内几乎不变化（标准差 < 阈值） | `FROZEN` |
| 3 | 跳变 (Jump) | 相邻采样点变化幅度超过跳变阈值 | `JUMP` |
| 4 | 尖峰 (Spike) | 单点突变且前后点回落，持续时间 < 阈值 | `SPIKE` |
| 5 | NaN/Inf | 数值为 NaN/Inf 或非数值 | `NaN` |
| 6 | 时间戳异常 (Timestamp Anomaly) | 时间戳缺失、重复、乱序、未来时间 | `TS_ANOMALY` |
| 7 | 质量码异常 (Quality Code Abnormal) | PV tag 携带的 OPC 质量码为 BAD/UNCERTAIN | `QC_BAD` |
| 8 | 高频噪声 (High-Frequency Noise) | 高频分量能量占比超过阈值 | `HF_NOISE` |

#### 5.5.3 控制类型差异化阈值 (Control-Type-Specific Thresholds)
异常值检测阈值按控制类型（流量/压力/温度/液位/成分）区分，不同控制类型的物理特性不同，冻结窗口长度与跳变阈值差异显著：

| 控制类型 | 冻结窗口 (默认) | 冻结标准差阈值 | 跳变阈值 (相对量程) | 说明 |
|---|---|---|---|---|
| 流量 (FLOW) | 30s | 0.1% | 20% | 流量响应快，冻结窗口短 |
| 压力 (PRESSURE) | 60s | 0.1% | 15% | 压力变化适中 |
| 温度 (TEMPERATURE) | 300s | 0.05% | 5% | 温度惯性大，冻结窗口长，跳变阈值小 |
| 液位 (LEVEL) | 120s | 0.1% | 10% | 液位变化较慢 |
| 成分 (COMPOSITION) | 600s | 0.05% | 3% | 成分分析周期长，跳变阈值最小 |

阈值支持用户自助配置（系统管理员权限），按回路控制类型默认赋值，可逐回路覆盖。

> **控制类型分类维度说明（v6.0 明确，避免混淆）**：本节的控制类型（FLOW/PRESSURE/TEMPERATURE/LEVEL/COMPOSITION，5 类）用于**异常值检测阈值差异化**，对应 `loop_ledger.control_type` 字段。与 §4.3.1 权重模板的 4 类控制类型（STABLE/SLOW/FAST/LOGIC，用于综合评分权重配置）是**两套独立的分类维度**，前者按物理过程分类，后者按控制动态特性分类。

#### 5.5.4 Metric Validity Mask (指标级有效性掩码)
不同指标对数据有效性的容忍度不同，系统应为每个指标配置 Metric Validity Mask，决定哪些异常类型的数据点参与该指标的计算：
* **掩码定义**：每个指标配置一个 validity mask（如 `MASK_STRICT` 仅接受 VALID 点；`MASK_ALLOW_FREEZE` 允许冻结点参与；`MASK_PV_QUALITY` 仅接受 PV 质量码为 GOOD 的点）。
* **默认掩码**：
  * 核心质量指标 (A/F/S)：`MASK_STRICT`（仅 VALID 点参与）。
  * 自控率 (`AUTO_MODE_RATE`)：`MASK_ALLOW_FREEZE`（冻结点仍可判定模式）。
  * 好值率 (`GOOD_VALUE_RATE`)：统计本身基于质量码，使用 `MASK_PV_QUALITY`。
  * 振荡率/饱和率等扩展指标：按算法特性配置对应掩码。
* 掩码支持用户自助配置，配置变更记录审计日志。

### 5.6 诊断标签管理需求 (Diagnostic Label Management)

本节定义诊断标签在管理维度的需求，是对 §5.2 诊断标签体系的补充。本节为 v4.0 新增需求。

#### 5.6.1 标签元数据要求
每个诊断标签实例除标签代码（详见 §5.2 表）外，必须记录以下管理元数据：
* **严重等级 (Severity)**：分为 INFO / WARN / ERROR / CRITICAL 四级，由诊断算法基于特征强度自动判定，支持人工修正。
* **来源指标 (Source Metric)**：触发该标签的来源指标（metric_code，对齐 §5.1.1 C 表，如 `OSCILLATION_RATE`、`STICTION`），用于证据链追溯。
* **触发条件 (Trigger Condition)**：触发该标签的具体条件快照（算法名/阈值/实际值/置信度），支持详情页下钻查看。
* **首次触发时间 / 最近触发时间**：标签首次出现与最近一次出现的时间戳。
* **关联回路 / 关联评估快照**：标签所属回路与触发时的评估快照 ID。

#### 5.6.2 标签状态管理
Diagnosis Tag 支持独立生命周期状态，区别于 §4.4.3 Action Tracker 的处理状态（`PENDING`/`IN_PROGRESS`/`IMPLEMENTED`/`IGNORED`）：
* **活跃 (ACTIVE)**：标签在最近评估周期内被诊断算法持续触发，处于活跃状态。
* **已处理 (RESOLVED)**：工程师确认该诊断标签已处理；这是 Diagnosis Tag 的有效枚举，不等同于 Action Tracker 的 `IMPLEMENTED`。
* **已抑制 (SUPPRESSED)**：已知问题暂不处置（如计划检修），手动抑制以避免持续告警，需注明抑制原因与到期时间。
* 状态变更记录审计日志，支持状态回退。

#### 5.6.3 标签查询与统计
* 支持按回路 / 装置 / 标签代码 / 严重等级 / 状态 / 时间范围多维查询标签列表。
* 支持标签活跃数趋势、严重等级分布、处置时长统计等报表（与 §4.4.5 诊断统计报表联动）。

## 8. 数据架构需求 (Data Architecture)

本节定义系统在数据编排、数据缓存与数据分组方面的架构需求，支撑 3+1+8 指标体系的指标驱动取数、预处理缓存复用与多采样率数据组织。本节工程实现细节对齐《CLPM 后端研发智能体系统提示词与开发指导文档》。

> **数据模型对齐说明（v6.1）**：当前 `backend/app/models/` 共定义 31 张 PostgreSQL ORM 表；完整清单以实现契约 v2.0 §10 的 `__tablename__` 盘点为准。DDS 提供字段/关系设计，但表总数不得再使用历史 17/26 张口径。TDengine 时序表结构独立统计。

### 8.1 DataPlanner 数据编排 (Data Orchestration)

系统应提供 DataPlanner 组件，负责评估任务的指标驱动取数编排：

* **指标驱动取数 (Metric-Driven Data Fetching)**：DataPlanner 接收评估任务（标准/自定义，详见 §4.3.7）与目标指标列表，根据每个指标声明的依赖 tagGroup（详见 §8.3）反推所需取数范围，生成取数计划，避免全量取数造成的资源浪费。
* **取数计划生成**：取数计划包含 tagGroup 列表、时间范围、采样频率、目标 DataBlock 缓存键，支持复用已有 DataBlock 命中缓存（详见 §8.2）。
* **tagGroup 分组取数**：按 tagGroup 分组向 AAS/时序数据库发起取数请求，不同分组按各自采样率获取（详见 §8.3）。
* **与预处理联动**：取数完成后触发数据预处理流水线（详见 §5.5），预处理结果写入 DataBlock 缓存。
* **失败处理**：取数失败按 tagGroup 粒度重试，部分失败时仍可基于已成功 tagGroup 计算依赖该分组的指标，并对其余指标标记 `INCONCLUSIVE`。

### 8.2 DataBlock 缓存 (Data Block Cache)

系统应提供分层缓存组件，缓存预处理数据块与组装结果，支撑多指标计算复用与性能优化。当前实现状态为：L1 DataBlock Cache 与 L2 MetricDataBundle Cache 已接入 DataPlanner；L3 Feature Cache 仅有实现与测试，尚未接入指标计算运行链路，属于预留能力。

* **缓存对象**：DataBlock 是一次预处理产物，包含某个 tagGroup 在指定时间窗口内、带 validity 标记的时序数据点集合（详见 §5.5 质量策略）。
* **缓存键 (Cache Key)**：由 `回路ID + tagGroup + 时间窗口 + 质量策略版本 + 阈值版本` 组合生成，确保阈值/策略变更后缓存自动失效。
* **压缩**：DataBlock 支持压缩存储（如列式编码 + delta-of-delta 压缩），降低存储与传输开销。
* **分层 TTL (Tiered Time-To-Live)**：按数据新旧与访问频率分层设置 TTL：
  * **热层**（近 1 小时 DataBlock）：常驻内存/SSD，TTL 1 小时，支撑标准任务每小时滚动复用。
  * **温层**（近 7 天 DataBlock）：SSD，TTL 7 天，支撑自定义任务历史回溯与 A/B 对比。
  * **冷层**（近 90 天 DataBlock）：对象存储/HDD，TTL 90 天，支撑长周期趋势分析与审计回溯。
* **命中统计**：缓存命中率指标化暴露，纳入系统管理运维看板，命中率低于阈值时告警。
* **淘汰策略**：达到 TTL 或容量上限时按 LRU 淘汰，淘汰记录不影响已落盘的 KPI 小时快照表 `kpi_snapshot_hourly`（持久化结果与 DataBlock 缓存生命周期解耦）。

### 8.3 tagGroup 分组 (Tag Grouping)

系统应按数据用途与采样率将回路关联的 tag 划分为多个 tagGroup，不同分组采用不同采样率与取数策略：

| tagGroup | 包含 tag | 默认采样率 | 用途 |
|---|---|---|---|
| `BASE` | PV / SP | 1 min | 基础性能指标计算（A/F/S 等核心质量指标），数据量小、覆盖广 |
| `OP_HF` | OP（高频） | 1 s | 输出饱和、阀门动作分析等需高频 OP 的指标（如 `SATURATION_RATE`、`OUTPUT_TRIP_RATE`） |
| `PVOP_HF` | PV / OP（高频） | 1 s | 阀门粘滞、过激/过保守等需 PV-OP 高频联合分析的指标（如 `STICTION`） |
| `MODE_HF` | MODE（高频） | 1 s | 自控率（`AUTO_MODE_RATE`，派生有效自控率 R）精确判定、模式切换事件捕捉 |
| `QUALITY_HF` | PV 质量码（高频） | 1 s | 好值率、质量异常率等基于质量码的指标（如 `GOOD_VALUE_RATE`） |

**分组设计原则**：
* **指标驱动选择**：DataPlanner 根据目标指标依赖的 tagGroup 选择性取数，简单指标（如平稳率）仅需 `BASE`，复杂诊断指标（如粘滞系数）需 `PVOP_HF`。指标与 tagGroup 的依赖关系由 §4.3.1 指标数据需求配置声明，对齐 DDS v6.0 §3.2 `clpm_metric_data_requirement` 表。
* **采样率对齐**：同一 tagGroup 内所有 tag 采样率一致，避免重采样对齐开销。
* **可扩展**：tagGroup 定义支持后续扩展（如增加 `SP_HF` 用于设定值变更事件分析），v6.0 默认提供上述 5 个分组。
* **配置化**：回路关联 tag 时系统按 tag 类型自动归入对应 tagGroup，支持用户覆盖。
