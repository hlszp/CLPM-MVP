## 1. 背景与决策

### 1.1 重排动因

v4.4 为工程分析视角：信息密度高（子弹图×6、六维雷达、四率对比柱图），但**结论性弱**——管理层首屏要回答的三个问题是"全厂健康吗、问题在哪、治理进展如何"，v4.4 的三率/快速率/准确率等工程指标对管理层是噪声，而治理闭环（处置待办/本期闭环/治理漏斗）在页面上完全缺席。

### 1.2 方案裁决：方案 A（workbench 直接管理者化） vs 驾驶舱路线

| 方案 | 内容 | 裁决 |
|---|---|---|
| **A（采纳）** | `/dashboard/workbench` 装置总览直接重排为管理者版：健康结论 + 问题清单 + 治理进展为主，工程指标下沉 tooltip / 次级页 | ✅ 用户裁决采纳（2026-08-24） |
| B | 保留 workbench 工程分析版，另起独立驾驶舱页（`docs/MVP设计/11-驾驶舱设计方案.md` 路线） | 搁置/延后：避免两个总览页并存分流；待管理层视图验证后再评估独立驾驶舱的必要性 |

裁决要点：**管理层视图以"健康结论 + 问题清单 + 治理进展"为主**，工程指标下沉；驾驶舱规划文档保留不删，作为后续独立门户/大屏形态的储备。

### 1.3 现状评估要点（v4.4 缺口）

| 维度 | v4.4 现状 | 管理者视角缺口 |
|---|---|---|
| 结论性 | 十一区块仪表盘带（子弹图×6 + MODE 微柱 + 2×2 统计 + 饼图），需逐图解读 | 缺"一句话结论"：评分/问题数/待办/闭环各是多少 |
| 治理闭环 | 页面无任何处置/工单数据 | 处置待办、超期、本期闭环、发现→闭环漏斗完全缺席 |
| 工程指标 | 快速率/准确率/好值率/六维雷达/四率柱图占据主视觉 | 对管理层是噪声，应下沉为 tooltip 或留在评估模块 |
| 实时状态 | §6 独立运行状态卡（MODE 分布 + 阀门越限列表）占中排整列 | 管理者只需 MODE 概览与越限**计数**，列表级细节属监控模块 |
| 趋势 | 五线 + 参评柱全量显示，视觉拥挤 | 默认只开评分 + 自控率两条管理层主线 |

## 3. 各区块设计要点与数据口径

### 3.1 行2 六张结论卡（components/conclusion-cards.vue）

| # | 卡片 | 主数字 | 副行 | 交互 | 数据口径 |
|---|---|---|---|---|---|
| 1 | 全厂综合评分 | avgScore（等级色） | 环比 ↑绿/↓红/→灰（±0.005 持平，缺基线提示"环比暂无基线"） | 无 | board/aggregate 当前窗口；环比 = 当前窗口 − 上一窗口（向前平移一个窗口长度） |
| 2 | 参评回路 | evaluatedLoops / totalLoops | "参评回路 / 总回路" | 无 | board/aggregate（时间窗口径） |
| 3 | 问题回路 | WARNING+POOR 合计（POOR>0 红 / WARNING>0 琥珀） | 警告 N · 不合格 N | 点击 → `/monitor/attention` | governance-summary badLoops |
| 4 | 处置待办 | openOrders（未闭环工单） | 超期 N 单（>0 红显） | 点击 → `/handling/tasks` | governance-summary handling |
| 5 | 本期闭环 | closedInWindow（翠绿） | "时间窗内闭环工单" | 无 | governance-summary handling |
| 6 | 实时自控率 | rate%（等级色）+ MODE 计数微条（自动/串级/远程/先控/手动，手动红显，tooltip 计数+百分比） | 实时角标（`实时 · HH:MM` / 中断置灰，阈值 `VITE_RT_STALE_MINUTES` 默认 10min） | 无 | auto-rate-rt（实时，不随时间窗） |

### 3.2 行3 A 列 全厂健康结构（components/health-structure.vue）

合并原行2 右端等级分布饼图、行2.5 适用性条、§6 运行状态 MODE 分布三块内容：

- **等级分布饼图**：grade-distribution（时间窗口径），扇区悬浮明细
- **适用性分层（L0~L4）**：堆叠横条 + 色块图例行；数据源 grade-distribution 的 `fitnessDistribution`；L0=不可评估（不适用，不计入差回路）
- **MODE 分布横条**：auto-rate-rt modeCounts（实时口径，手动 >0 红色强调），与卡6 微条同源
- **阀门越限计数行**：loop-snapshots 前端过滤（OP min ≤5% 或 max ≥95%，最新快照 50 条一次拉取），仅展示计数 N，点击 → 关注队列；明细列表留在监控模块

### 3.3 行3 B 列 装置-单元排名（components/node-ranking.vue，主区）

- 树形结构沿用 v4.4：装置行（粗体、灰底、排名序号红显前三、▼/► 折叠）+ 单元行（缩进）+ 未挂载兜底组；层级 join 用 plant-node 树
- **管理者版列收敛**：排名 / 名称 / 回路数 / 评分（等级色）/ 等级徽章（A/B/C/D/E）/ 平稳率 / 自控率
- **工程指标下沉**：快速率/准确率/好值率 → 单元行名称 Tooltip（`快速率 x% · 准确率 x% · 好值率 x%`）
- 表头（回路数/评分/平稳率/自控率）点击排序；点击行 = 选中节点（排名即导航，联动 D 趋势与 E 重点回路；再点取消选中回全厂）
- NodeRankingItem 无"问题回路数/环比"字段，未自行扩字段（零后端改动原则下保持接口现状）

### 3.4 行3 C 列 治理漏斗（components/governance-funnel.vue，新增）

- 四级纵向条：**发现 → 诊断 → 方案 → 闭环**（蓝阶梯 → 闭环翠绿），每级显示数值与相对上一级转化率（上一级为 0 显示 —；各级计数口径不同，**转化率可超 100%，如实展示**，底部注记"各级计数口径不同，转化率仅供参考"）
- 下方一行"未闭环处置建议 N 条"（openItems）；纯展示，无跳转
- 数据源：`GET /api/v1/dashboard/governance-summary`（口径见 §4）

### 3.5 行4 D 绩效趋势（components/perf-trend.vue）/ E 重点关注回路（components/focus-loops.vue）

- D：搬运原 §5 全部功能（双轴柱线、悬浮十字线+统一悬浮框、图例 toggle、告警线、参评数柱）；**管理者版默认图例收敛：默认仅 综合评分主线 + 自控率，平稳率/快速率/准确率默认关闭（点击图例叠加）**
- E：沿用原 §4 重点回路（评分最低/最高 10 切换，随 B 列选中节点切换口径），点击回路跳回路工作台（`from=overview`）

## 4. 新增后端端点：GET /api/v1/dashboard/governance-summary

位置：`backend/app/api/v1/endpoints/dashboard.py`；schema：`backend/app/schemas/dashboard.py`（GovernanceSummary / GovernanceHandlingSummary / GovernanceFunnel / GovernanceBadLoops）。前端 API：`frontend/apps/web-antd/src/api/governance.ts`（`getGovernanceSummaryApi`）。

时间窗与 board/aggregate 同口径（复用 `_resolve_aggregate_window`，naive UTC；支持 last_8/24/72/168_hours + custom，custom 缺起止回退 last_24_hours）；**全部为本地 PostgreSQL 查询，无远端 API**（符合"导入走远端、计算全本地"数据架构）。

### 4.1 handling（处置闭环计数，双实体）

| 字段 | 口径 |
|---|---|
| `openItems` | `loop_action_item` 未闭环建议数：status ∈ PENDING/ACCEPTED（CONVERTED/REJECTED/IGNORED 为终态，处置 v2.0 状态机） |
| `openOrders` | `handling_order` 未闭环工单数：status ∈ PENDING/EXECUTING/VERIFYING/REOPENED（CLOSED/CANCELLED 为终态） |
| `overdueOrders` | 超期未闭环工单，**复用关注队列 `monitor_attention` HANDLING 来源口径**：REOPENED 全部计入；EXECUTING/PENDING 且 `planned_at < now`；VERIFYING 且 `submitted_at < now − 24h` |
| `closedInWindow` | 时间窗内闭环工单数：status=CLOSED 且 `verified_at ∈ 窗口`（CLOSED 为终态，verified_at 即闭环时间） |

### 4.2 funnel（治理漏斗）

| 字段 | 口径 |
|---|---|
| `discovered` | 时间窗内每回路最新快照定级为 WARNING/POOR 的**去重回路数** = badLoops.warning + badLoops.poor（复用 grade-distribution 定级口径）。**未采用 monitor_attention**：关注队列为"当前状态"聚合，无时间窗语义；快照定级口径确定性更强且与 badLoops 自洽 |
| `diagnosed` | 时间窗内完成诊断的运行数：`diagnosis_run`.status ∈ SUCCESS/PARTIAL 且 `finished_at ∈ 窗口` |
| `planned` | 时间窗内生成的处置/整定方案数：`handling_order.created_at ∈ 窗口` ＋ `tuning_record.created_at ∈ 窗口 且 recommended_pid 非空`，两者求和 |
| `closed` | = handling.closedInWindow |

### 4.3 badLoops（问题回路分布）

窗口内每回路最新快照定级分布的 WARNING/POOR 档计数，复用 `app.services.performance.get_grade_distribution`，与 `GET /api/v1/performance/grade-distribution` 同口径，阈值取 sys_config 当前生效值。

### 4.4 前端兜底

接口未就绪/失败时 governance 置 null，各卡按 0/— 显示（不影响行2 其余卡片与行3/行4 主数据）；治理聚合请求并入时间窗总开关 watch，与 loadCards/loadRankings 同批刷新。

## 6. 前端组件拆分结构

原单体 `workbench.vue`（v4.4 约千行级）拆分为组装层 + 六组件 + 共享工具（`frontend/apps/web-antd/src/views/dashboard/`）：

```
views/dashboard/
├── workbench.vue                  # 组装层：布局骨架 + 数据加载编排
│                                  #   （loadCards / loadRankings / loadTopLoops /
│                                  #     loadTrend / loadValveAlerts / loadGovernance /
│                                  #     loadNodeTree）+ watch 联动（时间窗总开关、
│                                  #     排名即导航、环比基线）；展示逻辑全部下沉组件
├── types.ts                       # 共享类型：ModeRow / TrendLines / WorkbenchSelection
├── use-grade.ts                   # 定级/格式化共享：getGrade / fmt / loadGradeCfgs
└── components/
    ├── conclusion-cards.vue       # 行2 六张结论卡（§3.1）
    ├── health-structure.vue       # 行3 A 列 全厂健康结构（§3.2）
    ├── node-ranking.vue           # 行3 B 列 装置-单元树形排名（§3.3）
    ├── governance-funnel.vue      # 行3 C 列 治理漏斗（§3.4）
    ├── perf-trend.vue             # 行4 D 绩效趋势（§3.5）
    └── focus-loops.vue            # 行4 E 重点关注回路（§3.5）
```

拆分原则：workbench.vue 只保留组装与数据加载编排；展示逻辑与 SVG 生成全部下沉 components/ 子组件；定级/格式化共享 use-grade.ts；组件间经 props/emits 通信，无跨组件状态耦合。
