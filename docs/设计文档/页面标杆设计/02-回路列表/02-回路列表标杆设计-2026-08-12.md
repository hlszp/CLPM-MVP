## 0. 现状诊断（为什么"列表塞进工作台"是错的）

当前回路列表**不是独立页面**：`/loop/monitor` 被 MW-P4-04 重定向到 `/monitor/loop-workbench` 的 table 模式，741 行 `LoopFleetView` 组件内嵌在工作台里，且 EXPERT/SPONSOR 无 table 模式权限（URL 直接输入会被守卫弹回）。问题：

1. **面被压进点里**：页型 B（回路集合，找例外）与页型 C（单回路，处置）是两种心智模式——前者要"扫视千级、锁定最差"，后者要"聚焦一条、看清证据"。合并后工作台背上两种职责，table/workspace 模式切换本身就是 IA 混乱的症状；这也是前几轮"工作台越改越重"的根因之一。
2. **卡片视图空转**：后端 `/loops/monitor` 早已支持 `view=list/card`（loops.py:273），前端只实现了 list——又一处"后端已对、前端没接"。
3. **列设计是数据库视图**：14 列平铺（量程/单位/类型等组态字段与 SP/PV/OP 实时值、评分、诊断标签同权重），没有等级、没有"谁最差"的排序导向，用户要自己扫 14 列找异常。
4. **EXPERT/SPONSOR 被排除**：治理层恰恰最需要"哪些回路在恶化"的面视角，当前却被挡在表格外。

好消息：`MonitorListItem` 字段已经足够丰富（score / scoreDelta / dayTrend / loopStatus / kpiStatus / confidenceLevel / effectiveAutoRate / dataHealth / currentValues 含 PV/SP/OP/MODE/质量码/时间戳），**本次重构主要是把面独立出来 + 信息分层，数据缺口很小**。

### 2.3 关键设计规则

1. **面点分离是本设计的第一决策**：回路列表独立成页，工作台回归单回路编排器（01 标杆）。MW-P4-04 的合并方向撤销，`/loop/monitor` 重定向改指 `/monitor/loops`；工作台内 LoopFleetView 组件随 01 实施迁移至本页并删除 table 模式（EXPERT/SPONSOR 的 table 权限限制随之消失——面视角全角色可见）。
2. **默认排序即观点**：评分升序（最差在前）。列表页的价值不是"数据全"而是"例外浮现"——用户打开第一屏就该看到最差的 20 条。日Δ恶化优先为第二排序选项（dayTrend=WORSENED 按 |Δ| 降序）。
3. **卡片视图的边界**：服务"班组长晨会扫视本单元 20~50 条"这类**已圈定小集合**场景；全量 1,000 条禁止卡片（切换按钮禁用并给出原因，F1 禁用显因规则的列表版）。
4. **组态字段克制（v1.2 修订）**：量程/单位/创建时间等组态字段从默认列撤出（进列配置），它们是"台账视角"不是"巡检视角"；**回路类型例外——v1.2 用户拍板保留为默认列**（类型是巡检时理解回路行为的必要上下文）；完整台账需求由配置模块回路台账页承担，本页不兼职。
5. **面→点上下文（E5，v1.4 补显式入口）**：下钻有三个等价入口——① 列表操作列"工作台 ↗"按钮（显式、可发现性最高，新用户首选）；② 行点击（快捷方式）；③ 卡片整卡点击与卡内"工作台 ↗"入口。三者均携带 `{from: '/monitor/loops', loopId, plantNodeId, keyword, filters, page}` 进入 01 工作台；工作台 R1 面包屑显示"← 回路列表"，返回时完整恢复筛选状态与页码。深链接（loopId 参数）不在当前筛选集中时显示提示条（沿用 MW-P0-03 既有模式："该回路不在当前筛选范围内 · 已为你单独加载"）。
6. **时间窗语义适用性（R-C）**：本页**无 A 类趋势元素**，全部为 B 类快照（评分/等级/日Δ/可信度，标注"KPI 快照 10:00"）+ C 类状态（MODE/loopStatus）；因此本页**不设时间窗选择器**——这是三层语义的正确应用，不是功能缺失。
7. **速览卡即筛选、数量即聚合（v1.1）**：R2.5 等级速览卡身兼三职——五档分布可视化、点击快速筛选、与 R2 摘要**同一聚合数据源**（E-1 `aggregate`），卡片数量之和必须恒等于范围总数；筛选态是分页查询条件（E-3 服务端参数），不是前端当前页遮罩。实时自控率卡为**实时口径**（`currentValues.mode` 分布），与 KPI 有效自控率（快照口径）并存时必须标注差异，防止用户把两个"自控率"混为一谈。
