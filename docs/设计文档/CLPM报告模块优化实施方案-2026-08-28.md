## 一、方案总览

### 1.1 背景与问题

报告模块（IA 优化 P0 建立，6 页：管理总览/绩效/诊断/处置/收益/订阅）骨架已就位，S1~S3 成熟度自适应模型本身即"可插拔友好"设计——阶段判定基于**数据存在性**（`determine_maturity_stage` 按诊断/工单/整定记录数判定），而非模块启用状态。当前存在三类结构性缺陷：

| 缺陷类 | 表现 |
|---|---|
| **已有承诺未兑现** | 订阅自动报表为空壳（占位 PDF、无落盘、无下载、无投递，Beat 四周期空转写垃圾记录）；管理总览"导出 Excel"实为单表 CSV；处置/收益报告无导出；处置报告无筛选 |
| **可插拔口径分裂** | reports 端点一半自持聚合直读表（overview/benefit/diagnosis-statistics），一半穿透到模块门禁 API（处置报告整页依赖 `/handling/statistics`、诊断报告明细/导出依赖 `/diagnosis/*`）——模块禁用时前者正常、后者 404 崩页 |
| **数据资产闲置** | `alert_event`（预警域零报表）、`loop_integrity_snapshot`（数据质量无明细）、`mv_staff_workload`（物化视图无消费者）、`sla_stage`/`sla_policy`（SLA 达成率未露出）、`loop_action_item`（建议漏斗缺失）、`tuning_record`（整定执行统计缺失）、`verify_result`/`kpi_before/after`（整改有效率与逐单对比未露出） |

### 1.2 目标与主线

**主线：P0 让已有的东西诚实可用 → P1 用基础模块数据补齐 S1 完整性 → P2 让闭环模块数据在报告中变现。**

| 目标 | 判据 |
|---|---|
| 报告体系诚实 | 无空壳功能；每份报告可导出；文案与实现一致 |
| 可插拔完整 | 诊断/整定/处置任意启用/禁用组合下，报告模块全部页面 200 可用；禁用时展示历史归档数据 + 状态横幅，查询/导出不受影响 |
| 基座独立 | 仅 monitor+assess（基础模块）在用时，报告体系自成闭环（S1 完整） |
| 闭环叙事完整 | 诊断→建议→工单→验证→KPI 改善全链路在报告层可举证 |

**明确不做（反堆砌边界）**：

- 不另建"大而全综合报表"——管理总览是唯一综合入口，12 格骨架不动
- 不做经济收益口径——维持技术指标量化决策
- 预警统计报告只做统计聚合，不做预警明细管理（明细管理属监控模块预警事件页）
- `overview_pdf_export` 的内存任务表 + daemon 线程实现（多副本不共享）登记为已知限制，本期不修
- 旧 `export_diagnosis_statistics` 死代码链按纪律登记不删

### 1.3 报告分层模型（可插拔架构口径）

| 层 | 报告 | 数据源域 | 模块依赖 |
|---|---|---|---|
| **基座层**（永远可用） | 管理总览（S1 视图）、绩效报告、**数据质量报告（新）**、**预警统计报告（新）** | monitor + assess | 无 |
| **闭环层**（诊断+处置启用时增强） | 诊断报告、处置报告、管理总览 S2 视图 | diagnosis_run / loop_action_item / handling_order | diagnosis、handling |
| **优化层**（整定启用时增强） | 收益报告、管理总览 S3 视图 | tuning_record / kpi_before/after | tuning |

**四条架构规则（本方案新增，作为后续报告类需求的验收口径）**：

- **R1 自持取数**：reports 模块端点一律自有聚合直读表，禁止前端报告页调用可插拔模块的 gated API
- **R2 数据存在性判定**：内容展示以数据存在性为准（与 S1/S2/S3 判定逻辑对齐），模块启用状态只影响横幅提示与升级引导文案，不影响数据可见性
- **R3 优雅降级**：模块禁用时，对应报告页正常渲染历史归档数据 + 顶部灰横幅（"XX 模块已停用，以下为历史数据归档"），筛选/导出不受影响
- **R4 基座不可拔**：报告模块是基础模块（base=true），自身不可禁用

## 四、P1 基座补域（详细设计）

| 区块 | 内容 | 数据源 |
|---|---|---|
| KPI 卡 | 参评率、数据健康率（PV 好值率均值，注意 0~1 量纲防重复放大兼容，同 `report_stats` 现有处理）、INCONCLUSIVE 率、可信度 A~E 分布 | `loop_ledger.include_in_evaluation` + `kpi_snapshot_hourly` |
| 趋势图 | 按天数据健康率 / INCONCLUSIVE 率双折线 | `kpi_snapshot_hourly` 按天聚合 |

**前端** `views/reports/data-quality.vue`：沿用报告模块统一筛选条 + KPI 卡 + 折线 + 表格的既有页面范式（视觉遵循 DESIGN.md active-baseline）。

### 4.2 预警统计报告（新页面）

**定位**：预警治理效果度量——"预警有没有用？误报多不多？确认快不快？"。监控是基础模块，此报告在任何模块组合下完整。

**后端** `GET /reports/alert-statistics?start&end&plantNodeId&severity&status`：

| 区块 | 内容 | 数据源字段 |
|---|---|---|
| KPI 卡 | 预警总数、活跃数、**MTTA**（avg(acknowledged_at−triggered_at)，已确认集）、**MTTR**（avg(resolved_at−triggered_at)，已解决集）、误报率（is_false_positive 占已标记集） | `alert_event` |

| 分布图 | 状态分布（ACTIVE/ACKNOWLEDGED/RESOLVED/SUPPRESSED）、严重度分布 | `status`/`severity` |
| TOP 榜 | TOP10 规则（按 rule_code 计数 + 误报数）、TOP10 回路 | 关联 `alert_rule`/`loop_ledger` |
| 抑制统计 | 当前活跃抑制条数（可选卡片） | `alert_suppression.is_active` |
| 导出 | 明细/聚合 CSV | — |

**前端** `views/reports/alert-statistics.vue`：同 4.1 范式。
