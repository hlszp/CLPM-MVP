## 1. 立卡项1：record source=None（已修，双缺陷叠加）

**归因**（两处独立缺陷，任一都足以让屏障 source/task_terminal 条件失败）：

1. **主成功路径漏传 source**（直接原因）：`kpi_calc._calculate_loop_kpi` 的主路径 `_timed_persist` 调用（`score=final_score` 那一处）未传 `source/source_task_id`——早退分支（取数失败/空 Bundle/composite-None INCONCLUSIVE）均显式传参，唯主路径缺失。`_save_snapshot` 的 UPSERT `update_cols` 含这两列 → 每次 NORMAL 评估把 source 覆写为 NULL。批 1' 与 Beat 两轮都在主路径落库，最终 1000 行全 None。**注意**：这同时解释了 taskRecordStatus=null（屏障从快照行 sourceTaskId 解析 TaskRecord，全 None → 解析不到）与 backfill 快照 source=None（BACKFILL 同样经主路径被丢弃——本修复顺带纠正）。
2. **判定顺序缺陷**（曾登记项，仍存在）：`_do_hourly_with_tracking` 在 Beat 路径 `task_id = await task_tracker.create_task(...)` 赋值**之后**才执行 `"MANUAL_STANDARD" if task_id else "SCHEDULED"` → Beat 路径即使传到也恒落 MANUAL_STANDARD。本次报告显示 None 而非 MANUAL_STANDARD，正是缺陷 1 把缺陷 2 的错值也一并抹成 NULL 的叠加结果。

**修复**（`backend/app/tasks/kpi_calc.py`）：

- 主路径 persist 调用补 `source=source, source_task_id=source_task_id`；
- `_do_hourly_with_tracking` 入口先判定 `manual_triggered = task_id is not None`（在创建系统任务记录之前），`_do_calculate` 用该标记取 source。语义：API 手动（带记录）=MANUAL_STANDARD；无记录触发（Beat 整点 / 工具 `.delay` 直投，Celery 入口不可区分）=SCHEDULED——两者都在屏障 `_ALLOWED_SOURCES={SCHEDULED, MANUAL_STANDARD}` 内。

**测试**：`tests/test_api_tasks.py` TestHourlyWindowMutex 新增 2 个功能用例（Beat→SCHEDULED / 手动→MANUAL_STANDARD，经 `_do_calculate` mock 断言 kwargs）；`tests/test_g5_pre_card_fixes.py` 源码级守护（主路径透传锚点 + 判定先于建记录）。
