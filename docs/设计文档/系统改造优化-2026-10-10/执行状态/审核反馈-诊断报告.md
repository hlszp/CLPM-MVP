## 1. 问题 1：总览页六维绩效——默认全厂 + 自控率/有效率偏低

### 1a. "须选装置/单元才显示" → 要求默认全厂

- **现象复现**：`/cockpit` 总览页右列"六维绩效"面板初始为空态文案"从「综合评分」排名区点击装置或单元行查看其六维绩效雷达"（浏览器实测复现）；点击排名区装置行后显示"EO 装置 · 参评回路均值 · 装置 · 参评回路 7"。
- **根因**：`views/cockpit/components/node-radar-panel.vue` 设计如此——2026-10-10 修订明确"未选中 → 空态提示（不造数）"，`props.node=null` 时直接清空（源码 34-56 行）。属**有意设计**，非 bug。
- **改造可行性（已核实）**：
  - 数据源 `/performance/nodes/{nodeId}/snapshot` 支持任意层级，**FACTORY 节点有现成快照**（EO 工厂 nodeId=`35af8328-…`，实测返回 score=5.66/autoModeRate=6.29/steadyRate=97.06/loopCount=9）；
  - node-tree 根节点即工厂（`/cockpit/node-tree` 返回 FACTORY→AREA→UNIT 三层）；
  - 改法：`overview.vue` 的 `selection` 初始值设为根 FACTORY 节点（或在 node-radar-panel 增加默认节点 prop），取消选中时回退全厂而不是空态。纯前端小改，后端无缺口。
- **定性：改造需求**（非缺陷）。

### 1b. 装置/单元自控率、有效率偏低

- **实测（三层 API）**：
  - 全厂（`/performance/nodes/overview`）：6 节点 `effectiveAutoRate` 全部 8.33（FACTORY 5.77），`autoLoopRatio=100`，`realtimeAutoRate=null`；
  - 装置 EO（snapshot）：`autoModeRate=8.33, effectiveAutoRate=8.33, steadyRate=95.76, accuracyRate=99.15, fastRate=100, goodValueRate=100, score=8.17`；
  - 单元（急冷分离）：同样 8.33/8.33，其余四维 95~100。
- **根因**：见 §0 根因链。补充两点：
  1. **不是 08d 名册稀释**：节点聚合 `_weighted_average` 的分母"仅累加有值快照的 loop_count"（`node_aggregation.py:98`），None 不稀释——8.33 是回路级本身算出的值，不是 N/E 分母效应；
  2. **`autoLoopRatio=100` 与 `autoModeRate=8.33` 并不矛盾**：前者是名册口径（配置为自动回路的占比），后者是时间口径（已证实处于自动模式的时长占比）——但 UI 无解释，用户必然困惑。
- **定性：计算缺陷（参数级）**——held_too_long 阈值未按角色信号形态分层；修法见 §5 修复批 A。
- **建议修法**：
  - `logical_wide_builder.py` 的保持阈值按角色分层：周期信号（PV/OP）保持 `max(3×step, 60s)`；COV 型角色（MODE/SP/PID_*）按"角色标称上报周期"推导（可用信号历史间隔中位数×安全系数，或 sys_config 每角色可配）；
  - 修复后对 08:00 UTC 起受影响窗口执行 backfill 重算（`backfill_kpi_range` 已有），预警/等级/适用性连锁自动消退；
  - UI 侧建议同时展示契约已携带的 `unknownSeconds/possibleRange`（details 已落库口径），把"8.33% 是已证实下界"显式化。

## 2. 问题 2：回路页六维图——"6 指标都高但综合评分很低"

- **现象复现**（浏览器）：`/cockpit/loops` 卡片墙全部回路 8.0~8.3 分（个别 4.5/0.0），每张卡片同屏显示"模式：自动"+"自控率 8"徽标+PV 紧贴 SP。详情面板（80TIC10402_PIDA）：综合 8.30"不合格"，实时 PV=100.04/SP=100.00/OP=49.97/模式=自动/P=1.50/I=0.03/D=6.00/可信度 A——实时一切正常。
- **手工复算（公式验证）**：综合分公式 `P = (A·a + F·f + S·s)/(a+f+s) × R/100`，权重 a=0.375/f=0.250/s=0.375（worker 日志实测值），R=有效自控率：
  - 回路 41LIC40404_PIDA：基础分 = 43.09×0.375 + 100×0.250 + 60.09×0.375 = 63.69；P = 63.69 × 7.03% = **4.48** ——与 API/DB 的 4.48 **完全一致**；
  - 回路 REF-LIC-401：基础分 = 100 → P = 100 × 0% = **0.00** ——与实测 0.00 一致；
  - 装置 EO 节点分 8.17 = 7 个参评回路按 loop_count 加权均值，一致。
- **结论**：**计算方法正确，无算术 bug**。综合分低 100% 由 R 折扣导致，R 低的原因即问题 1 的 held 阈值缺陷——不是"六维显示参考分而综合只认正式"（本次数据中无 PARTIAL/referenceOnly 分裂情形：六维与综合同源自同一份小时快照）。
- **但存在两个展示语义缺陷**（归入修复批）：
  1. **归因缺失**：R≈0 时综合分 0/状态 SUCCESS（如 19da595e：amr=1.69/ear=0.00/status=SUCCESS），把"无法证实"渲染成"确定为 0 分"。契约 details 里有 unknownSeconds/possibleRange，UI 未消费——建议雷达中心分旁标注"有效率 N%（已证实下界，未知占比 X%）"或 worst-dim 徽标扩展；
  2. **08d 裁决"E=0 为 null"未覆盖 N=0 大 unknown 场景**：E（名册）=3600s 非空、N（分子）=0 且 unknown≈98% 时按"真实 0 分计入"处理，合理性存疑，建议裁决补充"unknown 占比超阈值时 R 显示下界+区间而非 0"。
- **定性：计算正确（语义解释）+ 两个展示缺陷**；综合分将随问题 1 修复自然恢复，无独立修复项。
