## 3. 被动任务事件与正式每批采证顺序

1. Keeper完成cold/hot准备、确认唯一Worker/master/Beat（Beat暂停派发）与配置/运行SHA。每次cold生命周期重启后由Keeper在唯一master执行一次control.enable_events；此接收器自身不发控制。
2. 先起接收器并保全stdout/stderr；不是看到“ready”字样就当订阅已收，至少见到该Worker真实heartbeat/event再开始正式投递。不同cold生命周期用独立事件输出目录；hot可连续收但按parentId/时间切片保留原件。
3. 启动下述collector，并至少保全投递前60s资源基线；启动时report路径必须是该批尚不存在的新文件，防读旧报告提前结束。
4. Keeper执行原benchmark的真实standard-hourly投递，SLO600，timeout2400，不改其它参数/分母/expected。collector从原report取父ID，event receiver保留快子任务request/root/parent/kwargs终态；用原父ID从事件/raw结果关联。
5. 首次读到benchmark终态checkpoint当轮，在该轮同一RR事务内额外保存四组完整数组；若当时partial，随后首次当前窗1000 ledger/1000 latest/全部预定nodes及recordRefs齐的当轮同RR再存一次。若两触发同轮，四查询只执行一次。终态后继续至少30s，末尾`finalFull`另存持久化原件；它不倒填早期轮次，也不把600秒门无意收紧30秒。collector正常退出再停止自身receiver并保存summary。先保存原字节hash，再无损适配，不覆盖原件。

```sh
NO_PROXY=localhost,127.0.0.1,::1 "$CLPM_AUDIT_PY" "$CLPM_AUDIT_E/f02/receive_capacity_events.py" --env-file "$CLPM_AUDIT_ENV" --out <该生命周期新events目录> --stop-file <Keeper结束后创建的私有stop文件> --max-seconds 3600
NO_PROXY=localhost,127.0.0.1,::1 "$CLPM_AUDIT_PY" "$CLPM_AUDIT_E/f02/collect_capacity_evidence.py" --env-file "$CLPM_AUDIT_ENV" --ts-start 2026-10-15T12:00:00 --report <本批新report.json> --out <本批新collector目录> --worker-log /Users/zhangping/DEV/clpm-g5-runtime-20261015/backend/logs/celery-worker.log --interval 2 --post-seconds 30 --max-seconds 2700 --containers clpm-mvp-postgres clpm-mvp-tdengine clpm-f02-redis-20261017-s01
```

实际worker log路径以运行原件核实；若不存在会标available=false，不能默认为有日志证据。`--smoke`只做一轮读并发SMOKE_ONLY，**不得正式批次使用**。输出目录拒绝复用，原始SHA/argv/时间/SQL都在其内；业务collector投前要求全局及PERF对象各恰1000。

## 4. 同一轮数据、最终全文与证据恢复

- `bootstrap.json`：真实1000对象、完整树、结构推导节点/后代、PG身份、环境文件SHA。它是结构scope事实，不代表业务完成。
- `sql-plan.json`：实际投影SQL/参数来源与事务模式。
- `observations.jsonl`：每轮一个REPEATABLE READ READ ONLY事务内ledger/latest/nodes/records/attempts全行关键列；每轮开始/结束、txid snapshot、父ID/child集合与单独Redis观测时刻。**不伪称PG/Redis分布式原子快照**。
- `objects/<kind>-<rawsha>.json.gz`：原规范JSON内容寻址，附gzipSha、rawSha、rows；解压后逐行可恢复。重复快照复用相同字节。
- record投影真实 `payload.fitness_tags`、`payload.snapshotStatus`、NODE `payload.loopRecordIds`。不能把未导投影字段当数据库NULL。
- `first-terminal-full-payloads.json`/`first-complete-full-payloads.json`：各含同一observation PG RR事务内的ledger/latest/nodes/records四原数组ref，直接附在触发poll的`firstTerminalFullPayloads`/`firstCompleteFullPayloads`；pgStartedAt/pgReadCompletedAt/pgEndedAt、snapshot、parentTaskId与单独taskObservedAt均保留。首次终态即使partial也留，完整触发仅按对象/窗/refs存在，不判断九条件、版本、run、状态或SLO。不得把后取payload标成前轮同事务。
- `final-full-payloads.json`：最后一个RR事务的ledger/latest/node全列与全部关联LOOP/NODE record全文。NODE immutable payload含loopRecordIds、assessment_stats.roster/members；它的logicalRunId是内容寻址，不能强等父task UUID。
- 若屏障poll缺完整payload，只允许使用**同不可变recordId且createdAt≤该见证时间**的最终全文补充不可变内容。不得把最终latest/node不同record投影混进早期poll拼屏障。
- `task-evidence.jsonl`和events.jsonl保原父/子raw。collector还读取关联父/子Celery backend、TaskRecord哈希和unacked原headers/body（只读），不凭空队列推成功。
- worker-log片段记录inode/offsetStart/offsetEnd/sha/pendingBytes；每轮最多32MiB。发生rotate、pendingBytes>0或关键期日志断片时需补齐或BLOCKED，不能COLLECTED即PASS。
- `resources.jsonl`保每轮实际起止及原命令rc/输出，Docker统计、三容器cgroup准确字节/事件、TD VM meminfo/queries、PG连接、Redis队列、runtime进程RSS。观察间隔实际>5s必须如实补充/标缺口，不能把interval参数当实测周期。
- 总采证退出0只为COLLECTED（或SMOKE_ONLY）；COLLECTION_TIMEOUT/FAILED/原命令rc非0明确留痕。独立gate必须从真实完整原件再算，不取report九布尔作事实。

## 5. 四维缓存

```sh

```

## 6. 原始受控错误与恢复

仅Keeper布置专属REST透传，固定1/1000合成PV/同窗，其余999真实、无真实资源压力。两次0x073a后真实成功与持续故障跨父3attempt×本地3次（至少9次匹配）耗尽分开做，不调原重试/分母/expected；raw SQL/请求/命中/响应/终末record证据齐全。两个故障工况不计正常20批。详见本目录方案§8；四用户豁免与历史6+3不变。


故障代理真实SQL边界须沿 `point_history_repository.read_events` 默认闭窗 `>=start AND <=end`，不得误用本审查半开上界匹配导致零注入；只匹配events，不扣initial-state。多个tagGroup可能共读PV，耗尽工况应持续armed至真实父/TaskRecord终末FAILED后撤销，至少9HTTP错误不自动证明父三attempt；恢复工况先冻结实际FLOW/BASE≤1s派生计划，逐attempt核对原日志。

本轮Keeper资源最终口径：3容器memory.current全charge + 宿主API/Worker master/全部pool/Beat PID RSS，6GiB预算、80%=4.8GiB、VM可用≥1GiB；采样目标2s、实测间隔≤5s。anon/shmem分列不在总计重复加，容器PID不再与容器charge重复计。
