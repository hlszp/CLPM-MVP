本补充在正式20批投递前冻结，只细化方法04所需的原始来源；不改变20×1000、A/B各冷/热5批、600s、四项用户豁免或原四个独立验收工具字节。

## 来源与边界

- 外置只读生产者：`observe_capacity_native_identity.py`，SHA-256 `f9ef43b64c5b3deeed24d8429f6a5d2eaaf96ccd40c3e41a99ddceff26a245f4`。原 d0b collector、其 resource/ownedProcesses 列、同事务四数组取证均保持不变。
- 原 d0b 的 ps 列为 pid/ppid/pcpu/rss/**state**/command，不包含 etime 或 lstart。前次将 STATE 误读 etime 的说法已撤回；不得将该列解释为出生时间。
- 新来源命令为实际 `ps -ax -o pid=,ppid=,lstart=,stat=,command=`，仅保全本 runtime 解释器下 uvicorn/Celery 的原选中行。lstart、STAT 各自保存，STAT变化不产生新出生身份。范围是该 runtime；不得声称已扫描所有其他解释器/其他项目。
- 每个新出生身份首次实际执行 lsof `-a -p <pids> -d cwd,txt -Fn`，保全命令、UTC时刻、真实rc/stdout/stderr和引用SHA。实际本机控制原件已证明 -Fn 包含 fcwd/ftxt，与 -Ffn 逐字相同；不凭参数名称臆断缺字段。
- plan/summary只是索引，不能把 `observationValid`、producer rc0、`acceptance:PENDING`、空进程smoke或摘要最大间隔当作七身份验收结论。最终protocol须绑定此源码、plan、整档observations末尾SHA/bytes、summary及所有实际 lsof 引用。每个文件均实际可读、重算哈希；缺少或变化即BLOCKED/REWORK。

## 每个真实业务span的独立门

1. 将原任务 received/started/terminal、实际PG完成屏障的时刻与该批原始启动/profile时刻交叉核对；连续原件须前后括住整个真实业务span。不能用post30末尾全量记录倒填早期屏障，也不能将post30算入600s来收紧原SLO。跨600临界只凭可复核真实持久化/终态时刻另判，否则BLOCKED。
2. 逐条重读原 selectedRawPsLines，独立解析并与members逐字段对照。每个span须始终恰为API×1、其master×1、master四个pool、该API的Beat×1，PID/PPID、规范化lstart、identity、argv与真实启动/profile一致。任一缺失/新增/出生变化/父链不符均不允许仅靠PID相同补齐。Beat的受控暂停按实际STAT与Keeper动作原件核；状态字母不能冒充出生身份。
3. 逐点从真实ps/git命令时刻与monotonic值重算相邻间隔，严格0<Δt≤5s（目标2s），并核原命令rc与UTC/本机时区。停止/启动过渡只允许在业务span之外；业务内缺口不得用前后相同identity插值为已观察。
4. 原始 git stdout 必须实际为冻结M和其backend tree；env/taos每轮原哈希与投前协议一致。实际启动记录、干净backend检查、完整tracked-source-catalog与源码原字节闭合，Keeper禁止运行中更改checkout。HEAD/tree只说明Git身份，不能单独代替实际源码字节或“已加载代码”事实。
5. 每一出生身份须可追溯到成功的首次原始lsof；按原pPID与fcwd/ftxt字段恢复实际cwd/加载的解释器文件，并与该次启动路径、解释器/依赖事实对应。lsof非0、缺PID/cwd/txt或无法对应时保持BLOCKED，不从argv猜测真实cwd/解释器。首次结果只对相同出生identity有效，不跨PID重用。
6. 仅满足方法04全部前提后，`runtimeShaProvenance=derivedFromClosedWorkerPoolIdentity`可引用这组原件。Celery event.pid仍只是producer master；实际executorPid保持unknown/NULL，绝不推断某个具体pool。
