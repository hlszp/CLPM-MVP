## 0. 钉死结论（首发点已钉死——静态链路 + 现场 A/B + 受控复现三重实证）

**毒化首发点 = `applicable_anchors_batch` 在 DataPlanner tagGroup 并发 gather 下直接使用共享 worker_db 会话。**

调用链（修复前）：

```
_calculate_once (kpi_calc.py)
  └─ AsyncSessionLocal() as worker_db          ← 每回路共享会话
     └─ data_planner.request_bundles
        └─ _execute_query_plan
           └─ asyncio.gather(5 个 tagGroup 任务并发)   ← data_planner.py:622
              └─ _query_fn_point → build_logical_wide
                 └─ meta.applicable_anchors_batch(db, ...)   ← logical_wide_builder.py:324
                    └─ await session.execute(...)            ← point_history_metadata.py:545
                       ★ 共享 worker_db 上唯一的 gather 内 DB 访问
```

三重证据：

1. **静态钉死**：`_metadata_execute` 的 docstring（logical_wide_builder.py）自己声明了这条红线——"DataPlanner 会并发执行多个 tagGroup 查询，这些查询共享同一个 AsyncSession……与 2026-07-20 事故同一根因"。G14 整改迁移了 `_resolve_role_segments`/`_load_gap_windows`/held limits 三处，**唯独漏了 anchors 批查**——这是 gather 并发窗口内仅存的共享会话访问（其余共享会话访问全部在 gather 前后顺序段）。
2. **A/B 由 P5-02 预载激活解释**：旧码每回路在取数前先执行 `_load_fitness_sys_configs(db)`（共享会话查询，L1844 旧位）→ gather 开始时 session 已持有连接+开启事务，`_connection_for_bind` 走同步快速路径（session.py:1158 `if bind in self._connections: return`），无 provisioning 竞态窗。P5-02 批预载移除该查询后，worker_db **首次建连（PROVISIONING_CONNECTION 状态窗，含 await asyncpg connect）被推迟到 gather 并发窗口内**（session.py:1170 置态）→ 兄弟 tagGroup 任务并发进入 `_connection_for_bind` → 复现 09/10/11 三窗各 87/90/96 次的 `InvalidRequestError("provisioning")`；连接已建立的回路则表现为 asyncpg `InterfaceError("another operation is in progress")`（prepare 段 `_Atomic` 竞态）。日志时序吻合：首毒化（09:00:01.378）恰在首批 tagGroup TDengine 读返回（REST 池建连 #2~#8，09:00:01.118~122）之后 256ms——正是首批任务到达 anchors 查询的时刻；L1 全 MISS 必然走 build_logical_wide → anchors。
3. **受控复现（dev 库只读，隔离 Python 进程，供验收者重放）**：见 §4 脚本。两协程并发驱动同一 AsyncSession → 第二个协程**确定性**抛出与现场逐字相同的风暴签名；各自独立会话则全部成功。泄漏链同样吻合：gather 首异常上抛但兄弟协程不撤销（asyncio.gather 文档行为）→ `_calculate_once` 异常路径 rollback/close 撞上仍在途的操作 → `close() can't be called here; _connection_for_bind() already in progress` → session 被弃、asyncpg 连接永不归还 → idle-in-transaction 挂满 100 → PG 5min 超时批量回收（09:05:01~14 恰 100 条）+ NullPool GC 延迟终结失败（09:07:55 200+ 条 "Event loop is closed"）。

**为何旧码全天 0 次而新码每窗 ~90 次**：见证据 2——激活条件是"取数时 session 尚未建连"，P5-02 预载把建连时机移进了竞态窗。该缺陷代码自 2026-09-07（P3 逻辑宽表，01e97f98）即存在，P5-02 是激活器。

## 1. 修复清单（对照诊断 §5 修法六条 + 补充指令）

### 首发点根因修复（诊断 §5.5"钉死后针对性修复"，18 号文"会话所有权"）

**`applicable_anchors_batch` 改内部独立短会话**（`backend/app/services/data_source/point_history_metadata.py`）：`session` 参数保留签名兼容（与 `_resolve_role_segments` 的 G14 模式一致），实际查询走 `async with AsyncSessionLocal() as own`。返回的 ORM 行属性已全部加载，detached 访问安全。全仓唯一生产调用方是 builder 热路径（另有 3 处测试 monkeypatch 假实现，签名不变不受影响）。修复后 gather 并发窗口内共享 worker_db 的 DB 访问归零。

### ① 毒化 session 关闭兜底（止血-核心）

- 新增 `close_session_guarded`（`backend/app/core/db.py`）：立即 close → 延迟重试 close（1s/3s/8s，等 gather 兄弟协程在途操作自然完成后正常归还连接）→ 重试耗尽则 `raw asyncpg connection.terminate()`（同步硬断 socket，服务端 backend 立即退出，宁可断连不泄漏）→ 连句柄都取不到（provisioning 从未完成，句柄在被弃协程中）则记日志交服务端 idle 超时 300s/GC 兜底。全程不抛出（不掩盖原始异常）。**无任何模块级 asyncio 原语**（红线合规）。
- 接入点（`async with` 全部改显式 try/finally + guarded close）：
  - `_calculate_once`（kpi_calc）：worker_db 生命周期收尾在任务 finally 内被等待（18 号文"清理工作在任务生命周期内被等待"）；except 路径 rollback 失败单独捕获记日志（原实现 rollback 抛错会掩盖原始异常）；
  - 巡检 `_do_patrol` 全局 session 与 per-loop session（§6.3 巡检链泄漏现场）；
  - `_load_manifest_rows`（history_layout_router）：原 `finally: try close except: pass` 静默吞掉 close 失败——正是短会话泄漏点，改 guarded；wait_for 超时取消留下的 provisioning 态由此兜底；
  - `_metadata_execute`（logical_wide_builder）：同改。

### ② retry countdown 下限 ≥30s（止血-核心）

`AsyncTask.retry()` 覆盖（`backend/app/tasks/celery_app.py`）：countdown 统一 `max(countdown, min_retry_countdown=30)`。autoretry 的 retry_backoff+full_jitter 首次重试可抽 0（现场 "Retry in 0s"、2ms 内再失败）——下限给故障窗（连接占满 ~90s）留自愈时间。既有显式 countdown≥30s 的任务零影响；`_backfill_window_batch` 的 BUSY 短轮询（10s 收敛节奏，非故障重试）经独立任务类 `_BackfillWindowBatchTask` 豁免保留。

### ③ G29 熔断不得触发"回退直算"全量重跑（止血-核心）

新增专用异常 `BatchSystemicFailure(RuntimeError)`（`backend/app/tasks/kpi_calc.py`，继承 RuntimeError 保持 G29 既有语义与测试兼容）；`_assert_batch_health` 改抛该类型；`calculate_hourly_kpi._body` 的 except 链在通用回退分支**之前**放行它（与 `HourlyWindowBusy` 同语义原样抛出）→ 熔断即中止，由 Celery 以 ≥30s 退避重试；真正的 task_tracker 故障（Redis 异常等）仍走回退直算（既有兜底语义不变，测试守护正反两向）。

### ④ 巡检错峰——**已按 17 号文裁决撤销降频**

"""形态 A=修复前（anchors 共享会话并发）；形态 B=修复后（独立短会话并发）。"""
import asyncio
from sqlalchemy import text
from app.core.db import AsyncSessionLocal, close_session_guarded

async def shape_a_shared_session():
    session = AsyncSessionLocal()
    async def anchors_task_a():
        return (await session.execute(text("SELECT 1 AS a"))).scalar()
    async def anchors_task_b():
        return (await session.execute(text("SELECT 2 AS b"))).scalar()
    results = await asyncio.gather(anchors_task_a(), anchors_task_b(), return_exceptions=True)
    try:
        await session.rollback()
    except Exception as e:
        print(f"  rollback 失败: {type(e).__name__}")
    await close_session_guarded(session, label="repro-A")
    return results

async def shape_b_independent_sessions():
    async def one(val):
        async with AsyncSessionLocal() as s:
            return (await s.execute(text(f"SELECT {val} AS v"))).scalar()
    return await asyncio.gather(one(1), one(2), return_exceptions=True)

async def main():
    print("=== 形态 A（修复前反例：共享 session 并发）===")
    for i, r in enumerate(await shape_a_shared_session()):
        print(f"  task[{i}]: {'异常 ' + type(r).__name__ + ': ' + str(r).splitlines()[0] if isinstance(r, Exception) else '成功 ' + str(r)}")
    print("=== 形态 B（修复后：独立短会话并发）===")

        print(f"  task[{i}]: {'异常 ' + type(r).__name__ if isinstance(r, Exception) else '成功 ' + str(r)}")
