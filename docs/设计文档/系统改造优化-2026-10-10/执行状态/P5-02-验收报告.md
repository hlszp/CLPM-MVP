## 2. 缺陷清单（REWORK 项）

### D1【必修·REWORK】`_do_calculate_single_loop` 漏接显式重评链门控

- **定位**：`backend/app/tasks/kpi_calc.py` `_do_calculate_single_loop`（约 1357-1460 行）——`_compute()` 调 `_calculate_loop_kpi` 时未传 `failed_source_ids`（也未做 `loop_ids_with_failed_records` 门查询）；其余三入口（`_do_calculate` / `_do_calculate_custom_loop` / `_do_calculate_custom_batch`）均已接。
- **违反口径**：P0-02 冻结 v2 §2.2"FAILED 后再次计算=显式重评：新 logicalRunId + sourceRecordId 指向该 FAILED 记录"——**单回路手动触发恰是显式重评最典型入口**（用户看到 FAILED 后手动重算单回路），该路径成功落库的 COMPLETED record `source_record_id` 恒为 NULL，审计链断裂；交接 §3"批/单回路入口经门查询判定"声明与实现不符。
- **复现（代码链证明）**：回路 X 窗口 W 存在他 lrid 的 FAILED record → `calculate_loop_kpi.delay(X)`（或 API 单回路触发）成功 → `_persist_snapshot(failed_source_ids=None)` → 不点查 → `append_result_record(source_record_id=None)`。同场景经 hourly 批或 custom_loop 重算则正确回链（真库 smoke 第 8 项已证 ledger 层行为）。
- **修法（约 4 行）**：`_do_calculate_single_loop` 内补 `failed_source_ids = await result_ledger.loop_ids_with_failed_records(db, ts_start_dt, ts_end_dt, object_ids=[loop_id])`，并给 `_calculate_loop_kpi(...)` 传 `failed_source_ids=failed_source_ids`；可顺带补一条单测断言。

### D2【文档更正·随 D1 一并修】"未声明 priority 落中位桶"表述错误

- **定位**：`backend/app/tasks/celery_app.py` 文件头注释（"未声明 priority 的既有投递落入中位桶（step 5），行为不回退"）+ 交接 §4 同句。
- **事实**：kombu 5.6.2 `PRIORITY_STEPS=[0,3,6,9]`，未声明 → default_priority=0 → **最低桶（default 本体），与 NIGHTLY 同桶**。行为无 bug，注释更正为"未声明 priority 的既有投递落最低桶（step 0，与夜间批量同桶，相对事件/人工让路）"。

### D3【低危·建议随 D1 补】FAILED→再次 FAILED 无回链

- `append_failed_result_record` 不设 `source_record_id`：同窗此前有他 lrid FAILED、本次新 lrid 重算仍失败时，新 FAILED record 不指向旧失败证据。P0-02 §2.2"再次计算=显式重评"字面含再次失败情形。修法：终末失败分支同样经门控解析（命中时传 source_record_id 给 append_failed_result_record 透传）。

### D4【登记·遗留】存量未声明 priority 投递点
