## 3. 统一契约

### 3.1 事实、时间窗与聚合

- 所有业务时间存储/传输为 UTC；界面转换本地时间。分析窗统一 `[tsStart, tsEnd)`，不得包含下一窗口的起点。
- 当前评估独立于历史列表页；历史详情使用指定 snapshot/run/record，不能自动查询最新标准评估冒充历史证据。
- 指标聚合使用 `sum(w_i * value_i)/sum(w_i for valid_i)`；每指标独立有效分母。无有效分母返回 null。质量与不可评覆盖单列；默认不把缺值按零绩效计算。
- 综合评分保留 A/F/S×R结构，零权重指标不要求存在；权重来源、归一化和置信度来源写入结果。
- 应评数来自授权范围内回路台账及明确参评资格；已评/有效/不可评/缺评分别报告。环比使用上一等长窗口，不能用本窗口末值减首值冒充环比。
- 显式区分“未计算”“不可评”“真实0分”“过期结果”“来源不可用”；统计卡与下钻共用过滤和快照口径。

聚合接口在现有 ApiResponse.data 内渐进增加元信息，不另建并行API栈：

```ts
type AggregateMeta = {
  scope: { type: string; id: string | null; authorizationScopeHash: string };
  window: { tsStart: string; tsEnd: string };
  computedAt: string;
  validUntil: string;
  configRevision: string;
  datasetRevision: string;
  coverage: { expected: number; evaluated: number; valid: number; inconclusive: number; failed: number; missing: number };
  metricCoverage: Record<string, { validCount: number; validWeight: number; totalWeight: number }>;
  blocks: Record<string, { status: 'READY' | 'EMPTY' | 'STALE' | 'UNAVAILABLE'; computedAt: string | null; reasonCode: string | null }>;
};
```

字段定义为新设计，并非声称已有。兼容期保留原业务字段，消费者逐页接入。分块失败必须显式UNAVAILABLE，不能返回正常0值。

覆盖分母要求 `expected=evaluated+missing`、`evaluated=valid+inconclusive+failed`；已评失败不冒充未评。metricCoverage按指标独立报告，综合评分有效数不能代替每个指标覆盖。

**结果身份必须先于数值修复落库。** P0冻结、P1-05先实施追加式 `calculation_result_record`：recordId、logicalRunId、objectKind(LOOP/NODE)、objectId、窗口、sourceRecordId、algorithmVersion、configRevision、datasetSnapshotId(历史可空)、status、payload、createdAt。唯一键为(logicalRunId,objectKind,objectId,tsStart,tsEnd)，同任务重试复用logicalRunId，显式重评生成新logicalRunId；已完成记录只追加，不原地更新。节点记录保存实际参与的loop recordIds及各指标分母。

暂态失败重试写独立attempt日志，尚未形成终态record时复用logicalRunId；达到重试终点才追加不可变FAILED终态。已形成FAILED终态后再次计算视为显式重评，生成新logicalRunId并关联sourceRecordId，不覆盖失败证据；P0冻结重试终点和幂等键。

现有hourly/latest/node表继续作为兼容的当前投影，增加resultRecordId；不直接取消现有唯一约束。写新记录与切换投影在同一事务，投影按最新业务窗口与明确发布的版本选择，历史迟到不得反向覆盖。迁移先归档现存结果、保存旧表ID→recordId映射；未知旧算法/输入标LEGACY_UNVERIFIABLE，不伪补版本。历史详情与后续工单引用recordId，按旧ID读可通过映射兼容。P1-05通过前禁止新算法同窗写入或回算；P2再补完整输入复现能力，P1尚未保存输入包的结果明确不可完整复现。

### 3.2 工程参数

每个参数的注册元数据至少包括：key、名称、业务含义、bool/int/float/enum类型、单位、默认值及依据、合法范围、有限数校验、组合约束、适用方法/回路、可维护角色、作用域、变更风险。前后端参数键以同一注册表为全集。

业务参数与算法内部/运维参数分别呈现；不是把每个内部常数开放为普通输入框。诊断方法字段优先改为注册表只读说明；允许切换的方法必须有显式注册映射和类型化参数。

统一作用域建议：全局默认<响应/控制特征模板<装置/单元<回路<本次任务临时覆盖。模板引用不可变版本。旧 `metric_config.threshold` 保持兼容读取，通过迁移诊断报告归入明确覆盖层，不静默改变旧权重或阈值优先级。

```ts
type EffectiveParameter = {
  key: string; value: boolean | number | string; unit: string;
  source: 'DEFAULT' | 'TEMPLATE' | 'NODE' | 'LOOP' | 'TASK';
  sourceId: string | null; sourceRevision: string;
};
type CalculationContext = {
  schemaVersion: '1'; loopId: string;
  tsStart: string; tsEnd: string; datasetRef: string;
  datasetSnapshotId: string; inputHash: string; resultRecordId: string;
  algorithmVersion: string; executableBuildDigest: string;
  configRevision: string; effectiveParamsHash: string;
  effectiveParams: EffectiveParameter[];
  modelVersionId: string | null; dcsTemplateRevision: string | null;
};
```

保存需 expectedRevision，冲突返回409及最新版本；每次发布有before/after、原因、操作者、作用范围、受影响回路和回退版本。任务开始固定CalculationContext，任务中不切参。广播用于加速通知，任务边界版本读取用于保证一致性；Redis故障不能静默采用已知过期值。

拟复用 `algorithm_parameter`、sys_config、配置版本历史与 SysAuditLog；新增工程配置版本/覆盖表仅补其缺少的统一发布快照，保留旧表为兼容入口。P0输出迁移字段与历史映射清单，P2落库，不能只有JSON表单。

现有datasetRef只表示绑定/改绑身份，不是数值输入身份。P2新增 `calculation_dataset_snapshot` 元数据，引用本地持久化共享目录的不可变NPZ数组+JSON manifest（复用NumPy，不使用pickle）；内容SHA256涵盖实际时间轴、值、质量、mask、dtype、单位/量程、绑定、窗口、网格与预处理版本。先原子写文件并核hash，再提交DB引用；未引用残留由隔离清理任务按保留契约处理。相同绑定但值/质量改变必须得到不同inputHash，重放读取原包，不能重查当前源数据冒充原输入。

输入包只用于经授权的人工离线复现，在线历史查询仍走本地TDengine/get_provider，不做缺数据自动降级。普通包建议保留90天（DEC-10冻结），被方案/实施/审核证据引用的包须固定保留，解除引用及超过保留期后才可清理。访问/下载继承回路scope，禁止开放静态目录。复现还须绑定代码SHA、依赖锁、构建digest及受控执行配方；旧执行环境在隔离环境按保留构建读取，不允许客户端指定任意代码路径。原包损坏/过期或执行版本未保留时明确“不可完整复现”。P0冻结存储容量与保留责任，P2实现并验收，不将保存hash当成复现完成。

### 3.3 诊断与整定

- 算子输入保留真实时间轴、有效段、UNKNOWN/HELD、逐槽mask、单位和量程；FFT/相关分析不得将删点后的不连续数组视为等距连续序列。
- 每个诊断结果记录选定/执行/跳过/失败算子、阈值及来源；零有效检查不能产出正常阴性。数据不足使用现有正式结论；内核异常记计算失败，不能吞为“未异常”。
- 规则融合输出称“证据支持度”；未经标注现场样本校准，不称正确率。外扰/SP关系只陈述经检查能支持的事实。
- 统一模型量纲，历史/STEP使用相同标准输入语义；K随量程归一化的定义明确记录。阶跃前时间保持负值，实际阶跃为0；AREA/IPDT不重复偏移。
- 标准PID与DCS表示通过现有转换器双向转换，记录原始值、标准值、PB/Kp、I/D单位、控制器结构和模板版本；不支持的结构明确拒绝，不能套用通用换算。
- 仿真按FOPDT/SOPDT/IPDT真实模型分派，扰动必须实际进入动力学；不支持则返回明确错误。模拟仅为候选证据，不能当现场改善证明。
- 60/20/20或其他划分须有独立终验段，不仅记录点数；未见充分激励/独立验证的模型不提升可信等级。
- 定时/事件/手动入口共用TaskTracker返回ID；按loop/window/operatorProfile/configRevision/triggerEvent建立幂等上下文和完成检查点。

### 3.4 人工实施与效果验证

建议→方案→工单→人工实施→观察窗→验证→归档保持关联。工单保留 plannedAt/startedAt/implementedAt/submittedAt/verifiedAt各自意义，新增implementedAt不能伪填历史提交时间；历史记录标明未知。

PID反馈按P/PI/PID及型号要求校验，填写完整有效项、单位、实施前后值和实施人。复诊选择同回路、实施后的完成记录，服务端校验loopId；不用手工UUID作为主要交互。

闭环证据类型建议为 `MANUAL_CONFIRMATION/DATA_VERIFIED/COMPARABLE_CONDITION_VERIFIED`，分别统计。无数据允许人工验收时必须有理由，不能标成数据验证。验证无效仍按现行裁决写ROLLED_BACK，但界面明确该状态来自验证判断；actualRollbackConfirmed单独存人工回退事实，不声称DCS已恢复。

效果比较基于统一窗口契约、覆盖率和工况可比性。人工可选确认窗口；若缺负荷/工况信号，明确“工况可比性未验证”，不自动推断收益因果。

### 3.5 权限

首期保留五预设角色、每用户一个角色及默认种子。先校准最新裁决：模块查看五角色；诊断/整定操作ADMIN/IC/PE/EXPERT；SPONSOR只读。取消、删除、配置发布等敏感动作按当前真实门禁逐项登记，不能把通配符展开为新增授权。

目标为服务端权限目录+角色授权+用户数据范围；菜单是页面授权的导航投影。模块开关、页面授权、操作授权、数据范围、业务状态和数据门禁分别检查，最终服务端AND执行。

拟新增 `sys_permission(code,kind,parent_code,requires_codes)`、`sys_role_permission(role,permission_code)`、`sys_user_scope(user_id,scope_type,node_id)`、不可变policy revision及审计；ADMIN必要管理能力与至少一个可用管理员保留保护。首期不加入复杂deny规则、单用户操作例外、多角色合并或自定义角色编辑。

建议接口：GET `/auth/effective-access`返回policyRevision/pages/actions/scope；GET `/system/authorization/catalog`；GET/PUT `/system/authorization/roles/{role}`（expectedRevision+pageCodes+actionCodes+reason）；PUT `/system/authorization/users/{id}/scope`；POST `/system/authorization/revisions/{revision}/rollback`。按现有API命名/响应封装接入，P0校对冲突。

页面码显式登记，例如 `page:tuning.records`；操作复用规范化的 `tuning:identify/tuning:tune/tuning:simulate/tuning:advanced/loop:delete/config:publish`。未登记码拒绝。写权限依赖必要读取码，发布时校验；入口隐藏不代替路由和API守卫。

列表、详情、聚合、导出、批量选择、任务、缓存及原始tag接口都执行数据范围。批量写入先验证全部对象；越界不返回外部对象详情。聚合缓存包含授权节点集合hash和policyRevision，防止跨范围共用全厂缓存。

实时HTTP与 `ws_realtime/ws_alert` 是独立活入口，同样服务端执行授权。tag按实际关系 `TagRegistry/tag_registry → LoopTagMapping/loop_tag_mapping → LoopLedger.unit_id → plant_node` 解析，复用`models/tag.py`与`models/loop.py`，不新建Point实体；首期有授权回路绑定才允许读取，共享tag只返回tag本身且不泄露其他回路元信息；未绑定tag默认仅ADMIN可读，不能推定ALL等于可看任何tag。订阅取请求集合与授权集合交集，越界只给通用拒绝；旧客户端未订阅时最多转发授权集合。预警按其关联loop/node过滤。连接固定主体而非固定永久授权，发送批次前检查当前policy及令牌撤销；与策略发布有发送栅栏，发布确认后不再发送越权帧，无法可靠校验时停止推送。连接内降权/禁用/重置密码要清缓冲并拒绝后续帧，最迟30s关闭或重协商失权连接；前端退订仅为体验措施。

配置变更后服务端下一请求取新版本；前端最迟下一次路由/操作前刷新授权，已打开无权页退出到可访问入口。密码重置/禁用复用现有令牌撤销。人工异步任务保存subjectId/action/object scope/policyRevision，在每对象开始与业务提交前重验；计算在事务外，写事务对该主体策略revision行加共享锁，撤权/禁用对同一行加排他锁，校验最新有效权限与对象范围后原子提交结果、模型及派生建议outbox。发布确认后旧权限计算不能再提交业务产物；失权任务允许必要审计终态REVOKED，不发布新结果/建议。outbox发送须再验授权且遵守同一发布栅栏。SYSTEM调度使用独立系统身份，人工来源派生建议不得换SYSTEM绕过撤权。P4冻结具体锁顺序、防死锁和发送确认协议并以并发反例验证。

首期采用单一 `policy_publication_guard` 行统一序列化授权相关变更：角色授权、用户scope/禁用/令牌撤销、节点归属和tag改绑均先取该行排他锁并递增revision；任务提交/WS发送批先取同一行共享锁再读取主体策略。按guard→主体→对象固定顺序锁定；计算不持锁，发送批有限大小与超时，失败停止发送。上段主体revision锁服从该统一guard，不能只锁用户而漏掉角色或层级变更。并发撤权与提交/发送按guard获得顺序线性化：撤权先完成则后续不得越权，提交先完成则保留之前合法证据；测试核服务端发送时刻，不把撤权前已发送的网络在途帧当作新发送。

### 3.6 容量与交互

先做有界lag/FFT相关、共享特征、批量IO、预计算复用；再按CPU/连接池/队列实测调整并发。事件快速诊断、人工整定、夜间批量分别管理资源；所有重计算有工作量预算、幂等、进度与取消语义。

缓存存computedAt/validUntil，Redis命中不重置完整TTL。相同key冷请求合并，任务/loop局部锁或Redis机制必须兼容Celery新事件循环；失效贯穿进程及Redis。

回路墙保留30卡分页/懒加载，筛选、排序和总数服务端执行；不靠34页全量抓取再前端筛选。复用 `use-latest-request`；刷新保留筛选、页码、选中对象和抽屉。实时更新按loopId定位、短时合并，仅更新可见对象及选中回路，聚合按自身周期刷新。

趋势使用真实时间轴、缺口和完整分数范围；不能将值压到78–92造成视觉改善假象。保留深浅主题与现有--ck-*体系，不新增分叉设计系统。

**装置性能优化已采纳：** 增强现有 `/metric/pid-dashboard`，首屏以综合评分、自控率、平稳率为核心，常驻完整P可评分N/E、未评分原因和截至时间；更多指标保留，F参考统计按10号文与正式F/P隔离。驾驶舱负责摘要观察，装置页负责集中分析，绩效报告负责周期汇总。装置/单元/回路下钻连续传递精确窗口、指标、版本和筛选并回显，最新快照与期间统计分开。正文及PL子例见[装置性能优化方案](/Users/zhangping/DEV/CLPM-MVP/docs/设计文档/工程师任务导向IA改造-2026-10-11/04-装置性能核查与增强建议.md)，归P6-01/02/03/04与P7-02，不新增主任务或重开P1。

现场样本按工况、仪表类型、诊断类别分层，记录标注者、争议和不可判断样本。测召回、误报、不可判定和覆盖率，避免只用模拟样本宣称现场有效。

## 6. 数据迁移、兼容与回退

采取扩展→兼容双读校验→显式发布切换→观察→后续清理。新增字段可空并标历史未知；不伪补历史参数、实施时间或现场收益。新配置先生成与旧值一致的有效快照，比较差异，经确认后发布。

每次模型变更与Alembic迁移同批，核单head、生产引导SQL及真实PG schema drift。旧算法结果保留版本，重算选择“原配置复现”或“当前配置重评”，不得默认覆盖原决策证据。新评估修正可产生不同分数，报告差异与原因，不为保持历史数字而保留错误。

回退应用版本时仍能读兼容字段；授权回退保留至少一个管理员；配置回退生成新revision。生产数据已写入后不以盲目downgrade/drop为回退手段，先备份并评估前向修复。任何部署另按生产运维技能及明确授权执行。
