## 3. 需要返修的问题

### R01 · P1：慢过程仿真窗口不够，仍可能返回鲁棒验证 PASS

**事实。** 当前鲁棒接口将仿真时长限制为不超过 600 秒，按该窗口内的最大响应计算超调，再直接参与 `overallPass`。它没有判断响应证据是否足以支持完整的超调结论。

验收方已经记录了反例：[G3 λ 验收 F2](/Users/zhangping/DEV/CLPM-MVP/docs/设计文档/系统改造优化-2026-10-10/执行状态/G3-lambda落地-验收报告.md:63)：慢 IPDT 在 λ=6、θ=60 的宽区间场景，600 秒内约 19.14%，返回 PASS，但窗口外超调超过 20%。该项被按“不是本批引入”登记为非阻断；这可以解释 λ 小批次的范围，不能证明整个 G3 的鲁棒验证能力已完整收口。

本次独立递推复核名义 K=0.1、θ=60、λratio=6，Kp≈0.044218、Ti=780；四个区间角点 K=0.095/0.105、θ=54/66。600 秒最坏超调约 19.1354%，延长观察至 1800 秒后约 20.2940%，峰值在约 730 秒。这里是独立数学对照，不是生产 API 重跑。

源码：[仿真时长约束](/Users/zhangping/DEV/CLPM-MVP-p1int/backend/app/schemas/tuning.py:348)、[窗内超调](/Users/zhangping/DEV/CLPM-MVP-p1int/backend/app/services/tuning_algorithms.py:2207)、[总体 PASS](/Users/zhangping/DEV/CLPM-MVP-p1int/backend/app/services/tuning_algorithms.py:2276)。

## 7. 学习笔记与自测

这个项目有三个不同的“完成”：算法函数能算、服务/API 能可靠处理真实输入、工程师能在页面上用证据作出行动。前一个完成不会自动推出后一个完成。

| 术语 | 在本项目中的含义 |
|---|---|
| Gate / G3 / G5 | 阶段晋级门槛；G3 关注算法与工程证据，G5 关注容量与集成运行 |
| REWORK | 某项需要返修并重新验收，不等于全部推倒重来 |
| SNR | 信噪比，反映有效变化相对噪声的强弱；低 SNR 时参数精度承诺受限 |
| CI / uncalibrated | 参数区间 / 未校准；名义区间不自动具有声称的真实覆盖概率 |
| 鲁棒验证 | 在多种候选模型和约束下检查建议；结论只适用于已验证的集合与条件 |
| latest | 最新业务窗口的当前投影；旧窗口可留历史，但不能冒充最新状态 |
| 完成屏障 | 等全部必要任务、正确业务结果及规定存储提交完成，而不是只看任务已投递 |
| 冷/热测试 | 缓存未准备/已准备时的性能；必须说明究竟哪些缓存被清空 |
| SHA | 固定代码版本的标识；磁盘版本、实际运行版本和文档版本需要分别核对 |

自测题：

1. 为什么 1000 条结果行不一定代表 1000 条有效评估完成？
2. 600 秒内超调低于 20%，为什么可能仍不能给“通过”？
3. 算法 API 已实现，而 UI 留到 P6，应该如何在看板上表述？
4. 只清 Redis 缓存，可以称所有缓存维度的冷启动测试吗？

参考答案：1）还要核本次运行、正确版本、业务终态、有效评分与必要节点提交；2）峰值可能尚未出现，证据窗口不足；3）分别登记后端接口已验收、产品消费待 P6，并保留限制；4）不能，要明确输入、预计算、进程等缓存各自的状态。
