## 1. 执行摘要

诊断模块是 CLPM 的**职能轴核心**——回答"全厂哪些回路有问题、什么问题、怎么处置"。经过 IA Phase C 三区重构、Batch 4-6 管理闭环、诊断标签面板与 A/B 对比增强，该模块在**诊断结果展示与状态机闭环**上已相当完整：5 类诊断标签 + 置信度等级 + 6 态状态机 + Action Tracker 闭环 + A/B 对比验证。但从第一性原理看，**诊断模块存在两个范式级问题**：①诊断总览与回路分析功能重叠、②诊断任务与异常跟踪的状态边界不清，导致用户在"总览→分析→任务→跟踪"的动线中存在认知摩擦。

**模块评分：2.9 / 4.0 — 良好（下沿，范式有优化空间）**

## 3. 模块架构分析

### 3.1 当前结构

```
诊断（order:3，职能轴 + 诊断闭环）
├─ 诊断总览 /diagnosis/overview        — KPI 卡 + 标签分布饼图 + 30 天趋势 + Top5 异常回路
├─ 回路分析 /diagnosis/loop-analysis    — 4 步引导式工作流（选回路→KPI评估→诊断分析→A/B对比）
├─ 诊断任务 /diagnosis/tasks            — Tabs：进行中（任务管理）+ 历史（归档记录+诊断标签面板）
├─ 异常跟踪 /diagnosis/tracker          — Action Tracker 状态机闭环（PENDING→...→CLOSED/IGNORED）
├─ [隐藏] 诊断详情 /diagnosis/detail/:loopId — 三区 Tab（证据/时间线/整定对比）+ 状态操作
├─ [隐藏] 诊断记录 /diagnosis/records    — redirect → /diagnosis/tasks?tab=history
└─ [隐藏] 诊断可视化 /diagnosis/visualization — redirect → /diagnosis/detail/:loopId
```

### 3.2 五页面认知层次分析

| 页面 | 认知层次 | 视角 | 用户任务 |
|---|---|---|---|
| 诊断总览 | 全厂视角 | 跨回路总览 | "哪些回路有问题？趋势如何？" |
| 回路分析 | 单回路视角 | 引导式工作流 | "手动走一遍评估→诊断→对比流程" |
| 诊断任务 | 管理视角 | 任务执行与归档 | "诊断任务跑完了吗？历史记录在哪？" |
| 异常跟踪 | 行动视角 | 状态机闭环 | "这个异常处置到哪一步了？该谁做？" |
| 诊断详情 | 深度视角 | 单回路证据+处置 | "这个回路具体什么问题？怎么处置？" |

**范式级发现**：
1. **诊断总览与回路分析功能重叠**：总览页 Top5 表格有"诊断"按钮跳转回路分析，但回路分析的 Step 3（诊断分析）与总览页的标签分布+异常列表在信息维度上高度重叠。用户从总览进入分析后，需重新选回路并走 4 步，认知路径不连续。
2. **诊断任务与异常跟踪的状态边界不清**：诊断任务管"诊断执行"（PENDING→RUNNING→SUCCESS/FAILED），异常跟踪管"处置闭环"（PENDING→IN_PROGRESS→VERIFYING→CLOSED）。两者都有 PENDING 状态但含义不同，用户可能混淆"诊断任务待处理"与"异常跟踪待处理"。

### 3.3 与监控模块的关系

| 诊断元素 | 监控模块对应 | 关系 |
|---|---|---|
| 诊断总览 Top5 异常回路 | 关注队列 TRACKER 来源 | 关注队列已聚合待处理跟踪项，总览页再展示一遍 |
| 诊断详情 | 回路工作台诊断行 | 工作台诊断行是摘要，详情页是完整证据 |
| 异常跟踪 | 关注队列 TRACKER 来源 | 同一数据源，不同视图（行动队列 vs 管理表格） |

### 4.2 范式级发现

| 编号 | 发现 | 级别 | 理由 |
|---|---|---|---|
| F-DIAG-001 | 诊断总览含 Top5 回路表格（回路级信息），与回路分析页的信息维度有交叉。但两页面功能不重叠——总览是跨回路统计，分析是单回路诊断流程。建议在总览页 Top5 表格中增加'进入分析'跳转按钮，实现信息维度的自然衔接 | 范式级 P1 | 总览 Top5 有"诊断"按钮跳转分析，但分析 Step3 与总览标签分布重叠；两页面信息维度交叉，用户认知路径不连续。建议：总览作为跨回路总览入口，分析改为从总览/工作台携带 loopId 直接进入 Step3，跳过 Step1。 |
| F-DIAG-002 | **诊断任务与异常跟踪状态边界不清** | 范式级 P2 | 诊断任务 PENDING=待执行诊断，异常跟踪 PENDING=待处置异常。用户在系统概览 KpiStrip 看到"诊断待处理"时，不确定是任务待执行还是异常待处置。建议：KpiStrip 卡片文案区分"诊断任务待执行 X 条" vs "异常待处置 X 条"。 |
| F-DIAG-003 | **诊断详情页 Tab3/Tab4 预留未实现** | P2 | detail.vue 注释标注 Tab3"整定对比"和 Tab4"A/B验证"为预留，但路由已存在 `?tab=` 参数支持。用户点击发现空内容会困惑。建议：未实现 Tab 隐藏或标注"敬请期待"。 |
| F-DIAG-004 | **回路分析 4 步引导仅允许回退不允许跳步** | P2 | `onStepChange` 限制 `target <= state.current`，用户不能从 Step1 直接跳到 Step4。但对于已选回路（query.loopId 预填）的场景，Step1 已自动完成，应允许跳步。 |

## 10. 结论

诊断模块是 CLPM **职能轴核心模块**（2.93/4.0），Phase C 三区重构 + 特征字典 + Batch 4-6 管理闭环已使诊断结果展示与状态机闭环达到良好水平——5 类标签 + 置信度 + 6 态状态机 + A/B 对比 + PDF 导出，**技术实现层面完整度较高**。

但从第一性原理看，存在两个范式级问题：
1. 诊断总览含 Top5 回路表格（回路级信息），与回路分析页的信息维度有交叉。但两页面功能不重叠——总览是跨回路统计，分析是单回路诊断流程。建议在总览页 Top5 表格中增加'进入分析'跳转按钮，实现信息维度的自然衔接（F-DIAG-001）
2. **诊断任务与异常跟踪状态边界不清**（F-DIAG-002）：PENDING 状态在两个子模块含义不同，用户可能混淆

**核心建议**：
