## 1. 页面定位与核心价值

### 1.1 定位

诊断任务页是诊断中心的**任务管理与历史记录页**——通过 Tabs 合并"进行中"（未归档诊断任务管理）与"历史"（已归档记录 + 诊断标签面板），替代原来分开的 tasks 和 records 两个页面。支持 URL query `?tab=history` 深链与浏览器前进后退。

### 1.2 核心价值

| 价值 | 实现 | 评估 |
|---|---|---|
| 任务全生命周期管理 | 触发/取消/详情/归档/删除 | ✅ |
| 历史记录查询 | 已归档记录 + KpiStrip 聚合 | ✅ |
| 诊断标签面板 | TagPanel 组件（筛选+处理+抑制） | ✅ FE-14 |
| 深链支持 | `?tab=history` URL query 双向同步 | ✅ |
| CSV 导出 | `exportDiagnosisStatisticsApi` | ✅ D5 |

## 3. 第一性原理评估（视角一）

### 3.1 用户核心需求

| 问题 | 回答方式 | 当前实现 |
|---|---|---|
| 诊断任务跑完了吗？ | 进行中 Tab + RUNNING 进度条 + 5s 轮询 | ✅ |
| 历史诊断记录在哪？ | 历史 Tab + 已归档记录表格 | ✅ |
| 诊断标签怎么管理？ | 历史 Tab 二级 Tabs + TagPanel | ✅ |
| 如何批量触发诊断？ | 触发诊断 Modal（多选回路+时间范围） | ✅ |
| 如何导出统计？ | CSV 导出按钮 | ✅ |

### 3.2 范式级评估

**优点**：
- Tabs 合并进行中/历史，减少菜单项（IA 减负），深链支持好
- 任务状态机控制按钮可用性（PENDING 可取消/运行，RUNNING 可取消，SUCCESS 可详情/归档/删除）
- RUNNING 状态行内进度条 + 5s 轮询，状态透明

**不足**：
- **与异常跟踪状态边界不清**：诊断任务 PENDING=待执行诊断，异常跟踪 PENDING=待处置异常。用户在系统概览 KpiStrip 看到"诊断待处理"时不确定是任务待执行还是异常待处置
- **双层 Page 问题已规避**：task-center.vue 不套 `<Page>`，子页 tasks.vue/records.vue 各自持有，避免双倍 padding（注释明确说明）
- **轮询清理**：tasks.vue 使用 `onBeforeUnmount` 清理 pollTimer，但需确认切换 Tab 时也清理（TabPane force-render 可能导致子组件不卸载）

### 3.3 范式级发现

| 编号 | 发现 | 级别 | 理由 |
|---|---|---|---|
| F-DT-001 | **诊断任务与异常跟踪状态边界不清** | P2 | 两子模块都有 PENDING 状态但含义不同。KpiStrip 文案需区分 |
| F-DT-002 | **TabPane force-render 可能导致轮询不清理** | P3 | [task-center.vue:L102-L107](file:///Users/zhangping/DEV/CLPM/frontend/apps/web-antd/src/views/diagnosis/task-center.vue#L102-L107) force-render 使子组件不卸载，切换 Tab 时 pollTimer 可能继续运行 |

## 10. 结论

诊断任务页是**诊断中心的任务管理枢纽**（2.98/4.0），Tabs 合并进行中/历史 + 深链 + legacy redirect 的 IA 设计合理，任务状态机控制 + 5s 轮询 + 进度条 + 批量触发的功能完整。

**核心问题**是与异常跟踪的状态边界不清（F-DT-001），KpiStrip "诊断待处理"的含义模糊。建议文案区分"诊断任务待执行" vs "异常待处置"。

**核心建议**：
1. **短期**：KpiStrip 状态文案区分（1 天）+ force-render 轮询清理确认（0.5 天）
2. **中期**：随双架构路径 B，进行中 Tab 作为驾驶舱活跃任务视图，历史 Tab 作为工作站完整管理
