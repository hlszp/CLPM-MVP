## 0. 评审哲学（v2 核心调整）

### 0.1 为什么不能只做"契约符合度"对账

契约 v2.10 是"当前实现的事实来源"，它记录了团队在 IA 重构 Phase A-D + UI/UX 整改 Phase 0-2 + 监控工作台闭环 MW-P0~P5 后的共识。但契约本身可能存在以下局限：

- **路径依赖**：契约是历史演进的产物，7 模块→6 模块的收敛、双轴导航的提出，都是在既有代码基础上的优化，未必是第一性原理下的最优解
- **自我证明**：以契约为裁判，等于让"实现者自己出的考卷"来判分，无法发现契约本身的盲区
- **范式锁定**：契约固化了"单架构 + 5 角色 + 6 模块"的范式，而《双架构产品方案》提出的"前台驾驶舱 + 后台工作站"可能是更贴合业务本质的范式

### 0.2 本评审的三层立场

| 层次 | 立场 | 回答的问题 |
|---|---|---|
| **L1 第一性原理** | 跳出契约，回归业务本质 | 危化企业控制回路性能评估与优化，本质要解决什么问题？当前范式是否最优？ |
| **L2 范式评估** | 评估架构选型与业务目标的匹配度 | 6 模块单架构 vs 双架构 vs 其他范式，哪个更匹配？注意力机制是否被尊重？ |
| **L3 实现质量** | 以契约为参考检查实现质量 | 在当前范式下，实现是否达标？契约条款是否被正确执行？ |

**关键原则**：L3 的"契约符合度"只是评审的一个子项，不是最高标准。当 L1/L2 发现范式级问题时，即使 L3 全绿，仍应输出根本性改进建议。

### 0.3 评审的勇气

本评审鼓励：
- 提出"契约条款本身不合理"的发现
- 提出"当前范式存在根本性改进空间"的建议
- 评估《双架构产品方案》等替代范式的可行性
- 从用户注意力机制出发，质疑信息密度与交互范式

## 1. 方法论总述

### 1.1 方法论名称

**第一性原理范式评估 + 五视角正交评审 + 三源证据交叉 + 加权评分 + 四级问题分级**

### 1.2 与已有评审的差异

| 已有评审 | 视角 | 基线 | 局限 |
|---|---|---|---|
| `clpm-ux-ia-audit-report`（08-05） | 仪控工程师工作流单视角 | 契约 v2.5 | 偏流程闭环，未覆盖视觉执行层，未做范式评估 |
| `ui-ux-critical-review`（08-07） | Nielsen 10 启发式 | UI/UX v6.1 | 偏视觉执行，未覆盖 IA 与角色任务，未质疑范式 |
| `loop-workbench-uiux-evaluation`（08-09） | 单页面深审 | UI/UX v6.2 | 仅回路工作台一页，未上升至范式 |
| `monitor-workbench-rectification`（08-09~10） | 监控模块闭环整改 | 契约 v2.9 | 偏实施，非独立评审，以契约为目标 |
| **本次评审** | **第一性原理 + 五视角正交** | **契约 v2.10 作参考** | **跳出契约做范式评估，敢于提出根本性改进** |

### 1.3 核心原则

1. **第一性原理优先**：先问"本质问题是什么、当前范式是否最优"，再问"实现是否达标"
2. **全量独立重评**：不预设已有结论，对每页面/模块/总体独立评审，再与已有 Backlog 交叉标注
3. **三源证据缺一不可**：代码走查（实现层）+ 设计文档对照（契约层）+ 角色场景走查（行为层）
4. **注意力机制为核心**：工业场景下用户注意力是稀缺资源，页面设计必须尊重注意力机制
5. **双架构标注不参与评分**：页面评审以当前单架构为基准，双架构归属仅作参考

## 2. 五视角操作化清单（v2 重构）

### 2.1 视角一：第一性原理与业务匹配度（权重 25%）— v2 新增

跳出契约，回归业务本质。评估当前设计是否从本质上解决了核心问题，架构选型是否与业务目标高度匹配。

#### 2.1.1 核心问题定义（评估起点）

危化企业控制回路性能评估与优化平台的本质问题：

| 本质问题 | 衡量标准 | 当前范式是否触及 |
|---|---|---|
| **早发现**：控制回路性能劣化的早期识别 | 能否在操作工察觉之前发现趋势性劣化？ | 待评估 |
| **准诊断**：劣化根因的精准定位 | 能否区分振荡/粘滞/外扰/参数问题/传感器故障？ | 待评估 |
| **可整定**：整定方案的可信辨识与仿真验证 | 辨识结果是否可信？仿真是否贴合实际？ | 待评估 |
| **能验证**：整定实施后的效果闭环验证 | 整定前后是否有 A/B 对比？验证是否有时效约束？ | 待评估 |
| **留痕审计**：所有决策与变更的可追溯 | 配置变更/参数调整/处置动作是否全留痕？ | 待评估 |
| **规模化**：从 27 回路到 500+ 回路的扩展能力 | 架构是否能支撑 10 倍规模？ | 待评估 |

#### 2.1.2 检查清单

| 子维度 | 检查项 | 证据采集方式 | 达标标准 |
|---|---|---|---|
| 核心问题覆盖度 | 当前设计是否覆盖"早发现/准诊断/可整定/能验证/留痕/规模化"六大本质问题 | 逐问题对照页面与能力 | 6 问题全覆盖 |
| 架构选型匹配度 | 6 模块单架构 vs 双架构 vs 其他范式，哪个更匹配业务本质？ | 第一性原理分析 + 双架构方案对照 | 选型有充分理由，或明确改进方向 |
| 业务目标达成度 | "产品化、工具化、减少开发团队介入"的目标是否达成？ | 用户自助配置能力评估 | 用户可自助完成配置组态 |
| 根本性改进空间 | 如果重新设计，会怎样？当前方案的最大范式瓶颈是什么？ | 范式反思 + 替代方案探索 | 识别范式瓶颈，提出改进方向 |
| 长期发展适配 | 技术实现是否符合项目长期发展（5 年）需求？ | 架构扩展性评估 | 架构可支撑 5 年演进 |

#### 2.1.3 评审提问模板（每页面/模块必答）

1. 这个页面/模块解决的本质问题是什么？
2. 当前解决方案是否是最优解？有没有更简单/更直接/更符合直觉的方式？
3. 这个设计是否符合用户的心智模型？用户期望是什么？
4. 这个设计是否符合工业现场的注意力机制？用户在什么场景下用？注意力能持续多久？
5. 如果去掉所有历史包袱重新设计，会怎样？

### 2.2 视角二：IA 与导航逻辑（权重 15%）

IA 是全站骨架。检查信息架构层级、菜单归类、双轴导航、跨模块上下文、权限可见性。

| 子维度 | 检查项 | 证据采集方式 | 达标标准 |
|---|---|---|---|
| IA 层级深度 | 一级菜单到叶子页点击数 ≤3；隐藏详情页可达性 | 路由树深度走查 `router/routes/modules/*.ts` | ≤3 次点击到达任意叶子页 |
| 菜单归类合理性 | 每菜单项归类是否符合双轴模型；是否有跨轴混装 | 契约 §2 IA 表 + 路由 meta.order 比对 | 归类符合双轴模型（或提出更优归类） |
| 双轴导航一致性 | 实体轴（回路工作台）与职能轴（评估/诊断/整定）互为入口是否成立；loopId 上下文是否双向传递 | 跨模块跳转代码走查 `useLoopContext` | 双向可达，loopId 完整传递 |
| 跨模块上下文 | `?loopId=`/`?taskId=` query 规范是否一致；来源页面包屑/返回按钮是否保留 | 跳转链路追踪 + URL query 断言 | query 规范统一，返回路径保留 |
| 权限可见性矩阵 | 5 角色 × 6 模块菜单可见性是否与契约 §5.1 矩阵一致；默认首页是否按角色分流 | 路由 meta.authority 与契约矩阵逐格比对 | 100% 符合契约矩阵（或提出更优权限模型） |
| 菜单命名一致性 | `route.meta.title` 与 `ClpmPageToolbar.title` 与菜单显示名是否字面一致 | grep 三处标题比对 | 三处字面一致（词表 §2） |
| Legacy redirect 覆盖 | 旧路由是否全量重定向；`route-compat.spec.ts` 是否守护 | 重定向表与 E2E 守护用例核对 | 旧路由 100% 重定向，E2E 守护全绿 |
| 隐藏路由必要性 | `hideInMenu` 路由是否确属详情/兼容/批量视图，无冗余 | 逐条 hideInMenu 路由审查 | 每条 hideInMenu 有合理理由 |

### 2.3 视角三：工业场景与注意力机制（权重 30%）— v2 强化

这是产品定位的核心。工业场景下用户注意力是稀缺资源，页面设计必须尊重注意力机制。本视角合并原"角色任务闭环"与"工业场景可用性"，并强化注意力机制评估。

#### 2.3.1 注意力机制评估框架

| 注意力原则 | 含义 | 检查标准 |
|---|---|---|
| **Glanceability（3 秒扫视）** | 用户首屏 3 秒能否掌握关键信息 | 异常优先、正常弱化、色彩语义、大字数值 |
| **信息层次（异常优先）** | 异常/告警/待办是否在视觉最上层 | F 型/Z 型视觉动线、异常置顶、正常灰化 |
| **认知负荷（最小化）** | 用户完成任务的点击数与决策点 | ≤3 点击完成核心任务、无多余决策点 |
| **操作效率（最少点击）** | 高频操作是否一键可达 | 巡检/处置/确认等高频动作的工具栏直达 |
| **注意力保护（不打断）** | 非关键信息是否避免打断用户 | 无自动弹窗、无 toast 刷屏、无视觉噪音 |
| **状态透明（可交接）** | 实时数据是否新鲜、WS 断连是否降级 | 时间戳可见、WS 状态指示、降级提示 |

#### 2.3.2 角色任务闭环走查

| 角色 | 任务路径 | 检查重点 | 闭环完成度标准 |
|---|---|---|---|
| ADMIN | ①新回路投用全流程（链路→测点→回路→Tag 关联→启用评估）②系统配置变更 ③审计追溯 | 配置向导引导、变更影响提示、审计完整性 | 100% 闭环，无断点 |
| IC_ENGINEER | ①上班巡检（工作台→关注队列→逐回路处置）②异常处置闭环（发现→诊断→整定→实施→验证）③新回路投用辅助 ④周/月度复盘 | 巡检动线、跨模块跳转、上下文传递、A/B 对比引导 | ≥90% 闭环 |
| PE_ENGINEER | ①装置绩效周报查阅 ②低效回路排查 ③异常跟踪参与 | 汇总视图首屏、下钻路径、只读边界 | ≥90% 闭环 |
| EXPERT | ①诊断深度分析（诊断详情→证据→AI 洞察）②整定方案评审（整定详情→仿真→方案确认）③专家建议提交 | 只读边界、AI 洞察可用性、整定安全边界 | ≥90% 闭环 |
| SPONSOR | ①全厂绩效概览 ②异常趋势关注 ③投资决策支撑 | 汇总视图权限、403 清零、首屏不报错 | 100% 无报错 |

每条路径输出：步数、断点位置、上下文丢失点、认知负担评分（1-5）、闭环完成度（%）、注意力打断次数。

#### 2.3.3 工业场景走查

| 场景 | 检查维度 | 关键问题 | 行业基线 |
|---|---|---|---|
| 巡检（每日 8:00） | Glanceability + 注意力保护 | 首屏 3 秒能否掌握"哪里坏了、多严重、要不要处理"；增量视图是否到位；扫视密度是否工业级 | ISA-101 |
| 处置（异常响应） | Poka-Yoke + 操作效率 | 危险操作是否有 typed confirmation；不可逆操作是否有警告；依赖链灰显是否有原因 tooltip；MOC 校验是否强制 | EEMUA 191 |
| 复盘（周/月度） | 数据墨水比 + 认知负荷 | 趋势图是否可读；A/B 对比是否自动引导；时间线是否完整；装饰图表是否退役 | Tufte-Few |
| 配置（新回路投用） | 向导化 + 认知负荷 | 配置流程是否有进度引导；Tag 关联是否有图解；保存后是否有数据验证；错误是否提前发现 | NN-g |
| 交接班 | 状态透明 + 注意力保护 | 实时数据是否新鲜（时间戳）；WS 断连是否有降级；关注队列是否跨班延续 | EEMUA 191 |
| 中控室值守 | Glanceability + 注意力保护 | 远距离可读性；大字数值；异常高亮；无视觉疲劳 | ISA-101 |

### 2.4 视角四：页面设计与实现质量（权重 15%）— v2 调整

契约是参考输入，不是唯一裁判。检查布局、组件、数据流、状态机、空错载态、色彩、文案、可访问性。当发现契约条款本身不合理时，应输出"契约改进建议"。

| 子维度 | 检查项 | 证据采集方式 | 达标标准 |
|---|---|---|---|
| 布局合理性 | 页面布局是否符合业务逻辑与注意力机制；四区/三区/4锚点布局是否最优 | .vue 模板结构 + 第一性原理分析 | 布局合理（或提出更优布局） |
| 组件规范符合度 | 是否使用规范组件；Emoji/装饰图表是否清零 | UI/UX §14 强制清单 18 项核对 | 18 项符合（或提出组件改进） |
| 数据流正确性 | API 调用是否正确；请求代次保护是否到位；AbortController 是否使用 | api/*.ts 与 endpoints 比对 | 数据流正确，无竞态 |
| 状态机完整性 | Action Tracker/Tuning/KPI 快照等状态是否完整渲染；中文映射是否准确 | 契约 §6 状态机表与前端枚举映射比对 | 状态完整渲染（或提出状态机改进） |
| 空/错/载态三要素 | 空态是否含"原因+动作+数据范围"；错误态是否有重试；加载态是否骨架屏 | UI/UX §7.9 + 词表 §5 | 三要素齐全 |
| 色彩纪律 | 是否走 `--status-*` token；hex 是否清零；类别是否中性化；零值是否中性 | `color-convention.md` 8 条纪律 | 8 条纪律符合（或提出色彩改进） |
| 文案规范 | 按钮动词/页面名/术语/枚举露出是否合规 | `copywriting-glossary.md` 6 节 | 6 节符合（或提出文案改进） |
| 可访问性基线 | aria-label/键盘可达/heading 层级/对比度 WCAG AA | UI/UX §13 | WCAG AA 达标 |

### 2.5 视角五：美观度与专业性（权重 15%）— v2 提权

视觉层影响信任与专业感。检查视觉层级、信息密度、工业设计语言、品牌一致性。

| 子维度 | 检查项 | 评分锚点 |
|---|---|---|
| 视觉层级 | 主信息/次信息/辅助信息三级层级是否明确；是否等权重平铺 | 整定详情页（4 锚点+折叠）为 4 分锚点 |
| 信息密度 | 高密度场景（表格）是否工业级；低密度场景（总览）是否留白合理；单位是否进表头 | 监控左栏为 4 分锚点 |

| 组件一致性 | 同类组件全站统一（BulletChart/EmptyState/DangerConfirm/Modal 头/KpiCard）；双轨色是否清零 | D3 死代码清除 + hex 棘轮成果 |
| 暗色就绪 | 暗色模式是否可用（未正式开放但需校准就绪）；对比度 WCAG AA | BL-8 暗色走查状态 |
| 专业感 | 是否传达"危化企业安全"的专业感与可信度 | 工业控制系统的视觉信任 |

## 3. 评分体系（v2 调整）

### 3.1 5 级评分（0-4）

| 分值 | 含义 | 判定标准 |
|---|---|---|
| 4 | 优秀 | 从第一性原理看是最优解，工业级标杆 |
| 3 | 良好 | 达标，局部可优化，范式合理 |
| 2 | 可接受 | 骨架达标，执行需返工，范式无根本问题 |
| 1 | 不足 | 存在明显缺陷，范式有改进空间 |
| 0 | 阻断 | 无法使用，范式有根本问题 |

### 3.2 加权计算（v2 调整）

总分 = Σ(视角得分 × 视角权重)，其中视角得分 = 该视角各子维度得分均值。

| 视角 | 权重 | v1 → v2 变化 | 理由 |
|---|---|---|---|
| ① 第一性原理与业务匹配度 | 25% | 新增 | 范式评估是最高层次，决定方向是否正确 |
| ② IA 与导航逻辑 | 15% | 25%→15% | 仍重要，但在范式确定后属于执行层 |
| ③ 工业场景与注意力机制 | 30% | 20%+20%→30% | 合并角色任务与工业场景，强化注意力机制，产品定位核心 |
| ④ 页面设计与实现质量 | 15% | 25%→15% | 契约符合度降为实现质量子项 |
| ⑤ 美观度与专业性 | 15% | 10%→15% | 提权，专业感影响工业场景信任度 |

### 3.3 评级映射

| 总分 | 评级 | 含义 | 行动 |
|---|---|---|---|
| ≥3.5 | 优秀 | 第一性原理最优解，工业级标杆 | 保持 |
| 2.8-3.4 | 良好 | 范式合理，局部可优化 | 排入 Backlog |
| 2.0-2.7 | 可接受 | 范式无根本问题，执行需返工 | 排入下批次 |
| 1.0-1.9 | 不足 | 范式有改进空间，存在明显缺陷 | 本批次闭环 |
| <1.0 | 阻断 | 范式有根本问题，无法使用 | 立即修复或重构 |

### 3.4 范式级发现标注

当视角一发现范式级问题时，问题级别自动升级：
- 范式级 P0：当前范式无法解决核心问题，需重构
- 范式级 P1：当前范式可解决但非最优，有根本性改进空间
- 范式级 P2：当前范式合理，但局部范式可优化

## 4. 问题分级标准

### 4.1 四级问题分级

| 级别 | 含义 | 判定标准 | 处置时效 | 示例 |
|---|---|---|---|---|
| **P0** | 阻断 | 数据错误/安全边界突破/死导航/权限漏洞/范式无法解决核心问题 | 立即修复 | 死导航 404、权限越权、DCS 下写漏洞、范式级重构 |
| **P1** | 严重 | 闭环断点/认知负担重/范式非最优/规范系统性偏离 | 本批次闭环 | 跨模块跳转断点、范式级改进建议、状态机缺失态 |
| **P2** | 中等 | 体验缺陷/规范局部偏离/信息密度失衡 | 排入下批次 | 列宽不足、术语不一致、图表选型不当 |
| **P3** | 轻微 | 打磨项/文案微调/视觉细节 | Backlog 持续 | 微交互、颜色微调、tooltip 文案 |

### 4.2 问题记录规范

每个问题必须记录：

```
| 编号 | 视角 | 级别 | 问题 | 证据 | Backlog 关系 | 建议方案 | 工作量 | 范式级 |
|---|---|---|---|---|---|---|---|---|
| P-001 | ①第一性 | P1 | 范式非最优 | 业务分析 + 场景 | 新发现 | 范式建议 | 预估 | 是 |
```

### 4.3 Backlog 交叉标注

| 标注 | 含义 |
|---|---|
| **已闭环** | 已有评审识别且已修复（引用闭环 commit/文档） |
| **已识别** | 已有评审识别但未修复（引用原文位置） |
| **新发现** | 本次评审新发现，已有评审未覆盖 |
| **部分闭环** | 已有评审识别且部分修复（说明剩余项） |
| **范式级新发现** | 本次评审从第一性原理发现的新问题，已有评审未触及 |

## 5. 三源证据规范

### 5.1 证据源定义

| 证据源 | 形式 | 权威性 |
|---|---|---|

- 范式级问题必须有第一性原理分析证据

## 6. 评审流程

### 6.1 单页面评审流程（v2）

1. **第一性原理分析**（新增）：这个页面解决的本质问题是什么？当前方案是否最优？
2. **读取路由定义**：从 `router/routes/modules/*.ts` 提取路由路径、组件、权限、meta
3. **读取页面代码**：精读 `.vue` 模板结构、script setup、样式
4. **读取 API 封装**：对照 `api/*.ts` 与后端 `endpoints/*.py`
5. **对照契约**（参考）：逐项比对契约相关条款，但允许提出"契约条款本身不合理"
6. **对照 UI/UX 规范**（参考）：逐项比对 UI/UX §14 + 色彩 + 文案
7. **角色场景走查**：按视角三任务路径走查该页面涉及的角色任务
8. **注意力机制评估**（新增）：按视角三注意力机制 6 原则评估
9. **工业场景走查**：按视角三 6 场景评估该页面表现
10. **美观度评估**：按视角五 7 子维度评分
11. **范式反思**（新增）：如果重新设计，会怎样？
12. **输出问题清单**：按 P0-P3 分级，标注 Backlog 关系与范式级
13. **输出评分**：五视角评分 + 总分 + 评级
14. **双架构标注**：标注前台/后台归属

### 6.2 模块评审流程

1. 汇总该模块所有页面报告
2. 补充模块级第一性原理分析（新增）
3. 补充模块级 IA 评审（菜单归类、模块内导航、模块间协同）
4. 输出模块级五视角评分（页面均值 + 模块级加分/减分）
5. 输出模块级问题清单（去重 + 模块级新增 + 范式级发现）

### 6.3 总体评审流程

1. 汇总所有模块报告
2. 总体第一性原理分析（新增）：6 模块范式是否最优？双架构是否更优？
3. 补充总体 IA 评审（6 模块层级、双轴导航、权限矩阵、跨模块上下文）
4. 输出总体五视角评分
5. 输出总体问题清单 + 范式级发现 + 整改路线图

## 7. 评审质量验证

### 7.1 自检清单

| 验证项 | 标准 | 验证方式 |
|---|---|---|
| 覆盖完整性 | 27 可见页面 + 2 隐藏详情 + 6 模块 + 1 总体均有报告 | 文档树对照路由表逐项核对 |
| 视角完整性 | 每页面报告含 5 视角无遗漏，含第一性原理分析与范式反思 | 模板 checklist 逐项勾选 |
| 证据可溯 | 每问题有 file:line 或契约 §X 或场景步骤或原理分析 | 抽样 20% 问题复核 |
| Backlog 闭环 | 已有 5 份评审 P0-P3 项在交叉矩阵有状态标注 | 逐项核对 |
| 评分一致性 | 同级问题评分偏差 ≤0.5；同类页面评分偏差 ≤1.0 | 跨页面评分比对 |
| 范式级发现 | 每模块至少 1 条范式级发现（新发现或确认无范式问题） | 逐模块核对 |

| 建议可执行 | 每问题有建议方案 + 工作量预估 | 抽样 10 条复核 |

### 7.2 一致性校验

- 第一性原理一致性：同一本质问题在不同页面的评估结论应一致
- 注意力机制一致性：同类页面的注意力评分偏差 ≤1.0
- 契约符合度参考：契约条款偏离项必须有"契约改进建议"或"实现改进建议"
- 色彩纪律扫描：复用 hex 白名单棘轮
- 文案词表扫描：按钮动词/页面名/术语/枚举露出 6 节全库 grep 比对
- 路由兼容性：`route-compat.spec.ts` E2E 守护用例全绿
