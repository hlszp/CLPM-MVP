## 0. 执行摘要

双架构方案提出了一个根本性的范式重构：将 CLPM 拆分为**前台智能驾驶舱**（全员日常监控/预警/轻分析，只读极简）与**后台专家工作站**（工程师深度分析/整定/建模/配置，专业可操作）。这一方案触及了当前单架构的根本范式瓶颈——**5 角色共用一套 IA，导致操作工与工程师的认知负担无法分层、注意力机制无法差异化匹配**。

本评审认为双架构方案的**核心理念正确**（用户心智分层、注意力机制匹配、风险物理隔离、AI 能力分层），但**物理分拆两套界面的实施成本与当前团队规模/回路规模不匹配**。建议**部分采纳**：吸收双架构的理念层，在当前 6 模块单架构基础上实现"角色化视图分层"——为 SPONSOR/操作工角色提供驾驶舱模式视图，为工程师角色保持工作站模式，通过顶部模式切换而非物理分拆实现范式升级。

## 1. 双架构方案核心理念解读

### 1.1 方案本质

《双架构产品方案》的核心主张：

> **前台 = 智能驾驶舱**（全员日常监控、预警、轻分析、结果消费）
> **后台 = 专家工作站**（工程师深度分析、整定、建模、配置、系统管理）
> **95% 高频日常操作极简前台承载，5% 低频高危高阶能力严格收拢后台**

### 1.2 五大核心理念

| 理念 | 含义 | 第一性原理依据 |
|---|---|---|
| **用户心智分层** | 操作工"我要知道哪里坏了、多严重、要不要处理" vs 工程师"我要知道为什么坏、怎么修、怎么优化" | 两种根本不同的心智模型，共用 IA 必然产生认知负担 |
| **注意力机制匹配** | 前台"低密度、大卡片、强视觉层级、问题高亮" vs 后台"高密度、结构化、多面板并列" | 中控室值守 vs 办公室分析，注意力机制完全不同 |
| **风险物理隔离** | 前台"只可读、不可改、不可配、不可整定" vs 后台"所有变更类能力唯一入口" | 权限过滤是逻辑隔离，物理分拆是更强的安全边界 |
| **AI 能力分层** | 前台 AI"结论化、口语化、低门槛" vs 后台 AI"推理化、数据化、可溯源、可干预" | 应用型 AI vs 专家型 AI，服务不同场景 |
| **场景隔离** | 前台"结果驱动、问题优先" vs 后台"过程驱动、能力优先" | 日常运维 vs 优化改造，不同工作场景 |

### 1.3 方案的前台/后台页面树

**前台（智能驾驶舱）6 大功能区**：
1. 装置总览驾驶舱（全厂回路健康度 + AI 洞察 + 热力图 + 异常汇总 + 性能趋势）
2. 回路监控工作台（健康列表 + 轻量详情 + 简易对比）
3. 异常预警中心（未处理聚合 + 归档追溯 + 风险统计）
4. AI 智能洞察中心（风险预警 + 设备劣化 + 节能机会）
5. 报告中心（自动日报/周报 + 异常简报 + 预览下载）
6. 个人待办工作台（待处理风险 + 待关注劣化 + 历史记录）

**后台（专家工作站）8 大功能区**：
1. AI 深度分析工作台（根因诊断 + 因果拓扑 + 相似检索 + 批量分析）
2. PID AI 整定仿真平台（模型辨识 + 三类方案 + 阶跃仿真 + 效果评估 + 下发审批）
3. 回路台账管理（回路 CRUD + 装置层级 + 参数台账）
4. 算法&诊断规则配置（阈值 + 规则 + 置信度校准）
5. 告警高级配置中心（级别 + 聚合 + 静默策略）
6. 数据采集管理（数据源 + 频率 + 质量监控）
7. 高级报告定制中心（模板 + 维度 + 定时任务）
8. 系统权限与运维（用户 + 日志 + 参数）

## 2. 维度一：战略可行性评估

### 2.1 核心问题：95%/5% 业务拆分是否成立？

**双架构假设**：95% 高频日常操作可由前台承载，5% 低频高危能力收拢后台。

**第一性原理分析**：

| 本质问题 | 前台可承载？ | 后台必须？ | 分析 |
|---|---|---|---|
| 早发现（劣化早期识别） | ✅ 可（AI 自动汇总 + 风险预警） | ❌ 不必须 | 前台 AI 一句话结论足够 |
| 准诊断（根因精准定位） | 🔶 部分（轻量结论） | ✅ 必须（根因推理链路） | 前台给"是什么"，后台给"为什么" |
| 可整定（辨识与仿真） | ❌ 不可 | ✅ 必须 | 整定是高危高阶能力 |
| 能验证（效果闭环验证） | ✅ 可（A/B 结果展示） | 🔶 部分（验证配置） | 前台看结果，后台配规则 |
| 留痕审计（可追溯） | ✅ 可（只读查看） | ✅ 必须（审计配置） | 前台查看，后台管理 |
| 规模化（500+ 回路） | ✅ 可（聚合视图） | ✅ 必须（批量配置） | 前台扫视，后台批量 |

**结论**：95%/5% 拆分基本成立。早发现/能验证/留痕可前台承载，准诊断/可整定/规模化必须后台。

### 2.2 核心问题：前台只读极简是否覆盖 IC_ENGINEER 日常？

**双架构假设**：前台"只可读、不可改、不可配、不可整定"。

**IC_ENGINEER 日常任务分析**：

| IC 任务 | 是否需要写操作 | 前台可承载？ |
|---|---|---|
| 上班巡检（查看状态/关注队列） | ❌ 只读 | ✅ |
| 异常处置（发起诊断/整定） | ✅ 发起任务 | 🔶 需"发起"能力，非纯只读 |
| 异常跟踪（更新状态/添加备注） | ✅ 写操作 | 🔶 需"更新"能力 |
| 新回路投用辅助 | ✅ 配置 | ❌ 需后台 |
| 周/月度复盘 | ❌ 只读 | ✅ |

**发现**：IC_ENGINEER 的"异常处置"与"异常跟踪"需要写操作（发起任务、更新状态），纯只读前台无法覆盖。双架构方案的前台"禁止任何参数修改"过于绝对。

**建议**：前台应允许"发起任务"与"更新跟踪状态"这类操作型写入，但禁止"配置/整定/建模"这类变更型写入。

### 2.3 战略可行性结论

| 评估项 | 结论 | 理由 |
|---|---|---|
| 95%/5% 拆分 | ✅ 成立 | 早发现/验证/留痕可前台，诊断/整定/规模化必须后台 |
| 前台只读极简 | 🔶 需调整 | 应允许操作型写入（发起任务/更新状态），禁止变更型写入 |
| 用户心智分层 | ✅ 成立 | 操作工 vs 工程师心智模型根本不同 |
| 注意力机制匹配 | ✅ 成立 | 中控值守 vs 办公室分析，注意力机制差异显著 |

## 3. 维度二：IA 演进路径评估

### 3.1 当前架构 vs 双架构的 IA 对比

| 维度 | 当前 6 模块单架构 | 双架构 |
|---|---|---|
| 顶层入口 | 6 一级菜单（监控/评估/诊断/整定/配置/系统） | 顶部 Tab【智能驾驶舱｜专家工作站】 |
| 角色差异化 | 菜单按 authority 过滤隐藏 | 前后台物理分拆 + 权限锁死 |
| 操作工体验 | 看到 3-4 个菜单（监控/评估/诊断/系统部分） | 只见驾驶舱 6 功能区 |
| 工程师体验 | 看到 5-6 个菜单 | 驾驶舱 + 工作站自由切换 |
| 配置入口 | `/config/*` 集中 | 后台第 3-6 功能区 |
| 整定入口 | `/tuning/*` | 后台第 2 功能区（PID AI 整定仿真平台） |

### 3.2 从当前架构演进到双架构的路径

**路径 A：物理分拆（双架构方案原版）**

```
当前 6 模块 → 物理分拆为两套界面
├─ 前台驾驶舱（6 功能区，新 UI 范式）
└─ 后台工作站（8 功能区，当前 UI 范式增强）
```

- **破坏性**：高（需重构路由、布局、组件库）
- **工作量**：预估 3-4 个月
- **风险**：双 UI 范式维护成本高

**路径 B：角色化视图分层（本评审建议）**

```
当前 6 模块 → 顶部增加模式切换
├─ 驾驶舱模式（SPONSOR/操作工默认，简化视图）
│   ├─ 装置总览（当前系统概览增强）
│   ├─ 回路监控（当前回路工作台简化）
│   ├─ 预警中心（当前预警事件）
│   ├─ AI 洞察（当前 AI 洞察增强）
│   ├─ 报告中心（当前 KPI 报表简化）
│   └─ 待办工作台（当前关注队列）
└─ 工作站模式（工程师默认，当前 6 模块完整 IA）
```

- **破坏性**：低（在当前架构上增加模式切换层）
- **工作量**：预估 1-2 个月
- **风险**：低（保留当前成果，渐进增强）

**路径 C：渐进式角色化（最小可行）**

```
当前 6 模块 → 仅优化角色差异化展示
├─ SPONSOR：默认进入简化概览，隐藏配置/整定/系统
├─ IC_ENGINEER：保持当前 IA
├─ EXPERT：保持当前 IA
└─ ADMIN：保持当前 IA
```

- **破坏性**：极低（仅调整 authority 与默认首页）
- **工作量**：预估 2-3 周
- **风险**：极低

### 3.3 路由兼容性评估

**路径 B 的路由设计**：

```typescript
// 顶部模式切换
const mode = useUserStore().preferences?.mode; // 'cockpit' | 'workstation'

// 驾驶舱模式路由（SPONSOR/操作工默认）
const cockpitRoutes = [
  '/cockpit/overview',      // 装置总览（复用 dashboard/workbench 增强）
  '/cockpit/monitor',       // 回路监控（复用 monitor/loop-workbench 简化）
  '/cockpit/alerts',        // 预警中心（复用 monitor/alerts）
  '/cockpit/ai-insight',    // AI 洞察（新增聚合页）
  '/cockpit/reports',       // 报告中心（复用 metric/kpi-report 简化）
  '/cockpit/todo',          // 待办工作台（复用 monitor/attention）
];

// 工作站模式路由（工程师默认，当前 6 模块）
const workstationRoutes = [
  '/monitor/*', '/assess/*', '/diagnosis/*', '/tuning/*', '/config/*', '/system/*'
];
```

**Legacy redirect 兼容**：当前 `/monitor/loop-workbench` 等路径在驾驶舱模式下重定向到 `/cockpit/monitor`，工作站模式保持不变。

### 3.4 IA 演进路径结论

| 路径 | 破坏性 | 工作量 | 风险 | 推荐度 |
|---|---|---|---|---|
| A 物理分拆 | 高 | 3-4 月 | 高 | ⭐ 不推荐（当前规模不匹配） |
| B 角色化视图分层 | 低 | 1-2 月 | 低 | ⭐⭐⭐ 推荐（平衡理念与成本） |
| C 渐进式角色化 | 极低 | 2-3 周 | 极低 | ⭐⭐ 可作 B 的第一阶段 |

## 4. 维度三：权限模型影响评估

### 4.1 当前权限模型

5 角色 × 6 模块的 authority 矩阵（实现契约 §5）：

| 角色 | 监控 | 评估 | 诊断 | 整定 | 配置 | 系统 |
|---|---|---|---|---|---|---|
| ADMIN | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| IC_ENGINEER | ✅ | ✅ | ✅ | ✅ | 🔶 查看 | ❌ |
| PE_ENGINEER | ✅ | ✅ | 🔶 | ❌ | 🔶 查看 | ❌ |
| EXPERT | ✅ | ❌ | ✅ | ✅ | ❌ | ❌ |
| SPONSOR | ✅ | ✅ | 🔶 | ❌ | ❌ | ❌ |

### 4.2 双架构权限映射

双架构方案的权限锁死：

| 角色 | 前台驾驶舱 | 后台工作站 |
|---|---|---|
| 操作工/班组长 | ✅ 仅可见前台 | ❌ 隐藏入口 |
| 工艺/仪表工程师 | ✅ 自由切换 | ✅ 自由切换 |
| 管理员 | ✅ 默认后台，可切前台 | ✅ 默认 |

**当前角色映射**：

| 当前角色 | 双架构映射 | 说明 |
|---|---|---|
| ADMIN | 管理员（默认后台） | ✅ 直接映射 |
| IC_ENGINEER | 仪表工程师（双模式） | ✅ 直接映射 |
| PE_ENGINEER | 工艺工程师（双模式） | ✅ 直接映射 |
| EXPERT | 专家工程师（双模式） | ✅ 直接映射 |
| SPONSOR | 管理层（双模式，前台为主） | 🔶 需新增"管理层"角色定位 |

### 4.3 是否需要新增角色？

双架构方案提到"操作工/班组长"，当前 5 角色中无此角色。

**分析**：
- CLPM 当前定位为"工程师工具"（PRD v6.2），操作工不是主要用户
- 但双架构方案的"前台驾驶舱"正是为操作工场景设计的
- 如果 CLPM 要扩展到操作工使用，需新增 `OPERATOR` 角色

**建议**：
- 短期：不新增角色，SPONSOR 承担"前台为主"的角色定位
- 中期：若产品扩展到操作工使用，新增 `OPERATOR` 角色，仅可见驾驶舱模式

### 4.4 权限模型结论

| 评估项 | 结论 |
|---|---|
| 当前 5 角色映射 | ✅ 可直接映射到双架构 |
| 新增角色需求 | 🔶 短期不需要，中期可扩展 OPERATOR |
| 权限锁死实现 | ✅ 路径 B 可通过 mode + authority 双重控制 |
| 权限漏洞风险 | ✅ 路径 B 物理隔离比当前逻辑过滤更安全 |

## 5. 维度四：成本与收益评估

| 收益项 | 路径 A | 路径 B | 路径 C |
|---|---|---|---|
| 操作工认知负担降低 | ✅ 根本解决 | ✅ 根本解决 | 🔶 部分缓解 |

| 品牌差异化 | ✅ 强 | ✅ 中 | ❌ 无 |
| 维护成本 | ❌ 翻倍 | 🔶 略增 | ✅ 不变 |

### 5.3 成本收益比

| 路径 | 成本 | 收益 | 成本收益比 | 推荐度 |
|---|---|---|---|---|
| A 物理分拆 | 4-6 月 | 根本解决 | ❌ 低（当前规模不匹配） | ⭐ |
| B 角色化分层 | 1.5-2.5 月 | 根本解决 | ✅ 高 | ⭐⭐⭐ |
| C 渐进式 | 2-3 周 | 部分缓解 | ✅ 最高（但收益有限） | ⭐⭐ |

### 5.4 规模适配性

当前规模：27 回路，5 角色，小团队。

| 规模指标 | 当前 | 双架构收益阈值 |
|---|---|---|
| 回路数 | 27 | ≥100 回路时驾驶舱价值显著 |
| 用户数 | 5 种子账号 | ≥50 用户时角色分层价值显著 |
| 操作工使用 | 无 | 有操作工使用时前台价值显著 |
| 团队规模 | 小团队 | 大团队可承担双 UI 维护 |

**结论**：当前规模下，路径 A（物理分拆）的成本收益比不合理；路径 B（角色化分层）在当前规模下已有收益且成本可控。
