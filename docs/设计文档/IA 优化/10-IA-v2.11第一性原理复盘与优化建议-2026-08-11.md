| 项目 | 内容 |
|---|---|
| 文档日期 | 2026-08-11 |
| 文档状态 | 决策建议，待产品/工程评审；未批准前不替代实现契约 |
| 评审对象 | CLPM 当前信息架构、导航、权限、跨模块上下文、任务与闭环对象 |
| 事实基线 | 实现契约 v2.11 + 当前代码 <code>d741569b</code> |
| 需求基线 | PRD v6.2 |
| 文档关系 | 对 2026-08-10 全量 IA 评审做增量复盘，不重复页面级视觉问题 |
| 核心方法 | 苏格拉底式追问 → 第一性原理拆解 → 奥卡姆剃刀收敛 |

> 本文回答的不是“菜单还能怎么挪”，而是三个更根本的问题：CLPM 的真实工作对象是什么、危化场景中的安全闭环在哪里、怎样用最少的结构变化让用户持续做出正确决定。

---

## 0. 一页结论

### 0.1 总体判断

当前“监控 / 评估 / 诊断 / 整定 / 配置 / 系统”六模块骨架已经基本合理，不应再次推倒重排，也不应恢复第七个“回路”一级模块。

当前 IA 的主要矛盾已经从“页面归类不清”转变为：

1. **业务闭环已存在，但关键动作入口仍可能失效**：推荐下一步、验证入口、深链接和返回路径存在确定断点。
2. **功能轴已清楚，但缺少工作状态轴**：用户能找到评估、诊断和整定，却难以持续回答“这件事归谁、何时到期、下一步是什么、是否真正闭环”。
3. **回路上下文存在，但不是全站契约**：监控内部上下文与跨模块上下文双轨，时间窗、来源事件、证据版本和返回路径会丢失。
4. **角色权限解决了部分‘能不能看’，没有可靠解决‘今天先做什么’**，且前端路由、后端权限、默认首页和权限说明存在多套事实。
5. **危化领域语义尚未完全守住边界**：CLPM 的绩效预警、DCS/SIS 报警、诊断发现、关注项和闭环案例需要明确区分。
6. **人工实施是产品安全边界，却仍是最薄弱的交接段**：建议者、实施者、MOC 审批人和验证者没有完整的职责与签核模型。

### 0.2 推荐目标

推荐采用：

> **一套 IA、三条坐标、角色化首页、一个持久闭环对象。**

三条坐标分别是：

- **对象与范围轴**：工厂 / 装置 / 单元 / 回路构成范围层级；测点按 PV、SP、OP、MODE、PID 参数等角色与回路关联，串级和复杂回路保留图关系，不强行压成树。
- **决策生命周期轴**：数据就绪 → 评估 → 诊断 → 选择干预 → 人工实施 → 验证 → 关闭或重开。
- **工作状态轴**：待关注 → 已受理 → 处理中 → 验证中 → 已闭环 / 已重开。

六个一级模块继续承载稳定能力；“今日工作、关注队列、闭环案例、全局上下文”承担跨模块协调。

### 0.3 保留、先修、补齐、暂缓

| 类别 | 建议 |
|---|---|
| 保留 | 六模块、实体轴/职能轴、关注队列、单回路工作台、可信度门禁、Tracker 验证状态机、legacy redirect |
| 先修 | 失效 CTA、坏链接、父子权限冲突、角色无权限按钮、Tracker 新旧状态混用、默认首页与契约漂移 |
| 补齐 | 统一业务上下文、关注项到持久案例的转换、责任人与时限、站点投用就绪度、角色化首页、实体搜索 |
| 暂缓 | 双“驾驶舱/工作站”模式、物理双应用、第七个一级模块、全功能超级工作台、全库统一事件表 |
| 永不进入 | DCS PID 参数自动下写或“审批后下发”能力；平台只输出建议、证据、风险、回退和人工实施留痕 |

## 1. 评审边界与证据规则

### 1.1 本次不重复什么

2026-08-05 至 08-10 的整改已经完成大量工作。本次不再把以下内容重复列为新建议：

- 空状态、Tooltip、表格列配置、刷新反馈、暗色与色彩统一；
- 回路工作台单页整合、workspace/table 双模式；
- 关注队列、预警事件与规则配置拆分；
- AI 洞察、预测预警、整定知识库；
- Tracker 的 VERIFYING、CLOSED、REOPENED、A/B 验证；
- 单回路新建向导。当前 <code>LoopEditDrawer</code> 已有“基础信息 → Tag 关联 → 投用定义 → 完成启用”四步流程和最近 5 分钟数据检查；
- 移动端适配。当前产品已经明确定位为桌面工程工作站。

本次重点是：**事实对账、领域语义、跨模块责任、规模化与可验证闭环。**

### 1.2 事实优先级

当资料冲突时，本文按以下顺序判断：

1. 当前代码与运行验证；
2. 实现契约 v2.11；
3. PRD v6.2 与 UI/UX v6.2；
4. 最新 Backlog 追踪；
5. 日期型出口报告与历史方案。

这一区分很重要：现有 IA 目录是 2026-08-10、契约 v2.10 的完整快照；本文是基于 v2.11 和当前代码的增量复盘。

### 1.3 外部领域依据

- [GB/T 44693.2-2024](https://openstd.samr.gov.cn/bzgk/std/newGbInfo?hcno=5E98B4CD584758CE54F989D1A414C512) 的现行标准名称即“危险化学品企业工艺平稳性 第 2 部分：控制回路性能评估与优化技术规范”，与 CLPM 的产品域直接对应。
- [ISA-95](https://www.isa.org/standards-and-publications/isa-standards/isa-95-standard) 区分了现场物理过程、感知与操纵、过程监视控制及制造运营管理。由产品“只读 DCS 数据、不下写参数”的边界推断，CLPM 是绩效治理与决策支持工具，不是 DCS/SIS 操作 HMI。
- [ISA-101](https://www.isa.org/standards-and-publications/isa-standards/isa-101-standards) 强调过程自动化界面的态势感知、一致导航、生命周期和持续改进；这些原则适用于 CLPM，但不能据此把 CLPM 等同于控制室 HMI。
- [ISA-18.2](https://www.isa.org/standards-and-publications/isa-standards/isa-18-series-of-standards) 强调报警哲学、合理化、优先级、操作响应与全生命周期管理。由此推断，CLPM 的咨询性绩效预警不应与要求操作员及时响应的 DCS/SIS 报警混称。
- [ISA-106](https://www.isa.org/standards-and-publications/isa-standards/isa-standards-committees/isa106) 强调连续过程中的异常处置、程序步骤、状态转换和物理对象层级，支持把“对象范围”和“处置状态”作为 IA 的显式坐标。
- [ISO 9241-210:2019](https://www.iso.org/standard/77520.html) 要求基于真实使用情境开展以人为中心设计。当前没有 OPERATOR 角色和经验证的操作员任务研究，因此不应以假设用户为由先建设第二套 IA。

## 2. 从第一性原理重建问题

### 2.1 CLPM 的最终产出是什么

不是 KPI，不是诊断标签，也不是整定建议。

CLPM 的最终产出是：

> **在可信证据基础上，完成一次有责任人、有风险控制、有人工实施留痕、并经过效果验证的回路改善。**

因此，“计算完成”“建议生成”“参数已实施”都不是终点。只有验证通过才闭环；证据不足应返回补数或修复组态；效果无改善应重开。

### 2.2 CLPM 的核心工作对象是什么

不是页面，也不只是回路。

更准确的对象是：

> **回路 × 时间窗 × 证据版本 × 一次治理事项。**

同一回路可能同时存在昨日评分恶化、当前数据质量问题、上周整定后的待验证事项。只传 <code>loopId</code> 会把不同时间和不同证据链混在一起。

### 2.3 用户为什么打开系统

用户不是为了“进入诊断模块”，而是为了回答一组连续问题：

1. 今天哪里需要注意？
2. 为什么它排在前面？
3. 数据足够可信么？
4. 是数据问题、工艺问题、设备问题还是控制问题？
5. 要观察、修数据、维修、改工艺，还是整定？
6. 谁负责，何时完成？
7. 现场实际做了什么？
8. 效果是否改善，证据是什么？

IA 必须让这些问题连续，而不是让用户记住模块之间的拼接关系。

### 2.4 十二条设计公理

| # | 公理 | 对 IA 的要求 |
|---|---|---|
| 1 | 验证后的改善才是价值终点 | 所有干预路径最终汇聚到验证，不以任务成功替代业务闭环 |
| 2 | 数据可信度先于业务结论 | 来源、时间窗、新鲜度、有效率、置信度必须伴随结论 |
| 3 | 人以例外驱动工作 | 高频首页首先展示已排序的小型行动队列，而不是完整功能地图 |
| 4 | 回路是对象，治理事项是工作单位 | 同一回路可有多个独立事项，必须有来源与证据关联 |
| 5 | 关注项不等于工作承诺 | 系统派生项可消失；一旦受理，应转为持久、可审计的闭环案例 |
| 6 | 实施不等于关闭 | canonical 状态应为 PENDING → IN_PROGRESS → VERIFYING → CLOSED / REOPENED |
| 7 | 整定只是诊断后的一个分支 | 数据修复、维修、工艺调整、观察和整定最终都汇聚到验证 |
| 8 | 平台不控制 DCS | 任何界面不得提供“应用参数”“审批后下发”的暗示 |
| 9 | 有后果的动作必须有责任 | 建议、批准、实施、验证要能区分参与人和时限 |
| 10 | 权限决定动作，不应无必要遮蔽事实 | 专家可以读证据但未必能发起任务；Sponsor 看结果但不见工程动作 |
| 11 | 组态按依赖和就绪门组织 | 链路、测点、回路、映射、数据验证、首评估应可见整体就绪度 |
| 12 | IA 事实源本身是安全基础设施 | 路由、RBAC、状态机、默认首页、权限页和测试不能各自手写一套 |

## 3. 真实领域任务流

### 3.1 主闭环不是一条直线

~~~mermaid
flowchart LR
  A["数据与组态就绪"] --> B["绩效监测与异常筛选"]
  A -- "不就绪" --> A1["修复链路 / Tag / 历史数据"]
  A1 --> A
  B --> C["评估：是否真的劣化"]
  C -- "证据不足" --> A1
  C --> D["诊断：原因与可行动性"]
  D --> E{"选择干预路径"}
  E --> E1["数据或组态修复"]
  E --> E2["工艺 / 设备处置"]
  E --> E3["PID 整定建议"]
  E --> E4["继续观察"]
  E1 --> F["人工实施 + 责任人 + MOC / 依据"]
  E2 --> F
  E3 --> F
  E4 --> B
  F --> G["效果验证"]
  G -- "改善" --> H["关闭 + 知识沉淀"]
  G -- "无改善 / 恶化" --> I["重开"]
  I --> D
  H --> B
~~~

这个模型修正了两个常见误解：

- 诊断不一定进入整定；
- 整定建议不等于现场实施，更不等于闭环。

### 3.2 关键场景

| 场景 | 起点 | 用户要做的判断 | 合格终点 |
|---|---|---|---|
| 班次开始 | 今日待办 / 关注队列 | 哪些事项风险最高、为什么、由谁处理 | 受理、指派、设定时限或明确观察 |
| 单回路劣化处置 | 回路或关注项 | 数据可信么、根因是什么、走哪条干预路径 | 建立持久案例并进入正确分支 |
| 数据不足 | INCONCLUSIVE / 数据质量项 | 缺什么、由谁补、修复后如何续跑 | 数据就绪，自动或一键回到原事项 |
| 整定协同 | 可整定诊断 | 模型可信么、建议风险和回退是什么 | 授权人员人工实施并记录实际值 |
| 实施后验证 | VERIFYING / 超期 | 时间窗够么、改善是否显著 | CLOSED 或 REOPENED，保留证据 |
| 新站点/新装置投用 | 工程组态 | 哪一步未就绪、影响哪些回路 | 链路、映射、数据和首评估全部通过 |
| 周/月治理复盘 | 绩效与闭环统计 | 风险是否下降、超期和重开在哪里 | 资源与规则调整决定可追溯 |

### 3.3 角色与责任

| 角色/参与者 | 默认关注 | 应有动作边界 |
|---|---|---|
| ADMIN | 平台健康、工程就绪、配置变更、审计 | 管理组态与系统；不应自动成为所有业务事项负责人 |
| IC_ENGINEER | 今日处置、诊断、整定协调、Tracker、验证 | 受理、分析、协调、记录；高风险事项不宜自建议、自实施、自验证 |
| PE_ENGINEER | 工艺/设备背景、生产影响、协同判断 | 查看完整证据、补充上下文、会签；不必拥有整定写权限 |
| EXPERT | 被升级的复杂案例、模型与整定建议 | 读取评估证据、深度诊断和建议；不接收全部日常噪声 |
| SPONSOR | 风险、超期、改善成效、资源决策 | 看聚合与升级事项；不呈现无权限工程按钮 |
| 现场实施者 | 按批准方案人工实施、记录实际参数和回退准备 | 至少实名记录，不一定需要完整平台账号 |
| MOC 审批人 / 独立验证人 | 批准高风险变更、复核效果 | 作为参与者与签核责任建模，支持四眼原则 |

最后两类参与者目前未被五角色 RBAC 完整表达。短期不必急于新增系统角色，但必须记录其身份、责任和签核结果。

## 4. 当前 IA 事实图

### 4.1 实际一级导航

| 一级模块 | 当前主要页面 | 真实意图 |
|---|---|---|
| 监控 | 系统概览、回路工作台、关注队列、预警事件 | 当前态、行动入口、单回路编排、历史事件 |
| 评估 | 性能总览、回路性能、评估任务、KPI 报表 | 回路群与单回路的绩效证据 |
| 诊断 | 诊断总览、回路分析、诊断任务、异常跟踪 | 原因分析、计算作业和人工闭环 |
| 整定 | 整定工作台、知识库、效果统计 | 模型辨识、建议、仿真和经验复用 |
| 配置 | 链路、测点、回路、数据源、指标、诊断、预警规则 | 低频工程组态和方法策略 |
| 系统 | 用户、审计、权限、自动报表、LLM | 平台治理 |

实际代码已经是六模块；独立“回路”只保留隐藏兼容路由。历史 7 菜单与 6 Tab 方案不应再作为现状。

### 4.2 已经做对的结构

1. **六模块稳定**：配置与运行分离，评估/诊断/整定保留专业深度。
2. **实体轴和职能轴并存**：回路工作台看单回路，职能模块做跨回路专业分析。
3. **关注队列聚合五来源**：预警、评分恶化、数据质量、Tracker、验证超期已经进入同一投影。
4. **工作台后端已具备正确生命周期**：组态/数据修复 → 评估 → 诊断 → 建单或整定 → 人工实施/MOC → 验证 → 持续监控。
5. **可信度是门禁**：INCONCLUSIVE 不再伪造确定性结论。
6. **Tracker 已有诊断/整定闭环基础**：负责人、实施人、MOC、实际 PID、验证与重开可承载 PID 类治理案例；扩展到数据修复、设备维修、工艺调整前，必须先补干预类型和按类型校验。
7. **工作台具备规模化基础**：列表分页/虚拟滚动、区级懒加载、请求代次保护和 summary 聚合已经落地。

这些能力应保留，而不是在新 IA 中复制一遍。

## 5. 深度反思：八个结构性矛盾

### 5.1 模块地图不等于工作地图

当前模块分类基本正确，但用户真正需要的是“异常被发现后如何持续处置”。模块只能回答“功能在哪里”，不能回答“事项现在在哪个状态、归谁、多久到期”。

关注队列已经开始承担工作状态轴，但它仍主要是派生列表：

- 没有 owner、due、SLA、“我的 / 团队”；
- 部分来源的一步主动作被隐藏；
- 派生条件消失后，事项可能从队列消失，却不一定留下受理和处置记录；
- 异步任务失败未进入五类关注来源。

**结论**：不新增一级模块；把关注队列明确为“系统派生的行动候选”。Tracker 先补齐通用干预类型、实施证据和按类型校验，再扩展为“人已受理的持久闭环案例”。

### 5.2 回路工作台正在从编排器退化为超级页面

原设计强调“四区、摘要、主图、明确动作”；实际模板已出现第五个闭环验证区。继续把专业能力嵌入工作台，会重新制造：

- 重复实现；
- 数据口径分叉；
- 页面加载和认知负担增加；
- 职能模块失去边界。

工作台的正确职责应是：

> **选择回路、显示可信摘要、标出生命周期、给出唯一下一步、保持上下文。**

复杂诊断证据、模型选择、仿真和报表仍应留在职能页。不要以 Modal 把整个职能页搬进工作台。

### 5.3 上下文不是全站业务契约

当前存在两套思路：

- <code>useMonitorContext</code>：覆盖 plant、loop、时间窗、event、tracker、section 等，但主要服务监控内部；
- <code>useLoopContext</code>：只覆盖 loopId/taskId，且当前没有生产消费者，导航还主动丢弃其他 query。

页面继续手拼 URL，已经产生可确认的后果：

- 诊断列表收到 <code>loopId</code> 却不消费；
- 关注队列收到 <code>loopId</code> 却不消费；
- 诊断返回整定使用错误的详情路径；
- 关注队列把 <code>plantNodeId</code> 错当成 <code>loopId</code>；
- URL 携带 diagnosisLabel、confidenceLevel 等派生展示字段，可能陈旧或被修改。

**结论**：需要一个 typed OperationalContext，而不是继续增加页面特例。

建议上下文信封：

| 分组 | 字段 | 规则 |
|---|---|---|
| scope | plantNodeId、loopId | 可分享、可持久；写操作前必须显式确认作用范围 |
| evidence | assessmentId、diagnosisId、tuningTaskId、evidenceVersion | 业务判断按 ID 从服务端重载，不信任 URL 中的标签和置信度 |
| work | attentionId/sourceType/sourceId、trackerId | 明确从哪个事项进入、是否已转持久案例 |
| time | timeWindow、snapshotAt | 区分实时态、分析窗和验证窗 |
| navigation | sourceRouteId、returnRouteId | 使用受控 route ID，不接受任意字符串路径 |

### 5.4 权限、可见性和任务适配混成了一件事

当前有多处事实冲突：

- <code>/config</code> 父路由仅 ADMIN，子路由又声明 IC/PE 可查看；父节点先被过滤，子权限实际失效；
- <code>/system</code> 父路由允许 ADMIN/IC，“权限矩阵”注释称所有角色可看，契约又写系统仅 ADMIN；
- 后端给 EXPERT <code>metric:view</code>，评估路由却完全排除 EXPERT；
- 默认首页在后端、前端 store、前端 API 常量中有三套定义；
- 通用 LoopLink 与诊断任务操作不按角色过滤，用户会看到点击后 403 的入口。

路由隐藏不是安全边界，模式切换更不是“物理隔离”。真正的安全边界是后端能力授权；前端的职责是只展示当前能力允许的动作。

**结论**：从“模块 × 角色”矩阵升级为“能力 × 对象 × 动作”模型，并让菜单、CTA、权限页和测试从同一清单派生。

### 5.5 绩效预警与工艺报警需要严格分界

CLPM 的预警主要来自 KPI、漂移、置信度和组合规则；它们是绩效治理信号，不是 DCS/SIS 报警。

建议统一定义：

| 对象 | 定义 | 是否天然要求操作员限时响应 | 在 CLPM 中的定位 |
|---|---|---|---|
| DCS/SIS 报警 | 过程异常，需要操作员按报警哲学响应 | 是 | 外部事实，只读引用，不由 CLPM 替代 |
| 绩效预警 | KPI、趋势、置信度或规则触发的咨询性信号 | 否，除非企业治理规则另行定义 | 预警记录 |
| 关注项 | 当前需要某角色判断的系统派生投影 | 取决于治理优先级 | 今日队列 |
| 诊断发现 | 对原因和可行动性的证据化判断 | 否 | 案例证据 |
| 闭环案例 | 已被人受理、有责任人与状态的治理工作 | 是，按 owner/due/SLA | 持久工作对象 |

UI 应使用“绩效预警”“治理优先级”，并在帮助、规则配置和事件详情中持续说明“非 DCS/SIS 报警、不替代操作规程”。

优先级不能只看算法严重度，应综合：

- 回路重要度 / 安全关键性；
- 影响范围；
- 异常严重度与持续时间；
- 证据可信度；
- 是否已受理、是否超期。

低可信度不应制造高置信风险结论；它应优先进入“数据修复”分支。

### 5.6 Action Tracker 的信息归属过窄

Tracker 当前位于诊断中心，但它已经承载：

- 预警或评分恶化建单；
- 非整定类处置记录入口，但尚无与其匹配的验证契约；
- 整定后的人工实施；
- MOC、实际 PID、负责人；
- 效果验证、关闭与重开；
- 知识沉淀。

它已经具备跨域闭环对象的关系基础，却仍被无条件 MOC/PID 校验限制为偏 PID 的验证模型；因此不能只改名称或菜单归属。

建议分三步：

1. **先补通用干预契约**：增加 `interventionType`、通用实施证据、来源关联，并按 PID 整定、数据修复、设备维修、工艺调整等类型执行不同校验。现有 MOC 与三项实际 PID 必填规则只适用于 PID 类干预，不能无条件套用到全部案例。
2. **再升级用户语义**：完成 schema、service、API、UI 和迁移后，把 Tracker 升级为“闭环案例”，以 trackerId 作为已受理事项的 caseId；Attention 仍是未受理投影。
3. **最后验证是否需要独立 case 表**：只有当多预警、多评估版本、多诊断、多次干预无法由扩展后的 Tracker 关系字段表达时，才引入 governance_case。不要先做全库统一事件模型。

菜单归属可先通过 Monitor 的今日工作和关注队列强化入口，保留旧路由；待行为数据确认后，再考虑把“异常跟踪”从诊断子菜单重命名并迁移为“闭环案例”。

### 5.7 人工实施交接没有形成可证明的职责分离

当前 Tracker 已记录 assignee、implementedBy 和 MOC，但状态更新主要由 IC 执行，且没有独立 verifier / approver 责任。

在危化场景中，建议至少记录：

- 建议人；
- 处置负责人；
- MOC 审批人或“不适用”依据；
- 现场实施人及实际实施时间；
- 实际 PID 与回退参数；
- 验证人、验证时间窗和结论；
- 是否要求验证人与建议/实施人不同。

短期可以把外部人员作为实名参与者字段；中期再按企业制度增加 <code>tracker:implement</code>、<code>tracker:approve</code>、<code>tracker:verify</code> 能力。不要为了补字段立即增加多个一级角色。

### 5.8 文档与代码没有共同事实源

当前可确认的 IA 相关漂移包括：

- 契约主表遗漏 <code>/monitor/attention</code>；
- 契约正文仍保留旧 IMPLEMENTED 状态机；
- IA 评审 README 仍是契约 v2.10；
- 历史 IA 方案主文仍写 7 菜单 / 6 Tab；
- 配置父子权限与契约承诺不一致；
- 权限页仍出现旧模块和旧角色称谓；
- 默认首页存在三套定义；
- E2E 角色说明仍描述旧菜单。

这种漂移不是普通文档卫生问题。它直接造成错误路由、403、错误状态表单和测试盲区。

## 7. 目标 IA：一套结构，三条坐标

### 7.1 目标模型

~~~mermaid
flowchart TB
  subgraph S["对象与范围轴"]
    S1["工厂"] --> S2["装置 / 区域"] --> S3["单元"] --> S4["回路"]
    S4 -. "PV / SP / OP / MODE / PID 角色关联" .-> S5["测点（Tag）"]
    S6["串级 / 复杂回路组"] -. "包含或关联" .-> S4
  end

  subgraph L["决策生命周期轴"]
    L1["数据就绪"] --> L2["评估"] --> L3["诊断"] --> L4["干预选择"] --> L5["人工实施"] --> L6["验证"]
  end

  subgraph W["工作状态轴"]
    W1["待关注"] --> W2["已受理"] --> W3["处理中"] --> W4["验证中"] --> W5["已闭环 / 已重开"]
  end

  S4 -. "作用对象" .-> L2
  L3 -. "形成或更新" .-> W2
~~~

模块只是进入这三条坐标的不同视角：

- 监控：当前态和工作状态；
- 评估/诊断/整定：决策生命周期中的专业证据；
- 配置：对象与方法的工程就绪；
- 系统：权限、审计和平台治理。

### 7.2 建议的信息所有权

| 信息对象 | 唯一职责 | 主入口 | 不应承担 |
|---|---|---|---|
| 今日工作 | 按角色显示最重要的 3–5 件事和系统健康 | 监控首页 | 完整历史、专业分析 |
| 关注项 | 系统派生、可消失、待判断的行动候选 | 关注队列 | 长期责任和闭环审计 |
| 闭环案例 | 已受理、有 owner/due/状态/证据/签核的持久事项 | Tracker 演进页 | 原始预警规则配置 |
| 回路工作台 | 单回路可信摘要、生命周期、唯一下一步、上下文编排 | 回路工作台 | 复制完整诊断/整定页面 |
| 计算作业 | 评估、诊断、整定、报告等异步执行记录 | 各职能任务页 | 代替人工工作项 |
| 绩效预警记录 | 规则触发历史、确认、抑制、审计、导出 | 预警记录 | 代替 DCS/SIS 报警 |
| 专业证据 | KPI、诊断链、模型、仿真、验证结果 | 评估/诊断/整定 | 自己管理跨部门责任 |

### 7.3 一级导航建议

一级导航数量与核心名称暂不改变：

1. 监控
2. 评估
3. 诊断
4. 整定
5. 配置
6. 系统

先通过子页边界和默认首页解决问题，避免新一轮路由迁移。

建议的子页语义：

| 模块 | 建议顺序 / 命名 | 说明 |
|---|---|---|
| 监控 | 今日工作 → 关注队列 → 回路工作台 → 绩效预警记录 | 从“今天做什么”到“看对象”再到“查历史”；菜单顺序保持全角色稳定 |
| 评估 | 性能总览 → 回路绩效证据 → 评估作业 → KPI 报表 | 明确“总览/单回路/计算作业/管理报表” |
| 诊断 | 诊断总览 → 回路分析 → 诊断作业 → 闭环案例（过渡期） | “任务”若主要是异步计算，建议统一称“作业” |
| 整定 | 整定工作台 → 知识库 → 改善效果 | 保持不变；所有实施入口继续强调人工与 MOC |
| 配置 | 投用就绪 → 数据与资产 → 方法与策略 | 不必立刻改 URL，可先增加分组和就绪摘要 |
| 系统 | 用户与能力 → 审计 → 自动报表 → LLM | 系统模块默认 ADMIN；权限说明若面向全员，应放个人帮助而非系统菜单 |

“系统概览”当前实际是跨模块待办门户和链路健康，应改为更准确的“今日工作”或“运行与待办概览”；“预警事件”应改为“绩效预警记录”，避免与 DCS 报警混淆。

### 7.4 角色化首页，不做第二套 IA

角色化应改变默认视角、信息密度和主动作，不改变基础术语与菜单树：

| 角色 | 推荐默认首页 | 首屏重点 |
|---|---|---|
| ADMIN | 工程就绪 / 平台健康 | 断链、失败任务、配置变更、待投用回路 |
| IC_ENGINEER | 我的工作 / 关注队列 | owner 为我、未受理、高风险、超期验证 |
| PE_ENGINEER | 待协作案例 / 性能总览 | 工艺背景、影响范围、待会签 |
| EXPERT | 被升级案例 / 回路工作台 | 完整证据包、模型质量、待复核建议 |
| SPONSOR | 治理成效 | 风险趋势、超期、重开率、改善收益 |

默认首页只能有一个机器可读映射。前端、后端、文档和测试必须从同一来源生成或校验。

## 9. 不建议采用的方向

### 9.1 暂不采用双“驾驶舱 / 工作站”模式

双模式抓住了角色认知差异，但当前不应作为主方案：

1. 当前主要用户是管理员、仪控、工艺/设备、专家和管理者，没有已验证的 OPERATOR 角色；
2. 当前问题主要是上下文、责任、权限和事实源，第二套路由不会自动解决；
3. 相同信息被两套视图表达，会增加数据口径、组件、培训和测试成本；
4. 前端 mode + authority 不是物理安全隔离；
5. “驾驶舱”容易把 CLPM 误解为 DCS 操作界面；
6. 历史双架构方案中的“下发审批”与当前禁止 DCS 参数下写的安全边界冲突。

更轻且更符合当前证据的方案，是一套 IA 内的角色化首页、信息密度和动作能力。

### 9.2 不继续扩张回路工作台

工作台应是编排器，不是所有专业页面的容器。每个区只保留：

- 当前结论；
- 证据时间与可信度；
- 一张主要图或少量关键指标；
- 唯一下一步；
- “查看完整证据”入口。

### 9.3 不立即建设全库统一事件中心

Attention 已经可以作为派生投影；Tracker 必须先完成类型化干预契约，才可承担跨域持久案例。只有扩展后的关系复杂度和审计需求证明现模型不足时，才新增 case/event 基础设施。

### 9.4 不大规模重命名 URL

用户可见名称和 route ID 可以先规范；现有 URL 继续通过 canonical route 和 legacy redirect 保持兼容。先消除坏链接，再讨论路径美化。

## 10. 可验证的 IA 成功指标

原页面评分和“点击数”不足以证明 IA 有效。建议建立任务结果指标：

| 指标 | 定义 | 建议目标 |
|---|---|---|
| 首个正确动作时间 | 登录后到完成正确受理/分析入口的时间 | 5 角色基线测量后持续下降 |
| 上下文完整率 | 跨模块后 scope/evidence/time/work 引用均正确 | 关键路径自动化测试 100% |
| 可见即有权率 | 可见 CTA 的请求不会因角色导致 403 | 100% |
| 悬空入口数 | 路由不存在、query 不消费、返回路径错误 | 0 |
| 受理转化率 | 高优先关注项被受理或明确驳回的比例 | 按企业治理目标设定 |
| 无主事项率 | 已受理但无 owner/due 的案例占比 | 0 |
| 验证超期率 | VERIFYING 超过规定窗口的比例 | 可追踪并持续下降 |
| 重开率 | 验证失败后重开的比例 | 作为质量信号，不追求机械归零 |
| INCONCLUSIVE 恢复时长 | 数据不足到补数/修复后重新评估的时间 | 可追踪并持续下降 |
| 事项重复率 | 同一根因形成多个未关联关注项/案例 | 通过 source/case 关联持续下降 |
| 文档漂移数 | 路由、权限、状态机、默认首页与文档冲突 | 自动检查为 0 |

运行验证至少覆盖：

1. ADMIN 新站点投用；
2. IC 班次处置；
3. PE 补充工艺证据；
4. EXPERT 接收升级案例并查看完整评估依据；
5. SPONSOR 查看风险与闭环成效；
6. 人工实施 → 验证通过 / 重开；
7. 数据不足 → 修复 → 续跑；
8. 异步任务失败 → 今日工作 → 重试或升级。

## 11. 决策记录

| 决策 | 建议结论 | 原因 |
|---|---|---|
| 是否重做一级导航 | 否 | 六模块已经稳定，问题不在菜单数量 |
| 是否恢复“回路”一级模块 | 否 | 回路是全站对象范围，不应再成为与职能并列的第七模块 |
| 是否建设双模式 IA | 当前否 | 缺少真实 OPERATOR 证据，且增加维护与语义风险 |
| 是否角色化 | 是 | 通过默认首页、信息密度和能力过滤完成，不复制页面 |
| 是否统一工作队列 | 是，但区分 Attention 与 Case | 派生关注项和持久责任对象不能混为一物 |
| 是否新增独立 case 表 | 暂不 | 先扩展 Tracker 的干预类型、通用证据和按类型校验；这不等于“零 schema 变更” |
| 是否移动 Tracker 菜单 | 分阶段 | 先改变语义和入口，行为验证后再迁移归属 |
| 是否继续增强工作台 | 只增强编排 | 专业深挖留在职能模块 |
| 是否允许 DCS 下写 | 否 | 产品安全边界 |

## 13. 最终建议

CLPM 已经完成了“把功能放对位置”的第一轮 IA 重构。下一轮不应继续围绕菜单和页面做大搬家，而应把系统升级为一个真正可交接、可追责、可验证的治理工作环境。

最小而有效的路径是：

1. 先修复现有闭环入口、权限和状态机事实错误；
2. 用统一 OperationalContext 串起对象、证据、时间和事项；
3. 明确 Attention 是待判断投影；先让 Tracker 支持类型化干预，再将其作为持久闭环案例；
4. 用角色化首页解决“今天先做什么”，不复制第二套 IA；
5. 补齐人工实施、MOC 与独立验证责任；
6. 用机器可读事实源约束路由、权限、状态机、文档和测试。

一句话概括：

> **保留六模块，停止页面扩张，把 IA 的中心从“功能在哪里”转向“一个高风险事项如何被可信地发现、负责地处理、独立地验证并留下证据”。**
