## 3. 第一性原理评估（视角一）

### 3.1 上下文传递的本质是什么？

从第一性原理看，跨模块上下文传递的本质是**用户任务连续性**——用户在处置一个回路时，不应因跨模块跳转而丢失"我在做什么、做到哪了、为什么来这里"的上下文。

| 本质要求 | 衡量标准 | CLPM 现状 |
|---|---|---|
| **实体标识连续** | 跳转后目标回路是否保持？ | ✅ `?loopId=` 全量传递 |
| **任务意图连续** | 跳转后系统是否知道用户"为什么来"？ | 🔶 诊断→整定传 diagnosisLabel，其他跳转无意图标记 |
| **决策上下文连续** | 当前 PID 参数/诊断结果是否带入？ | ❌ 诊断→整定未传当前 PID 参数 |
| **来源可追溯** | 用户能否一键返回来源页？ | ✅ returnTo 机制（诊断→整定有） |
| **浏览器上下文保留** | 前进/后退是否保持状态？ | ✅ query 参数在 URL 中，浏览器原生支持 |
| **标签页上下文** | 多标签页是否独立？ | ✅ fullPathKey=false + affixTab |

### 3.2 范式级追问

**追问 1：为什么 useLoopContext 定义了却没人用？**

[use-loop-context.ts](file:///Users/zhangping/DEV/CLPM/frontend/apps/web-antd/src/composables/use-loop-context.ts) 定义了 `navigateWithLoop`、`withLoop`、`navigateWithTask` 三个方法，注释明确写着"所有跨模块跳转（评估→诊断→整定→回路）统一走本 composable"。但全项目搜索发现**没有任何 view 或 component 使用它**——它是死代码。

实际跨模块跳转走的是两条路：
- LoopLink 组件（5 个 view 使用）：内联 `router.push` 逻辑
- 各 view 自己的 `router.push`（如 diagnosis/detail.vue 的 `buildTuningContextQuery`）

**范式级问题**：上下文传递规范有设计但未执行，各 view 自行拼 query 字符串，存在上下文丢失风险（如某 view 忘记传 loopId）。

**追问 2：诊断→整定为什么不传当前 PID 参数？**

[detail.vue:L576-L588](file:///Users/zhangping/DEV/CLPM/frontend/apps/web-antd/src/views/diagnosis/detail.vue#L576-L588) 的 `buildTuningContextQuery` 传递了 loopId、diagnosisLabel、confidenceLevel、from、returnTo，但**没有传递当前 PID 参数（P/I/D）**。

用户的实际任务流程：
1. 诊断详情页看到"振荡"问题
2. 点击"回路整定"跳转整定工作台
3. 整定工作台需要知道**当前 PID 参数**作为基线
4. 当前实现：整定工作台需重新请求回路详情获取 PID 参数（额外 API 调用）
5. 理想实现：诊断→整定直接传递当前 PID，整定工作台立即展示"当前 vs 推荐"对比

**范式级问题**：诊断→整定的上下文传递不完整，缺少"当前 PID 参数"这一关键决策上下文，增加了 API 调用和用户等待时间。

**追问 3：评估→诊断为什么没有直接跳转入口？**

评估模块的"回路性能"页（`/metric/loop-performance`）展示回路评分趋势，发现低分回路后，用户需要：
1. 记住回路位号
2. 切换到诊断模块
3. 在诊断搜索框输入位号
4. 点击诊断详情

虽然 LoopLink 组件支持"performance→diagnosis"跳转，但需要确认评估页是否实际使用了 LoopLink。从搜索结果看，`views/metric/` 目录下**没有使用 LoopLink 组件**。

**范式级问题**：评估→诊断的跳转链路虽然 LoopLink 支持，但评估页未接入，导致用户需手动切换模块。

### 3.3 范式级发现

| 编号 | 发现 | 级别 | 理由 |
|---|---|---|---|
| F-CTX-001 | **useLoopContext composable 是死代码，上下文传递无统一规范** | 范式级 P2 | 设计了统一 composable 但从未使用，各 view 自行拼 query，存在不一致风险。 |
| F-CTX-002 | **诊断→整定未传递当前 PID 参数** | 范式级 P2 | 传递了标签/可信度/返回路径，但缺少关键决策上下文（当前 PID），整定工作台需重新请求。 |
| F-CTX-003 | **评估→诊断缺少直接跳转入口** | 范式级 P2 | LoopLink 支持该跳转，但评估页未接入 LoopLink，用户需手动切换模块搜索。 |

## 9. 结论

CLPM 跨模块上下文传递在**机制层面建立了有效规范**（3.0/4.0）：`?loopId=` query 统一、LoopLink 组件提供 4 方向跳转、returnTo 机制实现来源页返回、useSavedView 权限安全过滤是最佳实践。诊断→整定的上下文传递（标签 + 可信度 + returnTo）已是**同类系统的良好水平**。

但存在 3 个范式级问题：

1. **useLoopContext 是死代码**（F-CTX-001）：设计了统一 composable 但从未使用，各 view 自行拼 query，存在不一致风险。建议删除并文档化 LoopLink 为唯一入口。
2. **诊断→整定缺当前 PID**（F-CTX-002）：传递了诊断标签和可信度，但未传当前 PID 参数，整定工作台需重新请求。补传后可实现"当前 vs 推荐"即时对比。
3. **评估→诊断无直接入口**（F-CTX-003）：LoopLink 支持该跳转，但评估页（性能总览/回路性能）未接入，用户需手动切换模块。

**核心建议**：优先实施评估页接入 LoopLink（2 天，收益最高）和诊断→整定传当前 PID（1 天，体验提升明显），useLoopContext 死代码处置为第二批。

## 10. 与回路工作台单页四区的关系

回路工作台（`/monitor/loop-workbench`）的单页四区设计（监控/评估/诊断/整定概况）是**上下文传递的最佳替代方案**——在同一页面内聚合四个模块的概况，用户无需跨模块跳转即可获取全链路信息。

这说明：**减少跨模块上下文传递需求的根本方式是提升实体轴（回路工作台）的聚合度**。当工作台能承载 80% 的单回路处置任务时，跨模块跳转变为"深度操作"而非"常规流程"。

这一观察支持范式级建议 F-IA-003（提升回路工作台聚合度）——实体轴聚合度越高，跨模块上下文传递的频率越低，用户认知负担越轻。
