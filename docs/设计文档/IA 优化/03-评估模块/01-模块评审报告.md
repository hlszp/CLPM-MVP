## 1. 执行摘要

评估模块是 CLPM 的**职能轴基础**——回答"全厂回路性能怎么样、哪些需要关注、趋势如何"。该模块以 3+1+8 KPI 体系（3 核心 + 1 综合 + 8 辅助）为算法内核，以 GB/T 44693.2-2024 五级定级为评价标准，覆盖跨回路总览、单回路性能、任务管理、报表导出四个层面。经过 IA 重构 Phase A（指标配置迁入配置模块）和 P1-04（表格 KPI 列精简），该模块在**信息架构与数据墨水比**上已有显著改善。但从第一性原理看，**性能总览与回路性能功能边界需进一步显式化**，且**评估→诊断无直接跳转入口**（F-CTX-003）导致跨模块闭环断裂。

**模块评分：3.0 / 4.0 — 良好**

## 3. 模块架构分析

### 3.1 当前结构

```
评估（order:2，职能轴 + 性能评价）
├─ 性能总览 /metric/pid-dashboard     — 装置级 KPI 聚合 + 子弹图 + TOP5 治理台账 + 装置树抽屉
├─ 回路性能 /metric/loop-performance  — 回路级 KPI 快照 + 等级分布 + 详情抽屉 + 诊断Modal
├─ 评估任务 /metric/tasks             — Tabs：手动/自动/历史/策略
└─ KPI报表 /metric/kpi-report         — 综合报表/回路报表 + 日/周/月 + CSV导出
```

### 3.2 四页面认知层次分析

| 页面 | 认知层次 | 视角 | 用户任务 |
|---|---|---|---|
| 性能总览 | 全厂视角 | 跨装置聚合 | "全厂性能怎么样？哪个装置最差？" |
| 回路性能 | 单回路视角 | 回路级快照 | "哪些回路评分低？具体指标如何？" |
| 评估任务 | 管理视角 | 任务执行 | "评估任务跑完了吗？历史快照在哪？" |
| KPI报表 | 结果视角 | 报表导出 | "日报/周报/月报怎么导出？" |

**范式级发现**：
1. **性能总览与回路性能功能边界需显式化**：总览页有 TOP5 治理台账（回路级），回路性能页有等级分布饼图（全厂级），两页面信息维度交叉。总览应聚焦装置级聚合，回路性能应聚焦回路级明细。
2. **评估→诊断无直接跳转入口**（F-CTX-003）：回路性能表格操作列有"诊断"按钮但跳转诊断 Modal（可视化），不是跳转诊断模块。用户看到低分回路后，无法一键跳转诊断分析。

| 辅助 KPI | AUTO_RATE / IAE / ISE / SETTLING / OVERSHOOT / STEADY_STATE / VARIANCE / PERFORMANCE | 8 |
| **合计** | | **12** |

> PRD 对外合规口径仍强调 6 大核心 KPI（好值率、自控率、平稳率、准确率、振荡率、饱和率）；实现以 3+1+8 体系为算法增强、排序与内部诊断的依据。

## 10. 结论

评估模块是 CLPM **职能轴基础模块**（3.03/4.0），3+1+8 KPI 体系 + GB/T 44693.2 五级定级 + 动态阈值 + 可信度评估 + P1-04 列精简 + UTC 时区处理的技术实现完整，**性能可量化能力达到良好水平**。

但从第一性原理看，存在两个范式级问题：
1. **回路性能页的诊断按钮打开 Modal 弹窗而非跳转诊断模块；pid-dashboard 有 `router.push('/diagnosis/tasks')` 跳转。建议统一为跳转模式，以便用户进入诊断模块进行深度分析**（F-EVAL-001）：用户看到低分回路后无法一键跳转诊断分析，跨模块闭环断裂
2. **性能总览与回路性能功能边界模糊**（F-EVAL-002）：两页面信息维度交叉

**核心建议**：
1. **短期**：评估→诊断跳转按钮（1 天）+ 总览/回路性能职责分离（2 天）
2. **中期**：随双架构路径 B，评估模块 4 页面天然适合驾驶舱/工作站分层——总览+报表=驾驶舱（跨回路概览），回路性能+任务=工作站（回路级深度）
3. 评估模块是**双架构路径 B 的第三试点模块**——4 页面认知层次清晰，可验证"驾驶舱看概览、工作站看明细"的分层范式
