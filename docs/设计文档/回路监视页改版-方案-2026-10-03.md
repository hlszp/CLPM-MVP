## 问题陈述

新版回路工作台（/loop/workbench360）已把单回路的评估/诊断/整定/处置全生命周期收进一个页面并全量上线。用户提出按此业务逻辑重新组织系统的业务应用架构，第一步落在**回路监视页**：把它改造成"回路清单 + 批量任务发起 + 单回路深入工作台"的管理入口。具体五项：

1. 行首多选框 + "批量评估""批量诊断"按钮 → 弹窗设定时间窗后发起批量任务
2. 删除按回路类型/性能等级的微型卡片，筛选条件全部收进筛选区
3. 操作列"详情"改为进入**精简版回路工作台**（去左侧装置/回路选择区，保留主显示区与右侧抽屉，直接定位该回路，带返回按钮）
4. 修复详情抽屉指标放大 100 倍问题
5. 顶部微型卡改为装置级三统计卡：A 综合评分均值、B 自控率、C 好值率（均为筛选范围内口径）

## 现状事实（2026-10-03 三路代码勘察结论）

- 页面壳 `views/monitor/loops.vue`（193 行）+ 主画布 `components/monitor/loop-fleet-view.vue`（1003 行），antd Table，服务端分页（GET /loops/monitor，page/pageSize + 排序 score asc 默认最差在前）。

### 后端·批量与统计能力（均已就绪或小改）
- **批量评估已有现成入口**：`POST /tasks/custom/evaluate`（CustomTaskCreate{loopIds[], metrics[], tsStart, tsEnd}，单用户≤3/系统≤20 并发），结果写 kpi_snapshot_custom（**不参与装置聚合**，不改变监视页行内 kpiSummary——它读 kpi_snapshot_hourly）。另一选项 `POST /tasks/backfill`（loopIds 优先于 plantNodeIds，30 天上限）会 **UPSERT 覆盖标准小时快照**、参与聚合、改变列表显示。
- **批量诊断已有现成入口**：`POST /diagnosis/run`（TriggerDiagnosisBody{loopIds 1~**50 硬上限**, timeWindow{preset 或 start/end}, operatorGroup}）。L0 回路**阻断整个请求**（400 + blocked[] 列表），L1/L2 随响应 conditionWarning[] 返回——弹窗可直接消费做"部分回路不可诊断"提示。定时全量任务的 50 回路/批自动分批编排（diagnosis_schedule.py:174-201）可作超限分批参考。
- **三卡数据现状**：
  - A 评分均值：已有——/loops/monitor 响应 aggregate.avgScore/scoredCount（最新快照简单平均，plantNodeId/keyword/loopType/controlMode 筛选全部生效）。
  - B 自控率：两种口径并存——aggregate.autoControlRate 是**实时 MODE 分布**口径（已随筛选生效）；评估窗口口径 auto_mode_rate 在 kpi_snapshot_hourly 有值但 monitor 聚合未输出。
  - C 好值率：kpi_snapshot_hourly.good_value_rate 有值，**monitor 聚合未输出**，需扩展 `_build_loop_monitor_aggregate`（monitor.py:435-460 已有最新快照批量查询模式，同查询补一列聚合即可）。
- 列表行 kpiSummary 已随行返回 composite_score/auto_mode_rate/good_value_rate 等（最新快照口径，无窗口参数）。
- **缺口**：`/loops/monitor`（loops.py:302-316）筛选参数只有 plantNodeId/keyword/loopType/controlMode，**无性能等级（grade）参数**——服务端分页下前端本地过滤只能过滤当前页（数字对不上，违反诚实化原则），等级筛选进筛选区必须后端同批扩展（minScore/maxScore 区间，五档映射）。

### 指标 ×100 bug 定位（第 4 项，已坐实）
- 后端所有 KPI 率字段按 **0-100 口径**写库：auto_mode.py 明确 `rate = ... * 100.0`（docstring "value 为自控率 0~100"），good_value.py:59 `* 100.0`，列类型 Numeric(5,2)。
- kpiSummary 由 monitor.py `_rate()` 原样透传（Decimal→float，不缩放）。
- **监视页详情抽屉 `loop-detail-drawer.vue:62-78` 的 `pct()` 闭包对 8 项率指标统一 `v * 100` 再拼 `%`（注释错误假设 0-1 口径）→ 全部放大 100 倍**（85.2 显示为 8520.0%）。
- 对照组：workbench360 评估详情抽屉（loop-performance-detail-content.vue，formatNumber 直拼）与驾驶舱弹窗均按 0-100 直拼**正确**——所以用户看到工作台与监视页数字对不上。
- 全前端扫描：该模式错用**仅此一处**。注意 `valid_rate` 独立为 0-1 口径（Numeric(5,4)），同文件 :249 `validRate * 100` 是对的，修复时不可误伤。
- 修复：pct() 改为 0-100 直拼（对齐 loop-performance-shared.ts formatNumber 约定，建议直接复用共享函数消灭本地口径假设）。属生产正确性问题（放大 100 倍的数字渲染给用户违反诚实化原则），**建议独立热修，不等改版**。

## 前提（Premises，需用户确认）

1. 本次范围=回路监视页五项；**全局业务应用架构重组**（评估/诊断/整定/处置四个一级菜单与工作台的关系、菜单去留）是另一个决策，不在本方案内先行实施，仅列为开放问题。理由：一次改一个模块，风险与验收都可控；全局重组值得单独一轮 IA 评审（先例：IA 优化 P0-P4 分阶段流程）。
2. "回路监视=横向清单管理 + 批量任务，回路工作台=纵向单回路全生命周期"的双入口结构成立。现有跳转/上下文携带（monitorCtx、loopId、from）已支持这个结构。
3. 批量评估结果走 **custom 快照口径**（不覆盖标准小时快照、不改列表行显示）。若用户期望"批量评估完列表评分跟着变"，需改走 backfill（覆盖语义，风险高）——默认不。
4. 三卡统一用**最新评估快照口径**（与列表行 kpiSummary 同源），B 卡自控率用评估口径 auto_mode_rate 而非实时 MODE 口径。实时自控率语义（"此刻多少回路在自动"）与"投用率"（评估时段自动时长占比）不同，用户表述"自控投用率"更贴近后者。
5. "较昨日恶化 worsenedCount"卡片随改版移除（其信息在行内 scoreDelta 仍可见），不迁入三卡。
6. 批量诊断 50 上限首版用**提示拦截**（超选时提示分批），不做自动分批派发（自动分批留给后续，复用 diagnosis_schedule 编排）。

## 评估结果落库统一（2026-10-03 用户裁决追加的设计项）

### 现状（回答"手动评估与自动评估是否同表"）

**不是同一个表。** 三条写入路径、读取方割裂：

| 评估来源 | 写入表 | 语义 | 当前读取方 |
|---|---|---|---|
| 自动调度（每小时 calculate_hourly_kpi） | kpi_snapshot_hourly | 整点小时窗，同回路同窗 UPSERT 覆盖 | 监视页 kpiSummary/评分（latest 子查询）、工作台评估历史（/performance/loops/snapshots）、装置聚合链路（unit_kpi_summary→workbench_window_summary） |
| 手动/自定义（/tasks/custom/evaluate） | kpi_snapshot_custom | 任务粒度追加（task_id 关联），任意时间窗 | **几乎无读取方**——工作台评估历史与监视页都只读 hourly（= 登记 G2 缺口的根源） |
| backfill 历史重算 | kpi_snapshot_hourly | 覆盖标准快照 | 同自动 |
| 可信度 | loop_confidence_latest | **latest 物化表（loop_id 一行）**，随 _save_snapshot 同步 UPSERT（kpi_calc.py:2727） | loops/monitor/attention/预警 DSL 多处 |

结论：手动评估结果"落了但没人看"，用户感知"手动评估不生效"即源于此。仓库已有 latest 物化表先例（loop_confidence_latest）。

### 设计（双表：明细 + 最新值）

用户倾向：所有评估结果统一历史明细 + 每回路一行最新结果表，读取统一走最新表。两个实现变体：

**变体 2（推荐，P2a 实施）：明细双表物理保留 + 新增 latest 统一出口**
1. 新表 `kpi_snapshot_latest`：loop_id 唯一约束，完整 KPI 字段 + source（SCHEDULED/MANUAL/BATCH/BACKFILL）+ window_start/end + task_id + calculated_at。
2. 写入挂钩：`_save_snapshot`（hourly/backfill 路径）与 `_save_custom_snapshot`（手动/批量路径）成功后**同事务 UPSERT latest，按 ts_end 新者胜**（`WHERE excluded.ts_end >= 现值`，防旧窗口任务迟到覆盖）。与 loop_confidence_latest 同模式。
3. 读取切换：监视页 kpiSummary/列表评分/三卡聚合（P3）改读 latest（消掉 monitor.py:435-460 两处 distinct-on 子查询，并把全量 KPI 字段带出）；"昨日基线"（worsened 计算）仍查 hourly 明细不动。
4. 评估历史补全（顺手解 G2）：/performance/loops/snapshots UNION custom 明细（source 列区分），工作台评估历史即可看到手动/批量评估记录。
5. 初始化：alembic 迁移从 hourly 每回路最新一行灌入 latest（ORM 与迁移同批，红线）。

**变体 1（用户原始表述的物理形态）：合并为单一明细表 kpi_snapshot（loop_id+window+source 唯一 UPSERT）**
产品表现与变体 2 完全一致，但聚合链路、趋势、backfill 幂等覆盖、评估历史全部读写方都要改造 + 存量两表迁移，改动面大一个数量级，hourly 的"整点窗覆盖"语义与 custom 的"任务粒度追加"语义强行合一还需要重验聚合正确性。**建议不一步到位**；变体 2 稳定运行后如仍有合并诉求，作为独立技术债清理立项。

### 批次调整

P2 拆两步：**P2a 后端统一落库**（latest 表 + 写入挂钩 + 监视页读取切换 + 评估历史 UNION，含 alembic 迁移）→ **P2b 批量弹窗**（前端行多选 + 批量评估/诊断弹窗；批量评估走 /tasks/custom/evaluate 写明细+刷 latest，实现"批量评估后监视页列表跟着变"）。P2a 先行可避免 P2b 按旧口径做完再返工。

## 方案选项

### Approach A：三批全做（推荐）
- **P1 正确性与减法（前端为主 + 一项后端小改）**：
  - 修 ×100 bug（可独立热修先行）；
  - 卡片收缩进筛选区：筛选区补回路类型 Select、性能等级 Select——**等级筛选需后端同批扩展** `/loops/monitor` 与 `list_loop_monitor` 增加 minScore/maxScore 区间参数（五档映射），与"无评分"档（score IS NULL）分支；
  - 详情改跳精简版工作台（embed 模式 + 返回按钮）。embed 模式区块去留清单：

    | 区块 | embed 模式 |
    |---|---|
    | LoopHeader | 保留，左侧新增返回按钮（route.query.from 优先，无 from 时 router.back()） |
    | LoopSpine + 拖拽条 | 删（index.vue 495-518） |
    | JourneyRail / TrendChart / 四剖面 / StatusBar | 全保留 |
    | AttentionDrawer 及各剖面 WbDrawer | 全保留（用户所指"右侧抽屉"） |

    实现注意：loadLoops() 必须保留（current 数据来源）、loadTree() 跳过、无效 loopId 回退首行的边界需提示。
- **P2 批量任务**：行多选 + 批量评估弹窗（/tasks/custom/evaluate）+ 批量诊断弹窗（/diagnosis/run）。
  - 多选状态规格：**跨页保留**（antd row-selection preserveSelectedRowKeys，selectedRowKeys 以 loopId 全集存于组件，不随翻页丢失）；筛选条件变更后**保留已选**（已选回路可能已不在当前筛选结果内，属预期）；工具栏"已选 N 个 [清空]"常驻；弹窗内回显已选清单、可逐个移除；未选中时两个批量按钮禁用。
  - 批量评估弹窗规格：请求体 CustomTaskCreate 的 **metrics 必填**——默认传全指标清单（与标准评估一致），弹窗可简化为不给用户选指标的入口；时间窗默认近 24h，提供预设（24h/7d/30d）+自定义范围（tsStart/tsEnd）；并发超限（单用户≤3/系统≤20）按后端 4xx 错误信息显式提示，不静默。
  - 批量诊断弹窗规格：时间窗同上（preset last_24h/last_7d/last_30d 或 start/end）；>50 回路提示拦截（前提 6）；L0 阻断（400 + blocked[]）与 L1/L2 警告（conditionWarning[]）逐回路回显，允许用户移除 blocked 回路后重发。
- **P3 装置级三卡**：后端扩展 _build_loop_monitor_aggregate 补 auto_mode_rate（评估口径）与 good_value_rate 聚合 + 前端三卡替换微型卡条。
- Effort: M-L ｜ Risk: 低-中 ｜ Reuses: 全部现成接口与组件骨架；工作台仅加 embed 模式不复制代码。
- Pros: 每批可独立验收上线；bug 最先出清；后端改动最小（等级筛选参数 + 三卡聚合补列）。
- Cons: 三批周期；P2/P3 依赖 P1 的筛选区改造完成（产品顺序依赖）。

### Approach B：仅做 P1（最小步）
先只做减法与 bug 修复，批量弹窗与三卡另立项。
- Effort: S ｜ Risk: 低
- Pros: 最快见效。
- Cons: 用户诉求的主体（批量任务、三卡）落空；筛选区改造后顶部留白需临时处理。

### Approach C：全局 IA 重组先行
先产出完整业务应用架构重组方案（含四模块菜单去留、导航重排），回路监视页作为第一个实施件。
- Effort: XL ｜ Risk: 高（牵动模块热插拔、角色路由、既有用户习惯）
- Pros: 一步到位，避免中间态。
- Cons: 周期长；工作台刚全量上线（1003 包尚未部署生产），全局重组应基于其使用反馈再做。
