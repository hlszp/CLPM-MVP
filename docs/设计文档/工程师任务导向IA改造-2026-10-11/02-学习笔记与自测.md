## 1. 这次到底要改变什么

想象一位仪控工程师早晨进入系统。过去他先看到全厂统计，然后逐个打开监控、诊断或整定页面，自己判断今天处理什么。拟议流程是先看到自己负责的工作，每项说明原因、证据和下一步；点进去后，继续使用原有专业工具完成工作。

因此，“我的工作”负责选工作，“回路工作台”负责处理具体回路，“驾驶舱”负责观察全局，“工程助手”帮助提问、解释和找入口。专业页面仍有价值，熟练用户可以直接使用。

推荐方案现已由用户采纳并纳入改造计划。菜单、首页、数据库和算法尚未因文档更新而改变。

## 2. 一个例子看懂完整路径

以下是假设场景，用于理解设计，不是实际回路数据。

系统发现某回路波动，放入“系统建议”。工程师先看数据是否完整，再认领一项“查明波动原因”的核查工作。如果证据指向阀门，下一步可能是检维修；如果指向参数且条件满足，才进入整定；如果数据不足，则先补证据。

核查结束可以有不同结果：确认无需进一步处理；形成一项需要审核的处置建议；关联已有工单。实际现场处置沿原工单执行和验证流程继续。核查完成、计算完成、工单闭环，分别表达不同事情。

## 3. 常见工程术语

| 术语 | 通俗解释 | 在本项目里的例子 |
|---|---|---|
| IA，信息架构 | 信息、页面和入口怎么组织 | 把诊断和整定放到专业作业组，把我的工作放到前面 |
| UX，用户体验 | 用户完成一件事的整体感受和效率 | 能否知道下一步；返回后是否还保留原来的回路和筛选 |
| 路由 Route | 页面在系统里的地址 | `/loop/workbench360` 指向回路工作台 |
| 上下文 Context | 处理这件事时必须带着的背景 | 哪个回路、哪段时间、哪次诊断、哪个工单 |
| 业务对象 Entity | 有独立身份和生命周期的一类记录 | 核查事项、处置建议、处置工单 |
| 状态机 | 规定一条记录允许怎样改变阶段 | 工单待执行→执行中→验证中→关闭或重开 |
| 投影视图 | 将多种原记录整理成一种阅读方式 | 我的工作同时展示本人核查和工单，原记录仍各自保存 |
| API / 接口契约 | 前后端约定怎样请求和返回信息 | 查询我的工作时，什么叫本人、待办和总数必须一致 |
| Schema / 数据迁移 | 数据保存结构，以及怎样升级旧结构 | 增加个人关注关系时，需要让已有数据库平稳支持它 |
| 权限与责任 | 权限是允许做什么；责任是谁负责处理 | 能看全厂回路，不代表全厂异常都分配给自己 |
| 算子 Operator | 输入、输出和适用条件明确的计算能力 | 评估、诊断、辨识、仿真 |
| 智能体 Agent | 理解目标并调用工具推进工作的 AI 过程 | 理解“为什么波动”，查证据，再引导到适用功能 |
| 幂等 Idempotency | 同一请求重试不会重复造成效果 | 网络重试不能再创建一张相同工单 |
| 端到端 E2E | 从用户入口一路检查到最终结果 | 从我的工作认领，经作业页处理，再回到原工作看到结果 |

## 5. 六条最值得记住的判断

1. **收藏不等于待办。**收藏表示经常看，待办表示有人负责、有目标和完成条件。
2. **异常不等于已分派工作。**系统发现线索以后，还要有人认领或分派，责任才明确。
3. **数据不足不等于性能差，也不等于正常。**它表示证据不足以作出相应判断。
4. **可整定不等于应该整定。**允许执行某种分析，还需要判断它是不是当前合适的行动。
5. **计算成功不等于现场改善。**产生结果、人工实施、效果验证是不同阶段。
6. **AI 要能指出依据和真实动作。**一段流畅解释不能替代算法结果、权限判断或业务回执。

## 6. 本次设计会带来哪些工程影响

第一类是界面影响：入口名称、菜单分组、默认首页和信息排列发生变化，旧书签仍应可用。

第二类是数据影响：个人关注要按账号保存，核查要保存负责人、过程和结论，工单责任要用稳定用户 ID。这需要后端和数据库支持，仅改前端页面不够。

第三类是协作影响：不同页面与助手要认得同一条证据和工作，返回后能继续，多人同时操作时不能重复认领或重复创建。

第四类是智能体影响：需要模型配置、对话记录、受控工具和可追踪运行；专业结论继续来自既有算法和有效配置，DCS 参数仍由授权人员人工实施。

项目还有代码分工：CLPM-MVP 保存本体业务能力，iCLPMagent 负责智能体协同层。两个代码仓库可以通过接口共同提供一条连续操作路径，不要求工程师在使用时理解这种工程划分。

1. 我的工作选工作；回路工作台处理具体回路；驾驶舱看全局；工程助手理解问题、查依据并引导行动。
2. 不应该。关注是个人快捷关系，没有产生实际工作目标和责任。

5. 不能直接建议。先确认数据充分性、原因、工况、现有诊断和适用门禁，排除应检维修或补数据的路径。

7. 有充分证据、结论和必要审核即可结束核查；定位只说明查清问题，修复还需要实际处理和恢复证据。

9. 可能拿错实施参数、时间和工况，导致错误归因；应绑定实际实施的方案和工单。

能够解释第 5、7、8、9 题，说明已经理解这次改造中“证据、行动、责任和完成”的关键区别。

## 9. 补充：为什么单回路工作台适合做组件

可以把组件理解为一套可以放进不同页面使用的完整操作面板。全回路工作台在左边放选择树，右边放这块面板；诊断页面则把同一块面板放进抽屉。两处使用同一份评估、诊断、整定和处置代码，修复一次即可同时生效。

宿主是“放置面板的页面”，负责对象选择和返回；`props` 是宿主交给面板的输入，例如回路 ID、时间窗口；`events` 是面板反馈给宿主的事情，例如某条诊断记录已生成。组件自己不猜当前网址对应哪个回路。

**实例**是组件的一次具体使用。A 回路面板和 B 回路面板可以使用同一份代码，但各自的预填参数和未保存内容必须独立。**生命周期**是打开、切换、隐藏、关闭的过程；关闭 B 面板时要清理 B 的监听，不能让 A 的实时更新也停止。

本次拆分影响入口、左侧树、数据读取、状态隔离和实时订阅；原有算法和专业剖面继续复用。现有 `embedLoopId` 已有内嵌基础，但仍读取宿主路由、加载全量列表，所以还需要进一步拆分。
