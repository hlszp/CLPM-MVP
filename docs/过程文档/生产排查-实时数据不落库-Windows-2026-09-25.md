# 生产排查任务明细：实时数据不落库 / 趋势图无数据（Windows VM）

> 适用版本：CLPM-MVP（后端 7101 容器内 / 17101 开发环境）。
> 生成日期：2026-09-25。全程**只读**，不写库、不改配置、不重启服务；需要动手修复的动作集中在 §5，需你授权。
> 采集脚本：`scripts/diag-realtime.ps1`（Windows 一键）、`backend/scripts/diag_realtime_pipeline.py`（五道闸门诊断）。

## 0. 先确定部署形态（决定后面所有命令）

```powershell
# 形态 A：Docker Desktop + 仓库根目录 docker-compose.prod.yml
docker ps --format "{{.Names}}"     # 期望看到 clpm-backend / clpm-postgres / clpm-redis / clpm-tdengine / clpm-celery-worker / clpm-celery-beat

# 形态 B：原生 Windows（venv + 服务/计划任务），没有 docker
Get-Process | Where-Object { $_.ProcessName -match "python|celery|uvicorn" } | Select-Object Id,ProcessName,StartTime
```

生产 compose 的 `backend` **不映射端口到宿主机**（只 `expose 7101` 给容器网络），所以形态 A 下必须用 `docker compose exec` 进容器执行命令，或在 VM 上通过前端 Nginx（7141）访问。

## 1. 一键采集（推荐，2 分钟）

```powershell
cd <部署目录>          # 含 docker-compose.prod.yml 的目录
powershell -ExecutionPolicy Bypass -File scripts\diag-realtime.ps1
```

脚本会依次采集 8 段证据并落盘为 `diag-realtime-<时间戳>.txt`：容器状态、五道闸门诊断、后端日志关键字、celery 日志、Redis 键、TDengine 行数、容器内环境变量、`sys_config` 真相源。**把这个 txt 回贴即可定位。**

若脚本不便执行，按下面 T1~T8 手工做。

## 2. 分步任务（T1~T8）

### T1 闸门总扫（最关键，一次看全）

```powershell
# 已部署镜像内没有 scripts/（Dockerfile 旧版只拷 app/alembic），先送脚本再执行：
docker compose -f docker-compose.prod.yml cp backend\scripts\diag_realtime_pipeline.py backend:/tmp/diag_realtime_pipeline.py
docker compose -f docker-compose.prod.yml exec -T backend python /tmp/diag_realtime_pipeline.py
```

> 重建镜像后（Dockerfile 已补 `COPY scripts/`）可直接 `exec backend python scripts/diag_realtime_pipeline.py`。

**期望**：五道闸门全 PASS，且 `st_point_data_v1` 最新 ts 在 15 分钟内。
**不通过**：记下是哪一道，直接跳到 §3 对应分支。

### T2 配置真相源（sys_config，不是 .env）

```powershell
docker compose -f docker-compose.prod.yml exec -T postgres psql -U clpm -d clpm -c "SELECT key,value FROM sys_config WHERE key LIKE 'history.%' OR key LIKE 'datasource.%' ORDER BY key;"
```

**看三个键**：

| 键 | 必须 | 不是时会怎样 |
|---|---|---|
| `history.storage_mode` | `point`（或 `shadow`） | `legacy` → **写入器根本不启动**，实时页有值但 TDengine 一条不写 |
| `datasource.signalr_enabled` | `true` | `false` → 订阅器直接退出 |
| `datasource.signalr_hub_url` | 非空 | 空 → `SIGNALR_HUB_URL 未配置，跳过实时数据订阅` |

> 注意：业务 URL/Token 的真相源是 `sys_config`，lifespan 启动时会用它**覆盖 `.env`**。只在 `.env` 里配、没在「链路配置」页保存过，等于没配。

### T3 订阅是否真的活着

```powershell
docker compose -f docker-compose.prod.yml logs --tail=3000 backend | Select-String "实时数据订阅任务已启动|已订阅|Leader|保持待命|跳过实时数据订阅|已禁用" | Select-Object -Last 40
```

**必须看到**：

```
实时数据订阅任务已启动 (hub=ws://..., writeback=True, leader=True)
已订阅 N 个 Tag (invocationId=sub_1)
```

**如果看到** `保持待命，不成为 Leader` 或 `订阅 Leader 锁抢占异常` → 走 §3 分支 B（Redis / Leader 锁），这是 Windows 上最常见的断点。

### T4 Leader 锁与实时缓存（Redis 是否在收数）

```powershell
docker compose -f docker-compose.prod.yml exec -T redis redis-cli GET realtime:subscriber:leader:lock
docker compose -f docker-compose.prod.yml exec -T redis redis-cli TTL realtime:subscriber:leader:lock
docker compose -f docker-compose.prod.yml exec -T redis redis-cli --scan --pattern "realtime:*" | Measure-Object -Line
```

**期望**：锁键是一个 `主机名:pid:...` 的值、TTL 20~60s 之间；`realtime:*` 键数量接近位号数（生产约 8600+）。
**锁为空**：没有任何实例在订阅 → 分支 B。
**锁有值但 `realtime:*` 为 0**：订阅器在跑但收不到数据 → 分支 C（Hub 网络/token）。

### T5 写入器是否启动（决定"落库"的那一步）

```powershell
docker compose -f docker-compose.prod.yml logs --tail=3000 backend | Select-String "PointHistoryWriter|点身份映射|批次写入失败" | Select-Object -Last 30
```

**必须看到**：

```
PointHistoryWriter 已启动（storage_mode=point）
PointHistoryWriter 点身份映射已刷新: N 点
```

**没有第一行** → `storage_mode` 不是 point/shadow，回 T2。
**有** `点历史批次写入失败` → TDengine 写入侧问题（分支 D）。
**只有映射刷新为 0 点** → 位号表为空或未同步（分支 E）。

### T6 TDengine 里到底有没有数据

```powershell
docker compose -f docker-compose.prod.yml exec -T tdengine taos -s "SELECT COUNT(*) FROM clpm_ts.st_point_data_v1;"
docker compose -f docker-compose.prod.yml exec -T tdengine taos -s "SELECT LAST(ts) FROM clpm_ts.st_point_data_v1;"
docker compose -f docker-compose.prod.yml exec -T tdengine taos -s "SELECT COUNT(*) FROM clpm_ts.st_loop_data;"
```

**判定**：

- 两张表都 0 行 → 写入侧从未成功（回 T5，或 storage_mode 为 legacy）
- 点表有行但最新 ts 是几小时/几天前 → 写入**曾经**成功、现在停滞（查 T5 的写入失败日志 + 容器是否 OOM 重启）
- 点表持续有新行 → 落库正常，问题在**读侧**（走 T7）

### T7 读侧：趋势为空但数据在（区分"没写"与"读不到"）

在浏览器打开「回路监视」，选一条具体回路：

1. 实时值是否在跳？
2. 点开该回路的趋势弹窗，把时间窗切到「近 24 小时」，是否有曲线？
3. 该回路的 7 个 tag（PV/SP/OP/MODE/PID_P/PID_I/PID_D）在「配置 → 测点配置」里是否都存在、且都属于同一个回路？

若实时值在跳、点表也有新行、但趋势空 → 大概率是**该回路的点位身份不全**（回路绑定的 tag 在 `tag_registry` 缺失 → 趋势查询按 point_id 查不到），把回路名和它的 7 个位号发我，我按 SQL 复现。

### T8 Celery（KPI/评估/导入为空时才需要）

```powershell
docker compose -f docker-compose.prod.yml ps
docker compose -f docker-compose.prod.yml logs --tail=40 celery-worker
docker compose -f docker-compose.prod.yml logs --tail=20 celery-beat
```

**期望**：两个容器 `Up`，worker 日志有 `celery@... ready`，beat 有调度节拍。
**注意**：`ENV=production` 时后端**不会**自启 worker/beat（[main.py:318](../../backend/app/main.py)），完全依赖这两个容器。

## 3. 判定树

```
T1 闸门1/2 失败
  └─ 分支 A：配置未生效（sys_config 里 signalr_enabled / hub_url）
       修：登录系统 →「配置 → 链路配置」填写并**保存**（写 sys_config + Redis 运行态键），观察日志是否出现"实时数据订阅任务已启动"

T1 闸门3 失败（无 Leader 锁 / 日志"保持待命"）
  └─ 分支 B：Redis 不可达或锁竞争（Windows 头号嫌疑）
       查：docker compose ps redis（是否 Up/healthy）；redis-cli PING
       因：代码对 Redis 异常是 fail-closed（realtime_subscriber.py:832-854）→ 抢不到锁就永不订阅
       修：先让 Redis 稳定（自启、持久化、内存上限），再重启 backend 容器观察是否 "已接管实时数据订阅（Leader）"

T1 闸门3 通过、realtime:* 键为 0
  └─ 分支 C：订阅在跑但收不到数据（Hub 网络/token/位号范围）
       查：日志 "negotiate 失败" / "已订阅 N 个 Tag" 的 N；VM 到 AAS 的连通性（Test-NetConnection）

T1 TDengine 表不存在或写入失败
  └─ 分支 D：写入侧（TDengine 容器/REST 端口/磁盘）
       查：docker compose logs tdengine；docker compose ps tdengine（是否 OOM/重启）
       因：REST 端口 = TDENGINE_PORT + 11（backend/app/core/tdengine.py:76）

T1 闸门5a 失败（tag_registry 为空）
  └─ 分支 E：位号未同步（AAS 同步任务没跑或失败）

闸门全 PASS、点表有新行、趋势仍空
  └─ 分支 F：读侧（该回路点位身份不全 / 查询窗口时区）→ 回 T7
```

## 4. 修复动作（需你授权，按分支）

| 分支 | 动作 | 影响面 |
|---|---|---|
| A | 「链路配置」页重新保存数据源配置 | 会重启订阅器（秒级中断） |
| B | 修 Redis 可用性 + `docker compose restart backend` | 后端重启约 30s，期间实时中断 |
| C | 网络/网关侧放通，或调整 Hub 地址 | 无副作用 |
| D | 修 TDengine 容器（内存/磁盘/端口） | 影响写入 |
| E | 触发一次 AAS 位号同步 | 只增不删 |
| F | 补该回路的 tag 绑定/点位身份 | 只增不删 |

**明确不要做**：

1. 不要改 `.env` 里的 `SIGNALR_*` 想"生效"（会被 `sys_config` 预载覆盖）。
2. 不要为了"补历史"就开 `gapBackfillEnabled`（那是断点续传，走远端历史导入，解决不了实时落库）。
3. 不要手工再起一个 worker/beat（AGENTS 红线：多 worker/beat 会重复消费）。

## 6. Windows 特有风险登记（本次排查中发现，待修，不动代码）

| 位置 | 调用 | Windows 行为 | 后果 |
|---|---|---|---|
| `backend/app/main.py:153` | `pgrep -f` | 命令不存在 → 探测失败 | fail-safe 认为"已有进程"→ **跳过自启 celery** |
| `backend/app/main.py:251` | `signal.SIGKILL` | 属性不存在 | 清理路径 `AttributeError` |
| `backend/app/main.py:293` | `os.killpg` | 不存在 | 同上 |
| `backend/app/main.py:457` | `start_new_session=True` | 无效，不建进程组 | 进程组清理失效 |
| `backend/app/main.py:191` | `os.kill(pid, 0)` 探活 | **会 TerminateProcess** | 探活变杀进程（危险） |
| `backend/app/services/data_source/realtime_subscriber.py:832` | Leader 锁 fail-closed | 无平台差异 | Redis 一断则链路全静默（Windows 若无 Redis 原生服务更易触发） |

这些不影响"实时是否落库"的判定，但说明**当前代码的进程自愈/清理逻辑是为 Linux 写的**，Windows 部署需要单独一轮兼容改造。

## 7. 本次代码修复清单（2026-09-25，供部署团队核对）

### 7.1 让“配置看似有效却不落库”显性化（核心修复）

| 修复 | 位置 | 作用 |
|---|---|---|
| 写入布局 与 读取路由 一致性自检 | `backend/app/services/data_source/history_layout.py`（`get_layout_selfcheck`） | 判定 writeMode/readLayout 是否自洽，并给出 diagnosis 与修复方向 |
| 订阅器每分钟自检、状态变化即 ERROR | `realtime_subscriber.py`（`_sync_point_writer`） | 以前这种情况日志一片安静，现在明确打出“宽表停写但读取路由仍是 legacy → 趋势会读到空表” |
| 回写开关语义陷阱提示 | `history_layout.writeback_trap_hint` | `realtime_writeback_enabled=true` 但 `storage_mode=legacy` 时明确提示“不会写点表” |
| `/datasource/health` 增字段 | `datasource_config.get_datasource_health` | 新增 storageMode / readLayout / layoutConsistent / layoutSeverity / layoutDiagnosis / pointTableWritten |
| 新增 `GET/PUT /datasource/storage-mode` | `api/v1/endpoints/datasource.py` | 此前 `set_storage_mode` 是**无调用方的死代码**，UI/API 都改不了，只能手工写库 |
| 链路配置页可视化 | `frontend/apps/web-antd/src/views/loop/aas.vue` | 顶部状态区新增「写入布局」下拉 + 不一致时红色告警；并修正“实时回写”的误导性文案 |
| 读取路由登记脚本 | `backend/scripts/register_layout_manifest.py` | 切读是一次性迁移动作，默认 dry-run，`--apply` 才写库 |

### 7.2 Windows 部署兼容修复

| 修复 | 位置 | 原来在 Windows 上的行为 |
|---|---|---|
| 跨平台进程探测 | `main._pgrep_probe` / `_windows_pgrep` | 无 `pgrep` → 探测恒失败 → fail-safe 误判“已有 worker”，worker/beat 永不启动 |
| 非破坏性探活 | `main._windows_pid_alive` | `os.kill(pid, 0)` 在 Windows 上等价 TerminateProcess（探活会真的杀进程） |
| 强杀降级 | `main._force_kill` | 无 `SIGKILL`/进程组语义会抛 AttributeError；现走 `taskkill /T /F` |
| Celery 池自动切换 | `main._start_celery_worker` | Windows 不支持 prefork，自动改用 `--pool solo` |
| 生产逃生阀 | `main._celery_autostart_forced` | `ENV=production` 时后端不自启 worker/beat，无容器接管则异步任务全不执行 → 设 `CELERY_AUTOSTART=1` 可自启 |

### 7.3 重新部署后的验证（三步，约 5 分钟）

```powershell
# ① 写入布局与读取路由自检（最关键）
#    期望：写入侧 point、读取侧 point、consistent=true、severity=ok
#    也可以用界面看：数据接入页顶部状态区新增的「写入布局」一行 + 红色告警（不一致时）
docker compose -f docker-compose.prod.yml exec -T backend python scripts/register_layout_manifest.py --layout point

# ② 订阅与写入器日志（应看到 PointHistoryWriter 已启动；不应看到“保持待命”）
docker compose -f docker-compose.prod.yml logs --tail=200 backend | Select-String "PointHistoryWriter|实时落库自检|已接管实时数据订阅|保持待命"

# ③ 点表是否在增长（间隔 1 分钟执行两次，COUNT 与 LAST(ts) 都应前进）
docker compose -f docker-compose.prod.yml exec -T tdengine taos -s "SELECT COUNT(*) FROM clpm_ts.st_point_data_v1;"
docker compose -f docker-compose.prod.yml exec -T tdengine taos -s "SELECT LAST(ts) FROM clpm_ts.st_point_data_v1;"
```

**判定**：

| 观察 | 结论 | 动作 |
|---|---|---|
| `storageMode=point` 且 `readLayout=point` | 读写一致，趋势读点表 | 无需动作 |
| `storageMode=legacy`（且库里没有 `history.storage_mode` 行） | 新库默认值陷阱：写入器从未启动，实时页有值但一条不落库 | 在数据接入页把「写入布局」改为 `shadow` 或 `point`，保存后 1 分钟内生效 |
| `storageMode=point` 但 `readLayout=legacy` | 点表在写、宽表停写，趋势读到空表 | 执行 `register_layout_manifest.py --layout point --apply` 登记 global 段完成切读；或把写入退回 `shadow` 双写 |
| 点表 `LAST(ts)` 持续前进 | 落库已恢复 | 继续观察 10 分钟确认稳定 |

### 7.4 登记但本轮未改的设计缺口

1. `history.storage_mode` 与 `history_layout_manifest` 的**默认值与部署引导缺失**：新建库不写 `history.storage_mode` 行即恒 `legacy`，而 MVP 的实时读路径（点表）与评估口径都以点表为终态，部署方极易踩坑。建议部署引导里随库写入初始布局，或首次启动自检提示一键切换。
2. 读侧切读仍**没有回滚/分段界面**（只有脚本），属迁移演练范畴；`set_layout` 的 loop/source 精确分段尚无运维入口。
3. Windows 与 Linux 的行为差异只在“容器外”出现：若生产=容器化部署，7.2 的兼容修复对本问题无影响（但也无害）；若改为原生 Windows 服务，则这些修复是必需的。建议部署文档固定一种形态。
