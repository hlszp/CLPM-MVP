# full-1046：MODE 与批量诊断修复

## 已确认的问题

- 现场 `01TV_06003_PID` 的 PV 量程为 185～215，MODE 量程为 0～10。共享异常检测误用 PV 工程量程校验 MODE，导致整小时 MODE 被标记 `OUT_OF_RANGE`，评估和诊断都可能误报数据不足。
- 批量诊断弹窗默认全选 1209 个回路。搜索 `04PIC03001_PIDA` 仅过滤可见项，提交仍携带全部已选 ID，超过后端单次 50 个上限后返回 HTTP 400。

## 实现与边界

| 文件/入口 | 改动 |
|---|---|
| `outlier_detection.OutlierDetector.detect_all` | MODE 复用 `ALL_STANDARD_MODES`（0～4）离散域；不参与 PV 工程量程、模拟量跳变、尖峰、冻结和频域噪声检测。保留 NaN、质量码和时间轴检查。Pipeline 与诊断使用的 DataQualityAssessor 同步生效。 |
| `pipeline.PREPROCESS_VERSION` | 更新为 `pre_v3`，失效旧预处理块。 |
| `data_planner.resolve_data_version` | 布局/时间策略版本后增加预处理版本，L2 命中前也隔离旧 MODE 掩码；批级预载和逐回路解析同源。 |
| `batch-diagnose-modal.vue` | 默认空选；打开弹窗及切换范围后清空选择；50 个上限同时用于勾选、全选、按钮和提交检查；全选超限明确拒绝，不静默截断。 |
| 同一弹窗的搜索选择 | 独立受控 Checkbox 维护全局集合，防止 Checkbox.Group 在搜索卸载选项后丢掉隐藏选择；提示隐藏已选数量，并提供清空全部入口。 |

本次不改变 DCS 原始编码映射、builder 既有 MODE 取整、OP 保持时限、评分公式、可信度门槛或时间窗边界。标准域检查作用于当前预处理输入，不宣称已修复所有上游编码问题。历史已保存结果不自动改写；部署后须明确重新计算原窗口进行对照。

现场两个样本的 OP 未知 3486 秒已归因为 `held_too_long`，这是另一个覆盖策略问题。本次不通过延长保持时限或降低门槛掩盖真实断流。

## 回归与交付

- 旧实现下，新测试复现 MODE 8 项失败、批量选择 5 项失败。
- MODE 回归覆盖 PV 量程 185～215、0～2.5 与全部标准模式，验证手动 R=0、自动 R=100；非法编码、NaN、坏质量保持无效。
- 批量诊断回归覆盖 1209 个回路默认空选、50/51 边界、超限全选拒绝、隐藏选择提示、重开清空及真实 Checkbox 跨搜索保留选择。
- 独立审查发现 Checkbox.Group 丢隐藏选择问题，已修复并增加真实组件回归。其余两条修改链未发现已证实的新缺陷。
- 冻结清单按本次用户显式授权重新固化：仅 pipeline 的 `pre_v3` 文件摘要及基线提交元信息变化；评分公式与其他受保护算法摘要保持原值。旧 L1/L2 预置缓存读取回归验证新版会回源并写入新键。
- 最终测试、镜像源码 SHA、压缩包大小与摘要登记在 `releases/manifest-1046.json`。

部署仅由用户通过 ToDesk 手工实施，应用版本 `v7.5.6-1046-full`，两个镜像均为 `linux/amd64`。无数据库迁移，预期 head 仍为 `p703report01`。10 分钟影子验证继续关闭；手册只提供停用与状态核对，不安排启用。

本机测试和镜像烟测不代表生产验收通过；部署后仍需核对 961 回路一小时评估的有效结果数量与耗时、单回路 24 小时诊断的实际阶段/进度、导入确认批次与效率。
