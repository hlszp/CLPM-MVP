# 961 回路小时评估性能排查

2026-10-21。现场基线为 `v7.5.6-1043-full`；本轮源码改动在 `macbook` 分支，尚未部署。原始数值、窗口及输入哈希见 [证据 JSON](验收证据/kpi-961-20261021.json)。

后续已进一步合并初值/锚点查询并精简结果落库，见 [流式预计算与 TDengine 评估及本地验证](../设计文档/评估诊断流式预计算与TDengine优化可行性-2026-10-21.md)。下表仍保留第一轮测量基线；未把后续局部收益外推为现场总耗时。

## 现场证据与结论

用户提供的 Worker 日志覆盖两个标准整点评估窗口，均完成 961/961，回路并发为 12：

| 窗口（UTC） | 整批执行 | read p50/p95 | compute p50 | persist p50/p95 |
|---|---:|---:|---:|---:|
| 2026-10-21 02:00–03:00 | 1519.281s | 16.47 / 22.16s | 0.12s | 2.99 / 5.69s |
| 2026-10-21 03:00–04:00 | 1499.770s | 15.96 / 21.74s | 0.12s | 2.98 / 6.09s |

同批尾部指标组查询约 6.9–8.2s，预处理约 0.09–0.75s。主要耗时落在数据准备和持久化，现有证据不支持把它归因于评分公式计算。旧 `read` 含整个 DataPlanner（缓存编解码、取数、预处理、组包），不是 TDengine SQL 的单独耗时；旧 `persist` 不含外层 commit/close。

这些是执行时间证据，不含 Celery 排队时间。`docker stats` 的 Block I/O 是容器运行以来累计量，不能由其数值推断当时磁盘饱和。PostgreSQL/Redis 持久化等待仍需现场补采，不能把未验证的配置调整算作已完成优化。

## 本轮改动

1. `point_read_scope.py`、`logical_wide_builder.py`、`tdengine_provider.py`：同一查询闭包、事件循环、回路和窗口的并发 TagGroup 复用相同事件、初值、绑定历史、锚点和缺口查询。仅共享只读结果；元数据会话保持独立。最后一个读者退出后收束 IO 并释放，后续任务、补数后复读和失败重试重新读取。
2. `logical_wide_builder._load_gap_windows`：只查询与网格相交的 gap。gap 仍按半开区间处理；含尾网格点，所以 `seg_start == grid_end` 保留、`seg_end == grid_start` 排除。
3. `point_history_metadata.applicable_anchors_batch`：PostgreSQL `DISTINCT ON(point_id)` 按既有时间降序选择每点最新行，减少返回的历史锚点。保留原有最新行有效性检查，不改变边界或回退选择。
4. `calc_snapshot._ns_int / serialize_data_blocks`：用整数微秒差转纳秒，同一对象的数据块仅转换一次，再按指标复制独立数组。NPZ 键、数组字节、NaN/None 掩码、元数据、inputHash 和重放格式保持一致；不同对象即使 ID 相同也不混用。
5. `data_planner.py / kpi_calc.py`：补充分段墙钟计时及每 50 个回路的批量进度日志。没有提高并发数、增加 Worker/Beat、修改阈值或更换数据源。

## 本地对照

真实本地 PostgreSQL + TDengine 点表；1h 窗口；每回路 25 个指标、5 个数据块。取数 A/B 仅关闭同窗复用作对照，两组均关闭 L1/L2；每回路交替运行 4 次取中位数。没有写入 KPI/结果账本，没有触发 Celery 任务。

| 样本类型 | 无同窗复用 | 有同窗复用 | 加速 |
|---|---:|---:|---:|
| FLOW | 174.23ms | 153.73ms | 1.13× |
| LEVEL | 487.67ms | 278.83ms | 1.75× |
| PRESSURE | 485.30ms | 311.57ms | 1.56× |
| TEMPERATURE | 483.05ms | 316.58ms | 1.53× |

非 FLOW 样本 TD 查询由 16 次降至 8 次，builder 的绑定/gap 元数据查询由 10 次降至 2 次（不含锚点查询）。FLOW 本来从 BASE 派生 HF，查询次数不变；其计时差不作为性能收益承诺。全部样本输入包哈希、各指标和综合评分/可信度相同。

人工评估输入包编码以 `d1cecbe4a` 为基线，交替运行 10 次取中位数：FLOW 270.29→87.87ms、LEVEL 152.09→55.98ms、PRESSURE 191.06→62.47ms、TEMPERATURE 147.93→58.21ms，约 2.54–3.08×。标准小时评估默认不保存此输入包，不能用这项收益解释上述现场整点评估耗时。

锚点查询另在本地 PostgreSQL 事务内临时表验证：返回行 7→3，所选最新行及有效性结论相同，测试事务回滚。新增回归覆盖取消隔离、在途 IO 收束、失败后复读、跨窗口隔离、质量/游程等价、时间戳字节、数组独立性及输入哈希。

以上均不是现场 961 回路总耗时验收，不能将取数倍率直接套用为整批耗时。

## 日志判读与现场复测

新 `[批量计时]` 一行包含 run、真实窗口起点、已返回计时的回路数、整批 elapsed 和以下阶段：

- `read`：整个 DataPlanner；`l2_read / groups / assemble / l2_write` 为其子段，`l1_write` 又包含在 `groups` 中。
- `input_snapshot`：人工输入包保存；`input_encode` 为其中的数组转换子段。
- `compute`：算法、门禁及其他处理，排除输入包；`algorithm` 为其中的三层指标计算子段。
- `persist / commit / close`：结果写入、事务提交、会话关闭分别计时。
- `wait`：本批回路等待并发槽位的时间，**不是 Celery 排队时间**；`total` 为获得槽位后到关闭会话的总耗时。

阶段有包含关系；并发回路的 sum 也不能相加当作整批 elapsed。`[评估批量进度]` 的“已处理”包括失败/不足数据回路，不表示全部成功。

部署新镜像后固定参评 961 回路和 1h 窗口，核对实际版本、任务身份、成功/不足/失败分母、最新结果及节点聚合，再比较整批 elapsed、取数/缓存/提交 p50/p95。至少重复三次并记录同期任务负载。源码测试通过和容器健康不替代此步骤。

只读取日志（生产 Linux root）：

```bash
docker logs clpm-celery-worker --since 2h 2>&1 | grep -E '\[批量计时\]|\[评估批量进度\]|并发计算完成|自定义批量计算' | tail -25
```

TDengine 原生 `LAST_ROW`、批量写入与趋势 `LAST/INTERVAL/FILL` 延续 full-1043 的实现。本轮不把需要 COV、质量码和连续片段语义的指标替换为未经等价验证的 AVG 等聚合；减少重复 IO 与是否使用原生聚合是两个不同问题。
