# CLPM 高保真原型重构设计方案

日期：2026-06-18
状态：approved-for-planning
适用范围：`/Users/zhangping/DEV/CLPM/prototype`

## 1. 背景

当前 CLPM 原型已经具备清晰的产品叙事、菜单信息架构和 P0 业务主链，但整体仍偏“概念验证型演示系统”：

- 页面存在较多说明型文案，弱于任务驱动。
- 主链页面虽然可跳转，但状态联动不足。
- 审核、实施、复评、证据包之间尚未形成共享状态源。
- 列表、筛选、批量动作、角色菜单权限等真实业务交互未成体系。
- 视觉风格偏通用 SaaS 原型，尚未建立工业治理平台的严肃感和高密度信息风格。

本次重构目标不是继续补静态页，而是建设一个可独立运行、可做正式业务评审、可支撑用户测试的高保真原型系统。

## 2. 范围与决策

### 2.1 本次已确认决策

- 采用“方案 A”：先定设计系统和状态机，再重构 6 个核心页。
- 仓库内产出 `DESIGN.md` 作为 1:1 还原标准。
- 第一阶段优先深做 6 个核心页面，而不是先做全量页面。
- 暂不做真实登录鉴权，但必须做菜单权限路由模拟。
- 权限模拟方式采用“顶部角色切换器”。

### 2.2 第一阶段重构范围

本阶段深做以下 6 个核心页面：

1. 首页工作台
2. 样本导入与就绪校验
3. 低效排行与指标总览
4. 单回路证据中心
5. 审核/实施/复评联动页
6. Sponsor 汇报与证据包

其余页面保留结构，但必须接入统一壳层、统一路由和统一状态语义。

### 2.3 非目标

以下内容不在第一阶段实现范围：

- 真实后端和数据库
- 真实用户系统和鉴权
- 真实文件导出
- 真实工业接口接入
- P1/P2/P3 深交互页面

## 3. 重构目标

### 3.1 视觉目标

- 建立统一视觉系统，形成工业治理平台的高保真视觉基线。
- 所有核心页面使用统一的布局、组件、状态色和文案语气。
- 页面应更像真实生产应用，而不是概念演示板。

### 3.2 交互目标

- 所有核心动作必须驱动状态变化。
- 跨页面上下文必须可保持，不能每页重置业务状态。
- 列表页必须支持真实业务常见操作：筛选、排序、分页、批量选择、批量操作。
- 所有核心业务流程至少具备顺畅路径、驳回路径、异常路径三类可验证分支。

### 3.3 业务目标

- 模拟“样本 -> 诊断 -> 审核 -> 实施 -> 复评 -> 证据包 -> 汇报”的完整闭环。
- 支持角色切换视角下的菜单和操作差异。
- 使原型可用于用户测试、需求评审、流程 walkthrough 和正式业务讨论。

## 4. 设计原则

### 4.1 任务优先

页面首先服务当前用户任务，而不是介绍系统概念。首屏优先展示：

- 当前对象
- 当前状态
- 当前风险
- 下一步动作

### 4.2 状态驱动

状态是本次重构的核心。任何页面都不应有自己的业务真相副本，必须共用统一状态源。

### 4.3 高密度但可读

CLPM 是工业治理系统，不是营销网站。应采用更高信息密度，但通过层级、对比和结构保持可读性。

### 4.4 审计化表达

Sponsor、EvidencePackage、审核和复评页面必须有“可审计、可回看、可追溯”的质感和信息结构。

### 4.5 原型也必须像真实系统

虽然第一阶段不接真实后端，但界面行为、流转约束和异常反馈必须接近真实生产系统的运行逻辑。

## 5. 信息架构与路由策略

### 5.1 页面等级

页面分为三类：

- 深做页：6 个核心页，必须具备高保真交互和共享状态。
- 配套页：与主链相邻的辅助页，可简化但必须与主链状态一致。
- 结构页：P1/P2/P3 暂不深做，仅保留统一模板和版本说明。

### 5.2 菜单权限路由

不做真实登录，但实现“视角化权限模拟”。

方案：

- 顶部状态栏加入角色切换器。
- 切换角色时，菜单树按角色显示/隐藏。
- 页面内按钮按角色做启用、禁用、只读三种状态。
- 如果用户以某角色访问无权限页面，展示“该角色当前不可操作”而不是空白页。

### 5.3 上下文保持

所有主链页面必须共享以下全局上下文：

- 当前角色
- 当前样本批次
- 当前选中回路
- 当前 EvidencePackage
- 当前筛选条件

### 5.4 菜单结构矩阵

第一阶段必须把菜单结构显性声明为设计源的一部分，而不是只留在运行时代码中隐式表达。

菜单矩阵至少包含以下字段：

- `menu_id`，代码字段映射为 `id`
- `label`
- `path`
- `parent_id`，代码字段映射为 `parentId`
- `version`
- `depth`
- `page_level`，代码字段映射为 `pageLevel`
- `stage`
- `roles`
- `default_entry`，代码字段映射为 `defaultEntry`
- `is_deep_page`，代码字段映射为 `isDeepPage`

菜单结构的代码源为 `prototype/src/routes/menuConfig.ts`。实现时不得再派生第二份独立菜单真相，类型声明必须能够表达上述字段，设计文档与代码配置需保持同步。

## 6. 数据模型与状态机

### 6.1 核心实体

- `SampleBatch`
- `LoopRecord`
- `DiagnosisFinding`
- `ReviewDecision`
- `ImplementationRecord`
- `ReevaluationResult`
- `EvidencePackage`
- `UiSession`

### 6.2 SampleBatch 状态

`draft -> importing -> validating -> ready -> partial -> frozen`

规则：

- `partial` 表示样本已可进入后续流程，但存在字段、质量码或事件缺口。
- `frozen` 后不可编辑，仅允许查看和派生后续动作。

### 6.3 Loop 状态

`eligible -> diagnosing -> review_pending -> approved -> rejected -> needs_evidence -> implemented -> reevaluated`

规则：

- `approved` 不等于闭环完成。
- `implemented` 不等于改善成立。
- `needs_evidence` 必须阻断 EvidencePackage 完成态。

### 6.4 EvidencePackage 状态

`partial / completed`

派生规则：

- 任一关键回路处于 `needs_evidence`、缺实施记录或缺复评结果时，EvidencePackage 为 `partial`。
- 只有闭环完整且不可证明事项已明确时，EvidencePackage 才允许为 `completed`。

### 6.5 页面状态表达

所有核心页统一支持：

- loading
- empty
- success
- partial
- error

并遵守规则：

- 数据不足不是错误。
- 不可判定不是失败。
- partial 必须解释缺口、允许动作和下一步。

## 8. 六个核心页面设计

### 8.1 首页工作台

**目标**

- 成为工程师当天治理动作的入口页。
- 减少无意义跳转，让选中对象与任务动作同屏完成。

**布局**

- 左：优先队列和筛选
- 中：当前回路证据摘要和趋势
- 右：待办、动作、风险提示

**关键交互**

- 点击回路切换中间和右侧联动内容
- 支持按风险、类型、状态筛选
- 支持批量标记“延后处理”“现场核实”

**关键状态变化**

- 提交审核后，该回路从“待处理”转为“审核中”
- 标记现场核实后，该回路在首页和排行页同步反映

### 8.2 样本导入与就绪校验

**目标**

- 以步骤式体验模拟真实数据准备流程。

**布局**

- 顶部步骤条
- 左侧问题清单
- 右侧当前任务明细和下一步动作

**关键交互**

- 选择导入方式
- 维护字段映射
- 查看解析结果
- 冻结样本

**关键状态变化**

- `draft -> importing -> validating -> ready/partial -> frozen`
- 冻结后，导入与映射表单变只读

### 8.3 低效排行与指标总览

**目标**

- 成为样本层面的高密度分析入口。

**布局**

- 顶部 KPI 概览
- 中部筛选与分布图
- 下方高密度表格

**关键交互**

- 筛选
- 排序
- 分页
- 批量选择
- 从表格直接进入证据页或闭环治理

**关键状态变化**

- 调整筛选条件后，图表和表格同步更新
- 批量标记操作会回写到工作流状态

### 8.4 单回路证据中心

**目标**

- 成为“趋势 + 规则 + 事件 + 人工判断”的单回路判断中枢。

**布局**

- 顶部回路头
- 中部趋势与事件线
- 右侧规则说明、证据完整度、建议动作

**关键交互**

- 切换时间窗
- 查看规则命中解释
- 录入人工复核意见
- 跳转审核或整定样例

**关键状态变化**

- 提交人工判断后，回路状态从 `diagnosing` 变为 `review_pending`

### 8.5 审核/实施/复评联动页

**目标**

- 用单页联动页表达整个闭环流转，不再分散为弱联动说明页。

**布局**

- 左：流程时间线
- 中：当前节点表单
- 右：证据摘要与历史记录

**关键交互**

- 审核通过/驳回/需补证据
- 登记实施动作
- 查看并录入复评结论

**关键状态变化**

- 审核决定改变回路工作流状态
- 实施记录生成后进入复评阶段
- 复评完成后更新包状态候选值

### 8.6 Sponsor 汇报与证据包

**目标**

- 成为高层和审计视角的只读结论页。

**布局**

- 顶部结论印章和包状态头
- 中部证据覆盖矩阵、代表性样例、风险列表
- 底部不可证明事项与口径边界

**关键交互**

- 查看包摘要
- 下钻代表性样例
- 切换 manifest / summary 视图

**关键状态变化**

- 页面不主动写状态，但必须实时反映整体流程是否可被判定为 `completed`

## 9. 异常与边界场景

本次重构必须显式模拟以下场景：

- 缺字段
- 缺质量码
- 缺事件
- 审核驳回
- 审核需补证据
- 实施后无改善
- 证据包仍为 partial
- 某角色无权限操作

这些情况都必须有清晰反馈，不允许静默失败。

推荐顺序：

5. 低效排行与指标总览
6. 单回路证据中心

## 12. 风险

### 12.1 视觉基线风险

当前没有 Figma 或现网统一设计源，因此 `DESIGN.md` 将成为唯一官方设计源。若后续补充外部设计资产，需要以此文档为对照进行更新。

### 12.2 状态扩散风险

如果继续沿用每页自己的本地数据拼装，重构很快会失控。因此必须先统一状态模型，再逐页落地。

### 12.3 范围膨胀风险

若把全量页面的深交互一并推进，会稀释第一阶段目标。必须优先把 6 个核心页做成真工作流原型。

## 13. 完成定义

当以下条件全部满足时，第一阶段重构才算完成：

- 6 个核心页全部达到统一视觉标准
- 角色切换器可驱动菜单与操作差异
- 主链状态在跨页面中保持一致
- 列表页支持筛选、排序、分页、批量选择
- 审核、实施、复评至少有一条真实闭环可跑通
- Sponsor 与 EvidencePackage 页面可自动反映 `partial / completed`
- 原型系统可独立部署运行
- 可支撑用户测试、需求评审和业务 walkthrough
