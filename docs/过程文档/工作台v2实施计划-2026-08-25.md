## 1. 实施概述

### 1.1 目标

按方案 v2.0 分三个里程碑（M1 基础壳 / M2 P0 闭环 / M3 增强优化），9 周日历内交付单屏高密度工作台，覆盖 21 项 P0 + 16 项 P1 + ≥6 项 P2 功能，最终替换首页为工作台。

### 1.2 实施方法

- **批次化推进**：每个里程碑拆为若干批次（Batch），每批次 0.5~1 天，产出可独立验证。
- **最小侵入**：不删除诊断/整定专属前后端文件；新表 + ADD COLUMN 为主，无破坏性 DROP。
- **双向迁移**：每个 alembic 迁移必须 upgrade/downgrade 双向可执行（`alembic check` EXIT=0）。
- **门禁前置**：每批次结束跑 `ruff check + format --check + pytest -q + alembic check`，全绿方可进入下一批次。
- **双机隔离**：macbook 机在 `macbook` 分支开发，`git push -u github macbook`；仅在用户显式要求时合并回 main。

## 9. 回滚机制

### 9.1 迁移回滚（最高频）

```
# 回退最近一个迁移
uv run alembic downgrade -1

# 回退到指定版本
uv run alembic downgrade <revision>

# 回退后重新升级验证
uv run alembic upgrade head
```

**规则**：每个迁移必须有对称 downgrade；downgrade 不得 DROP 生产数据表（仅 DROP 新增表/列/索引/约束）。

### 9.2 代码回滚

- **批次级**：`git checkout <file>` 丢弃单文件；`git reset --hard HEAD` 丢弃全部未提交（仅未 push 时安全）
- **已提交未 push**：`git reset --soft HEAD~1` 撤销 commit 保留改动
- **已 push 到 github/macbook**：`git revert <commit>` 创建反向 commit（禁止 force push 共享分支）

### 9.3 数据回滚

- **种子数据**：`module_plugin` 种子由迁移 INSERT，downgrade 对应 DELETE WHERE module_key IN (...)
- **ALTER COLUMN**：新增列 downgrade = DROP COLUMN；改类型列需先备份（本方案无改类型，仅 ADD COLUMN）
- **物化视图**：DROP MATERIALIZED VIEW（无数据损失，可重新 REFRESH）

### 9.4 部署回滚（M3 dev 部署）

- 部署脚本内置健康检查（`/health` 200 + DB 连通），失败自动回滚到上一版本
- 数据库迁移如需回退：先停应用 → `alembic downgrade` → 启动旧版本应用

### 9.5 回滚决策权

- **批次内**（未 push）：Agent 自主回滚
- **跨批次 / 已 push**：报告用户，由用户决策
- **里程碑级**：必须用户显式批准
