# 诊断闭环链路核验：评估 → 诊断 → 结论/证据/处置建议

- **核验日期**：2026-10-01
- **核验人**：diagnosis-verifier（task-3）
- **核验方式**：只读。静态代码走查 + 实测后端 API（curl，仅 GET）+ 实测前端 DOM（Playwright 只读导航，未点击任何「发起诊断」）
- **核验对象**：用户核心诉求 2 ——「根据具体回路的评估结果，发起诊断，并显示诊断结论和相应的证据和处置建议」
- **结论一句话**：**功能不缺，链路断在"承接"上**。全站真正能发起诊断的按钮只有 **1 个**，而通向它的「去诊断」入口有 **12 个**；工程师从"看到评估差"到"拿到三件套"实际要 **9 步 / 跨 2 个页面**，且中间有 3 处会掉上下文、1 处会掉进空列表。

## 2. 链路断点：工程师实际要操作几步、哪里会断

### 2.1 端到端路径图（实测走查）

```

   └─(1) 打开 /metric/loop-performance（回路性能，服务端按评分排序）

## 4. 处置建议落地链路

```
诊断结论 (recommendations, JSONB)            ──✗ 不落地──▶ 仅在工作台 Tab3 展示，随 run 生命周期
                                                              （D3：与下面这条路互不相通）

诊断落库 → generate_system_actions_best_effort ──▶ loop_action_item (source=SYSTEM)
   [diagnosis_system_actions.py:103]              ▲ 幂等：该 run 已有 SYSTEM 项则跳过 (:56-64)
                                                  │
GET /diagnosis/runs/{id}/actions ─────────────────┘ 懒生成兜底 (:483-486)
                                                  │
                                                  ▼
概览详情弹窗 Tab3「处置建议」              处置模块 /handling/suggestions
  [diagnosis-detail-modal.vue:1079+]        [handling.py:518 → _suggestion_to_dict :230]
  ├ 人工新增 POST actions (MANUAL)                       │
  ├ 行内编辑/删除（仅 MANUAL）                            ▼
  └「去处置」→ /handling/suggestions?focus={actionId}   建议审核：accept / reject / ignore

                                                         │  [handling/workbench.vue:362-419]

**要产生 `loop_action_item`，用户需要做什么？** 正常路径下**不需要**任何操作——诊断落库时自动生成（`:103`），GET 查询时兜底补生成（`:486`）。
**要产生 `handling_order`，用户需要做什么？** 5 步：进入 `/handling/suggestions` → 找到建议 → 点「接受」→ 勾选 → 「转工单」并填表（actionType/plannedAt/handler/title）。

**是否存在重复录入？存在，且有两层：**
1. **同一建议内容被两处独立维护**（D3）：`recommendations` 与 `loop_action_item` 文案不同、互不影响，工程师若想按引擎原文处置，得在诊断弹窗里"人工新增"再抄一遍。
2. **人工新增入口只在概览弹窗**（`createRunActionApi` 的唯一生产调用点 `diagnosis-detail-modal.vue:326`）：主入口诊断工作台**没有**新增/编辑处置建议的能力，用户必须在工作台看完结论后跳到概览页再开弹窗才能补录 → 又一次跨页 + 重新定位回路。

## 6. 产品设计问题 vs 功能缺失（明确切分）

| 类别 | 断点 | 说明 |
|---|---|---|
| **产品设计问题（入口分散/组织不当，功能其实都在）** | D1、D5、D7、D10、D11、§5 整定衔接 | 全站 13 个入口、1 个真按钮；三件套拆 3~4 个 Tab；工作台诊断为只读分析页；诊断任务页串评估按钮；返回链缺 8/12。**不需要新功能，需要收敛入口与统一布局** |
| **功能缺陷（真断，需要改代码/数据）** | D2（UUID 回显）、D3（双来源建议）、D4（未见异常→空处置）、D6（字段缺失） | D2 是消费参数不完整；D3/D4/D6 是数据/接口层断裂 |
| **环境问题（非产品缺陷，改运维）** | D8（后端陈旧导致编造常量）、D9 的部分（口径分母） | 重启后端即可消除 D8 |
| **口径/一致性问题** | D9、D6、D7 | 需要定一个唯一口径并登记 |

**给用户的直接回答**：功能**没有缺失**——"发起诊断""结论""证据""处置建议"四件东西都存在且数据是真的（后端 30 条 run、27 条回路适用性、11 个算子结果、波形 2000 点、诊断落库即时生成系统建议，都能验）。**断的是承接关系**：入口分散成 13 个、真正的动作按钮只有 1 个藏在最深处；评估→诊断的"一键"手势被一个只读 Tab 接住；看完结论后"处置建议"有两份不一样的文案，跳去处置还可能看到空列表。
