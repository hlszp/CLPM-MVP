# 生产环境只读检查清单（交给 zcode 执行）

| 项 | 值 |
|---|---|
| 文档版本 | 2026-09-28 |
| 执行者 | zcode（可经 ToDesk 连生产环境） |
| 发起者 | 主会话（CLPM-MVP 开发侧） |
| 性质 | **全程只读**——不重启容器、不改配置、不删数据、不执行 DDL |
| 目的 | 为三件事取证：① 实时数据是否真的落库 ② 工作台装置/单元排名为空白的成因 ③ CLPM 挂到 AAS 82 端口子路径 `/clpm/` 的前置条件 |

## 0. 铁律（请先读完再动手）

1. **只允许操作 VMware 里的 `clpm` 虚拟机**；宿主机只做"切窗口/点 VMware 标签"这类最小动作；**AAS 相关虚拟机一律不碰**。
2. **只读**：不得 `restart` / `up -d` / 改 `.env.prod` / 改 Nginx / 删数据 / DDL / 建表。若某条命令可能改状态，**停下并回报**。
3. **一条一条粘贴执行**，不要整块多行粘贴——`sudo` 密码提示会"吃掉"后续行（本项目已踩过）。
4. **口令不明文回传**：涉及密码的检查只回报"是否有值 / 是否一致 / 能否连上"，不要贴明文、不要贴含密码的完整命令回显。
5. **原始输出优先**：每条命令请把**命令原文 + 原始输出**一起回传（可截断超长行），不要只给结论；若命令失败，把**完整报错**贴回来。
6. 若发现"任务要求与实际不符"（例如找不到文件/容器名不同），**如实报告并停止该条**，不要自行猜测替换。

## 1. 环境拓扑（便于理解命令上下文）

```
办公网 ──ToDesk──▶ 宿主机 Windows（远程入口，仅用于进 VM）
                    └─ VMware Workstation ─▶ 虚拟机 clpm（Ubuntu 24.04，IP 192.168.60.132）
                                              └─ CLPM 全栈 7 个容器（docker compose）
进 VM 的标准通道：宿主机 cmd → ssh clpm@192.168.60.132 → sudo -s（密码单独一条）
```

- 容器名：`clpm-backend` / `clpm-celery-worker` / `clpm-celery-beat` / `clpm-frontend` / `clpm-postgres` / `clpm-redis` / `clpm-tdengine`；
- 部署目录：`/opt/clpm-delivery-<时间戳>/`（含 `docker-compose.prod.yml` 与 `.env.prod`）；
- **配置真相源是 PG 的 `sys_config`**，不是 `.env.prod`（后者只在启动预载/无 sys_config 行时兜底）；
- 库内时间戳为 **UTC**（+8 换算北京时间）。

## 2. 必查 A —— 实时数据是否真的落库（最高优先级）

### A1 五道闸门诊断

```
docker exec clpm-backend python scripts/diag_realtime_pipeline.py
```

**判读**：点表那条（`TDengine st_point_data_v1`）是 PASS 还是 FAIL？若 FAIL，**错误类别**是什么——连接失败 / 认证失败（`0x357`、`Authentication failure`）/ 库或表不存在？
**注意**：若脚本版本较老，FAIL 文案可能统一写成"表不存在→writer 建表失败"，那是**误导性提示**，请以错误原文为准；新版脚本会按类别区分。

### A2 点表是否存在、多少行、最新时间（落库是否活着的金标准）

```
docker exec clpm-backend sh -c "curl -s -u root:\$TDENGINE_PASSWORD -d \"SHOW DATABASES\" http://tdengine:6041/rest/sql"
```
```
docker exec clpm-backend sh -c "curl -s -u root:\$TDENGINE_PASSWORD -d \"SELECT COUNT(*), LAST(ts) FROM clpm_ts.st_point_data_v1\" http://tdengine:6041/rest/sql"
```

**判读**：`clpm_ts` 是否存在？行数多少？`LAST(ts)` 离"现在"多久（若超过几分钟未更新，说明写入已停）？
⚠️ **不要用 `MIN(ts)/MAX(ts)`**——TDengine 分组聚合里对 TIMESTAMP 用 MIN/MAX 会返回空错误信息，一律用 `FIRST/LAST`。

### A3 口令三处是否自洽（**只回报 yes/no，不要贴明文**）

```
grep -c '^TDENGINE_PASSWORD=.\+' .env.prod
```
```
docker exec clpm-backend sh -c 'test -n "$TDENGINE_PASSWORD" && echo backend_env_set=yes || echo backend_env_set=no'
```
```
docker exec clpm-tdengine sh -c 'test -n "$TAOS_ROOT_PASSWORD" && echo container_root_pwd_set=yes || echo container_root_pwd_set=no'
```

**判读**：三处口径（`.env.prod` 有值 / 后端容器有值 / 容器 root 口令有值）是否自洽；再结合 A1 的认证类错误判断是否"后端口令 ≠ 库内 root 口令"。
**背景**：2026-09-27 事故根因正是——生产校验要求 `TDENGINE_PASSWORD` 非空，而 TDengine root 是默认**空密码** → 所有写入被拒 → `clpm_ts` 从未建成 → "实时页有值但一直没有历史数据"。

### A4 容器健康与 TDengine 是否反复重启

```
docker ps --format '{{.Names}}  {{.Status}}' | grep clpm
```

**判读**：7 个容器是否都 `Up (healthy)`？`clpm-tdengine` 的状态是不是 `Up N seconds`（**小数字 = 刚重启过**，反复出现说明崩溃循环）。

### A5 后端日志里的落库/订阅/认证线索（近 30 分钟）

```
docker logs clpm-backend --since 30m 2>&1 | grep -iE "PointHistoryWriter|已接管实时数据订阅|保持待命|0x357|authentication" | tail -20
```

**判读**：有没有 `PointHistoryWriter 已启动`？有没有`本进程已接管实时数据订阅（Leader）`？有没有出现`保持待命`（无人订阅）或认证失败刷屏？

### A6 运行态开关（Redis 镜像键）

```
docker exec clpm-redis redis-cli get datasource:rt:signalr_enabled
```
```
docker exec clpm-redis redis-cli keys "realtime:subscriber:leader:lock"
```

**判读**：`signalr_enabled` 是否 `true`？Leader 锁键是否存在（不存在 = 没有实例在订阅）？

### A7 配置真相源

```
docker exec clpm-postgres psql -U clpm -d clpm -c "SELECT key,value FROM sys_config WHERE key LIKE 'datasource.%' OR key LIKE 'history.%' ORDER BY key;"
```

**判读**：重点看 `history.storage_mode`（应为 `point`）、`datasource.signalr_hub_url`、`datasource.realtime_writeback_enabled`、`datasource.gap_backfill_enabled`。

## 3. 必查 B —— 工作台装置/单元排名为何空白

### B1 组织树有没有 AAS 整数编号（**决定性**）

```
docker exec clpm-postgres psql -U clpm -d clpm -c "SELECT count(*) AS nodes, count(source_node_id) AS with_id FROM plant_node;"
```

**判读**：`with_id` 为 0 或部分为 0 → 排名会空白（旧版代码会"跳过没有编号的节点"）。新版代码有**回退**（用节点 UUID 派生稳定整数），部署新版后即可出数；若希望用真实编号，则需 AAS 同步。

### B2 组织树层级结构

```
docker exec clpm-postgres psql -U clpm -d clpm -c "SELECT type, count(*) FROM plant_node GROUP BY 1 ORDER BY 1;"
```

**判读**：`FACTORY` / `AREA` / `UNIT` 各多少；是否有节点 `is_kpi_enabled=false`（这类不计入排名）。

### B3 工作台预计算表有没有节点级行

```
docker exec clpm-postgres psql -U clpm -d clpm -c "SELECT scope_type, count(*), max(snapshot_at) FROM workbench_window_summary GROUP BY 1 ORDER BY 1;"
```

**判读**：**只有 `GLOBAL` 一行 = 排名空白**（这是本次要修的现象）；若出现 `FACTORY/AREA/UNIT` 行，说明排名正常。

### B4（可选）节点级指标汇总是否新鲜

```
docker exec clpm-postgres psql -U clpm -d clpm -c "SELECT min(snapshot_time), max(snapshot_time), count(DISTINCT node_id), count(*) FROM unit_kpi_summary;"
```

**判读**：该表是"节点级指标计算"的产物（自动、每小时），它是排名预计算的**上游**。若它新鲜而 B3 为空，就确认问题出在"预计算的节点级行"这一跳。

## 4. 必查 C —— 挂到 AAS 82 端口子路径 `/clpm/` 的前置条件

### C1 82 的 Nginx 配置（**在哪台机器上以实际为准：宿主机或 VM**）

```
nginx -T 2>/dev/null | grep -nE "listen|server_name|location" | head -40
```

**判读**：是否已有 `/clpm`？`location /` 是否为 AAS？是否有通配 catch-all？是否已有 WebSocket 升级头（`Upgrade`/`Connection`）配置？

### C2 82 是 http 还是 https；有没有 443

```
curl -sI http://127.0.0.1:82/ | head -5
```

**判读**：决定前端该用 `ws://` 还是 `wss://`（若走 https，因前端 API 用相对路径会自动匹配，一般无需改代码）。

### C3 82 所在主机到 CLPM 前端是否可达

```
curl -sI http://127.0.0.1:7141/ | head -5
```

**判读**：返回 200/301 说明本机 7141 可直连，网关 `proxy_pass http://127.0.0.1:7141/` 可行。

### C4 路径冲突预检

```
curl -sI http://127.0.0.1:82/clpm/ | head -3
```

**判读**：现在返回 404 还是被 AAS 接管；决定是否需要先占位。

## 5. 必查 D —— 部署能力（决定"新版镜像怎么出"）

### D1 生产当前跑的版本

```
docker images --format '{{.Repository}}:{{.Tag}} {{.CreatedSince}}' | grep -E "clpm-(backend|frontend)"
```
```
ls -d /opt/clpm-delivery-* 2>/dev/null
```

### D2 生产是否具备构建前端镜像的条件（子路径改造**必须重打前端镜像**）

```
docker version --format '{{.Server.Version}}'
```
```
ls /opt/clpm-delivery-*/ | head -20
```

**为什么问这个**：子路径改造要改两个 **构建期** 变量（`frontend/apps/web-antd/.env.production` 的 `VITE_BASE=/clpm/` 与 `VITE_GLOB_API_URL=/clpm/api/v1`），`Dockerfile.frontend` 是 `RUN pnpm vite build --mode production`——**改容器 env 或重启都没用，必须重打镜像**。
**判读**：若生产能构建（有源码/包 + 联网拉基础镜像），则由 zcode 侧构建；否则由开发侧在本机出好镜像 tar 再传过去。

## 8. 收到输出后的判定树（供参考，不必执行）

| 观察 | 结论与下一步 |
|---|---|
| A2 行数在增长、`LAST(ts)` 是"刚刚" | 落库已通，本次只需版本升级 |
| A2 库不存在或 0 行 + A3 三处不自洽 | 即 2026-09-27 事故根因，**先修口令**（轮换并统一 + `--force-recreate` 三容器）再看其余 |
| A1 报认证类错误（`0x357`） | 同上一行 |
| B1 `with_id = 0` | 排名会空白 → **部署含"回退"逻辑的新版**，或走 AAS 同步补编号 |
| B3 只有 `GLOBAL` | 印证上面一条 |
| C1–C4 | 决定 `/clpm/` 网关那段怎么加、要不要先占位、是否需处理 https/wss |
| D2 生产不能构建 | 改由开发侧在本机出两套前端镜像（`VITE_BASE=/` 与 `VITE_BASE=/clpm/`）——请尽早告知 |
