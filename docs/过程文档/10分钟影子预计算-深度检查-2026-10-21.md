## 规范与正确性检查

| 等级 | 问题与反例 | 修复与证据 |
|---|---|---|
| P1 | 发布前最后一次配置查询期间租约被替换，旧执行者仍可发布 EQUAL | `fenced_step` 在同一 Redis Lua 验证 token+原 cohort，并原子推进/解锁；报告 PENDING 后才可终态发布。真实 Redis 原实现失败反例已保留 |
| P1 | 同一 cohort 的接管者使用新 token，旧任务失锁清理却删除 ACTIVE、覆盖其报告 | 失败清理使用同一 fencing；无所有权仅写独立 REJECTED；不覆盖接管者 cohort |
| P1 | 批量锚点先选全历史最新行，未来/过期锚点遮蔽旧适用行 | SQL 先过滤 `anchor_ts<=windowStart` 和半开 coverage，再 DISTINCT ON；真实 PG 对照单点查询，覆盖四类边界 |
| P2 | 步骤投递发生在解锁之前，空闲 Worker 收到 BUSY 后额外等待 30 秒 | 状态交接与解锁原子完成，再投递后继；真实 Redis 在投递时直接检查租约为空 |
| P2 | 报告盘满后错误报告再次失败，清理未执行且原异常被掩盖 | 先 fenced 清理，再 best-effort 写报告，保留原始异常；真实 Redis+故障注入验证 |

提交后报告写入或投递仍可能失败：已提交的单项结果与整批完成不同。仅清除尚无租约接手、raw 身份一致的待投递状态；接管者状态保留。跨 Redis/文件/消息没有共同事务，进程崩溃仍可能留下 PENDING/STALLED，不能把它当通过；持久 outbox 不属于本阶段。

## 方案符合度与性能检查

| 问题 | 修改 / 判断 |
|---|---|
| 正式完成路径等待配置、报告和派发最多 6 秒 | 移为轻量背景请求，正式只等 broker ≤0.2 秒；绝对消息寿命 120 秒，消费端再拒绝过期请求；影子消息 priority=9，不抢占正在运行的正式任务 |
| 256 块不能覆盖 24×4×6=576，旧时间排序会马上淘汰新建历史块 | v2 改 1024 块 + 32 MiB 压缩值双预算，按访问序号 LRU、Lua 原子计费；24×4/7 点两轮暖缓存均完整块命中，尾点仍精确回源 |
| 影子对照自身是否提速 | 原本机样本暖候选 0.9472s、直接 0.8738s；冷候选 1.1487s、直接 1.0315s，均无净加速证据。三遍完整对照还会增加 IO，保持默认关闭和小白名单 |
| 锚点、初值、质量及算法是否被缓存替代 | 仍完整窗口运行原算法、质量预处理、门禁和上下文恢复；未平均分钟评分，未改算法阈值/golden |
| TDengine 原生能力 | 已有 LAST_ROW、批量 INSERT/定向事件读取；未引入 Stream/TSMA。事件聚合不能替代 COV、联合质量与波形算法；继续遵守本地计算唯一数据源 |
| 正式结果隔离 | 影子会话只读 PG，结果 sink 仅捕获，不写 KPI/账本/latest/正式输入包；来源和精确窗口保留 |

1024 块是数量上限而非驻留承诺：高密度数据可能先达到 32 MiB。v1/v2 升级隔离期间旧值自然过期，短时双代 payload 最多约 64 MiB，不含 Redis 元数据；影子缓存仅允许 `noeviction`，首次更新只读检查，不满足或无 CONFIG 读取权限则拒绝写入，不自动改 Redis 全局策略。曾启用 v1 的现场可停用后等待 6 小时再启用 v2。
