## 一、这次修了什么（部署团队需要知道的背景）

**问题现象**：生产实时数据采集后没有落库，趋势图没有任何数据。

**代码层确认的缺陷**（本次全部修复）：

1. **两个决定"数据往哪写、从哪读"的开关，此前谁都改不了**：写入布局（`sys_config: history.storage_mode`）与读取路由（`history_layout_manifest`）是两套独立开关，而 `set_storage_mode` / `set_layout` 都是**无调用方的死代码**，UI、API、脚本都没有入口。二者不一致时，现象就是"实时数据在采、库里却没有 / 趋势图全空"，且**日志一句提示都没有**。
2. `realtime_writeback_enabled`（实时回写）的文案写成"写回 TDengine 宽表"，但它**不控制点表写入**，真正决定点表落库的是 `storage_mode`。
3. Dockerfile 未拷贝 `scripts/` 目录，运维诊断脚本无法在容器内执行。
4. Windows 容器外场景有 5 处 Unix-only 调用（`pgrep` / `os.kill(pid,0)` / `SIGKILL` / `killpg` / prefork 池）。

**本次带来的新能力**（部署后即可用）：

- 启动与每分钟自检：写入/读取布局不一致时**直接打 ERROR 日志**，并给出修复方向；
- 新端点 `GET/PUT /api/v1/datasource/storage-mode`（PUT 仅 ADMIN，写审计）；
- `/api/v1/datasource/health` 新增 `storageMode / readLayout / layoutConsistent / layoutSeverity / layoutDiagnosis / pointTableWritten`；
- 数据接入页（`/config/link`）顶部新增「**写入布局**」下拉 + 不一致时的红色告警；
- 镜像内置运维脚本：`scripts/diag_realtime_pipeline.py`（五道闸门诊断）、`scripts/register_layout_manifest.py`（读取路由登记，默认 dry-run）。

## 二、部署步骤

### 0) 取码

```powershell
cd <部署目录>          # 含 docker-compose.prod.yml 的目录
git pull github main   # 若你们的取码通道不同，按既有方式拿到 commit 3552d422 即可
git log --oneline -1   # 期望输出：3552d422 fix(platform): 修复实时落库静默失败与系统性缺陷
```

### 1) 重建镜像

```powershell
# backend / celery-worker / celery-beat 三个服务共用 clpm-backend:latest，构建一次即可
docker compose -f docker-compose.prod.yml build backend

# 前端本次也有改动（数据接入页「写入布局」下拉与告警），同样需要重建
docker compose -f docker-compose.prod.yml build frontend
```

> 也可使用既有脚本：`./deploy/build-and-deploy.sh --backend-only` 与 `--frontend-only`。
> 脚本构建的后端镜像 tag 为 `clpm-backend:latest`，与 compose 引用一致，`up -d` 会取到新镜像。

### 2) 替换容器

```powershell
docker compose -f docker-compose.prod.yml up -d --force-recreate backend celery-worker celery-beat frontend
docker compose -f docker-compose.prod.yml ps    # 确认四个服务均为 Up / healthy
```

**预期日志**（新出现的 WARNING 属正常，不要误判为故障）：

```
WARNING | 生产环境：Celery Beat/Worker 应由独立进程或容器接管，本进程未启动它们。（容器化部署下可忽略）
WARNING | 本进程已接管实时数据订阅（Leader）: token=...
INFO    | PointHistoryWriter 已启动（storage_mode=...）
```

## 三、部署后验证（必做，约 5 分钟，结果请回传）

```powershell
# ① 写入布局 与 读取路由 自检（最关键；dry-run，不会写库）
docker compose -f docker-compose.prod.yml exec -T backend python scripts/register_layout_manifest.py --layout point

# ② 订阅与写入器日志
docker compose -f docker-compose.prod.yml logs --tail=200 backend | Select-String "PointHistoryWriter|实时落库自检|已接管实时数据订阅|保持待命"

# ③ 点表是否在增长：间隔 1 分钟执行两次，COUNT 与 LAST(ts) 都应前进
docker compose -f docker-compose.prod.yml exec -T tdengine taos -s "SELECT COUNT(*) FROM clpm_ts.st_point_data_v1;"
docker compose -f docker-compose.prod.yml exec -T tdengine taos -s "SELECT LAST(ts) FROM clpm_ts.st_point_data_v1;"
```

界面侧同样可见：登录 → 配置 → 数据接入页（`/config/link`）顶部状态区新增「**写入布局**」下拉与「读取侧：xxx」；不一致时会出现红色告警并写明修复方向（可截图回传）。

### 结果判读表

| ① 自检输出 | 含义 | 处置动作 |
|---|---|---|
| 写入侧 `point` + 读取侧 `point`，`consistent=true` / `severity=ok` | 读写口径一致，写点表也读点表 | 看 ③ 是否增长；不增长才查 TDengine 侧 |
| `storageMode=legacy` | **新库默认值陷阱**：写入侧只写宽表，点表无数据（实时页可能有值） | 数据接入页把「写入布局」改为 **`shadow`（推荐，双写保回退）** 或 `point`，保存后 1 分钟内生效 |
| 写入侧 `point` 但读取侧 `legacy` | 点表在写、宽表停写，趋势读到空表 | 执行 `register_layout_manifest.py --layout point --apply` 登记 global 段完成切读（或把写入退回 `shadow`） |
| 日志出现 `保持待命` 且无 `已接管实时数据订阅（Leader）` | 订阅器没起来（Redis 不可达 / Leader 锁竞争） | 检查 `docker compose ps redis` 是否 healthy、`redis-cli PING`；这是 Windows 部署的头号嫌疑 |
| 日志出现 `点历史批次写入失败` | TDengine 写入侧问题 | 检查 `docker compose logs tdengine` 与容器内存；把报错原文回传 |

## 四、异常处置

### 4.1 一键取证（查不出来时执行）

```powershell
cd <部署目录>
powershell -ExecutionPolicy Bypass -File scripts\diag-realtime.ps1
```

产出单个报告文件 `diag-realtime-<时间戳>.txt`，含 8 段证据：容器状态、五道闸门诊断、后端日志关键字、celery 日志、Redis 运行态键与 Leader 锁、TDengine 行数与最新时间、容器内关键环境变量、`sys_config` 真相源。**把该文件整体回传即可定位。**

### 4.2 回滚

- 本次**无数据库迁移**，回滚无数据风险；
- 构建脚本会同时打 `clpm-backend:${GIT_COMMIT}` 与 `clpm-backend:${BUILD_VERSION}` 标签，可用 `deploy/rollback.sh` 回到上一版本；
- 也可临时把 compose 中的 `image:` 改为上一版本 tag 后 `up -d --force-recreate`。

### 4.3 明确不要做的三件事

1. **不要**只在 `.env.prod` 里改 `SIGNALR_*` 想让它生效 —— 业务 URL/Token 的真相源是 `sys_config`，后端启动预载会覆盖 `.env`；要改就在数据接入页保存。
2. **不要**为了"补历史"打开 `gapBackfillEnabled` —— 那是断点续传（走远端历史导入），解决不了实时落库，反而引入导入负载。
3. **不要**再手工启动一份 celery worker/beat —— 会与容器内的重复消费（AGENTS 红线）。
