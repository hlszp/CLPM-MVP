## 1. 背景概述

### 1.1 现状与问题

CLPM v6.1 已完成 7 阶段重构，技术闭环（评估→诊断→整定→跟踪）已打通，但《UX/IA 专业评估报告》（`docs/过程文档/clpm-ux-ia-audit-report-2026-08-05.md`）从仪控工程师视角识别出 21 项问题，核心结论是：**技术闭环已通，用户操作闭环存在断点**。集中表现为：

1. **认知负担过重**：6 个一级菜单中 4 个"配置/监控/分析/系统"混装，工程师难以快速定位功能。
2. **回路实体无权威入口**：回路是 CLPM 核心实体，但其管理功能分散在回路管理、性能评估、诊断中心、回路整定四模块，处理单个回路需跨 3 个模块跳转且每次丢失上下文。
3. **跨模块跳转断点**：评估→诊断→整定之间无上下文传递，UX 审计 P0 项"整定上下文传递"未闭环。
4. **关键功能隐藏过深**：诊断详情 5 层 Tab、整定向导 5 层路由、AI 洞察埋在 Tab 末尾。
5. **配置与操作混杂**：结构性配置（回路/测点/链路）与操作性调参（阈值/算法参数）混在同一模块，违背工业软件"工程/操作分离"原则。

### 1.2 重构动因

- 修复 UX 审计 P0/P1 项，降低工程师认知负担。
- 建立回路全生命周期一站式工作台，闭环"评估→诊断→整定→效果对比"。
- 统一 AI 洞察入口与交互，使 LLM 能力在系统中显著、一致地呈现。
- 对齐工业控制软件（DCS/SCADA/CLPM 工具）主流 IA 范式：监控顶层 + 实体/职能双轴 + 工程/操作分离。

## 2. 总体目标

### 2.1 设计目标

| 编号 | 目标 | 验证指标 |
|---|---|---|
| G1 | 一级菜单按"监控→回路→评估→诊断→整定→配置→系统"重构，符合工程 workflow | 菜单 7 项，帮助悬浮 |
| G2 | 建立"回路"实体轴工作台，单回路 6 Tab 一站式处置 | 处置时间线 + 效果对比可用 |
| G3 | 诊断详情三区重构（结论先行 + 可视化定位 + 证据折叠） | 特征字典 ≥20 项 |
| G4 | 整定单页整合，路由层级 5→2 | 任务详情单页 + 锚点导航 |
| G5 | 统一工具栏 + AI 洞察右抽屉，全模块一致 | AI 图标状态机可验证 |
| G6 | 后端零改动（除标注微调） | §7 逐接口清单 |

### 2.2 设计原则

1. **双轴导航**：实体轴（回路·按回路聚合）与职能轴（评估/诊断/整定·按职能批量）正交并存，互为入口。
2. **工程/操作分离**：结构性配置集中到"配置"模块；操作性调参保留在业务模块内联。
3. **少改后端**：菜单重组/页面 reparenting/跨模块动作均纯前端；新视图优先前端组合现有 API。
4. **Calm UI / Glanceability / Poka-Yoke**：结论先行、工具栏灰显而非隐藏、数据墨金比最大化。
5. **安全边界不破**：整定仅输出建议/证据/风险/回退，不直写 DCS；"定稿"实为"方案确认 + 留痕"。
6. **AI 洞察可选可降级**：LLM 未启用时图标灰显，"诊断小结"模板兜底，不阻断核心闭环。

### 2.3 约束条件

- 不破坏现有后端 API 与数据库结构。
- E2E 测试（55 用例，硬编码路由）需随路由重组同步更新并保持全绿。
- 兼容现有权限模型（ADMIN/IC_ENGINEER/PE_ENGINEER/EXPERT）。
- 前端技术栈不变（Vue 3 + Vite + vue-vben-admin）。

## 3. 总体架构：双轴导航

### 3.1 双轴模型定义

```
                    ┌─────────────────────────────────────┐
   实体轴（按回路）  │           回路（工作台）             │
   单回路 360°      │  概览/评估/诊断/整定/效果对比/时间线  │
                    └─────────────────────────────────────┘
                                  ↕ 互为入口（loopId 上下文）
                    ┌─────────────────────────────────────┐
   职能轴（按职能）  │  评估    诊断    整定               │
   跨回路批量       │  (总览/任务/记录)  (列表/记录)  (工作台/任务/记录) │
                    └─────────────────────────────────────┘
```

- **实体轴**回答："这个回路现在怎么样、怎么处置"——以回路为聚合单位，编排各职能的摘要 + 跳转。
- **职能轴**回答："全厂哪些回路有问题、任务进展如何"——跨回路批量管理与记录。
- **回路工作台是编排器，不是功能副本**：只做"摘要 + 一键跳转（带 loopId）+ 嵌入式快照"，完整功能留在职能模块。守不住这条则退化为重复展示。

## 4. 详细设计方案

### 4.1 回路模块（实体轴·回路工作台）

#### 4.1.1 布局与 6 Tab 定义

> **⚠️ 实施变更（2026-08-07，commit `5e216ba8`）**：Phase B 在实施过程中从 6 Tab 重构为**单页四区垂直布局**（概览 10% + 性能评估 30% + 回路诊断 30% + 回路整定 30%）。原 6 Tab 设计（概览/评估/诊断/整定/效果对比/处置时间线）已废弃。下方 6 Tab 描述保留作为历史方案备查，现行实现以实现契约 v2.7 §Phase B 为准。

```
┌─ 回路 ───────────────────────────────────────────────────────────┐
│ [搜索回路...]  [筛选: 评分▼ 标签▼ 可信度▼]   [工具栏: 刷新|AI|帮助] │
├──────────────┬───────────────────────────────────────────────────┤
│ 回路列表      │ 选中回路工作台                                    │
│ ┌──────────┐ │ ┌─ 概览 ─ 评估 ─ 诊断 ─ 整定 ─ 效果对比 ─ 时间线 ─┐ │
│ │LIC-101 A │ │ │ 回路基本信息 | 7 tag | 当前评分 85 | 标签:正常   │ │
│ │LIC-102 C │ │ │ 可信度 A(97%) | 数据质量: Good                  │ │
│ │FIC-203 D │ │ │ [发起评估] [发起诊断] [开始整定]                │ │
│ │...       │ │ └────────────────────────────────────────────────┘ │
│ └──────────┘ │                                                   │
└──────────────┴───────────────────────────────────────────────────┘
```

| Tab | 内容（摘要 + 跳转，禁止搬全表） | 数据来源 | 后端影响 |
|---|---|---|---|
| 概览 | 基本信息+7tag+评分+诊断标签+可信度+数据质量；3 个动作按钮 | loop detail + metric snapshot + diagnosis label | 零（组合现有 API） |
| 评估 | 最近评估快照 + 评分趋势小图 + "去评估任务"（带 loopId） | kpi snapshot | 零 |
| 诊断 | 诊断标签+置信度 + 模板小结 + "查看诊断详情"（带 loopId）+ "发起诊断" | diagnosis detail | 零 |
| 整定 | 整定历史列表 + "开始整定"（带 loopId 进向导） | tuning task list | 零 |
| 效果对比 | 选两次整定，并排对比 PID/响应曲线/评分/标签 | tuning + metric + diagnosis | 零（前端组合） |
| 处置时间线 | 该回路全部事件时间轴（评估/诊断/整定/Tracker） | 三源 + tracker | 零（前端组合） |

**硬性规则**：每个 Tab 最多"摘要 + 1 主图 + 跳转入口"，禁止内嵌完整职能表格。

#### 4.1.2 处置时间线 Tab

- 聚合该回路全部生命周期事件：评估快照、诊断结果、整定任务、Tracker 动作。
- 前端并行调用评估记录/诊断记录/整定记录/tracker 四个 API，按时间合并排序。
- 统一在视图层，不在存储层新建表（详见 §6）。
- 支持按事件类型筛选、时间窗筛选。

#### 4.1.3 效果对比 Tab

- 选择该回路的两次整定任务（或整定前后），并排对比：
  - PID 参数（P/I/D）
  - 闭环响应曲线（PV/OP）
  - 综合评分变化
  - 诊断标签变迁
- 数据来自现有整定任务 + 评估快照 + 诊断结果，零后端改动。

### 4.3 诊断模块（职能轴·三区重构）

#### 4.3.1 列表页（回路为中心）

| 回路 | 诊断标签(徽章) | 置信度(进度条) | 严重度 | 发现时间 | 状态 | 操作 |
|---|---|---|---|---|---|---|

标签与置信度直接在列表显示（Glanceability），无需点进详情。操作含：详情（带 loopId）、发起整定（带 loopId）、Tracker。

#### 4.3.2 详情页三区重构

```
┌─ ① 结论区（顶部，一眼可见）─────────────────────────────────────┐
│ [标签徽章]  置信度 82%  严重度:中  发现于 2h 前                  │
│ 诊断小结(模板): "PV 振荡 0.05Hz，疑似阀门粘滞"                    │
│ [AI 洞察] ← 工具栏按钮（LLM 启用才亮，见 §5.2）                  │
├─ ② 问题定位路径区（可视化）────────────────────────────────────┤
│ 现象(PV振荡) ──→ 特征(振荡指数0.8/非线性0.6) ──→ 根因(阀门粘滞)  │
│ 横向流程图，节点可点展开证据                                      │
├─ ③ 证据区（可折叠，技术细节）──────────────────────────────────┤
│ 特征值表: 名称|值|阈值|工程含义（默认折叠）                       │
│ 波形/散点/频谱（默认折叠）                                        │
└──────────────────────────────────────────────────────────────┘
```

| 区 | 设计要点 | 后端影响 |
|---|---|---|
| ① 结论区 | 标签徽章+置信度+严重度+模板小结+AI 洞察入口 | 零（模板已存在） |
| ② 问题定位路径 | 横向流程图（现象→特征→根因），数据来自 evidenceChain | 零（前端渲染） |
| ③ 证据区 | 特征值表+可视化，默认折叠，带工程含义列 | 零 |

**问题定位路径设计约束**：先做简单横向流程（3-4 节点），不过度设计成复杂决策树；节点点击展开对应证据。数据全来自现有 evidenceChain，零后端。

#### 4.3.3 特征字典（内容工作）

为③区特征值提供"工程含义"列，需编写 ~20 项特征字典（非代码，内容工作）：

| 特征值 | 含义 | 工程意义 | 阈值参考 |
|---|---|---|---|
| oscillationIndex | 振荡指数 | PV 周期性波动强度，>0.5 提示存在振荡 | >0.5 异常 |
| stictionIndex | 粘滞指数 | 阀门静摩擦估计，>0.4 提示阀门粘滞 | >0.4 异常 |
| timeConstant | 时间常数 | 过程响应快慢，偏离期望值提示模型失配 | 与期望比值 0.7-1.3 正常 |
| ... | ... | ... | ... |

（完整 20 项在实施阶段补充，独立 JSON 配置，非硬编码）

### 4.4 整定模块（职能轴·单页整合）

#### 4.4.1 双入口

| 入口 | 位置 | 选回路方式 | 适用场景 |
|---|---|---|---|
| 实体轴入口 | 回路工作台 → "开始整定" | 回路列表全量可选 | "我在看回路 X，想整定它" |
| 职能轴入口 | 整定工作台 → "新建整定任务" | 弹出回路选择器（全量可搜索） | "我在整定模式，开始新任务" |

整定工作台的"待整定清单"是**推荐工作队列**（按评分/标签自动筛选），不是入口限制。

#### 4.4.2 整定任务详情单页

替代当前 3 页向导（model/algorithm/simulation），整合为单页 + 锚点导航：

```
┌─ 整定任务详情 ───────────────────────────────────────────────────┐
│ 顶部常驻: 回路信息 | 辨识可信度 | 当前 PID | [工具栏: AI(下线) |帮助] │
├─ 锚点导航: ①过程辨识 ②PID推荐 ③闭环仿真 ④方案确认 ─────────────┤
│                                                                  │
│ ① 过程辨识   [运行辨识] → G(s)=... | 阶次 | 可信度 A             │
│ ② PID 推荐   算法推荐 + 多组候选对比表                            │
│ ③ 闭环仿真   参数微调 + 响应曲线实时对比                          │
│ ④ 方案确认   确认建议 + 导出方案 + 风险与回退 + 留痕             │
└──────────────────────────────────────────────────────────────────┘
```

**安全边界**：第④步命名"方案确认"（不叫"定稿"避免误导为下写），仅输出建议+证据+风险+回退+留痕，**绝不直写 DCS**。

#### 4.4.3 流程对比

| 维度 | 现状 | 优化后 |
|---|---|---|
| 路由层级 | 5 层（workbench→flow→model→algorithm→simulation） | 2 屏（工作台选回路→任务详情单页） |
| 切换方式 | 整页路由切换，上下文靠 store 易丢 | 单页内锚点导航，上下文常驻 |
| PID 确认 | 分散在仿真页 | 独立第④步，强调"建议确认+留痕" |

### 5.2 AI 洞察右抽屉交互机制（核心技术规范）

#### 5.2.1 图标状态控制逻辑

AI 洞察图标受**两级独立门禁**控制，两级均通过才可交互：

**门禁 1（全局 LLM 门禁，用户明确要求）**：
- LLM 服务**未配置**（endpoint/apiKey/model 任一为空）→ 图标置灰，不可点击
- LLM 服务**已配置但未在系统设置启用**（`llm.enabled = false`）→ 图标置灰，不可点击
- LLM 服务**已完成配置且在系统设置启用**（`llm.enabled = true` 且配置完整）→ 通过门禁 1

**门禁 2（页面上下文门禁，场景相关）**：
- 场景需要 loopId 但未选中回路（如诊断/评估/回路场景）→ 图标置灰，tooltip"请先选择回路"
- 场景无需上下文（如监控全局场景）→ 通过门禁 2

| 门禁1 | 门禁2 | 图标状态 | tooltip |
|---|---|---|---|
| 未通过 | — | 灰显不可点 | "请先在系统管理配置并启用 LLM" |
| 通过 | 未通过 | 灰显不可点 | "请先选择回路" |
| 通过 | 通过 | 激活可交互 | "生成 AI 洞察" |

#### 5.2.2 图标激活条件（明确结论）

> **仅当 LLM 服务完成配置（endpoint + apiKey + model 均非空）且在系统管理—LLM 配置中显式启用（`llm.enabled = true`）后，且当前页面具备有效上下文（如已选回路），工具栏 AI 图标才显示为可交互激活状态。**

#### 5.2.3 交互行为定义

用户点击激活状态的 AI 图标后：

1. **展开形式**：从界面**右侧**以 **overlay（覆盖层）** 形式展开抽屉（非推挤式，主内容不被推）。
2. **动画时长**：展开/收起过渡动画**控制在 300ms 以内**，缓动函数 `cubic-bezier(0.16, 1, 0.3, 1)`（ease-out-quint），确保视觉过渡自然。
3. **遮罩**：抽屉外区域显示半透明遮罩（rgba(0,0,0,0.45)），点击遮罩或按 Esc 关闭。
4. **宽度**：默认 480px（响应式：窄屏 100%）。
5. **关闭**：遮罩点击 / Esc / 抽屉内关闭按钮，任一触发收起（300ms 内）。
6. **加载态**：展开后立即触发 `POST /ai-insight/{scene}`，加载中显示骨架屏，失败 fallback"诊断小结"模板。

**Ant Design 实现参数**：
```
<Drawer
  placement="right"
  :open="aiDrawerOpen"
  :width="480"
  :mask="true"
  :mask-closable="true"
  :body-style="{ padding: '16px' }"
  :root-style="{ '--drawer-transition': '300ms cubic-bezier(0.16,1,0.3,1)' }"
  @close="closeAiDrawer"
>
```

## 6. 历史记录与跨时段对比机制

### 6.1 现状

- 评估记录：`/assess/tasks`
- 诊断记录：`/diagnose/records`
- 整定记录：`/tune/records`
- action_tracker：跨职能处置生命周期表（PENDING→IN_PROGRESS→IMPLEMENTED）

问题：按职能分散存储，缺单回路聚合视图与跨时段对比。

### 6.2 方案：统一在视图层，不新建统一存储

| 层 | 机制 | 位置 | 后端影响 |
|---|---|---|---|
| 跨回路批量记录 | 保留各自记录页 | 评估/诊断/整定模块 | 零 |
| 单回路统一历史 | 处置时间线 Tab | 回路工作台 | 零（前端组合三源+tracker） |
| 跨时段对比 | 效果对比 Tab + 评估趋势 + 诊断标签变迁 | 回路工作台 | 零（前端组合） |

### 6.3 为什么不建统一事件存储

1. 现有三套任务/结果表 + tracker 已覆盖全部事件，新建统一 event store = 大后端迁移，违背"少改后端"。
2. 90% 需求是"单回路看历史 + 单回路做对比"，前端组合满足（3-4 个 API 并行，可控）。
3. tracker 本身已是跨职能生命周期表，时间线以它为骨架 + 补评估/诊断快照即可。
4. **唯一短板**：跨回路跨职能统计分析（如"全厂整定后诊断改善率"）需 N+1 调用或聚合端点——属 Phase 2 报表需求，非核心闭环，暂不做。若未来需要，加 `GET /loops/{id}/timeline` 聚合端点即可，不返工。

| 整定单页过长 | 中 | 体验差 | 锚点 Tab（非折叠），保留步骤语义 |
| AI 洞察依赖 LLM，离线无方案 | 中 | 功能降级 | "诊断小结"模板兜底，始终可用 |
| 问题定位可视化过度设计 | 低 | 返工 | 先简单横向流程，验证后再加交互 |
| 整定待整定清单前端组合性能 | 低 | 慢 | 监控点数；必要时 Phase 2 加聚合端点 |

## 12. IA 再收敛补充（2026-08-09）

Phase A-D 已完成后，基于回路工作台专项评估与用户场景复核，补充以下当前口径（以实现契约 v2.9 为准）：

1. **预警不设一级模块**：预警规则归配置 `/config/alert-rules`；预警事件归监控 `/monitor/alerts`，全局通知铃铛作为跨页面入口。旧 `/alert/*` 仅做兼容重定向，API 不迁移。
2. **回路工作台成为监控下的实体入口**：规范路径 `/monitor/loop-workbench`，左侧列表呈现跨回路 PV/SP/OP/模式/评分/可信度，右侧四区按概览→评估→诊断→整定提供单回路连续处置。
3. **监控与工作台合并方式**：合并一级导航与回路上下文，不把跨回路巡检和单回路深度处置强行合成一张普通表格。原 `/loop/monitor` 作为隐藏高密度表保留，用于批量巡检、导出和旧书签兼容。
4. **工作台边界**：每区最多摘要 + 1 个主图 + 明确动作；列表承担选择/优先级，完整证据留在对应职能模块或详情弹窗，避免超级页面膨胀。

以上补充已在前端路由、工作台组件、实现契约 v2.9、UI/UX v6.3 与整改清单 §4.1 同步。

**文档结束。Phase A→B→C→D 已实施；后续 IA 再收敛按第 12 节与现行实现契约执行。**
