## 三、经验教训

### 技术类

1. **同义/派生双字段是脱节之母**。`is_active`（布尔）与 `status`（三态派生）并存，写路径只更新一处——批量路径漏同步，数百行不一致累积数月才暴露。**教训：派生字段必须有唯一重算收口；新增任何写路径时，必答"派生字段谁维护"**。长期解：status 降级为读时派生（引用面 62 文件，需专项排期）。
2. **运行态开关必须有跨进程镜像**。多进程部署下，配置保存只更新处理请求的进程；订阅器 Leader 可能是另一个进程。signalr/writeback 有镜像键而 gap 漏了——补齐时漏一个。**教训：新增运行态开关，镜像机制是 checklist 必选项**。
3. **实时热路径禁止读回比对**。千万行点表上 write_events 的宽读比对两次把写入协程挂死。**教训：热路径写操作用 UPSERT 语义（TDengine 同键 INSERT 天然覆盖），对账/审计放离线路径**。
4. **批量与单条路径行为必须一致**。单条 PUT 会重算 status，批量不重算——同一业务两个入口行为分叉。**教训：同一业务的多个入口（单条/批量/API/脚本）要维护一份"行为一致性矩阵"并配对拍测试**。
5. **跨架构构建的退路是薄补丁镜像**。OrbStack amd64 模拟失败时，以生产运行镜像为底座、仅 COPY 改动文件（无 RUN 指令即无需模拟），配合产物 diff 校验，绕开整个构建问题。代价：APP_VERSION 等元信息需手动 ENV 覆盖。
6. **`.dockerignore` 的通配拦截是隐性地雷**：`**/dist` 连暂存目录里的 dist 都拦——构建上下文里的"绕行目录"要用不命中通配的名字。

### 协作类

7. **权威数据只认 API/SQL，截屏读数必须二次确认**。视觉接口在低分辨率工控截屏上多次编造细节（HDS 装置、"934 回路分布"、"江苏总部"均系幻觉）；zcode 自己的读屏也出现过 261/262 行误读。**所有结论以 API/SQL 查询为准，截图仅用于定位视觉元素**。
8. **ToDesk 键盘合成丢包是硬约束**：鼠标点击可靠、键盘长串必丢。**标准分工 = zcode 出命令 → 用户粘贴（GUI 复制可同步）→ zcode 读屏验证**；程序设置的剪贴板（pbcopy）不同步是另一坑。
9. **共享远程会话要打招呼**：用户与 zcode 同线操作时，屏幕内容突变 = 对方在动，先确认再继续，避免互相打架。
10. **公网 API 一旦可用，验证效率数量级提升**：/clpm/ 上线后，登录+GET 即可完成大部分检查（任务状态/排名/落库间接证据），不再依赖远程桌面逐条敲命令。

### 流程类

11. **只读纪律 + 每步确认**：发起方清单的"全程只读、一条一条粘贴、口令不落屏"三规则在共享会话下依然有效，是全程零事故的保障。
12. **审计日志是事后定责的铁证**：LOOP_BATCH_UPDATE 的 before/after 记录让"批量操作到底改了什么"无需猜测。
13. **检查报告即部署交接单**：报告附录 A/B/C 沉淀后，发起方可直接按单排期（镜像双打包、网关审批、安全三关）。
