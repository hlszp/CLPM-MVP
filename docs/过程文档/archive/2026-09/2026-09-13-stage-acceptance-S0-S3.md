## 1. 本档的读法（先读这段）

本次治理最重要的产出**不是**修了 18 个问题，而是**发现原评审清单的误诊率高达 4/10**，
且在执行过程中**我方自身也发生 2 次误判、2 次工具事故**，全部如实记录在案。

因此本档把"**已修属实 / 误诊 / 待裁决 / 未验证**"四类**严格分列**，
不做"整改完成率"之类会把误诊洗成成果的统计。

判读原则：
- 只有「已修属实」且「有修复前失败证据 + 行为测试 + 集成证据」的条目才计为已修复；
- 「误诊」条目**不是**我方成果，其价值在于**阻止了错误整改**；
- 「待裁决」条目**不得**视为已完成，也不得由执行方自行拍板；
- 「未验证」条目如实标注，不假设其成立。

## 9. 方法论沉淀（本次治理的可复用产出）

1. **先定位事实来源，再动手**：算法条目必须先找到国标/设计文档/规格章节；三项误诊全部源于跳过此步。
2. **"现象复现"不等于"缺陷成立"**：误诊的推理都能复现现象，错在定性。
3. **守卫要验数值，不能只验调用**：可信度统一 Phase 1 的三链一致性守卫是 `inspect.getsource` 结构性断言，R14-2 把口径重新劈开时它**保持全绿**——这是该缺陷潜伏一个月的直接原因。
4. **不可达分支要实测**：条件数、R² 这类"阈值门控"必须用实测确认分支可达；本次两侧各出现一次（stiction R² 门是真的死代码、PE 条件数门是真的可达）。
5. **未经验证的修复比已知缺陷更危险**：G27#1 首版修法验证失败后选择回退并保留原实现，而非带着未验证改动上线。
6. **不自造规格**：需要阈值/语义决策时登记待裁决，不擅自选定数值。

## 13. G37 状态机无锁：**已确认，本轮未修**（附完整定性与修法）

### 13.1 事实核实（实跑，非引述）

| 检查 | 结果 |
|---|---|
| `handling.py` 中 `with_for_update` | **0 处** |
| 全仓 `with_for_update` 分布 | 仅 3 处，全部在 `app/services/process_model_version.py` |
| `_get_order_or_404`（`handling.py:305-312`） | 普通 `select(...).scalar_one_or_none()`，**无锁** |

### 13.2 TOCTOU 机制（以"开工"为例，`handling.py:1176-1198`）

```
order = await _get_order_or_404(db, order_id)      # 无锁 SELECT
if order.status not in ("PENDING", "REOPENED"):    # 基于【读到的值】的守卫
    raise _err_order_state(order, "开工")
...
order.status = "EXECUTING"                          # 无条件写
await db.commit()
```

并发下两个"开工"请求可**同时读到 PENDING、同时通过守卫、同时写 EXECUTING**。
守卫与写入之间没有原子性保证——**状态机约束是可被绕过的**。

### 13.3 受影响的迁移站点（约 8 处）

| 行 | 迁移 | 守卫条件 |
|---|---|---|
| 1176 / 1198 | → `EXECUTING`（开工） | `status not in ("PENDING","REOPENED")` |
| 1248 | → `VERIFYING`（提交验证） | 需查读值 |
| 1292 | → `CLOSED` / `REOPENED`（验证结论） | `verifyResult` 分支 |
| 1316 | → `CANCELLED`（取消） | 需查读值 |
| 633 / 657 / 677 | 建议 → `ACCEPTED`/`REJECTED`/`IGNORED` | 需查读值 |
| 737 | → `CONVERTED` | 需查读值 |
| 391 | `rec.status = status` | 待定（需查上下文） |

### 13.4 为什么这不是风格问题

这是**数据正确性**问题：并发下处置工单的状态可被写坏（重复开工、跳过验证、
已关闭工单被改回 reopened），且**守卫给出的错误提示会与实际发生的状态迁移矛盾**。
在与 G23/G27 同级的"可信度"主题下，它属于"**状态终态不可信**"这一类
（S4 的 G28~G32 处理的正是"任务终态不可信"，本项是同一主题在业务状态机上的体现）。

### 13.5 应有的修法（本轮未实施）

1. 增加**加锁读**变体（如 `_get_order_for_update_or_404`，查询加
   `with_for_update()`），**不要**直接给 `_get_order_or_404` 加锁——
   它被只读 GET 端点共用，会给读路径也加行锁、损害并发；
2. 上述约 8 个**状态迁移**站点改用加锁变体（只读端点不动）；
3. 真实 PG 上做**并发回归**（SQLite 会忽略 `FOR UPDATE`，在 SQLite 上写此测试
   会**假绿**——必须用真 PG，参照既有 `*_real_pg_g*.py` 的做法）。

### 13.6 本轮未修的理由（如实说明）

- 改造涉及 8 个端点 + 新增锁变体 + **真实 PG 并发测试**，在当前剩余预算内
  **无法完成完整证据链**（修复前失败证据 → 修复 → 行为测试 → 集成证据 → 残余风险）；
- 给状态机留下**未经验证**的锁改动，风险高于留下**已完整定性**的缺陷——
  死锁、事务边界变化、只读路径被误加锁，任一都可能比原缺陷更难排查；
- 与 §25/G27#1 的处置一致：**未验证的修复不上线**。

### 13.7 残余风险与移交

- 缺陷**仍在生产路径上**（并发下状态机约束可被绕过）；
- 移交所需材料已齐备：受影响站点清单（§13.3）、修法（§13.5）、
  测试注意点（SQLite 假绿）；
- **切勿**只加锁不加并发测试——那样会得到一个"看起来修好了"但无法证明的改动，
  正是本次治理反复识别的那类问题。
