# 宽表（st_loop_data）退役清理方案（2026-09-25）

> 触发：生产趋势/评估/诊断读不到历史数据（数据在点表、读取路由按 legacy 读已退役的宽表）。
> 目标：把"宽表"这条已退役链路从**读取、写入、结构、数据**四个层面彻底清理，全部收敛到点表 `st_point_data_v1`。
> 纪律：分三阶段，每阶段独立跑门禁；**数据删除（S3）必须单独授权**。

## 一、检查结论（先回答"是否需要改读取路径"）

**结论：趋势、评估、诊断、整定、预警的读取链路已经是点表口径，不需要改读路径。**证据：

| 链路 | 实现 | 读哪张表 |
|---|---|---|
| 算法数据组装 | `app/services/data_source/logical_wide_builder.py`（文件头声明"**唯一**从 `st_point_data_v1` 组装算法数据的实现"） | 点表 |
| Provider（13 处 `get_provider()` 调用） | `tdengine_provider.py` → `build_logical_wide` | 点表（该文件内**零** `st_loop_data` 引用） |
| 趋势 | `trend_service.py:377` point 快路径 + Provider 兜底 | 点表 |
| KPI/评估 | `kpi_calc.py:2129` | 点表 |
| 诊断 | `diagnosis_engine.py:471/677`、`diagnosis_orchestrator.py` | 点表 |
| 整定/预警/波形 | `tuning.py:313`、`alert_rule_engine/evaluator.py`、`tags.py:386` | 点表 |
| 历史导入 | `data_import.py:660`（`storage_mode = "point"`，注释写明"宽表已退役"） | 点表（写） |
| 实时采集 | `realtime_subscriber.py`：point/shadow 写点表；**legacy 仍写宽表** | 点表 + 宽表（遗留写） |

真正遗留的只有两件事：**① 实时路径在 legacy 模式下仍往宽表写；② 宽表的写入代码、函数、DDL 与监控分支没删**。

### 不能删（易误伤）

- **`logical_wide_builder.py`**：名字含 "wide"，但它是**新的点表组装器**，删了等于把算法数据源拆了。
- **`point_history_repository.py` / `point_history_writer.py` / `st_point_data_v1`**：目标形态。
- **`history_layout_manifest` 路由机制**：若保留"按窗口切布局"的能力则保留；**若确认读侧只剩点表，可一并删除**（需你决策，见 §五）。

## 三、数据处置（S3，不可逆，需单独授权）

**风险**：切到 point 模式之前，实时数据**只写宽表**。宽表可能持有那段时间的唯一副本。

先取证（生产，只读）：

```powershell
docker compose -f docker-compose.prod.yml exec -T tdengine taos -s "SELECT COUNT(*), FIRST(ts), LAST(ts) FROM clpm_ts.st_loop_data;"
docker compose -f docker-compose.prod.yml exec -T tdengine taos -s "SELECT COUNT(*), FIRST(ts), LAST(ts) FROM clpm_ts.st_point_data_v1;"
```

| 结果 | 处置 |
|---|---|
| 宽表时段 ⊆ 点表时段 | 可直接 `DROP STABLE clpm_ts.st_loop_data` |
| 宽表有点表没有的时段 | **先归档**（`taosdump` 导出或 CSV）或迁移进点表，再删 |
| 宽表为空 | 直接 `DROP STABLE` |

> 删除前建议先 `taosdump -D clpm_ts -o <备份目录>` 整库备份一次。

## 四、执行计划（分阶段 + 门禁）

| 阶段 | 范围 | 门禁 | 数据动作 |
|---|---|---|---|
| **S1 写入收敛** | 删 `realtime_subscriber` 宽表写路径与 legacy 分支；实时只写点表；删除 `_writeback_enabled` 的宽表语义 | ruff + pytest 全绿；本地重启后点表持续增长、宽表零写入 | 无 |
| **S2 依赖清理** | `tdengine_native` 宽表函数与 4 处外部调用改点表；`data_link_monitor` 简化；文案与自检收敛；DDL 去 `st_loop_data` | ruff + pytest + 前端 typecheck/vitest；契约对账 0；趋势/评估/诊断三条链路本地实测 | 无 |
| **S3 结构与数据** | 生产 `DROP STABLE`（+ 归档） | S3 前的取证结论 + 你的书面确认 | **不可逆** |

## 五、需要你决策的两点

1. **`history_layout_manifest` 路由是否保留？** 保留 = 未来仍可按时间窗口切换读取布局（多一层复杂度）；删除 = 读取恒点表，代码更简单，但失去回退能力。我的建议：**保留机制但把默认值改为"无 manifest 即 point"**，这样既简化又保留回退。
2. **`storage_mode` 三态（legacy/shadow/point）是否收敛为单态？** 建议收敛为单态（不再有 legacy 写入），`sys_config` 键保留但仅作展示，避免现场再被误导。

## 六、风险与回退

- S1/S2 只改代码，回退 = `git revert`；不涉及数据。
- S3 删除宽表后无法回退（除非有 `taosdump` 备份），因此**必须**先归档。
- 清理期间保持点表写入不受影响：S1 只删宽表分支，不触碰点表写入路径（`PointHistoryWriter`）。
