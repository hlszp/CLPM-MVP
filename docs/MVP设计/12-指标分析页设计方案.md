# 指标分析页设计方案（评估模块第 5 页）

| 项 | 内容 |
|---|---|
| 日期 | 2026-08-25 |
| 状态 | 已实施（M1/M2/M3 全部落地，2026-08-25；验收证据见 §11 修订记录） |
| 来源 | 评估模块系统性反思 Quest 延伸讨论（指标维度横切分析的管理价值评估） |
| 决策口径 | 不做"每指标一张散图"，做"一套骨架服务多指标"；综合评分不设专题（与总览重复） |

---

## 1. 背景与动机

现有评估模块均为**回路维度（纵切）**视角（"这个回路怎么样"），缺少**指标维度（横切）**视角（"这个指标全厂怎么样"）。管理者（SPONSOR/装置负责人）的核心问题——"哪类问题系统性存在？弱在哪套装置？资源投向哪里？"——现有页面只能靠逐装置点开或逐回路排序回答。

现状缺口矩阵：

| 能力 | 现状 |
|---|---|
| 单指标全厂均值 | ✅ 总览仪表盘已有 |
| 单指标时间趋势 | ✅ 总览趋势图已有 |
| 单指标最差回路排行 | ❌ 仅综合评分有（TOP5/低效排行） |
| 单指标×装置对比 | ❌ 明细表是均值并列，不能"按某指标找最差装置" |
| 单指标分布形态 | ❌ 暂缓（回路规模 <100 时信息量薄，触发式启动） |

## 2. 设计定位与四层职责

指标分析页补齐第三个认知视角，并顺势显式化评估模块四层职责（F-EVAL-002 的正面回答）：

| 页面 | 认知层次 | 回答的问题 | 视角 |
|---|---|---|---|
| 性能总览 | 发现（30 秒） | "整体怎么样？" | 全厂快照 |
| **指标分析（新）** | **定位（5 分钟）** | **"哪类问题系统性存在？弱在哪套装置？"** | **指标横切** |
| 回路性能 | 分析（逐个） | "哪些回路差？具体指标？" | 回路明细 |
| 评估记录/评估任务 | 支撑 | "历史快照在哪？评估跑了吗？" | 档案/执行 |

## 3. IA 变更

### 3.1 菜单树（评估 4 页 → 5 页）

```
评估（order:2）
├─ 性能总览   /metric/pid-dashboard          （不变）
├─ 指标分析   /metric/indicator-analysis     （新增，插位第 2）
├─ 回路性能   /metric/loop-performance       （不变）
├─ 评估记录   /metric/history                （不变）
└─ 评估任务   /metric/tasks                  （不变）
```

- 插位第 2 的理由：管理者动线"总览→指标分析"相邻；工程师动线"回路性能→诊断"不受干扰。
- 路由：name `AssessIndicatorAnalysis`，icon `lucide:bar-chart-3`，leaf 路径遵循 `/metric/*` 稳定策略。
- 权限：ADMIN / IC_ENGINEER / PE_ENGINEER / SPONSOR（与总览一致；EXPERT 不可见，对齐 F-EVAL-003 固化口径）。
- 深链：`/metric/indicator-analysis?metric=auto_mode_rate&plantNodeId=&window=last_24_hours`，URL 为真相源、可分享、可从总览跳入。

## 4. 页面架构（页型：分析工作台）

```
┌─ 控制条：指标选择器 │ 时间窗(8h/24h/168h/30d) │ 工厂节点 │ 适用性过滤(默认开)
├─ A 指标概览卡：全厂均值 + 参评回路数 + 最差装置名（3 个数字，非仪表盘墙）
├─ B TOP10 排行：横向条形图，最差优先；fitness L0/L1 中性灰排除；条形点击→回路工作台
├─ C 装置对比：节点级横向条形（按所选指标均值排序），点击装置→下钻该节点
└─ D 行动清单：TOP N 回路明细表格（ClpmLoopLink 位号 + 指标值 + MODE + 可信度 + fitness），
   行内直达诊断/整定 —— "图表给结论，表格给行动"
```

设计约束（冷静界面）：一张结论性图表 + 一份行动清单，不做仪表盘堆砌；图表颜色复用 use-loop-palettes / use-clpm-theme 既有预设。

## 5. 一期指标集（6 个）

| 指标 | 后端 sort key | 最差方向 | 说明 |
|---|---|---|---|
| 自控率 | `auto_mode_rate` | asc（低在前） | **默认**；合规第一指标，管理抓手 |
| 准确率 | `accuracy_rate` | asc | 整定收益直接预测因子 |
| 快速率 | `fast_rate` | asc | 已支持 |
| 平稳率 | `steady_rate` | asc | 已支持 |
| 好值率 | `good_value_rate` | asc | 已支持 |
| 综合评分 | `score` | asc | 即 TOP5 页面化，兼容旧习惯 |

- 指标元数据 `METRIC_META` 集中声明（key/label/unit/worstOrder/说明），前端单一定义点；未来加入"越高越差"指标（如振荡率）在 worstOrder 字段扩展。
- 明确不做：综合评分专题分析（与总览重复）、评分构成分析（属详情抽屉下钻）、分布直方图（触发式：回路规模 >100）。

## 6. 数据依赖与 API 变更

| 能力 | API | 现状 | 动作 |
|---|---|---|---|
| 单指标回路排行 | `GET /api/v1/performance/ranking` | 支持 score/steady_rate/good_value_rate/fast_rate + 节点/时间窗/limit≤100 | **M1 扩白名单**：+accuracy_rate/auto_mode_rate（effective_auto_rate 视快照列名同批评估）；返回体若缺 autoModeRate/accuracyRate 字段则补 |
| 装置对比 | `GET /api/v1/node-performance/ranking` | 支持 score/steady_rate/auto_loop_ratio/effective_auto_rate | M2 直接使用；accuracy_rate 装置维度缺列则一期装置对比仅对可用指标开放（前端按 METRIC_META 声明能力位） |
| 适用性过滤 | ranking 返回 fitnessLevel/includeInEvaluation | 已返回 | 前端过滤（与 TOP5 现状一致）；后端过滤参数留触发式 |
| 前端类型 | `#/api/metric` RankingItem | — | M1 补字段类型 |

实施前必须核实：`KpiSnapshotHourly` 实际列名（auto_mode_rate vs autoModeRate）、`get_ranking` 返回 dict 的字段拼写（前端 pid-dashboard 消费 camelCase，需确认转换层）。

## 10. 风险与控制

| 风险 | 控制 |
|---|---|
| 快照列名/返回字段拼写与预期不符 | M1 首步核实 `KpiSnapshotHourly` 模型与 ranking 返回构造，再定字段清单 |
| ranking limit≤100 截断导致 fitness 过滤后不足 TOP10 | 当前回路规模 <100 可接受；文档记录触发条件（规模 >100 时后端加 fitness 过滤参数） |
| 页面信息密度超标（冷静界面红线） | 四区块固定骨架 + 单指标单屏；不叠加仪表盘墙 |
| 与总览职责再交叉 | 指标分析=横切定位，总览=快照发现；M3 只加"跳转入口"不搬数据 |
