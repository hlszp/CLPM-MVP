## 1. 背景与目标

### 1.1 重设计动机

MVP 精简时诊断模块被整体屏蔽（后端注释保留、前端物理删除）。现需重新建设诊断功能，但**不沿用原设计**，原因与方向：

| 原设计问题 | 本设计对策 |
|---|---|
| 5 页结构（总览/回路分析/任务/详情/跟踪）动线冗长、信息重叠 | 两页式：诊断工作台（发起+结果一体）+ 诊断记录 |
| 8 类标签按"现象"分类（振荡/粘滞/过激…），用户拿到结果仍不知道"该找谁、干什么" | 结果按"原因/处置方向"分类（参数问题、仪表问题等） |
| 全量算法一次性丢入单一 D-S 融合器，跨族证据互相稀释 | 族内融合 + 分类决策表 |
| 全闭环（Action Tracker 7 态状态机）对 MVP 偏重 | 只诊断 + 建议，处置在线下进行 |

### 1.2 核心决策清单（已确认）

| # | 决策项 | 结论 |
|---|---|---|
| 1 | 闭环深度 | **只诊断 + 建议**，不做线上处置跟踪（不恢复 Action Tracker） |
| 2 | 触发方式 | **仅手动触发**（不做评分阈值自动预诊、不做定时体检） |
| 3 | 页面形态 | **一级模块「诊断」**（菜单第 3 位，监控→评估→诊断→配置→系统）+ 回路工作台「发起诊断」入口 |
| 4 | 结果分类 | **按原因/处置方向分类**，6+1 类体系（见 §3） |
| 5 | 算子架构 | **元算子 = 无状态纯函数 + 自描述元数据**，注册表统一管理，为 AI 诊断智能体预留 |
| 6 | 输出形式 | 页面查看 + 列表 CSV 导出（不做 PDF 建议书） |
| 7 | 页面结构 | 方案 A 两页式：诊断工作台 + 诊断记录 |

## 2. 产品定位与范围

### 2.1 定位

诊断 = 回路性能问题的**定性归因工具**：

```
评估发现问题（评分差/指标异常） → 诊断回答"为什么、归哪类、怎么办" → 处置在线下进行
```

诊断是"针对一个回路的分析动作"，天然发生在回路上下文中；一级模块保证功能完整性与历史可追溯，工作台入口保证动线最短。

### 2.2 范围内

- 手动发起：选回路（单个/批量）+ 时间窗 + 算子组
- 异步执行：细粒度进度可见，证据波形快照落库
- 结果呈现：原因分类（主/次/待复核）+ 症状标签 + 证据链 + 处置建议
- 历史管理：诊断记录列表、筛选、CSV 导出、抽屉查看详情
- 算子阈值配置（复用原四级阈值覆盖机制：回路>装置>类型>全局）

### 2.3 范围外（非目标）

| 项 | 说明 |
|---|---|
| Action Tracker 处置闭环 | 不做线上建单/状态机/效果验证 |
| 自动触发 | 不做评分阈值预诊、定时全回路体检 |
| PDF 诊断建议书 | 不做（原 reportlab 异步生成能力保留在代码中不启用） |
| AI/LLM 诊断 | 本期不做，仅做架构预留（§10.2） |
| DCS 参数下写 | 平台安全边界不变：只输出建议，不动 DCS |

## 3. 结果分类体系（7+1 类）

### 3.1 分类定义

| # | 分类代码 | 分类名 | 处置方向 | 期次 |
|---|---|---|---|---|
| 1 | `TUNING` | 参数问题（PID 整定不当） | 重新整定参数 | Phase 1 |
| 2 | `VALVE` | 阀门/执行机构问题 | 检修/更换配件 | Phase 1 |
| 3 | `INSTRUMENT` | 仪表/测量问题 | 校验/维护 | Phase 1 |
| 4 | `COMMUNICATION` | 通信链路问题 | 检查通信链路 | Phase 1（2026-08-17 增补） |
| 5 | `PROCESS` | 工艺/外扰问题 | 工艺分析/前馈/解耦 | Phase 1（Phase 2 算子强化） |
| 6 | `UTILIZATION` | 投用/操作问题 | 恢复自动投用/管理措施 | Phase 1 |
| 7 | `DESIGN` | 组态/设计问题（阀门选型、量程组态） | 重新组态/改造 | Phase 2 |
| 8 | `DATA_INSUFFICIENT` | 数据不足/无法判定（兜底） | 先补数据/人工分析 | Phase 1 |

**两层设计**：算法层保留**症状标签**（机器输出，9 类症状：OSCILLATION/VALVE_STICTION/OVERAGGRESSIVE/OVERCONSERVATIVE/EXTERNAL_DISTURBANCE/QUALITY_ABNORMAL/LINK_ABNORMAL/OUTPUT_SATURATION/MANUAL_REVIEW），呈现层做**原因分类**（人看的）。算法可解释性不受损，用户拿到的是"该找谁、干什么"。

> 原设计 8 类标签中 `MANUAL_REVIEW` 由 `DATA_INSUFFICIENT` 语义化升级替代。
>
> **COMMUNICATION 增补（2026-08-17）**：质量码算子（Q001-Q005）从 sensor 族拆出为独立 **link 族**（症状 `LINK_ABNORMAL`）。判定依据：连续 Bad 断流段（Q001）+ 最长连续 Bad 点数 + Bad 占比 + 落库缺口率（>10% 作佐证）。与 INSTRUMENT 的分工：**链路断流（信号中断）→ COMMUNICATION；测量值本身异常（冻结/漂移/噪声）→ INSTRUMENT**。决策优先级"先通信后仪表"（工业排查惯例），且 COMMUNICATION 污染下游全部波形类分类（仪表/阀门/工艺/参数）——断流期间波形结论全部失真。

### 3.2 算子盘点与缺口

现有引擎（`backend/app/tasks/diagnosis_engine.py`，174KB 单体）11 个算法对 4 类主分类的覆盖：

| 目标分类 | 已有算子 | 覆盖度 |
|---|---|---|
| 参数问题 | 阶跃响应分析（超调/衰减比/Harris）、响应迟缓检测（IAE 累积/收敛时间） | 充分 |
| 阀门/执行机构 | 椭圆拟合粘滞、Choudhury NGI/NLI、Kano 统计法、OP 限位统计 | 充分 |
| 仪表/测量 | 传感器故障三子检测（卡死/噪声突增/漂移，含 SP 同向排除） | 充分 |
| 通信链路 | 质量码规则（Q001 连续断流分级 + 断流段定位，落库缺口率佐证） | 充分 |
| 工艺/外扰 | 偏差突变检测（频次统计） | 偏弱 |

缺口算子（Phase 2）：

| 算子 | 价值 | 启用 |
|---|---|---|
| 振荡传播/振荡源定位（多回路同频，NiP 非整数周期） | 区分"自身振荡（参数）vs 外部传入（工艺）"的分水岭，替代当前排除法 | 强化 PROCESS |
| 阀位分布分析（长期 <10% 或 >90%） | 区分"阀门坏了检修" vs "选型不当改造" | 启用 DESIGN |
| 滞环/间隙检测（定位器 backlash） | 阀门类子型细化 | VALVE 细化 |
| 积分饱和判定（饱和+偏差持续） | OP 饱和归因细分：参数 vs 阀容量 | 归因细分 |

**投用/操作分类 Phase 1 即可用**：分类映射层直接读 KPI 快照 `effective_auto_rate`（每小时持续落库），无需新算子。

## 4. 总体架构

### 4.1 后端分层

```
┌─ API 层 endpoints/diagnosis.py（重写，5 端点）──────────────┐
│ POST /diagnosis/run        发起诊断（异步任务）                 │
│ GET  /diagnosis/runs       诊断记录列表（筛选/分页）             │
│ GET  /diagnosis/runs/{id}  诊断详情（算子结果+证据链）           │
│ GET  /diagnosis/operators  算子注册表元数据（前端+AI 共用）       │
│ GET  /diagnosis/export     记录 CSV 导出                       │
│ （复用现有 GET /tasks/{taskId} 任务进度轮询）                    │
├─ 编排层 services/diagnosis_orchestrator.py（薄编排）───────────┤
│ DataPlanner 取数 → 数据门禁 → 并行执行元算子                     │
│ → 族内 D-S 融合 → 原因分类映射 → 结果落库                       │
│ （TaskTracker 分阶段进度上报）                                  │
├─ 算子层 services/diagnosis_operators/（无状态，核心资产）────────┤
│ base.py            算子契约 + 注册表 Registry                   │
│ oscillation_*.py / stiction_*.py / sensor_fault.py / ...       │
│ classification.py  症状→原因分类映射（纯函数）                    │
├─ 数据层 ──────────────────────────────────────────────────┤
│ 新表 diagnosis_run（一次诊断一条完整结论）+ alembic 迁移          │
│ 旧 diagnosis_result 等 7 张表原样保留不动                       │
└──────────────────────────────────────────────────────────┘
```

### 4.2 数据流

```
发起：诊断工作台 / 回路工作台「发起诊断」按钮（带回路上下文跳转）
  ↓
POST /diagnosis/run → 即时校验（回路存在/tag 齐全/时间窗合法）→ 创建 Celery 任务（TaskTracker）
  ↓
编排器：本地 TDengine 取数（DataPlanner 统一入口）
  → 数据门禁（消费已有质量结论，见 §4.3）
  → 并行执行元算子（11 个）
  → 族内 D-S 融合 → 分类决策表 → 污染链降级 → 建议生成
  → 落库 diagnosis_run（含波形快照）
  ↓
前端轮询任务进度（细粒度阶段）→ 完成后渲染结果区
  ↓
诊断记录页：历史检索 / 筛选 / 导出 / 抽屉查看详情
```

### 4.3 数据质量三层职责（设计澄清）

数据质量**不是诊断时才监测**，诊断时做的是两件不同性质的事：

| 层 | 时机 | 动作 | 性质 |
|---|---|---|---|
| 1. 入库层 | 实时 SignalR → TDengine | 原样保存原始值 + 源侧质量码（Good/Bad/Uncertain），不做有损加工 | 轻量保全 |
| 2. 日常监测层 | 评估链路每小时自动 | kpi-calc-hourly 全量预处理+质量统计（good_value_rate/valid_rate/可信度 A-E 落库）；每日完整性巡检 loop_integrity_snapshot | 监测主体（MVP 已有） |
| 3. 诊断层 | 诊断执行时 | ① **数据门禁**＝查询第 2 层已有质量结论，判断该时间窗数据能否支撑诊断（消费结果，非重新监测）；② **面向算子的数据加工**＝按算子需要做适配（去趋势、降采样、有效性掩码） | 消费结论 + 数据整形 |

**预处理不在入库时做的理由**：① 原始数据保全（诊断证据需原始波形，预处理有损）；② 不同算子需要不同加工（FFT 去趋势 vs 粘滞检测保留 OP 跳变）；③ 实时链路轻量原则（高频写入不跑重检测）；④ 预处理参数演进后读时加工立即生效、可回溯。

### 4.4 关键架构决策

| # | 决策 | 理由 |
|---|---|---|
| 1 | 新建 `diagnosis_run` 表，不复用旧 `diagnosis_result` | 旧表"一行一标签"语义 vs 新设计"一次运行一条完整结论"，语义不匹配；旧表数据按 MVP 约束原样保留 |
| 2 | 旧引擎 `diagnosis_engine.py` 保留不删、继续不注册 | 新算子层从中**等价迁移**算法逻辑（带新旧对照回归测试）；回滚安全 |
| 3 | 算子契约不含诊断特有假设 | 评估计算器（metric_calculator，20+ 独立计算器）已是同构形态，二期可迁入同一注册表，形成"评估+诊断+整定"统一算子平台（§10.2） |
| 4 | 波形证据快照自包含落库 | 诊断结论可追溯：历史详情不依赖重查 TDengine（数据可能已覆盖/变化），保证"看到的证据=下结论时的证据" |

## 5. 元算子契约

### 5.1 契约定义（`services/diagnosis_operators/base.py`）

算子 = 无状态纯函数 + 自描述元数据，装饰器绑定：

```python
@dataclass(frozen=True)
class OperatorMeta:
    name: str                     # 唯一标识，如 "stiction_ellipse"
    display_name: str             # 中文名："椭圆拟合粘滞检测"
    family: str                   # 算子族：oscillation/stiction/sensor/tuning/disturbance/saturation
    description: str              # 一句话原理（人读 + AI 读）
    required_signals: list[str]   # 输入契约：["pv","op"] 等
    min_sample_rate: float        # 最低采样率要求
    outputs_schema: dict          # 输出特征定义（名/类型/工程含义）
    threshold_schema: dict        # 可配参数 + 默认值 + 范围
    symptom_tags: list[str]       # 命中时产出的症状标签（原 8 类症状体系）
    enabled_by_default: bool

@dataclass
class OperatorInput:              # 编排器组装，算子不得自行取数
    loop_id: str
    signals: dict[str, np.ndarray]   # pv/sp/op/mode 时间序列
    timestamps: np.ndarray
    meta: dict                       # 量程/工程单位/实际采样率
    kpi_context: dict | None         # KPI 快照只读上下文（auto_rate 等）

@dataclass
class OperatorResult:
    operator: str
    executed: bool                   # False = 输入缺失/数据不足跳过
    skip_reason: str | None
    detected: bool                   # 是否命中
    confidence: float                # 0~1
    features: dict                   # outputs_schema 实例化（特征值）
    evidence: list[EvidenceItem]     # 特征名/实测值/阈值/判定结论
```

**注册表**：`OPERATOR_REGISTRY: dict[str, OperatorMeta]` + `@operator(meta)` 装饰器。`GET /diagnosis/operators` 直接序列化输出——前端算子选择与 AI 智能体工具目录共用。

### 5.2 无状态纪律（架构红线）

1. 禁止 import DB/Redis/session，禁止全局缓存——纯 numpy 计算
2. 可调参数全部经 `threshold_schema` 注入；阈值四级覆盖（回路>装置>类型>全局）复用现有 `diagnosis_threshold` 服务
3. 确定性：同输入必同输出（单测与 AI 编排的前提）

## 7. 融合与分类映射

### 7.1 族内 D-S 融合（与原设计的关键差异）

```
同族算子（如 3 个粘滞算子）→ 族内 D-S 融合 → 族级置信度
全部族级结果（症状集合）→ 分类决策表 → 原因分类
```

原设计把全部 10+ 算子丢进单一融合器；本设计仅**族内融合**。理由：D-S 适合"同一假设的多证据"聚合（3 个算子交叉验证"是否粘滞"有意义）；跨族融合把不相关证据搅在一起（振荡证据和仪表证据融合出的数字无物理含义）且互相稀释。

融合公式沿用原实现：`C_fused = (Π cᵢ) / (Π cᵢ + Π (1-cᵢ))`，等价迁移为纯函数。族内证据完全冲突时融合置信度趋近 0.5，按低置信处理。

### 7.2 分类决策表（初始规则，优先级自上而下，命中即定主因）

| 级 | 条件 | 主分类 | 判定依据示例（给人看的） |
|---|---|---|---|
| 0 | 数据门禁不过（有效点数不足/可信度 E 级/断点 >30%） | DATA_INSUFFICIENT | "有效数据率 43%，低于诊断门槛" |
| 1 | 仪表族命中（sensor_fault 卡死/噪声/漂移任一，或 quality_code_rules 命中） | INSTRUMENT | "PV 存在 2.1h 连续冻结段" |
| 2 | 粘滞族融合置信 ≥0.7（≥2 算子命中） | VALVE | "椭圆拟合+NGI/NLI 双命中，粘滞指数 1.8%" |
| 3 | OP 长期贴限（>80% 时间） | VALVE | "OP 98% 时间贴上限，疑阀容量不足" |
| 4 | 外扰命中，或（振荡且无粘滞且无过激） | PROCESS | "偏差突变 8 次/h 且与 SP 变更无关" |
| 5 | 过激/过保守命中 | TUNING | "超调 35%、衰减比 0.6" |
| 6 | 自动投用率 <50% | UTILIZATION | "自动投用率 31%，长期手动" |
| 7 | 兜底：全部低置信（各算子置信均 <0.5） | DATA_INSUFFICIENT | "各算子置信度均 <0.5" |

**优先级设计原则**（三条工程经验）：

1. **数据可信优先于一切**——数据不可信时后续判定无意义
2. **仪表 > 阀门 > 参数**——测量失真会污染下游所有判定；阀门粘滞的经典表现就是限幅振荡，极易误诊为参数过激（先排除阀门再动参数，否则白整定）
3. **外扰优先于参数**——先排除外因再整定内因

决策表配置化后置（Phase 1 硬编码 + 单测全覆盖，Phase 2 视需要迁入配置）。

### 7.3 证据污染链机制

**分类优先级顺序本身就是证据污染方向**：

```
仪表 ──污染──> 阀门 / 外扰 / 参数    （PV 信号失真 → 下游全部判定失真）
阀门 ──污染──> 参数                  （粘滞引起限幅振荡 → 超调/衰减比失真）
外扰 ──污染──> 参数                  （扰动污染阶跃响应特征）
投用 = 独立维度（来自 MODE 统计，与 PV 证据无关，不参与污染）
```

例：仪表故障 + 参数过激同时命中——参数判定依据的超调量是从 PV 算的，而 PV 正处故障状态，该超调量本身不可信。两者**不是平等并列的两个问题**，而是"真问题 + 被污染的疑似问题"。

**结果分级三层次**：

| 层级 | 进入条件 | 展示方式 |
|---|---|---|
| 主分类 primary | 决策表最高优先级命中，唯一 | 大卡：分类名+置信度+严重度+处置方向一句话 |
| 次分类 secondary | 其他命中且**不被主因污染**（≤2 个） | 普通 chip 并列 |
| 待复核 pending_review | 命中但位于主因污染链下游 | 灰色虚线 chip + "需复诊"标记，hover 显示污染原因 |

数据结构：

```python
@dataclass
class CategoryJudgement:
    category: str
    confidence: float
    basis: list[str]
    status: str            # primary | secondary | pending_review
    contamination_note: str | None   # 被污染原因说明（pending_review 时必填）
```

污染链为声明式配置 `CONTAMINATION_MAP`（非硬编码 if-else），Phase 2 新增算子/分类时只需登记污染关系。

**粒度说明（MVP 简化）**：污染按**分类粒度**声明（如仪表命中→阀门分类整体降级待复核），不区分个别阀门证据是否恰好基于 OP 信号（OP 不受 PV 故障污染）；证据级精细化污染判定后置到 Phase 2。

**MVP 简化**：不做"剔除故障时段后复算"（仪表故障仅占时间窗小部分时理论上可剔除复算，但时段对齐/采样率补偿复杂度高）。统一走"待复核 + 复诊"，Phase 2 再优化。

### 7.4 处置建议排序规则（固定）

| 规则 | 内容 |
|---|---|
| R1 | 主分类建议置顶，标"优先处置" |
| R2 | **投用前置**：投用/操作命中且自动投用率 <30% 时，"恢复自动投用"建议升至第 2 位（长期手动的回路，其他处置与复诊均无意义） |
| R3 | 不被污染的次分类建议正常列出 |
| R4 | **被污染命中项不生成处置建议，只生成复诊指引**（Poka-Yoke：不让用户拿着失真结论去改参数——"先修仪表再整定"是工业标准顺序） |
| R5 | 每条建议必须引用算子特征值作依据 |

**投用是独立维度**：可与任何主因并存。长期手动回路的参数诊断意义弱，建议"先恢复自动投用再复诊"。

**建议内容**：每分类预设建议模板（从原 R01-R08 建议库按新分类重组），每条含：内容 + 依据（引用算子特征值）+ 处置方向。

### 7.5 置信度显式定义（2026-08-17 增补）

每个诊断结果的置信度必须有可查的口径。定义随详情 API `confidenceDefinitions` 动态返回（不入库），结果面板置信度旁"?"图标点击展示。

**分类级口径**（主分类置信度如何得出）：

| 分类 | 置信度口径 |
|---|---|
| COMMUNICATION | 质量码算子 Q001 档位：按最长连续断流段时长分级（≤60s→0.60 / ≤600s→0.75 / >600s→0.90）；落库缺口率仅作佐证不计分 |
| INSTRUMENT | 传感器波形特征定档取最高：卡死 0.85 / 噪声突增 0.70 / 漂移 0.65 |
| TUNING | 过激 = min(0.95, 满足指标数/3)；迟缓 = min(0.9, τ比/10)（响应窗到达率 <63.2% 时 τ 外推不可靠记 0）；同族取最大 |
| VALVE | 粘滞方向：族内 ≥2 算子命中经 D-S 交叉验证融合；饱和方向 = min(1.0, OP 贴限时长占比) |
| PROCESS | 外扰算子 min(0.95, 突变频率/20 次/h)；纯振荡推断（无粘滞/过激证据）固定 0.50 |
| UTILIZATION | min(0.95, 1 − 时间窗自动投用率)，来自 KPI 快照统计 |
| DESIGN | Phase 2 启用前不参与置信度评估 |
| DATA_INSUFFICIENT | 门禁短路输出，不参与置信度评估（记 0） |

**算子级口径**：11 个算子各自公式见 `OperatorMeta.confidence_basis`（GET /diagnosis/operators 可查），如 FFT 振荡 = min(1.0, 主峰能量占比×1.5)、椭圆粘滞 = min(1.0, (拟合分+粘滞指数)/2)。

**融合与门槛规则**：同族 ≥2 算子命中按 Dempster-Shafer 交叉验证融合（高置信互证上调、证据冲突趋近 0.5），单算子命中原样传递；次分类纳入门槛 0.60。

**严重度口径**：综合评分 <40 且主分类置信 ≥0.8 → HIGH；评分 <60 或置信 ≥0.6 → MEDIUM；否则 LOW（DATA_INSUFFICIENT 恒 LOW）。

## 9. API、前端、异常与测试

### 9.1 API 设计

| 端点 | 方法 | 说明 |
|---|---|---|
| `/api/v1/diagnosis/run` | POST | Body：`{loopIds[], timeWindow(preset: last_24h/last_7d/last_30d 或自定义), operatorGroup(full\|fast, 默认 full)}`；即时校验（回路存在/tag 齐全/时间窗合法）；返回 `{taskId, accepted}` |
| `/api/v1/diagnosis/runs` | GET | 筛选：loopId / category / severity / status / 时间范围；分页 |
| `/api/v1/diagnosis/runs/{id}` | GET | 完整详情：分类结果（主/次/待复核+污染说明）+ 建议 + 全算子结果 + 门禁结论 + 波形快照 |
| `/api/v1/diagnosis/operators` | GET | 算子注册表元数据 |
| `/api/v1/diagnosis/export` | GET | 按列表筛选条件导出 CSV |
| `/api/v1/tasks/{taskId}` | 复用 | 任务进度轮询 |

**进度上报（细粒度按阶段）**：每回路 `取数(0.1)→门禁(0.2)→算子逐个(0.2~0.8)→融合分类(0.9)→落库(1.0)`；多回路按回路均分段。

**算子组预设**：`full`=全部启用算子（默认）；`fast`=每族 1 个代表算子（oscillation_iae / stiction_ellipse / step_response_overshoot / slow_response / disturbance_burst / sensor_fault / output_saturation，共 7 个），用于快速初筛。

**权限**：发起=工程师及以上；查看=登录用户；算子阈值配置=管理员。复用现有角色与权限框架，不新增角色。

### 9.2 前端两页设计

**P1 诊断工作台 `/diagnosis/workbench`**

```
┌─ 工具栏（固定标题栏、右对齐）：发起诊断 | 算子说明 | 刷新 ──────┐
```

### 9.3 异常处理

| 场景 | 处理策略 |
|---|---|
| 数据门禁不过 | **不算失败**：正常完成，输出 DATA_INSUFFICIENT 分类 + 补数指引（衔接现有数据导入功能） |
| 单算子异常 | 捕获隔离：该算子 `executed=False`+错误信息，不阻断其余算子；族内融合忽略失败算子 |
| 族内算子全失败 | 该症状无结论（不参与分类），详情页标注 |
| 部分回路失败 | run 状态 PARTIAL，逐回路记录状态 |
| 取数超时/基础设施故障 | AsyncTask autoretry（3 次退避），复用现有机制 |
| 回路无关联 tag/数据源缺失 | 发起时即时校验，拒绝并提示 |
| 重复发起同一回路 | 允许（手动场景），记录按时间区分，不加锁 |
| 波形快照超限 | LTTB 固定 2000 点（项目既有性能边界） |

### 9.4 测试策略

| 层 | 内容 |
|---|---|
| 算子单测 | 合成信号验证（正弦+噪声→振荡、死区+滞环→粘滞、冻结段→卡死）；边界（空数组/点数不足/NaN/全常数） |
| **迁移等价性测试** | 同一输入下新旧算法输出一致（容差内）——11 算子逐一对照 `diagnosis_engine.py` |
| 融合/分类单测 | 族内冲突证据→融合≈0.5；决策表逐规则覆盖；**污染链场景**（仪表+过激→pending_review、不生成参数建议） |
| API 集成测试 | 发起→轮询→列表→详情→导出全链路；门禁各档；PARTIAL 场景 |
| 前端 | vitest（ResultPanel 分类卡/chips/建议排序渲染）+ E2E（发起→进度→结果→记录筛选→抽屉） |
| 门禁 | ruff / pytest / check:type / alembic check / vitest 全绿 |

## 10. 分期计划与演进

### 10.1 分期

**Phase 1（本期，诊断 MVP）**

1. 后端：算子契约+注册表 → 11 算子等价迁移 → 族内 D-S 融合 → 分类映射（6 分类：TUNING/VALVE/INSTRUMENT/PROCESS/UTILIZATION/DATA_INSUFFICIENT）→ `diagnosis_run` 表+迁移 → 编排器 → 5 API
2. 前端：两页 + `DiagnosisResultPanel` + 回路工作台入口 + 跨模块跳转
3. 测试与门禁全部通过

**Phase 2（数据积累后）**

- 新增 4 算子（振荡传播/阀位分布/滞环/积分饱和）→ 启用第 7 分类 DESIGN
- 污染链精细化（自动剔除故障时段复算）
- 诊断概览统计页（分类分布/趋势/Top 回路，视数据量决定）
- 决策表配置化
- 评估计算器迁入统一注册表（统一算子平台第一步）

### 10.2 AI 诊断智能体预留（不排期）

- `GET /diagnosis/operators` 元数据 = 机器可读工具目录
- 每个元算子 = 独立可调用单元（输入数组+参数→结果），智能体可单算子试探调用（如"只跑粘滞算子看看"）
- 规则分类做兜底校验，LLM 归因做增强；编排调用元算子
- 评估计算器（metric_calculator）二期迁入同一注册表后，智能体工具目录自然覆盖评估+诊断+整定全部能力

## 11. 与原设计的对照总结

| 维度 | 原设计 | 本设计 |
|---|---|---|
| 页面 | 独立诊断中心 5 页 | 一级模块 2 页 + 工作台入口 |
| 结果语义 | 8 类症状标签并列 | 症状标签（算法层）→ 6+1 原因分类（呈现层） |

| 闭环 | Action Tracker 7 态全闭环 | 只诊断+建议 |
| 触发 | 手动+评分阈值+定时体检 | 仅手动 |
| 算子形态 | 174KB 单体引擎 | 元算子注册表（无状态纯函数，AI 可编排） |
| 报告 | PDF 建议书 + CSV | 页面 + CSV |
| 后端复用 | — | 算法逻辑等价迁移；阈值四级覆盖；TaskTracker；DataPlanner；预处理管线 |
