## 1. 背景与目标

### 1.1 现状

诊断模块（两页式：诊断工作台 + 诊断记录）的**单次诊断能力已完整**：11 元算子 + 族内 D-S 融合 + 8 类原因分类 + 证据链 + 人工复核 + 即时生成处置建议。引擎已统一到 `diagnosis_run` 单一事实源（14 号文）。

### 1.2 缺口（用户视角）

工程师工作旅程六步：**发现 → 诊断 → 复核 → 转处置/整定 → 验证效果 → 周期回顾**。当前前四步扎实（深链接打通），后两步在诊断模块内无落脚点：

| 用户问题 | 现状 | 归类 |
|---|---|---|
| "处置完成后到底**变好没**？" | 验证数据在处置域（`kpi_before/after`、`verify_run_id`），诊断侧无视图 | 纵向闭环 |
| "这个回路的问题**什么时候开始的、一直在恶化吗**？" | 仅有简单历史时间线抽屉（列表态，无趋势、无事件叠加） | 纵向闭环 |
| "哪些回路**从来没诊断过**、调度实际跑了没有？" | 无覆盖台账 | 群体管理 |
| "装置里 8 个回路**同一个毛病**，共因还是巧合？" | Pareto 仅一层下钻到记录列表，无回路组对比 | 群体管理 |
| "点了诊断又 **DATA_INSUFFICIENT**，白等一趟" | 门禁只在发起后生效，发起前不可见 | 诊断质量 |
| "这个算子**老误报**，被改判 8 次了，阈值该调了吧？" | 复核数据已积累，无反馈统计 | 诊断质量 |

### 1.3 数据基础盘点（本方案零新采集、零 schema 迁移）

| 数据资产 | 位置 | 支撑功能 |
|---|---|---|
| `diagnosis_run` 历史存量（category/confidence/severity/metric_summary/operator_results/trigger_type/data_gate） | `models/diagnosis_run.py` | F1/F2/F3/F4/F6 |
| `kpi_snapshot_hourly` 12 列 KPI（score/oscillation_rate/stiction_index/settling_time…） | 评估域 | F1/F2 |
| `handling_order.verify_run_id` FK + `kpi_before/kpi_after` + `created_at/closed_at` | 处置域 | F1/F2 |
| `tuning_record` 批次时间点 | 整定域 | F1 |
| `loop_ledger` 等级（调度分级 1/2/3 级） | 监控域 | F3 |
| 复核字段（`review_status/review_results/reviewed_at`） | `diagnosis_run` | F6 |
| TDengine 密度探测先例（调度侧门禁）+ `kpi_snapshot_hourly` 密度 | `tasks/diagnosis_schedule.py` | F5 |

**原则：本方案全部功能为纯查询 + 前端渲染，不新增 ORM 模型、不新增 Alembic 迁移。**

### 1.4 执行原则（2026-08-28 用户确认）

| # | 原则 | 落地口径 |
|---|---|---|
| P1 | **遵守 7 号文既定精简设计策略** | 7 号核心决策继续有效：两页式 IA（不新增菜单页，新视图一律抽屉/折叠块/页签形态）、元算子无状态纯函数架构（本方案不触碰算子层）、输出形式页面+CSV（不做 PDF 建议书）、轻量波形可视化（仅趋势+散点，不引入重型图表） |
| P2 | **补全功能按完整设计推进，不做精简砍半** | F1~F6 每项做全四层：数据口径、交互闭环（点击/下钻/悬浮）、空态与样本不足态、跨模块降级态；不留"先做列表后补图表"式的半成品 |
| P3 | **热插拔自包含**（诊断/整定/处置三模块弹性启用禁用） | ① 诊断的新功能在其他模块禁用时必须可用（降级形态，见 §5.4 矩阵），不形成对处置/整定 service 层的硬依赖；② 反向同理：工作台等处对诊断新功能的引用随诊断禁用自然不可达（现有模块 4 态机制）；③ service 层 import 纪律：诊断 insights service 允许 import 其他模块 **ORM 模型**（物理表恒在，符合"不删数据"原则），**禁止 import 其他模块 service 层**（避免耦合链） |

## 4. 功能需求（What——用户视角）

### F1 回路诊断档案

**用户故事**：作为工程师，我想在一个视图里看到某回路全部诊断结论随时间的演变、关键 KPI 趋势、以及处置/整定干预事件的位置，从而判断"问题是何时开始的、干预之后好了没"。

**功能点**：

1. 入口：诊断工作台概览操作列"历史"按钮（现有 history-drawer 升级，D2）；记录页详情抽屉、工作台 Tab3 回路详情抽屉同步增加"诊断档案"入口。
2. 布局（自上而下）：
   - 顶部摘要行：回路名/等级/最新主分类/最新置信度/累计诊断次数/首末诊断时间；
   - 主分类泳道时间轴（横轴时间，8 类色码复用 `CATEGORY_META`，每条 run 一个色块，高度映射严重度三档；DATA_INSUFFICIENT 用灰色斜纹区分"无结论"）；
   - 置信度 + KPI 迷你趋势（复用 spark 组件，无动画，默认显示评分与振荡率两条，可切换 `kpi_snapshot_hourly` 其余列）；
   - 事件竖线叠加：处置工单（创建/关闭）、整定批次（开始/完成）在时间轴与趋势图上打标记，悬浮显示事件摘要；
   - 底部 run 列表：现有历史抽屉的倒序列表保留，点击跳详情。
3. 交互：泳道色块点击 → 打开该 run 详情弹窗（复用 DiagnosisResultPanel）；时间窗缩放（30d/90d/全部）。
4. 空态：从未诊断的回路显示引导态（"该回路尚无诊断记录" + 发起诊断按钮）。

### F2 复诊对比视图

**用户故事**：作为工程师，处置工单关闭后，我想并排看到处置前后两次诊断的结论与特征值差异，自己确认问题是否消除，而不是只看处置域的 KPI 快照；即使没有处置关联，我也想对比任意相邻两次诊断看变化趋势。

**功能点**（D3：双模式对比，v1.1）：

1. 入口：诊断详情弹窗/抽屉顶部增加"前后对比"页签，页签内两种模式切换：
   - **相邻对比**（默认）：与该 run 之前最近一条 SUCCESS run 对比，纯诊断域数据，恒可用（P3 自包含兜底）；
   - **验证对比**：`handling_order.verify_run_id` 关联的处置前后两条 run；处置模块启用且存在关联时可用，否则该模式入口隐藏（非置灰——禁用模块的功能概念不应残留在 UI 上）。
2. 对比内容（左=基准 run，右=对比 run，两模式共用渲染）：
   - 结论变化卡：主分类/次分类/严重度/置信度 before → after，变化方向着色（恶化红/改善绿/持平灰）；
   - 特征值对照表：两次 run `operator_results` 中同算子同特征名逐行对照，delta 列着色（反向指标如 stiction_index 下降=改善绿）；
   - KPI 对照：`metric_summary` 关键指标 delta（验证对比模式下与处置域 `kpi_before/after` 口径对齐，数据源相同应一致，不一致时以诊断 run 为准并标注）；
   - 证据波形并排（30 天保留期内可用；超期显示"证据已按保留策略清理"占位，复用现有占位逻辑）。
3. 边界：两次 run 时间窗可能不同，头部明示各自窗口，不做归一化；首条 run 无相邻前序时显示占位说明。

### F3 诊断覆盖台账与新鲜度

**用户故事**：作为工程师/管理者，我想知道哪些回路诊断数据已过期或从未覆盖、分级定时调度实际执行情况如何，避免"三分钟热度"后出现管理盲区。

**功能点**（D6：诊断工作台概览区折叠块"诊断健康度"）：

1. 新鲜度分布单行摘要：按回路最新 SUCCESS 诊断时间分档（24h 内 / 7d 内 / 30d 内 / 超期 / 从未诊断），条形占比 + 从未诊断计数徽标，点击下钻记录页。
2. 调度执行情况（仅管理员可见或全员只读）：1 级（每日）/2 级（每周）回路应跑 vs 实际最近一次 SCHEDULED run 时间，滞后的回路计数与列表；3 级回路标注"不排程，仅手动"。
3. 数据不足率 Top5：近 30d DATA_INSUFFICIENT 占比最高的回路（提示先补数据，联动 F5/F1）。
4. 与调度分级口径一致：等级来源 `loop_ledger`，与 `diagnosis_schedule.py` 分级逻辑共用同一判定，避免两套口径。

### F4 共性问题回路组对比

**用户故事**：作为工程师，看到 Pareto 图"本装置 8 个回路都是 VALVE 类"时，我想快速拉出这些回路并排对比指标，判断是共因（仪表风/检修批次）还是各自独立问题。

**功能点**：

1. Pareto 第二层下钻：工作台 Tab3 / 诊断记录页的 Pareto 柱或分类筛选，新增"(分类 × 装置)"维度的回路组列表（每回路一行：最新结论/置信度/KPI 摘要/最近诊断时间）。
2. 多回路对比抽屉（D5，兑现 v2.0 方案 F-DG-06）：回路组列表勾选 2~3 回路 → 并排 6 指标雷达图（评分/自控率/振荡率/粘滞指数/回复时间/好值率，取最新 run `metric_summary`）+ 关键特征值对照表。
3. 交互：雷达图顶点悬浮显示数值；回路超出 3 个时提示分批对比。

### F5 发起前数据预检

**用户故事**：作为工程师，发起诊断前我想直接在回路勾选列表上看到"这个回路这个时间窗的数据够不够诊断"，避免发起后收到 DATA_INSUFFICIENT 白等一趟。

**功能点**（D1：廉价代理口径）：

1. 诊断工作台左脊柱回路清单：每行增加数据充足性徽标（复用 FitnessBadge 视觉模式，三态：充足绿/疑似不足琥珀/不足红），依据 `kpi_snapshot_hourly` 近 24h 行数密度（分级阈值与调度侧密度门禁同口径）。
2. 徽标悬浮显示依据（"近 24h 快照 N 行，低于预期 M 行"）。
3. 与现有 fitness 门禁的关系：本徽标是**事前提示**，不替代发起时的 fitness 检查（L0/L1 阻止、L2 警告放行，行为不变）；红态回路不阻止勾选，仅在发起按钮旁汇总提示"N 个回路数据可能不足"。
4. 成本控制：密度查询走 PostgreSQL 快照表，批量一次查询，不触 TDengine。
5. 降级态（P3）：徽标依据是评估域产出的快照密度——评估模块禁用或回路无任何快照时，徽标显示中性隐藏态（"无评估数据"），**不得误报"不足"**；此为数据源缺失，非数据质量结论。

### F6 复核反馈统计与阈值调优提示

**用户故事**：作为诊断配置管理员，我想看到每个算子/分类的人工复核确认率与改判去向，当某算子改判率异常高时收到"建议调整阈值"的提示。

**功能点**：

1. 入口：诊断配置页（`config.vue`）新增"算子表现"卡片区块（仅 ADMIN 可见）。
2. 统计维度（每算子 + 每 8 类分类，D4 样本门槛 ≥10）：
   - 检出次数、复核率（已复核/已检出）、确认率（复核维持主分类比例）、改判率（复核改判比例）、改判去向分布（改判到哪些分类，Top3）；
   - 样本不足时显示占位（"样本不足（N<10），暂不统计"）。
3. 阈值调优提示：算子改判率 > 40% 时该行标琥珀色，附"建议复核阈值（当前四级覆盖：回路>装置>类型>全局）"按钮，链接到该算子的阈值配置区（复用现有四级阈值覆盖编辑，不新建交互）。
4. 口径说明区块内常驻一行小字：统计范围为全部历史已复核 run，改判=复核结论不含机器主分类。

## 5. 技术设计（How）

### 5.1 API 设计（全部挂 `endpoints/diagnosis_v2.py`，模块启用门控内）

| 方法+路径 | 功能 | 数据来源 |
|---|---|---|
| GET `/diagnosis/runs/loop-archive?loopId=&window=` | F1 档案聚合：run 时间轴摘要列表 + KPI 趋势（LTTB）+ 关联事件（处置/整定，**模块启用时才查询该段**） | `diagnosis_run` + `kpi_snapshot_hourly` + `handling_order`* + `tuning_record`*（*条件查询） |
| GET `/diagnosis/runs/{run_id}/compare?mode=adjacent\|verify` | F2 对比：两次 run 结论/特征值/metric_summary 结构化对照（后端组装 delta，前端只渲染）；verify 模式返回关联 run 对（处置启用时） | `diagnosis_run` × 2（+ `handling_order` 条件查询） |
| GET `/diagnosis/coverage` | F3 台账：新鲜度分档 + 调度执行 + DATA_INSUFFICIENT Top | `diagnosis_run` 聚合 + `loop_ledger` |
| GET `/diagnosis/category-cohort?category=&plantNodeId=` | F4 回路组列表：该分类×装置下每回路最新 run 摘要 | `diagnosis_run` latest per loop（可复用 `runs/latest` 逻辑泛化） |
| GET `/diagnosis/precheck?loopIds=&window=` | F5 密度徽标：批量回路快照密度分级 | `kpi_snapshot_hourly` count 聚合 |
| GET `/diagnosis/review-feedback` | F6 复核统计：算子/分类维度确认率与改判矩阵 | `diagnosis_run.operator_results` + `review_results` 展开 |

实现要点：

- 所有端点走只读 service（新增 `services/diagnosis_insights.py` 统一承载，或按功能拆分到现有 service），不修改 `diagnosis_orchestrator.py` 主链路；
- **跨模块查询门控（P3）**：F1 事件段、F2 verify 模式对 `handling_order`/`tuning_record` 的查询，一律先判 `is_module_enabled("handling"/"tuning")`，禁用时跳过该查询段并在响应中标记 `events_enabled: false` 之类的能力字段，前端据此隐藏对应图层/模式（而非报错）；import 纪律见 §1.4 P3——允许 ORM 模型 import，禁止 service 层 import；
- F1 的 KPI 趋势查询复用现有 LTTB 降采样工具；**性能边界口径说明**：核心决策"30 天时间窗口"约束的是 TDengine 原始宽表计算查询，F1 的 KPI 趋势来源是 `kpi_snapshot_hourly` 小时快照（PostgreSQL，90d≈2160 点，LTTB 后 ≤2000 点），run 泳道是离散元数据，均不触碰该边界；"全部"窗口截断到 90d 并在 UI 提示；
- F4 的 latest-per-loop 查询注意复用/泛化 `GET /diagnosis/runs/latest` 已有实现，避免两套"最新 run"口径；
- F6 展开算子结果时只统计 `executed=true` 的算子，`pending_review` 命中不计入改判分母；
- 权限：F1/F2/F4/F5 全员（与记录页一致）；F3 调度执行块、F6 卡片限 ADMIN（与诊断配置页口径一致）。

### 5.3 性能与边界

- F1 档案聚合单回路查询，run 数量上限保护（窗口截断 90d）；
- F5 precheck 批量 ≤10 回路（与发起上限一致），单次 PostgreSQL 聚合查询；
- F6 统计可全量扫 `diagnosis_run`（MVP 数据量级可控），后续量级增长再考虑物化（参照 `mv_diagnosis_pareto` 先例）；
- 所有新端点不引入新表、新迁移、新 Celery 任务。

### 5.4 模块自包含与联动降级矩阵（P3）

诊断模块自身被禁用时：6 个新端点随 `diagnosis_v2.router` 不注册（现有 `main.py` 门控机制）、前端入口随页面不可达，无需额外处理。**本矩阵约束的是反向——其他模块禁用时，诊断新功能的降级形态**：

| 功能 | 联动模块（禁用项） | 降级形态（禁用时） | 核心可用性 |
|---|---|---|---|
| F1 档案 | 处置 | 工单事件竖线图层隐藏（查询段跳过） | 泳道 + 置信度趋势照常 |
| F1 档案 | 整定 | 整定批次事件竖线图层隐藏 | 同上 |
| F1 档案 | 评估 | KPI 趋势区隐藏（无快照数据），仅留置信度趋势 | 泳道照常 |
| F2 对比 | 处置 | "验证对比"模式入口隐藏；**"相邻对比"模式不受影响（默认模式，纯诊断域）** | 对比功能完整可用 |
| F3 台账 | 无（`loop_ledger` 属基础域，非热插拔模块） | — | 完整可用 |
| F4 回路组 | 无 | — | 完整可用 |
| F5 预检 | 评估 | 徽标中性隐藏（"无评估数据"），不误报不足 | 发起流程不受影响（本就不阻止） |
| F6 反馈统计 | 无（纯 `diagnosis_run` 自身字段） | — | 完整可用 |

降级实现约定：后端响应携带能力字段（如 `events: {handling: false, tuning: true}`），前端按能力字段条件渲染图层/入口——**隐藏而非置灰**（禁用模块的功能概念不应残留在 UI 上，与工作台模块 4 态的呈现口径一致）。

## 6. 实施排期建议

> 按分阶段实施工作流（2026-08-24 沉淀），每阶段启动时按 `docs/过程文档/staged-implementation-workflow-2026-08-24.md` 骨架模板生成阶段任务提示词，以其 §3 第 4 节核验清单为晋级门槛。

| 阶段 | 内容 | 依赖 | 验收要点 |
|---|---|---|---|
| Phase A 纵向闭环 | F1 档案 + F2 复诊对比 | 无（数据全在） | 抽 3 个有处置历史的回路人工核对泳道/事件位置正确；对比视图 delta 与处置域 kpi_before/after 一致性抽查 |
| Phase B 群体管理 | F3 台账 + F4 回路组对比 | 无 | 新鲜度分档计数与 SQL 手工对账；Pareto→回路组→雷达链路可用；3 回路上限生效 |
| Phase C 诊断质量 | F5 预检徽标 + F6 复核反馈 | F5 依赖密度阈值口径确认；F6 依赖复核数据积累量 | 徽标分级与调度侧密度门禁同口径验证；改判率统计与人工抽样 20 条复核记录对账 |

建议顺序 A → B → C：A 直接衔接已落地的处置闭环（`verify_run_id` 最后一公里），用户感知最强；C 的 F6 依赖复核数据自然积累，放最后统计意义才充分。
