## 1. 背景与目标

### 1.1 业务流全景（v2.0 定位升级）

```
监控发现回路异常 → 诊断并提出处置意见（诊断模块）
    → 处置建议清单（本模块入口：唯一编号/回路/建议/类型/建议人与时间）
    → 审核诊断意见（接受 / 驳回：原因+时间留痕）
    → 生成处置计划与工单（明确动作、排程；多建议可合一单；亦支持手动新建）
    → 作业人员处置执行与反馈（工单内反馈处置情况与状态）
    → 验证流转（验证是处置环节的一部分：有效闭环 / 无效重开）
    → 处置记录沉淀（档案追溯 + 统计回顾）
```

### 1.2 v1.x 的结构性缺陷（重构动机）

v1.x 将"建议"与"处置执行"合在 `loop_action_item` 一张表一个状态机：

1. **审核环塞不进去**：PENDING 直接开工，无"接受/驳回"环节，驳回（原因/时间/人）无承载；
2. **建议与工单语义混淆**：建议是审核对象，工单是执行对象——排程、执行反馈、处置编号均无字段承载；
3. **多建议合一单无法表达**：现场一个停工窗口常做多件事（阀门+仪表一起检修）；
4. **`run_id` NOT NULL**：手动建议/手动工单无诊断 run 可挂（已 mock 验证该缺口）。

### 1.3 核心决策清单（v2.0）

| # | 决策项 | 结论 |
|---|---|---|
| 1 | 模块形态 | 一级模块「处置」，三页式：工作台（双 Tab）/ 档案 / 统计（沿用 v1.1） |
| 2 | **实体模型（v2.0 裁决）** | **双实体分离**：处置建议（`loop_action_item` 改造，审核对象）+ 处置工单（`handling_order` 新建，执行对象）；支持多建议合并转一单 |
| 3 | **驳回语义（v2.0 裁决）** | 驳回为**终态**；"驳回后发现有价值"走重新诊断/手动新建（与 CLOSED 不可重开口径一致） |
| 4 | 建议状态机 | 4 态：PENDING 待审核 → ACCEPTED 已接受 → CONVERTED 已转工单；REJECTED 已驳回 / IGNORED 已忽略（终态） |
| 5 | 工单状态机 | 6 态：PENDING 待执行 → EXECUTING 执行中 → VERIFYING 验证中 → CLOSED 已闭环（终态）；验证无效 → REOPENED 重开（可再处置）；CANCELLED 作废（终态） |
| 6 | 排程 | `planned_at` 字段承载（计划处置时间 + 排程人），**不设独立状态** |
| 7 | 执行反馈 | 工单 `feedback_log` JSONB 数组（时间/人/内容），执行中可多次追加 |
| 8 | 处置编号 | 工单业务编号 `order_no = HD-YYYYMMDD-NNN`（唯一约束）；建议沿用 UUID |
| 9 | 验证方式 | 沿用 v1.x：KPI 前后窗对比（前窗 handled→started 口径平移）+ 可选复诊关联；结论人工判定 |
| 10 | 安全边界 | 平台只跟踪与验证，不执行任何 DCS 操作（不变） |
| 11 | 手动新建 | 建议与工单均支持手动新建（建议侧 `run_id` 放空迁移；工单 `source=MANUAL`） |
| 12 | CLOSED 不可重开 | 终态；复发走重新诊断 → 新建议 → 新工单，历史不改写（不变） |
| 13 | 流转审计 | 行级人/时间字段够用，不建流转日志表（feedback_log 除外——业务数据非审计） |

## 2. 产品定位与范围

### 2.1 定位

处置 = 回路问题的**执行闭环管理器**：承接诊断产出与人工登记的待处置内容，经审核转化为排程工单，跟踪"谁在什么时候做了什么、效果如何、何时关闭"，为回路治理沉淀可追溯的处置档案。

### 2.2 双实体概念模型

```
处置建议 Suggestion（loop_action_item 改造）        处置工单 Work Order（handling_order 新建）
├─ 来源：诊断带出(SYSTEM) / 手动新增(MANUAL)          ├─ 来源：建议转化(DIAGNOSIS，可多建议合一单) / 手动新建(MANUAL)
├─ 职责：待处置内容汇聚 + 审核判定                     ├─ 职责：排程、执行反馈、验证、闭环
├─ 出口：accept → convert 转工单                      ├─ 生命周期：待执行 → 执行中 → 验证中 → 闭环/重开/作废
└─ 终态：REJECTED / IGNORED / CONVERTED               └─ 闭环后即"处置记录"（档案/统计的数据源）
```

**多建议合一单**：审核通过的多条建议（同回路，如"阀门检修"+"仪表校验"）可合并转一个工单——对应现场"一个停工窗口做多件事"；工单 `suggestion_ids` 记录来源建议，各建议回链 `converted_order_id`。

### 2.3 范围内

- 建议清单：跨回路聚合，唯一编号展示，按状态/类型/装置/等级/来源筛选
- 建议审核：接受 / 驳回（原因必填）/ 忽略；手动新增建议
- 转工单：多选建议 → 明确处置类型/计划时间/处置人 → 生成工单（编号自动）
- 工单管理：手动新建、排程、作废；清单与详情
- 处置执行：开工认领、执行反馈（多次追加）、提交验证
- 验证：KPI 前后对比卡（预览+固化）+ 复诊关联；有效闭环/无效重开
- 档案与统计：回路维度全史追溯 + 管理报表（闭环率/驳回率/排程周期等）

### 2.4 范围外（非目标）

| 项 | 说明 |
|---|---|
| 多级审批流 / 工单派发指派 | 审核为单人接受/驳回；处置人手工填写记录（沿用 v1.0 裁决） |
| DCS 参数下写 | 平台安全边界不变 |
| 验证自动判定 | 有效/无效由人工依据 KPI 对比与复诊结论判定 |
| 移动端 / 消息通知 | 不做 |
| 排程超期提醒 | Phase H3 候选（超 planned_at 未开工统计） |

### 3.3 处置编号规则

- 格式：`HD-YYYYMMDD-NNN`（如 `HD-20260820-001`），**按日重置序号**；
- 生成：服务端生成（`SELECT COUNT(*) WHERE order_no LIKE 'HD-YYYYMMDD-%'` + 1），并发冲突由唯一约束兜底（捕获重试一次，序号+1）；不做跨日连续性保证；
- 前端展示与检索（清单/详情/档案/打印口径）均以 `order_no` 为准，UUID 仅内部关联。

### 3.4 表数量与迁移要点

- 新增 1 表（`handling_order`）→ 表数 47 → 48（更新 `test_process_model_version.py` 断言）；
- `loop_action_item`：放空 `run_id` + 换状态 CHECK + 加审核 4 列 + 删处置执行 14 列（alembic 单迁移完成，DDL 同步 `01_schema.sql`）；
- 存量数据迁移见 §9。

## 4. 状态机

### 4.1 建议（4 态）

| 状态 | 中文 | 含义 |
|---|---|---|
| `PENDING` | 待审核 | 建议已产生（诊断带出/手动新增），等待审核 |
| `ACCEPTED` | 已接受 | 审核通过，待转工单 |
| `CONVERTED` | 已转工单 | 已生成处置工单，回链 order_no（终态） |
| `REJECTED` | 已驳回 | 审核驳回，原因留痕（**终态**，不重新审核） |
| `IGNORED` | 已忽略 | 建议不适用/重复，轻量关闭（终态） |

**合法迁移**：

| # | from | 事件 | to | 守卫 | 记录 |
|---|---|---|---|---|---|
| 1 | PENDING | `accept` 接受 | ACCEPTED | — | reviewed_by/at |
| 2 | PENDING | `reject` 驳回 | REJECTED | rejected_reason 必填 | reviewed_by/at, rejected_reason |
| 3 | PENDING | `ignore` 忽略 | IGNORED | ignore_reason 必填 | ignore_reason |
| 4 | ACCEPTED | `convert` 转工单 | CONVERTED | 生成工单并回链；**多建议合一单时各自转 CONVERTED** | converted_order_id |

### 4.2 工单（6 态）

| 状态 | 中文 | 含义 |
|---|---|---|
| `PENDING` | 待执行 | 工单已生成（转化/手动），含排程属性，可编辑/作废 |
| `EXECUTING` | 执行中 | 处置人已开工，执行中可多次反馈 |
| `VERIFYING` | 验证中 | 处置已实施提交，等待效果验证 |
| `CLOSED` | 已闭环 | 验证有效（终态，不可重开） |
| `REOPENED` | 重开 | 验证无效，可再次开工 |
| `CANCELLED` | 已作废 | 计划变更等作废（终态） |

**合法迁移**：

| # | from | 事件 | to | 守卫 | 记录 |
|---|---|---|---|---|---|
| 1 | PENDING | `start` 开工 | EXECUTING | handler 手工填写（缺省当前用户）；TUNING 建议回填 pidBefore | handler, started_at |
| 2 | PENDING | `cancel` 作废 | CANCELLED | cancel_reason 必填 | cancel_reason |
| 3 | EXECUTING | `feedback` 反馈 | EXECUTING | content 必填；**状态不变**，追加 feedback_log | feedback_log[] |
| 4 | EXECUTING | `submit` 提交验证 | VERIFYING | action_detail 必填（TUNING 必填 pidAfter） | submitted_at, action_detail |
| 5 | VERIFYING | `verify` 有效 | CLOSED | 服务端固化 kpi_before/after | verify_*, kpi_* |
| 6 | VERIFYING | `verify` 无效 | REOPENED | 建议填写 verify_note | 同上 |
| 7 | REOPENED | `start` 再次开工 | EXECUTING | 清空上轮验证字段 | 同 #1 |

**规则**：非法迁移一律 `ERR_STATE` 400 后端强校验；CLOSED/CANCELLED/REOPENED 中 verify 字段保持不变；每次流转写 `updated_at`。

### 4.3 KPI 验证窗口（沿用 v1.x 口径）

```
suggested_at ──(建议审核)── started_at ──(执行期)── submitted_at ──(验证)── verified_at
                    │←── 前窗 KPI ──→│                │←── 后窗 KPI ──→│
```

- `kpi_before`：verify 时取 `[started_at − 24h, started_at]`（开工前最后基线）；
- `kpi_after`：verify 时取 `[submitted_at, submitted_at + 24h]`；
- 快照来源与摘要字段沿用 v1.x（`kpi_snapshot_hourly` 窗口内最新有分快照）；窗口不足侧存 null。

## 5. 处置类型与 action_detail（沿用 v1.x）

`action_type` 8 类（TUNING/VALVE/INSTRUMENT/LINK/PROCESS/UTILIZATION/RECONFIG/OTHER）与 `action_detail` JSONB schema、TUNING 必填 `pidAfter` 校验**原样沿用**，仅载体从建议表移至工单表。展示元数据（中文 label/表单 schema）沿用前端 `views/handling/constants.ts`。

## 6. API 定义

前缀 `/api/v1/handling`，响应 `{code, message, data}`，时间 naive UTC（前端补 Z）。角色守卫见 §7。

### 6.1 建议侧 `/handling/suggestions`

|---|---|---|
| GET | `/suggestions` | 建议清单（分页）。Query：`status`（多值）/ `source` / `plantNodeId`（递归）/ `loopId` / `importanceLevel` / `keyword` / `startTime`/`endTime` / `page`/`pageSize`。返回：建议域字段 + 审核域 + `convertedOrderNo`。排序：状态分组（PENDING→ACCEPTED→其他）+ suggested_at DESC |

| POST | `/suggestions/{id}/reject` | 驳回：PENDING → REJECTED。Body：`{rejectedReason}` 必填 |

### 6.4 与既有接口的关系

- 诊断侧 `GET/POST /diagnosis/runs/{run_id}/actions`、`PUT/DELETE /diagnosis/runs/actions/{id}` **不变**（建议生成与增删改仍在诊断上下文，产出的建议 status=PENDING 进入本模块审核流）；
- 复诊联动沿用：验证页跳诊断工作台，run_id 回填 verifyRunId。

## 8. 页面设计（三页式演进）

### 8.1 处置工作台 `/handling/workbench`（双 Tab）

**Tab1 建议清单**（默认）：
- 统计卡：待审核 / 已接受 / 已驳回 / 本周转化（工单数）
- 筛选：状态 / 类型 / 来源 / 装置 / 等级 / 关键字
- 表格：建议内容摘要 / 回路位号+名称 / 诊断分类 / 来源 / 建议人+时间 / 审核状态 tag / 操作（接受 · 驳回 · 忽略）
- 行操作：`[接受]`（确认弹层）`[驳回]`（原因必填弹层）`[忽略]`（原因弹层）
- **批量转工单**：多选行 → `[转工单]` 弹窗：处置类型（8 选 1）/ 计划时间 / 处置人 / 标题（缺省拼接）→ 生成后提示工单编号并跳 Tab2

**Tab2 工单清单**：
- 统计卡：待执行 / 执行中 / 验证中 / 本月闭环
- 筛选：状态 / 类型 / 来源 / 处置人 / 编号或回路关键字 / 计划时间窗
- 表格：**处置编号** / 回路 / 标题 / 类型 / 处置人 / 计划时间 / 状态 tag / 最近更新
- 行点击开工单详情抽屉（v1.x 详情抽屉平移）：
  - 上部：工单编号+标题+回路信息+来源建议列表（含"查看建议"回链）
  - 中部流转操作区（按状态渲染）：PENDING（开工/作废+排程信息）/ EXECUTING（**反馈输入框+追加**+历史反馈列表+提交验证）/ VERIFYING（KPI 对比卡+有效/无效+复诊）/ 终态只读
  - 下部时间线：工单生成（排程）→ 开工 → 反馈×N → 提交 → 验证

### 8.2 处置档案 `/handling/archive`（双实体口径）

- 聚合行：回路 / 装置.单元 / 等级 / **建议数（含审核分布）** / **工单数（六状态分布 tag）** / KPI 改善 / 最近处置时间/人
- 排序：最近处置 / 重开最多（沿用）

### 8.3 处置统计 `/handling/statistics`

- 汇总卡（本月）：工单闭环数 / 闭环率 / 平均处置时长 / 无效重开率 / 平均 KPI 改善 / **驳回率** / **平均排程周期**
- 月度趋势 / 类型分布 / 装置分布 / Top 问题回路：口径换工单（沿用 v1.1 布局）
- 数据不足空态原则不变（null 显 —）

### 8.4 诊断详情弹窗联动（沿用+扩展）

- 处置建议 Tab 行：显示审核状态 tag（ACCEPTED/CONVERTED 等非 PENDING 可见）+「去处置」跳工作台 Tab1；
- CONVERTED 行额外显示工单编号。

## 9. 存量数据迁移方案

**迁移原则**：幂等可重跑；历史闭环记录不改写语义。

| 存量状态 | 迁移动作 |
|---|---|
| `PENDING`（仅建议，无执行字段） | 原地保留：status 保持 PENDING（语义从"待处置"变"待审核"），等待审核 |
| `IGNORED` | 原地保留（终态） |
| `HANDLING` / `VERIFYING` / `CLOSED` / `REOPENED`（已进入处置流程） | 生成 `handling_order`：状态映射 EXECUTING/VERIFYING/CLOSED/REOPENED，执行与验证字段整体搬移，order_no 补发，`source=DIAGNOSIS`，`suggestion_ids=[自身 id]`；建议本身转 `CONVERTED` + 回链 |
| mock 手工工单（basis=手工处置工单前缀） | 按上述规则转为 MANUAL 工单 |

迁移以 alembic data migration 实施（随 schema 迁移同批提交）；迁移后 `loop_action_item` 删除的执行列在 downgrade 中不还原数据（仅结构）。
