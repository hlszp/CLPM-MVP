## 1. 背景与目标

### 1.1 动机

诊断模块已完成「评估 → 诊断 → 复核 → 建议」链路，但建议产生后停留在"待处置"——**闭环断点**。本模块把处置过程搬到线上，补齐最后一环：

```
评估发现问题 → 诊断归因 → 人工复核 → 系统带出/人工新增处置建议（已有）
    → 【处置执行 → 效果验证 → 关闭/重开】（本模块）
```

07 文档 §1.2 曾决策"只诊断 + 建议，不做线上处置跟踪（不恢复 Action Tracker）"。本次**升级该决策**：处置闭环价值已在诊断建设中显现（`loop_action_item` 表已落建议数据），且原 Action Tracker 的 7 态状态机对 MVP 偏重的问题，由本设计的 5 态轻量状态机解决。

### 1.2 核心决策清单（已评审确认）

| # | 决策项 | 结论 |
|---|---|---|
| 1 | 模块形态 | 一级模块「处置」，菜单第 4 位（监控→评估→诊断→**处置**→配置→系统） |
| 2 | 数据模型 | **扩展 `loop_action_item` 表**（不新建表）：诊断产出的建议与处置执行记录同源同表，天然"诊断产建议 → 处置管理"一体 |
| 3 | 状态机 | 5 态 + 忽略终态：`PENDING → HANDLING → VERIFYING → CLOSED`，验证无效 → `REOPENED`（可再次处置），`PENDING → IGNORED` 终态 |
| 4 | 参数整定 | 处置类型之一（`TUNING`），**记录式**闭环：处置时人工填写调整前后 P/I/D 值（JSONB），不依赖整定模块；预留 `tuning_record_id` 可空关联，未来整定模块开放后无缝挂接 |
| 5 | 验证方式 | 通用 KPI 前后对比（处置时间点前后两窗口快照）+ 可选关联复诊诊断记录；验证结论由人工判定（有效/无效），不做自动判定 |
| 6 | 安全边界 | 延续平台红线：平台只跟踪与验证，不执行任何 DCS 操作；参数整定仍由授权人员线下实施后回填记录 |
| 7 | 旧数据兼容 | 存量行全部 `source=SYSTEM/MANUAL, status=PENDING`，自动进入本模块待办，无需迁移数据 |
| 8 | KPI 验证窗口（评审定） | 前窗以 `handled_at` 为界（处置开始前基线），后窗以 `submitted_at` 为界（提交验证后），见 §4.3 |
| 9 | CLOSED 不可重开（评审定） | 终态；"闭环后复发"走**重新诊断 → 新建议 → 新处置项**，历史闭环记录不改写 |
| 10 | 流转审计（评审定） | 行级人/时间字段够用，不建流转日志表 |
| 11 | 处置人记录（评审定） | 本期不做指派；`handled_by` **手工填写**（默认当前登录用户），只做处置人+处置时间记录 |
| 12 | 装置列（评审定） | 清单页 unitPath 走 plant_node 树回溯（复用诊断详情弹窗现有实现） |
| 13 | 二级模块三页式（2026-08-19 评估定） | 处置下设三页：**处置工作台**（执行闭环）/ **处置档案**（回路维度追溯）/ **处置统计**（管理报表）；单页清单无法承载"回路处置全史回看"与"管理回顾"两类高频场景，见 §8.1 |

## 2. 产品定位与范围

### 2.1 定位

处置 = 回路问题的**执行闭环管理器**：承接诊断/复核产出的建议，跟踪"谁在什么时候做了什么、效果如何、何时关闭"，为回路治理沉淀可追溯的处置档案。

### 2.2 范围内

- 处置清单：跨回路聚合，按状态/类型/装置/回路等级/来源筛选，待办置顶
- 处置流转：开始处置 → 提交处置详情 → 验证 → 关闭/重开，全程留痕（人/时间/内容）
- 结构化处置详情：按处置类型记录关键字段（参数整定记 P/I/D 前后值，阀门检修记换件与停工时长等）
- 验证辅助：KPI 前后对比卡（评分 + 六率）；一键跳转诊断工作台对该回路复诊
- 诊断详情弹窗"处置建议"Tab 与本模块双向联动（建议行「去处置」跳转）

### 2.3 范围外（非目标）

| 项 | 说明 |
|---|---|
| 处置工单派发/审批流 | 不做多级审批；不做指派（处置人手工填写记录，见决策 #11） |
| DCS 参数下写 | 平台安全边界不变 |
| 验证自动判定 | 有效/无效由人工依据 KPI 对比与复诊结论判定 |
| 处置到期提醒/超期统计 | Phase 3 候选（对齐原"VERIFYING 超 24h 计待办"口径），首版不做 |
| 移动端/消息通知 | 不做 |

## 4. 状态机细则

### 4.1 状态定义（中文口径）

| 状态 | 中文名 | 含义 |
|---|---|---|
| `PENDING` | 待处置 | 建议/措施已产生，未开始执行（存量数据即此态） |
| `HANDLING` | 处置中 | 已认领开始，处置动作进行中（线下执行） |
| `VERIFYING` | 验证中 | 处置已实施并提交，等待效果验证 |
| `CLOSED` | 已闭环 | 验证有效，处置关闭（终态） |
| `REOPENED` | 重开 | 验证无效，问题仍在，可再次发起处置 |
| `IGNORED` | 已忽略 | 建议不适用/重复，忽略关闭（终态） |

### 4.2 流转表（唯一合法迁移）

| # | from | 事件 | to | 守卫条件 | 记录字段 |
|---|---|---|---|---|---|
| 1 | PENDING | `start` 开始处置 | HANDLING | `action_type` 必填；`action_detail` 可先填；`handler` 可选（**处置人手工填写**，缺省=当前登录用户） | handled_by=handler??当前用户, handled_at=now, action_type |
| 2 | PENDING | `ignore` 忽略 | IGNORED | `ignore_reason` 必填 | ignore_reason |
| 3 | REOPENED | `start` 再次处置 | HANDLING | 同 #1；`verify_result` 等验证字段清空待新轮回 | 同 #1 |
| 4 | HANDLING | `submit` 提交验证 | VERIFYING | `action_detail` 必填（该类型必填子字段校验） | submitted_at=now, action_detail |
| 5 | VERIFYING | `verify` 验证有效 | CLOSED | `verify_result=EFFECTIVE`；kpi_before/after 由服务端此刻固化 | verify_result, verify_note?, verified_by/at, kpi_before/after, verify_run_id? |
| 6 | VERIFYING | `verify` 验证无效 | REOPENED | `verify_result=INEFFECTIVE`；建议填写 verify_note 说明原因 | 同 #5 |

**规则**：
- 所有非法迁移（如 PENDING→VERIFYING）返回 `ERR_STATE` 400，后端强校验，不依赖前端
- CLOSED / IGNORED 为终态，**CLOSED 不允许重开**（评审决策 #9）；"闭环后复发"走重新诊断 → 新建议 → 新处置项（关联同一 run_id 天然可追溯），历史闭环记录不改写
- 每次流转写 `updated_at`；审计依赖行级人/时间字段（评审决策 #10，不建流转日志表）
- 状态与操作人权限：流转操作角色见 §7；handled_by 默认当前用户、支持手工填写他人（评审决策 #11），REOPENED 再 start 时更新为新一轮处置人

### 4.3 状态与 KPI 验证窗口的关系（评审决策 #8：前窗以 handled_at 为界）

```
suggested_at ──────── handled_at ──────── submitted_at ──────── verified_at
     建议产生            开始处置            提交验证              验证结论
      │←── 前窗 KPI ──→│ ←── 处置执行期 ──→ │←── 后窗 KPI ──→│
      （baseline）       （处置动作在此区间）   （验证时固化）
```

- `kpi_before`：verified 时取 `[handled_at − 24h, handled_at]`（**处置开始前的最后基线**——处置实施前的"病情"快照，与处置执行期完全隔离）
- `kpi_after`：verified 时取 `[submitted_at, submitted_at + 24h]`（提交验证后线上效果；不足 24h 按实际窗口）
- 两侧窗口隔离：处置执行期 `[handled_at, submitted_at]` 的过渡数据不参与对比，避免处置过程中参数逐步调整造成的口径混淆
- 快照来源：`kpi_snapshot_hourly` 按 loop_id 取窗口内最新一条有 score 记录，摘要字段：`score / goodValueRate / effectiveAutoRate / steadyRate / accuracyRate / fastRate / oscillationRate / saturationRate / confidenceLevel / tsStart / tsEnd`
- 窗口不足/无快照：对应侧存 `null`，前端对比卡显示"数据不足"

## 5. 处置类型与 action_detail 结构

### 5.1 action_type 枚举（8 类）

| 代码 | 中文名 | 默认映射来源（category → 建议默认类型，可改） |
|---|---|---|
| `TUNING` | 参数整定 | category=TUNING |
| `VALVE` | 阀门检修 | category=VALVE |
| `INSTRUMENT` | 仪表校验 | category=INSTRUMENT |
| `LINK` | 链路修复 | category=COMMUNICATION |
| `PROCESS` | 工艺调整 | category=PROCESS |
| `UTILIZATION` | 恢复投用 | category=UTILIZATION |
| `RECONFIG` | 组态改造 | category=DESIGN |
| `OTHER` | 其他 | 其余情况 / MANUAL 行默认 |

诊断详情"开始处置"时按建议 category 预填默认类型，用户可改。

### 5.2 action_detail JSONB schema（按类型）

```jsonc
// TUNING 参数整定（核心场景：记录式闭环，不依赖整定模块）
{
  "pidBefore": { "p": 1.2, "i": 20, "d": 0 },   // 调整前（处置开始时人工回填当前值）
  "pidAfter":  { "p": 0.8, "i": 35, "d": 0 },   // 调整后（提交验证时必填）
  "method": "Lambda 整定法",                      // 整定方法（可选）
  "tuningRecordId": null                          // 未来整定模块关联（也可走列字段）
}

// VALVE 阀门检修
{ "parts": "更换填料函", "downtimeHours": 4, "vendor": "××检修队" }

// INSTRUMENT 仪表校验
{ "instrument": "变送器 PT-5121", "calibrationResult": "零点偏移 0.5%，已校正", "nextDue": "2027-02-01" }

// LINK 链路修复
{ "action": "更换交换机端口", "rootCause": "网口松动" }

// PROCESS 工艺调整
{ "measure": "上游增设缓冲罐投用", "operator": "工艺一班" }

// UTILIZATION 恢复投用
{ "autoRateBefore": 0.32, "autoRateAfter": 0.95 }

// RECONFIG 组态改造
{ "change": "量程 0-2.5MPa 改 0-1.6MPa", "dcEngineer": "×××" }

// OTHER 其他
{ "note": "自由文本" }
```

**校验规则**：submit 时按类型做服务端必填校验（TUNING 必填 `pidAfter`；其余仅要求非空对象）。schema 存前端常量 + 后端轻校验（不建 schema 表，MVP 从简）。

## 6. API 定义

前缀 `/api/v1/handling`，响应格式 `{code, message, data}`，时间均为 naive UTC（前端补 Z 转本地，同诊断模块口径）。角色守卫见 §7。

### 6.1 清单与详情

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/handling/items` | 处置清单（分页）。Query：`status`（多值逗号分隔）/ `actionType` / `source` / `plantNodeId`（递归下钻）/ `loopId` / `importanceLevel` / `keyword`（回路位号/内容模糊）/ `startTime` / `endTime` / `page` / `pageSize`。返回行：id、loopId、loopTagName、loopDescription、importanceLevel、unitPath、source、category/Label、content 摘要、actionType/Label、status、priority、suggestedBy/At、handledBy/At、submittedAt、verifyResult、verifiedBy/At、updatedAt。排序：status 分组优先级（PENDING→REOPENED→HANDLING→VERIFYING→其他）+ updatedAt DESC |
| GET | `/handling/items/{id}` | 详情：清单行全部字段 + action_detail + kpi_before/after + verify_run_id + ignore_reason + basis |
| GET | `/handling/items/stats` | 状态统计（清单页顶部卡片）：各状态计数 + 本月闭环数 |

### 6.2 流转操作

| 方法 | 路径 | 请求体 | 说明 |
|---|---|---|---|
| POST | `/handling/items/{id}/start` | `{ actionType, handler?, actionDetail?, pidBefore?* }` | PENDING/REOPENED → HANDLING；`handler` 处置人手工填写（≤64 字符，缺省=当前登录用户）；`*`TUNING 类型建议此时传 pidBefore。返回更新后详情 |
| POST | `/handling/items/{id}/submit` | `{ actionDetail }` | HANDLING → VERIFYING；服务端按类型校验必填子字段 |
| POST | `/handling/items/{id}/verify` | `{ verifyResult: "EFFECTIVE" \| "INEFFECTIVE", verifyNote?, verifyRunId? }` | VERIFYING → CLOSED / REOPENED；服务端固化 kpi_before/after 后落 verify 字段 |
| POST | `/handling/items/{id}/ignore` | `{ ignoreReason }` | PENDING → IGNORED |
| POST | `/handling/items/{id}/kpi-comparison` | 无 | 预览：VERIFYING 阶段实时拉取前后窗口 KPI（不落库，供验证决策参考；verify 时才固化） |

错误码：`ERR_NOT_FOUND`(404) / `ERR_STATE`(400 非法迁移) / `ERR_PARAM`(400 缺必填/枚举非法) / `ERR_FORBIDDEN`(403)。

### 6.3 与既有接口的关系

- 诊断侧已有 `GET/POST /diagnosis/runs/{run_id}/actions`、`PUT/DELETE /diagnosis/runs/actions/{id}` **不变**（建议的生成与增删改仍在诊断上下文）
- 本模块只新增 `/handling/*` 流转与查询端点；两类端点操作同一张表
- 复诊：验证页"发起复诊"跳转诊断工作台（`/diagnosis/workbench?loopId=xx`，已有 URL 上下文能力），复诊完成后在诊断记录中复制 run_id 回填 `verifyRunId`

### 6.4 档案与统计接口（v1.1 新增，配套 §8.3/§8.4）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/handling/loops` | 按回路聚合（档案页主查询）：loopId/loopTagName/unitPath/importanceLevel + 各状态计数（pending/handling/verifying/closed/reopened/ignored）+ totalCount + lastSuggestedAt/lastHandledAt/lastHandledBy + lastClosedKpiDelta（最近一次闭环 `kpi_after.score − kpi_before.score`，无闭环为 null）。Query：plantNodeId（递归下钻）/importanceLevel/keyword/activeOnly（仅看有在途）/sort（recent\|reopened）/page/pageSize。排序：recent=最近建议时间倒序（默认）；reopened=重开次数倒序（问题回路 Top） |
| GET | `/handling/statistics` | 统计页数据。Query：`months`（默认 6，1-12）。返回：summary（本月闭环数/闭环率/平均处置时长 h（suggested_at→verified_at 均值）/无效重开率/平均 KPI 改善分）+ monthly（近 N 月序列：月份/闭环数/闭环率）+ byType（8 类处置项计数）+ byUnit（装置级闭环数）+ topLoops（重开次数 Top 10：回路/装置/累计处置/重开/最近 KPI 改善）。无 CLOSED 记录时 summary 相关项返回 null（前端显示空态，不出误导性 0） |

档案抽屉的处置全史复用已有 `GET /handling/items?loopId=`（按回路拉全量建议+处置记录，前端按"同一处置项重开轮次归并"渲染）。

| 操作 | 角色 |
|---|---|
| 清单/详情/统计查看 | 全部登录用户（EXPERT/SPONSOR 只读） |
| start / submit / verify / ignore | IC_ENGINEER / PE_ENGINEER / ADMIN（复用诊断触发角色口径 `_DIAGNOSIS_TRIGGER_ROLES`） |

## 8. 页面设计

### 8.1 二级模块结构（v1.1 三页式）

```
处置
├── 处置工作台  /handling/workbench    执行闭环：统计卡 + 清单 + 流转抽屉（执行者视角）
├── 处置档案    /handling/archive      回路维度聚合 + 跨 run 处置全史（追溯视角）
└── 处置统计    /handling/statistics   管理报表：月度趋势 / 分布 / Top 回路（管理视角）
```

- 一级菜单第 4 位不变（监控→评估→诊断→**处置**→配置→系统），下挂三个二级菜单
- **旧路由兼容**：`/handling` → `/handling/workbench` 重定向；`/handling?focus={id}` 透传 focus 自动开抽屉（保护诊断侧「去处置」深链接与书签）
- 角色可见性：三页全部登录角色可见；流转操作仍按 §7 角色守卫（SPONSOR/EXPERT 只读）
- 拆分动机：单页清单是"事"视角（一项一项流转），无法回答"这回路以前处置过没、效果如何"（高频回看）与"本月闭环了多少、哪些回路反复出问题"（管理回顾）——分别由档案页与统计页承载

### 8.2 处置工作台（/handling/workbench）

- **顶部统计卡**：待处置 / 处置中 / 验证中 / 本月闭环 四个数字（点击即筛选）
- **筛选行**：状态 tabs（全部|待处置|处置中|验证中|已闭环|重开|已忽略）+ 类型/装置/等级/关键字下拉
- **表格**（一回路多行，行点击开详情抽屉）：回路 | 装置.单元 | 类型 | 建议摘要（ellipsis） | 来源 | 状态（着色 tag） | 建议人/时间 | 处置人 | 最近更新
- 状态色：待处置=橙 / 处置中=蓝 / 验证中=青 / 已闭环=绿 / 重开=红 / 已忽略=灰（对齐项目工业色约定）
- 深链接 `/handling/workbench?focus={id}`：自动打开对应详情抽屉

### 8.3 处置档案页（/handling/archive，v1.1 新增）

回答"**这个回路被处置过几次、每次做了什么、效果如何**"——诊断/整定/复核前的回看入口，处置档案的沉淀面。

- **表格**（一行 = 一个回路，仅列出有过处置建议的回路）：
  | 回路 | 装置.单元 | 等级 | 累计处置 | 状态分布（待/处/验/闭/重开/忽略 计数 tag） | KPI 改善 | 最近处置 | 最近处置人 |
  - KPI 改善 = 最近一次闭环的 `kpi_after.score − kpi_before.score`（正绿负红，无闭环记录显示 —）
- **排序**：默认按最近建议时间倒序；支持"重开次数最多"（问题回路 Top）
- **筛选**：装置树 / 回路等级 / 仅看有在途（pending+handling+verifying>0）/ 关键字
- **行点击开档案抽屉**（右侧 640px，比流转抽屉宽，容纳全史）：
  - 上部：回路摘要（位号/装置/等级/累计处置数/闭环率）
  - 下部：**跨 run 处置全史时间线**（倒序）：每次处置一张卡——时间/类型/处置人/结论（有效绿·无效红·在途青）/TUNING 显示 P·I·D 前后值/KPI 前后对比摘要（score + Δ）；同一处置项的重开轮次归并为一组（一诊多轮不散排）
  - 卡片操作：「查看详情」跳工作台并 focus 定位该处置项（只读历史不再提供流转入口，流转统一回工作台）

### 8.4 处置统计页（/handling/statistics，v1.1 新增；原 Phase 3"月度统计报表"提前）

回答"**处置活动整体做得怎么样**"——主管/管理者回顾面。

- **汇总指标卡**（本月）：闭环数 / 闭环率 / 平均处置时长（建议产生→验证闭环，小时）/ 无效重开率 / 平均 KPI 改善分
- **月度趋势**（近 N 月，默认 6，可切 12）：闭环数柱状 + 闭环率折线组合图（微型图不加动画，对齐项目约定）
- **处置类型分布**：8 类占比饼图（无引线，悬浮框显示明细）
- **装置分布**：各装置闭环数横向条形
- **Top 问题回路**：按重开次数降序 Top 10 表（回路/装置/累计处置/重开/最近 KPI 改善），行点击跳档案页定位该回路
- 数据不足（无 CLOSED 记录）时各区块显示空态提示，不显示误导性 0%

### 8.5 处置详情抽屉（右侧，520px）

- **上半 · 建议信息**：来源（系统建议 R1/人工新增）、依据、关联诊断结论（run 摘要 + "查看诊断详情"跳转）
- **中部 · 流转操作区**（按当前状态渲染）：
  - PENDING：`[开始处置]`（弹层选类型 + 填详情 + **处置人输入框**：默认当前用户可改他人，如"仪表班-张三"）`[忽略]`
  - HANDLING：`[提交验证]`（填 action_detail 表单，TUNING 类型渲染 P/I/D 前后值输入组；处置人/开始时间只读回显）
  - VERIFYING：KPI 前后对比卡（预览接口）+ `[有效-关闭]` `[无效-重开]` + 复诊入口
  - REOPENED：同 PENDING + 上一轮验证结论灰字展示
  - CLOSED/IGNORED：只读 + 忽略原因/验证结论展示
- **下半 · 时间线**：建议 → 开始处置 → 提交验证 → 验证 各节点（人/时间/动作摘要），垂直 timeline

### 8.6 诊断详情弹窗联动（小改）

- 处置建议 Tab 行操作增加「去处置」：携带 actionId 跳 `/handling/workbench?focus={id}`，工作台自动打开对应详情抽屉
- 建议行显示当前状态 tag（PENDING 之外的状态在诊断侧可见，避免"建议已闭环但用户不知道"）

## 11. 修订记录

### v1.1（2026-08-19）二级模块三页式修订

**动机**：Phase 1 前端以单页 `/handling`（清单+抽屉）交付后，从实际应用场景推演发现两类高频需求单页无法承载：

1. **回路处置全史回看**（档案视角）：诊断/整定/复核前需要回答"这回路以前处置过没、上次 PID 调到多少、效果如何"——清单按事项流转组织，跨 run 的回路史分散难查；`action_detail` 的 pidBefore/pidAfter 等记录性数据无沉淀展示面，成了死数据。
