# CLPM 客户现场部署手册

> 适用版本：v7.0.0（交付包 `clpm-delivery-<版本时间戳>.tar.gz`）
> 本文档已经 2026-08-31 真实服务器全链路演练验证（全新装机 56 秒完成部署）。
> 面向现场部署工程师，按步骤顺序执行即可，无需了解系统内部原理。

---

## 1. 服务器要求

> **客户现场为 Windows 服务器时：在 Windows 上以虚拟机（Hyper-V / VMware / VirtualBox）方式部署一台 Linux 虚拟机，CLPM 全部组件安装在虚拟机内**。交付包面向 Linux x86_64 + Docker，虚拟机内的部署步骤与物理 Linux 服务器完全一致，交付包无需任何改造。

Windows 宿主机 + Linux 虚拟机的要求：

| 项目 | 要求 |
|---|---|
| 虚拟机平台 | Hyper-V / VMware / VirtualBox 均可（Windows 宿主机需开启 CPU 虚拟化 VT-x/AMD-V） |
| 虚拟机操作系统 | Linux x86_64（推荐 Ubuntu 22.04/24.04 Server） |
| 虚拟机资源 | 分配 ≥4 核 CPU / 8GB+ 内存 / 40GB+ 磁盘（镜像 + 数据增长预留） |
| 虚拟机网络 | **桥接模式（Bridged）**：虚拟机获得独立局域网 IP，厂内用户经 `http://<虚拟机IP>:7141` 访问；不要用 NAT 模式（外部无法直接访问，还需手工端口映射） |
| 时钟同步 | 虚拟机与宿主机/NTP 保持时钟同步（时序数据对时间敏感） |
| 开机自启 | 虚拟机随 Windows 宿主机自动启动；CLPM 容器已配置 `restart: unless-stopped`，虚拟机开机后自动恢复运行 |
| 共存 | **不可与原 CLPM 系统同机（同一虚拟机）部署**（容器名 `clpm-*`、端口 7141 会冲突） |

物理 Linux 服务器直装时，仅需满足：Linux x86_64 / Docker 24+（含 Compose v2）/ 4 核 CPU / 8GB+ 内存 / 20GB+ 磁盘 / 7141 端口空闲。

> 不支持在 Windows 宿主机上直接用 Docker Desktop 部署（部署脚本为 bash、文件路径与权限模型不同，未验证）。

虚拟机内部署前自检：

```bash
docker version && docker compose version
ss -tln | grep -w 7141   # 有输出说明端口被占用，需先释放
df -h /var/lib/docker    # 确认磁盘 ≥20GB
```

## 2. 获取并解压交付包

```bash
# 将交付包传送到服务器（示例）
scp clpm-delivery-<版本时间戳>.tar.gz <user>@<服务器IP>:/tmp/

ssh <user>@<服务器IP>
cd /tmp
tar xzf clpm-delivery-<版本时间戳>.tar.gz
cd clpm-delivery-<版本时间戳>
```

> 解压时若出现 `tar: 忽略未知的扩展头关键字` 警告，属正常现象（macOS 打包元数据），不影响部署。
> 目录下的 `._*` 小文件同样是打包元数据残留，可忽略。

交付包内容：

```
deploy.sh                 ← 部署主脚本（自动校验/迁移/健康检查/失败回滚）
deploy/                   ← 备份 backup.sh / 回滚 rollback.sh / 迁移工具
docker-compose.prod.yml   ← 生产编排（7 个服务）
.env.prod.example         ← 环境配置模板
db/                       ← 数据库初始化 SQL
images/                   ← 预构建镜像（离线环境无需联网拉取）
DEPLOYMENT-GUIDE.md       ← 完整操作手册（排障参考）
```

## 3. 配置 .env.prod（关键步骤）

```bash
cp .env.prod.example .env.prod
vi .env.prod
```

**必须修改的项**（部署脚本会强制校验，占位符直接拒绝启动）：

| 配置项 | 要求 |
|---|---|
| `JWT_SECRET_KEY` | 执行 `openssl rand -hex 32` 生成（64 位） |
| `POSTGRES_PASSWORD` | 强密码，无特殊限制 |
| `REDIS_PASSWORD` | 强密码，无特殊限制 |
| `TDENGINE_PASSWORD` | **⚠️ 特殊规则：8~16 个字符，且必须包含大写字母、小写字母、数字、特殊字符中的至少三类**。示例：`Clpm#Td2026aZ`。纯数字字母组合（如 32 位 hex）会被 TDengine 拒绝导致部署失败 |
| `ENV` | 必须为 `production`（模板默认值，勿改） |

**按需修改的项**：

| 配置项 | 说明 |
|---|---|
| `CORS_ORIGINS` | 保持 `__AUTO__` 即可，部署脚本按服务器 IP 自动生成 |
| `SIGNALR_HUB_URL` / `SIGNALR_ENABLED` | 实时数据源地址（写法见下方"同机 AAS 地址规则"）；现场无数据源时设 `SIGNALR_ENABLED=False` |
| `AAS_*` | OPC UA 数据源（写法见下方）；暂不接数据源时设 `AAS_SYNC_ENABLED=False` |
| `HISTORY_DATA_API_URL` / `HISTORY_DATA_API_TOKEN` | 历史数据导入接口（数据管理→历史数据导入功能使用，写法见下方）；不用可留空 token |
| `APP_VERSION` | 改为交付包版本号（如 `v7.0.0-17-g424c779f`），仅影响页面版本展示 |

### 同机 AAS 地址规则（重要）

**现场 AAS 服务与 CLPM 部署在同一台物理服务器上，实时（SignalR）和历史数据接口都访问"本机"服务。但 CLPM 后端运行在 Linux 虚拟机的 Docker 容器内——容器里的 `localhost`/`127.0.0.1` 指容器自己，不是虚拟机，更不是 Windows 宿主机**。数据源地址必须按 AAS 实际运行位置书写，否则连接失败：

| AAS 运行位置 | 地址写法 | 说明 |
|---|---|---|
| Windows 宿主机上（**虚拟机方案的典型形态**） | Windows 宿主机的局域网 IP（如 `192.168.x.x`） | 要求 AAS 监听 `0.0.0.0` 或该网卡地址（不能只绑 `127.0.0.1`）；虚拟机桥接网络下同网段直连 |
| 与 CLPM 同一 Linux 虚拟机/主机内 | `host.docker.internal` | 编排已内置该域名到容器宿主机的映射。例：`ws://host.docker.internal:81/signalr/realValueForClpmHub` |
| 网络中其他服务器 | 该服务器 IP | 常规写法 |

**禁止**在任何场景下写 `127.0.0.1` / `localhost`——它指向容器自身，连接必失败。

另外两个要点：

- **运行期以系统内"链路配置"页面为准**：`.env.prod` 中的地址仅是初始兜底值；交付包种子数据里预置了一个示例 SignalR 地址（`ws://192.168.100.2:81/...`），部署后务必在 UI 的链路配置页改为现场实际地址（改后即时生效，无需重启）。
- 验证连通性（在虚拟机内执行）：`docker exec clpm-backend curl -sv telnet://<AAS地址>:<端口>` 或 `docker exec clpm-backend ping -c2 <AAS地址>` 应能通。

配置完成后收紧权限：`chmod 600 .env.prod`

## 4. 执行部署

```bash
./deploy.sh
```

脚本自动完成（全程约 1~2 分钟）：

1. 环境校验（含密码合规性检查，不合规会直接拒绝并提示原因）
2. 加载离线镜像（7 个服务镜像 + 3 个基础镜像）
3. 启动全部服务（PostgreSQL / TDengine / Redis / 后端 / Celery Worker / Celery Beat / 前端 Nginx）
4. 数据库初始化与版本同步（首次部署自动完成建表与种子数据）
5. TDengine 时序库 schema 校验
6. 健康检查（失败自动回滚并生成排查清单 `/tmp/clpm-deploy-troubleshooting-*.md`）

看到 `=== 部署完成 ===` 并输出访问地址即成功。

## 5. 部署后验证（逐项确认）

```bash
# ① 7 个容器全部 healthy
docker compose --env-file .env.prod -f docker-compose.prod.yml ps

# ② 后端健康（应返回 {"status":"ok","version":"..."}）
curl http://localhost:7141/health

# ③ 浏览器访问 http://<服务器IP>:7141
#    使用 admin / admin123 登录，应能进入工作台并看到回路数据
```

| 验证项 | 预期 |
|---|---|
| 登录 | admin/admin123 成功进入工作台 |
| 回路数据 | 工作台/回路管理显示回路列表 |
| 实时数据（配置 SignalR 后） | 回路监控页 PV/SP/OP 实时刷新 |
| 历史数据 | 回路趋势曲线有数据 |

默认账号（密码均为 `admin123`）：`admin`（管理员）、`ic_engineer`（仪控工程师）、`pe_engineer`（工艺工程师）、`sponsor`（项目发起人）、`expert`（外部专家）。

## 6. 日常运维

```bash
cd /tmp/clpm-delivery-<版本时间戳>   # 以下命令均在此目录执行

# 查看状态/日志
docker compose --env-file .env.prod -f docker-compose.prod.yml ps
docker compose --env-file .env.prod -f docker-compose.prod.yml logs -f backend

# 数据备份（PostgreSQL + TDengine，备份到 ~/backups/clpm/）
./deploy/backup.sh

# 完全卸载（含数据，⚠️ 不可逆）
docker compose --env-file .env.prod -f docker-compose.prod.yml --profile tdengine down -v
```

> 注意：停止/卸载命令必须带 `--profile tdengine`，否则 TDengine 容器和网络残留。

## 7. 版本升级

收到新版本交付包后：解压到新目录 → 复制旧目录的 `.env.prod` 到新目录 → 执行 `./deploy.sh`。脚本会自动：备份当前数据 → 更新镜像 → 执行数据库迁移 → 健康检查，失败自动回滚到旧版本。手动回滚：`./deploy/rollback.sh`。

## 8. 常见问题

| 现象 | 原因与处理 |
|---|---|
| deploy.sh 报 TDengine 密码不合规 | 密码须 8~16 字符且含大写/小写/数字/特殊字符中至少三类，见 §3 |
| TDengine 容器一直 starting/unhealthy | 多为密码问题：检查 `.env.prod` 的 `TDENGINE_PASSWORD` 是否符合规则；改后执行 `docker compose --env-file .env.prod -f docker-compose.prod.yml --profile tdengine up -d --force-recreate tdengine` |
| 启动初期后端日志有 `Table does not exist` | 时序库初始化窗口期的瞬时报错，约 30 秒后自愈，持续超过 2 分钟才需排查 |
| `curl /api/v1/health` 返回 404 | 健康检查地址是 `/health`，不是 `/api/v1/health` |
| 端口 7141 被占用 | `ss -tlnp \| grep :7141` 找到占用进程并释放 |
| 实时/历史数据连不上 | 检查数据源地址是否误写 `127.0.0.1`/`localhost`（容器内必失败），按 AAS 实际位置写 Windows 宿主机 IP 或 `host.docker.internal`，见 §3"同机 AAS 地址规则"；并确认 UI 链路配置页地址已改为现场实际值 |
| Windows 宿主机重启后系统没起来 | 检查虚拟机是否配置为随宿主机自动启动、虚拟机内 Docker 服务是否自启（`systemctl enable docker`）；容器已配 `restart: unless-stopped`，虚拟机与 Docker 起来后会自动恢复 |
| 部署失败 | 查看自动生成的 `/tmp/clpm-deploy-troubleshooting-*.md` 排查清单 |

---

**技术支持**：部署失败且按 §8 无法解决时，请收集以下信息反馈开发团队：
`/tmp/clpm-deploy-troubleshooting-*.md`、`docker compose --env-file .env.prod -f docker-compose.prod.yml logs --tail 200` 输出、`docker ps -a` 输出。
